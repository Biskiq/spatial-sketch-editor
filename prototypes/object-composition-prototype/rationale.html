Compose a reusable display light

An object-first home in Biskiq: bring material in and learn what it honestly supports, combine it into something reusable, place several uses, change one or all of them on purpose, and accept or repair a revision without losing track of what changed.

This is a design proposal, not a description of shipped behaviour. Production today has catalogue models, primitives, lights and clusters — not definitions, components, attachments or offered revisions. Wherever this page says “the prototype does…”, it means the prototype. Usability conclusions are hypothesis — nobody has tested it with users yet.

1. The proposition in one screen

Begin with an object

An empty project says “no room is needed”. The Contents list opens with In this world, not a Room. Architecture can arrive later as its own Layout section; objects stay world-local and nothing gets re-parented under it.

Say what arrived

Every import produces a capability card: Supported, Found, not active (a clip that won't play until you bind or preview it), Not supported. The flat relief states plainly that its 14 meshes are render data, not parts.

Show reach before the edit

Hovering a value previews it in the viewport on exactly the uses it would reach. Uses that won't change get a “◆ keeps its own” tag. Reach is part of the control, not a mode buried in a menu.

Keep lifetimes apart

Accepted edits, a view-only separation, a runtime preview and an offered revision each have their own line style, glyph and word. None of them turns into another without an explicit action.

Revision as a decision

An offered revision is compared before anything changes: linked, kept, not allowed now, unresolved. Repairs are chosen per use. Accepting is one action with one Undo; if someone else wrote in the meantime, Accept is refused.

Reuse with a clear choice

A second project uses the definition by reference with a retained copy. When a new revision arrives it can accept, stay pinned (same identity, offer kept) or fork (a new identity, no more offers).

3. Terminology and scope rules

Word in the UIWhat it meansRule
DefinitionA reusable thing: imported (D-DK12 Desk light), flat (D-TR05), or a composition made here (D-DL01 Display light). Typed resource, versioned on its own.Edits to it reach every use that doesn't keep its own value. The UI never says “prefab” or “asset”.
UseOne placement of a definition in this world (U-A4D1, U-B7Q2). Owned by Scene.Has its own placement and only the overrides the definition allows. Duplicating makes another use, never a copy of the definition.
Component / partA component is a definition placed inside a composition (Lamp, Plinth). A part is a declared, stable-id piece of an imported model (Base, Arm, Shade, Diffuser).Only declared parts exist. Render meshes (bulb_glow, cable_01) are never selectable parts.
GroupAn organisational set of uses.“Organizes only”: no identity for its members, no reuse, no physical link. Dissolving it changes no placement.
Hung on (attachment)A declared relationship between a use's mount and a Layout host (wall + distance along + height).Proximity is never attachment. A host move carries hung uses; a host removal needs a decision.
Rests onPlacement on top of something, derived at drop time.Written as placement only; later moves of the support don't carry it.
This use / Every useThe reach control for a value edit.Every use means “the definition's default”; uses with their own value keep it and say so.
Offered revisionA newer source or library revision that has not been accepted here.Nothing changes until someone in this project accepts it. Staying pinned is a real choice, not a failure.
Detach / ForkMake an independent definition from one use / from a library definition.Always a new identity with provenance (“forked from…”). Never a silent rename of the old one.

Scope rules the prototype enforces

  • Identity is never a name or a path. Both lights are called “Display light”; the UI tells them apart with their reference (U-A4D1), their place, and a viewport highlight. Renaming a component or a use changes nothing that points at it.
  • Correspondence is declared, not guessed. Revision comparison uses the file's part manifest ids. Similar names (diffuser_ring vs Diffuser) are pointed out as not linked.
  • One accepted action, one Undo, one set of domains. Every history entry lists the domains it touched (Scene, Layout, Resources). Removing a wall that hosts a light is one cross-domain entry.
  • Stale writers are refused. A review is prepared against a project revision; if the project moved on, Accept is refused and the review re-checks.
  • View return is not Undo. Leaving an inspection restores the view; it never reverts edits. Undo never moves the camera.

5. Selection depth, names and return

  • Click selects the outermost thing in the current context (a use, or a group when you're outside it). Double-click or Enter goes one level in; Esc goes one level out. Alt-click goes straight to the deepest declared part. [ / ] step between siblings at the current depth; Tab leaves the canvas for the next control.
  • The strip shows a breadcrumb (Display light U-B7Q2 › Lamp › Shade) whenever you are inside something, so the context is visible without the Contents list.
  • Hidden and enclosed parts (the Diffuser sits inside the Shade) are reachable from Contents and Find; the viewport then draws an edge beacon and suggests Inspect, answering “why can't I see it?”.
  • Duplicate names are always shown with their reference; Find (/ or ⌘K) lists kind and location for every hit.
  • The Inspector is property-first: the value, its lifetime cue, its reach control; identity and IDs live under Technical details.

6. Contextual reach vs Definition bench

The brief asks for a comparison between a direct contextual approach and a more explicit resource-editing surface, judged on predictability rather than clicks. Both are built; the presenter's Compare toggle (or ?approach=bench) switches them over the same fixture.

A. Contextual reach default

Edit in place. Each value row has a reach control: This use or Every use. Hovering an option previews the value on exactly the uses it would reach, with “◆ keeps its own” on uses that won't change. One click commits; the return summary lists what changed and offers Undo.

Strengths: the edit happens where the object is; reach is visible before commit; no mode to enter or leave.

Risks: an accidental Every use is one click away (mitigated by preview + summary + Undo); several definition edits in a row have no shared draft.

B. Definition bench

Value rows in the world only offer This use. To change the definition you open its bench: the world is swapped for a single specimen on a disc, edits collect as ✎ draft, and Apply commits them as one action listing how many uses change.

Strengths: a very clear “I am editing the definition” boundary; several edits batch into one accepted action; Discard is honest.

Risks: you lose sight of the placed uses while you edit (the band of use chips is a weak substitute); it's another place to learn; small edits cost more.

Recommendation hypothesis: make contextual reach the default and keep the bench as the place for multi-value definition work (and for definitions with no use in view). The deciding factor is that reach is predictable at the point of decision in A, while B makes it predictable only after you've navigated away from the uses it affects. This should be tested with the brief's first exercise (“change only the second light, then improve the shared definition, then inspect without editing”) and a count of wrong-scope edits in each version.

7. Revisions, repair and reuse

  • The review swaps the Inspector for a wider comparison (384 px) with four blocks: parts (same, changed, removed, new, look-alikes that aren't linked), values, effect on each use (with a radio for each repair and a “detach this use” checkbox), and presentation references.
  • The viewport can show rev 1, rev 2, or both (the accepted revision as a slate ghost behind the offered one).
  • Every repair defaults to keep (visibly unresolved) rather than a destructive guess. Accept is still allowed with unresolved items; they stay flagged.
  • Detaching creates a new definition locked to the old revision: new identity, provenance kept.
  • Library reuse keeps a retained copy in the project, so unavailability degrades to “can't check offers”, not “missing object”. Storage, network and the library are simulated and labelled as such.

8. Rejected alternatives

AlternativeWhy it was rejected
Classic scene-tree hierarchy as the primary surfaceIt makes hierarchy paths look like identity and turns groups, definitions and attachments into the same indentation. Contents stays, but grouped by kind of truth (world, Layout, definitions, references), with badges for relationships.
Prefab “open to edit” as the only way to change a definitionThis is option B taken alone: predictable but slow, and it hides the uses you're affecting. Kept as the bench, not the default.
Name/mesh-order matching for revisionsIt's the failure the brief warns about. The prototype shows look-alikes explicitly as not linked and relies on declared ids only.
Auto-repair on accept (clamp everything, drop the missing)It hides loss. The default is to keep things visibly unresolved; repairs are chosen.
Snap-to-wall means attachedProximity isn't attachment. Hanging is a separate tool with a mount, refusals and a tape; objects near a wall say “near, not attached”.
Exploded view as an editing modeA displaced part would need an inverse transform to edit safely. Inspection is view-only; edits inside it are value edits and are listed on return.
Architecture as a special group (“Room”)That would merge Layout into Scene. The bay arrives as its own Layout section with its own mode and history domain.
A permanent asset browser panelToo much chrome for a one-object start. Import and library are sheets; definitions live in Contents.

10. Keyboard, focus, reduced motion, density

  • Keyboard: Contents is a roving-tabindex tree (↑↓←→, Enter); the canvas takes brackets for siblings, Enter/Esc for depth and arrows for nudging or orbiting. Tab exits to controls. Hang has a host selector and exact along-wall/height fields; the wall handle is focusable and moves with arrows. Sheets cycle focus, and Find announces its active result and returns focus on close. ? lists the keys.
  • Focus: an ink ring offset from the element, separate from selection blue and hover lift.
  • Reduced motion (?motion=reduced, the OS setting, or the viewbar toggle): camera moves become cuts, intake checking is instant, and the articulation preview shows its two limits as static ghosts plus the chosen pose instead of a sweep — the same meaning (range, baseline, current) without motion.
  • Density: ?density=compact and widths below 1280 / 1080 px narrow the Contents list and Inspector and tighten rows. Contextual instruments wrap so their acceptance/return controls remain reachable; see the narrow specimen.

11. Usability hypotheses and how to test them

None of this has been tested with users. Each line is a hypothesis with the observation that would disprove it.

HypothesisWould be disproved if…
Hover reach halos let creators predict which uses change before they commit.More than 1 in 5 participants commit an Every-use edit when asked to change only the second light.
“Make reusable” next to “Group”, each with its consequence, prevents grouping from being mistaken for reuse.Participants expect a group member to follow another's finish change.
View-only slate cues let creators tell inspection from editing.Participants believe the separated layout persists or needs undoing after return.
Creators can tell ! not allowed now from ✕ unresolved and pick different repairs.Participants choose the same repair for both without reading, or can't explain the difference.
Accept / Stay pinned / Fork are understood as different identity outcomes.Participants expect a fork to keep receiving library revisions, or stay pinned to lose the offer.
Renaming a component during the exercise doesn't break identity comprehension.After a rename, participants think references or overrides were lost.
