# P23.14 — Editor Shell & Visual System Foundation: precedent research

**Date:** 2026-09-17  
**Status:** design-research input; **not** an implementation plan and **not** a final design specification  
**Primary product baseline:** [`P23.14-shell-design-context.md`](../../design/P23.14-shell-design-context.md)  
**Settled Plan-language baseline:** [`P23.13-final-design-specification-Designer-D.md`](../../design/P23.13-final-design-specification-Designer-D.md)  
**Forward pressure only:** [`P24 Scene/Staging Depth`](../../plans/2026-09-08-P24-scene-staging-depth-umbrella.md), [`P26 Architectural Spatial Depth synthesis`](../P26-research/P26-architectural-spatial-depth-synthesis.md)

This research asks how Museum Editor can become a coherent, distinctive, extensible professional editor without collapsing into sparse SaaS minimalism, inherited CAD clutter, or a collection of unrelated workspace skins.

The answer is not to copy one mature tool. The strongest pattern across CAD, DCC, creative, GIS, IDE and timeline software is a **stable visual operating system with contextual depth**: persistent landmarks establish where the user is and what owns the current state; contextual tools, inspectors and temporary instruments appear inside those known regions. Richness comes from hierarchy, repeated grammar, useful state and material/tonal structure — not from showing every command at equal weight.

---

# 1. Executive synthesis

## 1.1 Strongest findings

### A. Professional richness comes from **stable geography + contextual depth**, not from hiding chrome

Blender, Unreal, Unity, Rhino, Vectorworks, ArcGIS Pro, VS Code, Logic Pro and After Effects all retain recognizable working regions while allowing their contents to change. Their exact layouts differ, but the durable pattern is consistent:

- a primary work surface remains visually dominant;
- hierarchy/navigation has a stable home;
- selection-scoped properties have a stable home;
- project/global commands do not compete with object tools;
- contextual controls appear near the work or in a known contextual region;
- bottom/status regions carry low-frequency state, hints, progress or transport rather than becoming another full toolbar.

This is important for Museum Editor because its current problem is not “too much UI” in the abstract. It is **too little ranking between kinds of UI**. Domain (`Scene | Camera`), view (`Plan | 3D`), local mode (`Layout | Arrange`) and active tools currently sit close together with near-peer visual weight. P24 and P26 will worsen that unless P23.14 establishes a rank grammar now.

**Research implication:** canvas-first should mean **the canvas owns attention**, not “everything disappears until hover.” A quiet persistent frame is more extensible and more learnable than repeated hiding.

### B. The most useful model is not “toolbar vs sidebar”; it is **semantic rank**

Mature tools assign distinct visual and spatial treatment to different lifetimes:

| Lifetime / rank | Typical mature-tool treatment | Museum Editor pressure |
|---|---|---|
| Project / application | top frame, title/menu, save/project state | project, persistence, Preview/Publish |
| Workspace / domain | stable tabs, workspace selector, major mode | Scene / Camera |
| View | viewport-local selector or named view state | Plan / 3D, future P26 instrument entry |
| Local stance | contextual tab, mode bar, local segment | Layout / Arrange |
| Tool | compact tool group, active-tool well | Wall, Door, Move, Connect, etc. |
| Selection | canvas + hierarchy + Inspector synchronization | one selection authority |
| Gesture | near-cursor tracker, handles, snap, ghost | P23.13 drafting instrument |
| Status / warning | status line, inline reason, transient report | save state, refusal, warnings |

ArcGIS Pro makes this particularly explicit through persistent core tabs and state-dependent contextual tabs. Archicad does it through a persistent work environment plus the Pet Palette and Tracker during editing. Rhino combines persistent mode/status panes with object-scoped properties. Unreal separates main toolbar, viewport toolbar, Outliner and selection-scoped Details. These are different products, but they solve the same semantic-rank problem.

### C. Density becomes usable when repetition is **highly regular**

Dense professional software is not successful because experts tolerate chaos. It is successful when the eye can learn a repeated cadence:

- fixed section/header hierarchy;
- repeated property-row geometry;
- predictable indentation and disclosure;
- consistent numeric alignment;
- clear type/icon positions;
- restrained but persistent separators;
- compact but stable hit targets;
- search/filter when depth grows;
- “advanced” or less-common material placed behind explicit disclosure rather than hidden by default everywhere.

Unreal’s Details panel is an especially relevant precedent: categories, search, default-value indicators, edit conditions, read-only treatment, and multi-object “Multiple Values” all live inside one repeated property grammar. Vectorworks’ Object Info palette similarly keeps object information in a stable property surface and separates Shape/Data/Render. Logic Pro’s Inspector changes with selection and focused working area without changing the Inspector’s role.

**Museum implication:** the Inspector should become more systematic, not emptier. Remove documentation residue from the property path, but retain visible section structure and explicit state.

### D. Educational UX works best when explanation is **attached to the current action**

The strongest precedents do not keep large permanent prose blocks above the working controls.

- SketchUp puts tips for the selected tool in the status bar and offers an Instructor panel for deeper help.
- Rhino supports dynamic command help that follows the running command.
- Logic Pro Quick Help can explain the UI element under the pointer.
- Archicad’s Tracker shows only parameters relevant to the current editing action.
- Archicad’s Pet Palette appears for the selected element, picked sub-part and active window, then disappears when the operation ends.

This suggests a layered teaching model for Museum Editor:

1. control label/icon makes basic purpose legible;
2. status or small contextual hint describes the current gesture;
3. disabled/refused state exposes a reason;
4. optional help surface explains concepts or advanced ownership;
5. onboarding/product tours teach durable mental models, then get out of the working path.

The present Scene Inspector prose is therefore solving a real need in the wrong layer.

### E. Visual identity should come from a **small number of repeated signatures**, not decorative variation

Professional products with character usually repeat a few traits everywhere: surface contrast, panel geometry, icon weight, active-state construction, typography rhythm, numeric treatment, and one or two recognizable interaction motifs.

Museum Editor does not need ornamental “museum” styling. It needs a visual system where a screenshot is recognizable because:

- shell surfaces have a deliberate material/tonal relationship to the canvas;
- selected/active/focus/refusal states use consistent constructions;
- section headers, property rows and hierarchy rows share one family grammar;
- Scene and Camera differ by context without becoming different products;
- precision controls look like instruments rather than generic form fields;
- typography distinguishes human-readable identity from measurements/references without becoming typographically noisy.

### F. P24 and P26 both reward **contextual insertion into stable slots**

P24 brings ordered multi-selection, mixed values, shared-vs-unique materials, support/refusal reasons, environment/light state and destructive reset. P26 brings contextual orthographic instruments, crop/depth/reveal state and derived display streams. Neither should create a new shell.

The common requirement is a shell with stable extension slots:

- selection summary/header;
- repeatable property section;
- contextual tool group;
- local instrument entry/exit with a clear return path;
- reason/refusal surface;
- view-local display control;
- hierarchy row variants;
- bottom temporal/instrument zone.

## 1.2 Main tensions

### Rich vs quiet

The product should feel rich without making every surface high contrast. The best precedent is **quiet persistence + loud relevance**: stable low-to-mid contrast structure; strong contrast reserved for current selection, armed tools, direct manipulation, errors and focus.

### Friendly vs precise

Friendliness should come from understandable labels, forgiving navigation, warm surface choices, good empty states and contextual teaching — not from oversized rounded cards or cartoon iconography. Precision still needs compact numeric fields, exact units, alignment, and visible constraints.

### Distinctive vs coherent

A strong identity cannot mean every domain gets a different theme. Shared primitives should remain shared. Domain identity should be a secondary layer — perhaps a marker, local accent or heading treatment — while selection, focus, invalid, warning and authored/derived semantics remain globally consistent.

### Flexible vs learnable

Blender/Rhino/After Effects show the power of highly configurable panes. Museum Editor does not yet need that degree of layout freedom. Too much rearrangement would make teaching and support harder. The useful lesson is **stable roles and collapsible/focusable regions**, not arbitrary pane plumbing.

### Contextual vs disorienting

P26’s contextual orthographic instruments create a known risk: contextual surfaces can make return navigation weak. Research supports contextual tools, but only when the shell preserves a strong location marker and explicit return path.

## 1.3 Most promising overall direction

The strongest research direction is a **structured workbench** rather than either extreme:

- persistent project frame;
- unmistakable domain/view hierarchy;
- contextual local mode/tool region;
- left hierarchy/navigation and right property surface with one shared row grammar;
- viewport visually dominant but not isolated from useful state;
- status line used for transient action/help and low-frequency status, not duplicate controls;
- Camera Timeline treated as a true docked working zone that aligns with the main grid;
- contextual instrument grammar capable of hosting P26 without pretending every instrument is a peer workspace;
- richer surface and typography system than generic flat SaaS;
- visible state construction that does not depend on hue alone.

This is a product-system direction, not a final visual territory. Section 8 offers deliberately different territories for designer exploration.

# 2. Design principles

| Principle | Problem it solves | Evidence / precedent |
|---|---|---|
| **1. Encode semantic rank before style.** Domain, view, stance, tool and gesture must not look like equal tabs. | Current Row 2 flatness; future P26 view/instrument pressure. | ArcGIS Pro core vs contextual tabs; Unreal main vs viewport toolbars; Archicad persistent environment vs Pet Palette. |
| **2. Quiet persistence beats hover-only minimalism.** Keep orientation and ownership visible; reduce contrast before removing structure. | Learnability, mode confidence, P24/P26 growth. | VS Code stable regions; Rhino status modes; Blender area/header model; Logic working areas. |
| **3. One fact gets one owner and at most one passive echo.** | Current Grid/Snap/status duplication; future state accretion. | Mature editors typically separate command control from status/reporting. |
| **4. Context should change content, not destroy geography.** | Cross-workspace disorientation. | Unreal Details/Outliner, Logic Inspector, Figma/Penpot sidebars, Rive hierarchy/Inspector. |
| **5. Precision belongs near the gesture.** | Avoid Inspector round-trips for every drafting action; keep canvas primary. | Archicad Tracker/Pet Palette, SketchUp Measurements, P23.13 local instrument. |
| **6. Properties need a strict row grammar.** | Inspector growth under P24/P26. | Unreal Details categories/search/edit conditions/multiple values; Vectorworks Object Info; Houdini parameters. |
| **7. Explanations belong on an escalation ladder.** | Permanent prose crowds working controls. | SketchUp status + Instructor, Rhino Dynamic Help, Logic Quick Help. |
| **8. Selection is a cross-surface sentence.** Same entity, same identity, different presentation in canvas/rail/Inspector. | Prevents three competing mental models. | Unreal viewport ↔ Outliner ↔ Details synchronization; Rive stage ↔ hierarchy; Penpot canvas ↔ layers. |
| **9. State needs more than color.** Use form, border, icon, text, placement and motion as redundant channels. | Selection/focus/tool/warning collisions and accessibility. | W3C Use of Color and Non-text Contrast; professional editors’ distinct pressed/disabled/read-only shapes. |
| **10. Richness should come from layering, not ornament.** | Avoid sterile minimalism without becoming busy. | DAW/DCC panel systems, CAD status/instrument zones, IDE workbench separation. |
| **11. Contextual capability enters through named slots.** | Toolbar accretion and visual forks. | ArcGIS contextual tabs, Vectorworks context-specific palettes, Archicad Pet Palette. |
| **12. Empty state is still an authored state.** | Camera no-flow dock, no selection, empty plan should not look broken. | Creative tools retain the surface/region while changing its body; Museum’s Timeline ownership contract requires this explicitly. |
| **13. | **14. Focus mode removes peripheral structure, not context.** | Panel collapse can otherwise erase orientation/selection. | VS Code Zen mode, Houdini pane maximize, Rhino Fullscreen. |
| **15. Product identity should be token-deep.** | Generic component-library feel. | Recognizable mature editors repeat surface, icon, control and state grammar across every workspace. |

# 3. Precedent patterns

This section is organized by transferable pattern, not by app.

## 3.1 Persistent frame, contextual content

### Pattern

Keep the major regions stable while changing what those regions contain.

### Evidence

- **Unreal Editor** identifies a Main Toolbar, Viewport Toolbar, Viewport, Outliner, Details panel, Content Drawer and Bottom Toolbar as distinct roles. Selecting an Actor in either viewport or Outliner synchronizes the other and drives the Details panel.
- **Unity** similarly keeps Hierarchy, Scene view, Inspector, Project and status regions stable while Inspector content changes with selection.
- **Logic Pro** keeps Tracks/working area central while Browser, Inspector, editors, mixer and other areas are shown/hidden through known controls.
- **VS Code** maintains Editor, Primary/Secondary Side Bars, Activity Bar, Panel and Status Bar as stable regions; views move inside that workbench grammar.
- **After Effects** uses saved workspace arrangements of consistent panel types rather than inventing a new visual language per task.

### Why it works

Spatial memory accumulates. Users learn “properties live there” before they learn every property. New capability can enter through known containers.

### Failure mode

If every context replaces both content and region layout, the user has to re-learn the application at every switch. Museum Editor already risks this because Scene/Camera inspectors and sidebars have materially different compositions.

### Adapt, do not copy

Museum Editor should keep stable ownership landmarks while allowing domain-specific internals. It does **not** need arbitrary free docking or Blender-style replace-any-area-with-any-editor.

---

## 3.2 Core controls vs contextual instruments

### Pattern

Separate durable/global commands from tools that only matter in a specific state.

### Evidence

- **ArcGIS Pro** keeps core ribbon tabs and adds contextual tabs only when selection/state makes them relevant.
- **Archicad Pet Palettes** show editing commands based on selected element, selected sub-part and current window; they disappear after the operation.
- **Vectorworks** exposes additional palettes/tool sets at the point of specialized workflows.
- **Unreal** separates general application toolbar from viewport manipulation/display controls.

### Why it works

It prevents permanent toolbar accretion while keeping tools discoverable when relevant.

### Failure mode

Contextual controls with no strong “where am I / how do I leave?” framing feel modal and disorienting. P26 explicitly names return navigation as a risk.

### Museum adaptation

The shell should have a clear **instrument slot** below the persistent domain/view frame. P26 Section/Wall Elevation/Ceiling Focus can later enter that slot without being hard-coded as top-level peer workspaces today.

---

## 3.3 Inspector as a property system, not a document

### Pattern

The Inspector/Details surface follows selection and organizes editable state in repeated sections and rows.

### Evidence

- **Unreal Details**: selection-scoped properties, categories, search, default indicators, edit conditions, read-only states, advanced properties, multi-object common properties and “Multiple Values.”
- **Vectorworks Object Info**: selected-object data grouped into Shape, Data and Render tabs.
- **Rhino Properties**: available pages change with selected object type; no selection can instead expose viewport properties.
- **Logic Inspector**: content depends on selected item and focused working area.
- **Houdini Parameter Editor**: selected node controls, with search for deep parameter sets.

### Why it works

The user can predict the interaction grammar even when the underlying entity is new.

### Failure mode

Putting overview prose, inventory counts, tutorials and properties in the same scroll path turns the Inspector into a junk drawer.

### Museum adaptation

A likely durable order is:

```text
selection identity / scope
→ high-frequency properties
→ grouped domain properties
→ advanced / secondary properties
→ contextual actions
→ destructive actions (clearly separated)
```

This is a grammar, not a proposed final layout. P24 mixed values and P26 larger architectural property sets should enter without changing the grammar.

---

## 3.4 Hierarchy as entity map, not explanation layer

### Pattern

Entity rows use consistent indentation, disclosure, type identity, selection and visibility/reveal actions. Metadata is visually subordinate.

### Evidence

- **Unreal Outliner** offers hierarchy, search/filter, customizable information and the same selection semantics as the viewport.
- **Rive** synchronizes hierarchy and stage selection; hover/selection techniques help navigate nested structures.
- **Penpot** supports search/filter, keyboard navigation, disclosure and multi-selection in its Layers sidebar.
- **VS Code Explorer** demonstrates high-density tree navigation with stable row rhythm and secondary indicators.

### Why it works

The hierarchy answers “what exists and where?” without forcing the user to parse prose.

### Failure mode

Rows that look selectable but are relation metadata, or relation rows that occupy the same weight as entities, make the tree cognitively expensive. Museum Editor’s current `Ends …` row is exactly this failure class.

### Museum adaptation

Entity rows, relation metadata, group headings and empty-state teaching should be visibly different row species. Search/reveal should preserve canonical P23.12 names/references and never create alternate identity labels.

---

## 3.5 Status line as active context, not duplicate toolbar

### Pattern

Use the bottom/status region for ephemeral guidance, mode state, operation reports, coordinates, transport/status and low-frequency information.

### Evidence

- **Blender Status Bar** shows active-tool keymap information, operation progress/messages and optional scene statistics.
- **Rhino Status Bar** keeps coordinate system, cursor coordinates, units and persistent modeling modes such as Grid Snap, Ortho, Osnap, SmartTrack and Gumball.
- **SketchUp for Web** uses the status area for selected-tool tips and the Measurements field.
- **Houdini** uses a status line for status/progress updates.
- **VS Code** uses the status bar for project/editor state rather than duplicating the main command surface.

### Why it works

The status region can reinforce the current context without competing with the main work surface.

### Failure mode

If a status bar repeats the same toggles and values already shown in a toolbar/canvas strip, it becomes visual noise rather than orientation.

### Museum adaptation

Grid/Snap/unit/control ownership should be reconciled. The status bar can echo current state and offer transient gesture/hint language; the primary control should live once.

---

## 3.6 Precision tracker near the action

### Pattern

Show numeric/constraint information in immediate relation to the active gesture.

### Evidence

- **Archicad Tracker** changes parameters based on the current editing operation and supports direct numeric entry.
- **Archicad Snap Guides** appear temporarily from current geometric context and disappear after the operation.
- **SketchUp Measurements** supports precise numeric entry during many tools.
- **P23.13** already establishes Museum Editor’s anchored numeric field, live dimension, snap marker and guide language.

### Why it works

It keeps precision in the flow of drawing rather than forcing round-trips to a side panel.

### Failure mode

A permanent tracker or too many simultaneous guides becomes clutter. Archicad’s distinction between temporary Snap Guides and explicitly placed permanent Guide Lines is instructive.

### Museum adaptation

P23.14 should visually support P23.13’s local instrument rather than competing with it. Shell contrast may quiet slightly during a gesture, but mode and ownership must remain legible.

---

## 3.7 Educational escalation instead of permanent tutorial prose

### Pattern

Teach in layers: hint → short contextual help → deeper optional help.

### Evidence

- **SketchUp**: active-tool tips in status plus optional Instructor panel.
- **Rhino**: F1/context-sensitive help and a Dynamic Help panel that tracks the running command.
- **Logic Pro**: Quick Help describes the interface element under the pointer.
- **Archicad**: contextual Pet Palette + Tracker teach available action and relevant parameter by use.

### Why it works

Beginners receive support without forcing experts to repeatedly scan explanations they already know.

### Failure mode

Permanent prose inside the Inspector costs vertical space exactly where properties will grow under P24/P26.

### Museum adaptation

Keep durable conceptual teaching available, but move it out of the default property path. Disabled/refused reasons should remain local and explicit because they are state, not tutorial copy.

---

## 3.8 Focus/maximize without losing the product

### Pattern

Give experts a way to enlarge the primary work surface while preserving an obvious escape and restoring layout state.

### Evidence

- **VS Code Zen Mode** can hide side bars, status and other chrome, then restore them.
- **Houdini** can maximize the pane under the pointer.
- **Rhino Fullscreen** can hide selected chrome while retaining configurable panel visibility.

### Why it works

Canvas-first becomes a user-controlled concentration mode instead of a permanently sparse shell.

### Museum adaptation

The existing focus/collapse architecture is directionally strong. P23.14 should make its state and exit affordance more coherent and keep selection context legible while rails are collapsed.

---

## 3.9 Timeline as a working zone, not an accessory card

### Pattern

Temporal surfaces use aligned rulers, tracks/rows and transport in a region that reads as part of the editor’s workspace geometry.

### Evidence

- **Logic Pro** makes time a first-class central working area with ruler, track headers and track rows.
- **Rive** combines timeline keys with selection-specific interpolation tooling.
- **After Effects** treats timeline/panels as peers in one workspace system.
- **Cubase** uses an integrated Lower Zone for specialized editors on single-screen layouts.

### Why it works

Temporal state feels spatially and structurally owned by the product, not bolted on over the canvas.

### Failure mode

A floating mini-player width or visual language unrelated to the main shell fragments the product. Museum’s current collapsed Timeline width mismatch is a direct example.

### Museum adaptation

The Camera Timeline should share shell grid, typography, divider and state grammar. The no-flow expanded state still needs intentional composition rather than a blank rectangle; however, removing or redefining lanes remains outside P23.14.

# 4. Visual-system dimensions

## 4.1 Hierarchy

Museum Editor needs more hierarchy than its current adjacent control runs communicate.

A useful visual stack is:

```text
project frame            strongest global landmark
  domain                 persistent authoring context
    view                  spatial representation
      local mode          stance within that cell
        tool              armed action
          gesture         temporary precision state
```

This hierarchy should be encoded through **position, container depth, type treatment, label/icon combination, and active-state construction** — not five unrelated accent colors.

Design question for concept work: should domain/view be a compact “location sentence,” two nested switchers, a split top bar, or another composition? Research does not force one answer. It does force the ranks to stop reading as peers.

## 4.2 Density

Target **structured density**, not sparse density.

Useful mechanisms:

- repeated 28–32-ish visual row cadence where desktop pointer targets permit it, with larger invisible/coarse targets where required;
- compact section headers that clearly reset scanning;
- indentation that means one thing consistently;
- labels before icon-only controls for concepts that users must learn;
- icon-only controls only for repeated, established commands with tooltips/shortcut reinforcement;
- property search only when depth justifies it;
- advanced disclosure for low-frequency attributes;
- consistent group spacing larger than row spacing;
- stable label/value columns for numeric scanning;
- tabular figures or monospace for measurements/references where useful;
- scroll position and disclosure persistence where it supports repeated work.

Avoid using whitespace as the primary hierarchy device. At 240–300px rails, whitespace is expensive and weak under load.

## 4.3 Typography

P23.13 already gives the Plan a deliberate drawing-language split: human-readable Room name, compact reference, measurement/reference numerics. Shell typography should harmonize without making the entire app feel like a drawing annotation layer.

Promising roles:

- **UI sans:** high legibility, compact x-height, calm at 11–13px-equivalent desktop sizes;
- **numeric/reference face:** tabular or monospace treatment for coordinates, units, stable references and timeline values;
- **display/editorial accent:** optional and very limited — project title, empty-state heading or educational surface — if a chosen territory needs warmth/identity.

Avoid all-caps as the universal way to signal hierarchy. It can work for rare micro-labels, but repeated all-caps section headings quickly become mechanical and “enterprise dashboard” coded.

## 4.4 Surfaces

A non-minimal editor still needs restrained surface count.

Promising system:

- one application/frame surface;
- one panel surface family;
- one inset/working-zone surface family;
- one canvas/paper/world surface;
- one elevated/transient surface family (popover, menu, tracker, toast);
- strong separators at ownership boundaries, weaker separators within sections.

Richness can come from **small tonal steps, edge treatment, inset depth and texture-like optical contrast**, not from cards around every group.

## 4.5 Color

Color should do work.

Museum already has semantic Plan colors from P23.13 (selection blue, snap teal, invalid crimson, graphite architectural mass). Shell design should not casually repurpose those hues for unrelated navigation.

A durable color policy should distinguish:

1. **semantic colors** — selection, focus, invalid, warning, success/save, snap;
2. **domain/context markers** — Scene/Camera or future instrument identity, used sparingly;
3. **surface palette** — warmth/temperature and depth, not semantic meaning;
4. **content colors** — artwork/material/light previews that must not be confused with chrome state.

W3C guidance reinforces that state must not rely on hue alone. Shape, outline, fill, iconography or text should reinforce color-coded state.

## 4.6 Iconography

Museum currently mixes Lucide, owner-ratified Plan icons and repo SVGs. A coherent shell does not require forcing every symbol into one generic stroke family if semantic distinction is useful.

Research suggests three useful icon roles:

- **navigation/system icons**: one consistent optical family;
- **authoring tool glyphs**: may be more bespoke/silhouette-driven where object recognition matters;
- **state/status glyphs**: simple shapes with strong contrast and redundant labels/tooltips.

The key is consistent optical size, stroke/fill logic and active/disabled treatment. “Same library” is less important than “same visual physics.”

## 4.7 State language

Museum needs a state construction that survives multi-selection, keyboard use and new instruments.

| State | Needed visual channels beyond hue |
|---|---|
| Hover | light contour / local highlight; no persistent handles |
| Selected | durable contour or row construction + identity synchronization |
| Primary/active in multi-selection | extra anchor/handle/emphasis, not just a different blue |
| Keyboard focus | distinct focus ring or outline geometry separate from selection |
| Active mode | persistent stance marker/container, not momentary pressed button |
| Armed tool | active tool well + label/icon + optional cursor change |
| Disabled | reduced affordance + reason path; never simply lower opacity with no explanation |
| Read-only/derived | visual treatment that says inspectable/contextual but not authorable |
| Invalid/refused | marker + text reason; transient refusal separate from standing warning |
| Warning | count/badge/icon + destination/detail; not identical to refusal |
| Temporary preview | ghost/guide/dashed or translucent construction distinct from committed state |
| Snap | relation marker + guide geometry + optional text; not color alone |
| Destructive | placement/grouping + explicit language + confirm where consequence warrants |

## 4.8 Motion

Motion in a professional editor should clarify state change, not decorate every interaction.

Useful motion classes:

- panel collapse/expand preserving spatial continuity;
- instrument entry/exit preserving return direction;
- selection reveal/scroll that shows where the entity went;
- transient toast/refusal arrival and expiration;
- timeline expansion/collapse;
- subtle active-tool or mode transition.

Avoid springy consumer-card motion for precision controls. Reduced-motion should preserve every state through static alternatives.

## 4.9 Panel grammar

A coherent panel family should define:

- header height and title treatment;
- optional contextual subtitle/selection identity;
- header actions position;
- section header/disclosure treatment;
- row padding/label/value alignment;
- inline status/reason placement;
- empty-state composition;
- footer/action strip rules;
- scrollbar and resize behavior;
- search/filter treatment;
- focus order.

Navigator, Inspector and Timeline should clearly be different **roles** built from related **primitives**.

## 4.10 Canvas chrome

Canvas chrome should answer only canvas-local questions:

- orientation/navigation;
- scale/coordinates where useful;
- view-local display controls;
- active gesture readout;
- safe selected-identity fallback when panels collapse;
- P26 instrument entry/exit and crop/depth controls later.

It should not repeat project save state, hierarchy inventory or Inspector content.

Plan and 3D currently use different chrome vocabularies. P23.14 should establish a shared placement/shape grammar even where the actual controls differ.

# 5. Professional + warm + educational + creative

These qualities can coexist if each is assigned to the right layer.

## Professional

Comes from:

- predictable ownership;
- crisp alignment and repeated control geometry;
- explicit units and numeric behavior;
- deterministic state;
- clear destructive/refusal treatment;
- dense but orderly information;
- visible keyboard/focus quality;
- stable names/references.

**Extreme failure:** “professional = gray flat enterprise UI.” This produces low memorability and often weak state hierarchy.

## Warm

Comes from:

- surface temperature and tonal relationships;
- humanist typography choices;
- careful microcopy;
- comfortable empty states;
- restrained depth/elevation;
- approachable labels rather than jargon-first icon walls;
- tactile but precise control affordances.

**Extreme failure:** oversized rounded cards, pastel everything, mascot-like illustrations in the working surface.

## Educational

Comes from:

- clear mode/tool language;
- contextual hints at the moment of action;
- visible reasons for disabled/refused states;
- optional deeper help;
- labels on unfamiliar controls;
- strong empty states that teach the next meaningful action;
- stable spatial memory.

**Extreme failure:** permanent prose blocks, every property carrying explanatory text, or tutorial copy competing with current selection.

## Creative

Comes from:

- a recognizable visual rhythm;
- richer surface treatment than default component-library UI;
- expressive but disciplined tool glyphs;
- meaningful color accents;
- responsive interaction feedback;
- canvas and timeline states that feel instrument-like;
- room for artwork/material color to remain visible without fighting chrome.

**Extreme failure:** decorative gradients, novelty shapes and animation with no semantic job.

## Combined principle

A useful target phrase for future concept review is:

> **Warm instrument, not friendly dashboard.**

Museum Editor should feel like a tool someone can learn and trust, whose interface has enough character to invite creative work but enough discipline to support architectural precision.

# 6. Anti-patterns

## 6.1 Generic minimal SaaS editor

Symptoms:

- near-white everything;
- borderless panels distinguished mainly by whitespace;
- icon-only actions hidden until hover;
- every state communicated through one blue accent;
- oversized empty regions that collapse under real document density;
- selection/property surfaces that resemble settings forms rather than instruments.

Why it fails Museum:

P24/P26 add state and depth; hidden affordances multiply discovery cost. The product also needs visible hierarchy between domain/view/mode/tool.

## 6.2 Flat editor chrome

Symptoms:

- domain, view, local mode, tool and display option all rendered as the same pill/button primitive;
- no structural break between global and local commands;
- active fill colors doing all semantic work.

Why it fails:

Users must read every label to know rank. New features create horizontal accretion.

## 6.3 Toolbar accretion

Symptoms:

- each new capability adds one more icon to Row 2;
- rarely used actions stay permanent because there is no contextual group grammar;
- P24/P26 become “just more buttons.”

Alternative:

stable groups + contextual instrument slot + Inspector sections + popovers for low-frequency commands.

## 6.4 Inspector as documentation page

Symptoms:

- project summaries, prose, inventory and selected properties share one vertical stream;
- the current object’s controls start below the fold;
- Scene and Camera open with different conceptual structures.

Alternative:

selection/property grammar first; teaching escalates elsewhere.

## 6.5 Hierarchy that mixes entities and explanation

Symptoms:

- relation rows look selectable;
- headings look like objects;
- debug IDs leak into normal identity;
- selection summary duplicates rows instead of reinforcing them.

Alternative:

explicit row species and P23.12 identity everywhere.

## 6.6 Excessive hiding

Symptoms:

- labels vanish until hover;
- active modes become tiny color dots;
- panel controls appear only when pointer enters the region;
- status disappears to achieve visual cleanliness.

Why it fails:

Screenshots look clean; working memory suffers. Authoring tools need persistent orientation.

## 6.7 Accent color as universal state

Symptoms:

same blue means selected entity, active tab, armed tool, focused input, primary action and information highlight.

Why it fails:

state collisions become inevitable; accessibility also suffers when hue is the main distinction.

## 6.8 “Warmth” via consumer-card styling

Symptoms:

large radii, floating cards everywhere, oversized spacing, soft gradients and large friendly headings in dense working surfaces.

Why it fails:

precision and density degrade. Warmth should live in material, typography and micro-interaction rather than cardification.

## 6.9 “CAD credibility” via inherited clutter

Symptoms:

tiny unlabeled icons, dense permanent toolbars, status switches everywhere, cryptic abbreviations.

Why it fails:

Museum Editor explicitly targets creators without CAD/DCC training. Credibility comes from precise behavior, not historical UI debt.

## 6.10 Duplicated state

Current Museum examples already include Grid/Snap in multiple places and several meanings of “Preview.” P24/P26 will make this worse unless P23.14 establishes ownership rules.

Rule:

> one authoritative control/location per state; passive echoes allowed only when they materially improve orientation.

# 7. P24 / P26 pressure tests

These are tests of shell qualities, not feature designs.

## 7.1 P24 staging pressure

P24 will introduce or deepen:

- ordered Scene multi-selection with one primary/active entity;
- mixed property values;
- transform and placement states;
- support/refusal reasons;
- material shared-vs-unique state;
- lights/environment;
- destructive resets;
- larger asset/scene hierarchy.

A P23.14 concept survives P24 if:

1. the Inspector can show one, many and mixed selections without changing its basic grammar;
2. the hierarchy can show more Scene content without inventing a separate staging tree;
3. active/primary selection is visually distinct from “also selected” without another selection authority;
4. placement preview/refusal uses the same transient-state language as architectural drafting;
5. material/light sections can grow behind clear section hierarchy rather than new top-level tabs for every capability;
6. destructive reset looks like an action with consequence, not a toggle;
7. `Local | World`, transform tools and placement state have a clear contextual home rather than permanent Row-2 accretion.

## 7.2 P26 spatial-instrument pressure

P26 may add contextual Section, Wall Elevation and Ceiling Focus instruments over one canonical LayoutDocument. These are not peer documents or independent workspaces.

A P23.14 concept survives P26 if:

1. entering an instrument changes the local working context without pretending a new document opened;
2. domain and canonical selection identity remain visible;
3. instrument kind has a visible home that is not hard-coded to exactly two view buttons;
4. crop/depth/reveal controls can appear contextually without becoming global toolbar clutter;
5. derived/read-only streams have a distinct presentation state but no second hierarchy truth;
6. exclusion/refusal reasons have a clear surface;
7. leaving the instrument has an obvious return path;
8. the same panel/property/state grammar applies in Plan, 3D and contextual orthographic work.

## 7.3 Shared pressure conclusion

P24 and P26 stress different product capabilities but the same shell architecture:

```text
stable frame
+ contextual tool/instrument slot
+ repeatable property sections
+ one hierarchy grammar
+ one selection/state language
+ one reason/refusal language
+ one transient-gesture language
```

If a concept needs a brand-new UI grammar for either P24 or P26, it is not durable enough.

# 8. Candidate design territories

These are deliberately different **directions**, not ranked options and not final designs. A designer should explore them far enough to expose trade-offs before synthesis.

## Territory A — Gallery Instrument

### Personality

Refined, warm, architectural, calm. Feels like a contemporary exhibition workspace crossed with a precision instrument — not literal museum branding.

### Hierarchy

Strong frame/panel geography. Domain/view location reads almost like a concise editor “address.” Local mode/tool layer sits beneath it as a lighter instrument rail. Canvas remains the lightest/openest field.

### Density

Medium-high. Compact rows, visible labels, restrained spacing, strong section rhythm. Little reliance on hover-only affordances.

### Surfaces

Warm neutral frame, slightly cooler paper/canvas, subtle inset panels, thin but confident separators. Floating/transient surfaces use sharper elevation and edge definition than permanent panels.

### Typography

Humanist UI sans; tabular/mono numerics; very limited editorial accent possible for project/empty-state identity.

### Color strategy

Surface warmth carries personality. Semantic colors remain disciplined: P23.13 selection blue/snap teal/invalid crimson stay meaningful. Domain identity uses low-saturation markers rather than recoloring whole panels.

### Interaction-state character

Precise outside contours, inset active wells, small state markers, crisp focus geometry. Selected tools feel mechanically “engaged,” not simply filled blue.

### Why it fits

It can make the product distinct without pushing it toward consumer design. The warm neutral frame can bridge architectural Plan paper and rich 3D/artwork content.

### Risks

Can become too tasteful/quiet and drift back toward minimalism. “Gallery” references can become decorative if taken literally. Needs a dense-state proof early.

---

## Territory B — Studio Console

### Personality

Dense, creative, energetic, expert-facing. Draws more from DAWs, animation/DCC tools and editing consoles than from SaaS or CAD.

### Hierarchy

Visually explicit zones with tool strips, meters/state markers and stronger dock boundaries. Camera Timeline integration becomes especially natural. Domain/view/mode ranks could read like nested console bands.

### Density

High. Compact labeled controls, strong repeated row metrics, little unused space. Information is allowed to remain visible if it is consistently placed.

### Surfaces

Dark or deep-neutral shell surrounding lighter/different canvas surfaces; layered panels with clear inset/raised relationships. Timeline and Inspector feel like instruments in the same machine.

### Typography

Neutral compact sans + strong numeric/tabular face. Labels can be slightly condensed if readability tests support it.

### Color strategy

Dark neutral foundation with purposeful colored state lights/lines and modest domain accents. Artwork/canvas color remains visually separate from shell state.

### Interaction-state character

Pressed/latched tool states, clear active lanes, strong focus/selection outlines, visible mode indicators. Motion restrained and mechanical.

### Why it fits

Museum Editor combines spatial editing and Camera direction; DAW/DCC console grammar makes the Camera Timeline feel first-class rather than attached. Richness without ornament comes naturally.

### Risks

Can intimidate novice creators, especially if icon labels disappear. Can resemble Blender/Houdini too closely if density becomes a goal in itself. Needs strong educational cues and generous first-use states.

---

## Territory C — Architectural Desk

### Personality

Precise, legible, drafting-forward, materially light. Feels like a contemporary architectural desk with technical instruments around a paper/model surface.

### Hierarchy

Clear tab/strip hierarchy, prominent view identity, compact left/right palettes, visible rulers/status. Local editing instruments can borrow from Archicad/Rhino-style precision patterns while preserving Museum’s simpler product model.

### Density

Medium-high. Labels remain visible; numeric fields and property sections are strongly aligned. Explicitness preferred over clever compression.

### Surfaces

Paper-like Plan field with neutral tool/palette surfaces, line-based separation, very limited card elevation. 3D retains the same chrome geometry even though the content surface changes.

### Typography

Clean technical sans + mono/tabular measurement face. References/units receive strong alignment discipline.

### Color strategy

Mostly ink/surface contrast with semantic colors carrying real meaning. Warmth can come from off-white/stone surfaces rather than colorful chrome.

### Interaction-state character

Drafting-like outlines, target markers, instrument readouts and explicit local guides. Active states are sharp and unambiguous.

### Why it fits

P23.13 already establishes credible architectural drawing language. This territory extends that credibility into the shell without turning the product into BIM.

### Risks

Can become bureaucratic, old-CAD or visually dry. Needs intentional creative identity in iconography, empty states and 3D/Camera integration. Must not let Plan aesthetics dominate Camera and staging surfaces.

---

## Territory D — Spatial Field Guide

### Personality

Approachable, educational, colorful in structure, exploratory. More willing to show named landmarks and contextual guidance than traditional CAD/DCC interfaces.

### Hierarchy

Strong navigation landmarks: domain/view location is unmistakable; contextual tool/instrument areas have named headers; hierarchy groups and Inspector sections use memorable but disciplined markers. Help lives one step away rather than in permanent prose.

### Density

Medium. More labels than icon-only expert UIs, but compact repeated rows keep the product from becoming card-heavy. Advanced properties disclose progressively.

### Surfaces

Layered neutral surfaces with small bands/markers that help orientation. Could use a narrow activity/location rail or stronger section edge markers rather than a uniformly colored toolbar.

### Typography

Highly readable humanist sans; numeric face remains precise. Slightly stronger editorial hierarchy in empty/learning states.

### Color strategy

Most expressive of the territories, but color assigned to **places/roles**, not arbitrary buttons. Semantic state colors remain protected. Domain marker may have an identity tint while controls remain neutral.

### Interaction-state character

Clear text + icon + shape reinforcement. Disabled actions can expose “why” directly. Empty states are concise and instructional. Instrument entry/exit gets explicit breadcrumb-like treatment.

### Why it fits

Museum Editor targets creators who may not have CAD/DCC training. This territory treats learnability as part of professional quality rather than as onboarding bolted on later.

### Risks

Easy to become toy-like, over-labeled or visually fragmented. Requires strict color budget and dense-screen testing. Educational cues must disappear or compress once understood.

---

## Territory comparison question

The designer should not choose by screenshot beauty. Each territory must be tested against the design-context screens A–F, especially:

- dense Plan + populated Inspector;
- active wall gesture;
- Scene 3D object selection;
- Camera Plan;
- Camera 3D with populated and empty Timeline;
- collapsed/focus state.

A territory that only looks excellent in an empty Scene Plan is not viable.

# 9. Questions for designer exploration

Research does not justify one answer to these. They should become explicit proposal decisions.

1. **What visual construction best expresses the semantic hierarchy** project → domain → view → local mode → tool without stacking five bars?
2. Should Scene/Camera identity be expressed through **position, heading, accent marker, iconography, or surface tone**? Which survives color-deficient viewing and theme changes?
3. How much of Row 2 should remain spatially stable across cells, versus allowing tools to reflow around a persistent location marker?
4. Does the shell want a clearly separate **global frame** and **workspace frame**, or can one top system carry both without flattening rank?
5. What surface relationship makes Plan, 3D and Camera Timeline feel like parts of one product while respecting their different content?
6. How should an eventual P26 contextual instrument show **entry, active kind and return path** without making `Ortho` a permanent peer workspace?
7. Which facts belong in the status bar after Grid/Snap/status duplication is removed?
8. What is the durable visual difference between **mode**, **armed tool**, **selected entity**, **keyboard focus** and **pressed control**?
9. How does future multi-selection show **selected set vs primary/active** in canvas, hierarchy and Inspector?
10. What is the Inspector’s minimum persistent header: entity kind, authored name, stable reference, selection count, ownership context?
11. Should Inspector sections use accordions, persistent stacked sections, tabbed groups, or a hybrid? Which works under P24/P26 load at ~300px width?
12. When does property search become justified? Is “advanced” disclosure enough for P23.14, or should the grammar reserve a search slot?
13. How should read-only/derived properties look compared with disabled-but-potentially-editable properties?
14. What is the one standard pattern for **“why disabled / why refused / why excluded”** across save, placement, topology and future P26 Reveal cases?
15. Should the Navigator keep `Hierarchy | Assets` as peer tabs, or should assets become a different navigation level/surface? P24 pressure makes this worth testing without solving P24 here.
16. What row species are needed for entity, group heading, relation metadata, selected off-page item and read-only context?
17. What is the signature panel/header geometry that can make Museum Editor recognizable without decorative branding?
18. Can a warm light shell coexist with dark 3D content and the settled cool Plan paper without theme discontinuity?
19. If a dark/console territory is explored, how does the light P23.13 Plan surface sit inside it without looking like an embedded foreign app?
20. How much educational help belongs in status, tooltip, popover, optional help panel and empty state respectively?
21. What concise teaching replaces the current Scene Inspector prose while preserving its useful concepts?
22. How should the Camera no-flow Timeline use its expanded body so the state reads intentional but does not invent fake lanes?
23. How can quiet/constant Timeline lanes be visually de-emphasized without changing Camera semantics?
24. What grid alignment should bind left rail, viewport, Timeline, Inspector and status so the shell reads as one constructed workspace?
25. Which controls can safely become icon-only, and which concepts need persistent text until users have learned them?
26. How does the shell handle the 240px left-rail minimum without truncating canonical identity or collapsing row meaning?
27. How should focus/collapse mode retain selection identity and location when both side panels become inert?
28. What coarse-pointer adaptations can be achieved without inflating every desktop control visually?
29. What motion vocabulary communicates panel/instrument transitions without introducing consumer-app softness?
30. Which parts of the visual identity remain invariant across themes, so seven themes do not become seven separate products?

# Closing synthesis

The highest-ceiling P23.14 direction is not “polish the existing two-row shell” and not “make the UI cleaner.” It is to establish a **visual operating system** whose semantic ranks, panel grammar, state language and contextual-instrument model are strong enough that the current shell can change substantially while the product architecture remains intact.

The best mature precedents do not choose between richness and clarity. They make richness **legible**. They use persistent landmarks, repeated dense grammar, explicit state and contextual precision. Museum Editor can take the same structural lesson while developing a warmer, more creative identity than traditional CAD/DCC software.

The next design phase should therefore explore materially different territories and judge each against dense working states, Camera Timeline states, focus/collapse, P24 mixed-selection pressure and P26 instrument-entry pressure — not against a single clean Scene Plan screenshot.
