# P23.14 — Editor Shell & Visual System Foundation: precedent research

**Status:** deep design research; input to designer exploration, **not** a visual specification and **not** an implementation plan.  
**Date:** 2026-09-17.  
**Primary product baseline:** [`docs/design/P23.14-shell-design-context.md`](../../design/P23.14-shell-design-context.md).  
**Related settled/future context:** [`P23.13 final design specification`](../../design/P23.13-final-design-specification-Designer-D.md), [`P24 Scene/Staging Depth umbrella`](../../plans/2026-09-08-P24-scene-staging-depth-umbrella.md), [`P26 Architectural Spatial Depth synthesis`](../P26-research/P26-architectural-spatial-depth-synthesis.md).

## Research posture

This document studies visual and interaction systems that could give Museum Editor a durable professional-editor identity. It deliberately does **not** select a final shell, prescribe CSS/components, or turn P24/P26 into P23.14 features.

The repository baseline remains authoritative for architecture and product ownership. In particular: Scene/Camera remains one domain axis over one project world; Plan/3D remains the top-level view distinction; P26 orthographic views are contextual instruments rather than peer document worlds; the viewport remains the primary work surface; the Camera Timeline stays Camera-owned; `LayoutDocument` and `SceneDocument` remain separate authorities; selection/history/navigation/camera-motion stay single-authority systems; visitor/editor isolation is non-negotiable.

The five current P23.14 shell screenshots were reviewed through the repository's screenshot inventory and the image-by-image evidence record in the P23.14 design-context document. The connected repository interface exposed the files and their metadata but not their raster pixels, so screenshot-specific claims here are limited to that checked-in evidence record rather than invented pixel-level observations. The screenshots remain orientation evidence, not a visual target.

External precedent research favors current official documentation where practical. The purpose is to extract transferable patterns, not to reproduce another product's UI.

# 1. Executive synthesis

## 1.1 Strongest finding: build a stable workbench, not a disappearing canvas

The most durable professional editors do not achieve canvas dominance by deleting the interface. They keep a **stable frame of landmarks** and let the content inside those landmarks become contextual.

Blender keeps Areas/Editors and task-oriented Workspaces; Unreal keeps viewport, Outliner and Details relationships stable while the selected object changes; VS Code keeps Editor, Side Bars, Panel and Status Bar roles stable while their content changes; After Effects keeps panels and workspaces stable while allowing grouping, stacking and soloing. These systems can become dense, but the user does not need to rediscover where hierarchy, properties, status or the main work surface live after every context switch.

For Museum Editor, the likely high-ceiling model is therefore:

> **persistent shell landmarks + visibly ranked context + contextual depth inside the landmarks.**

This is different from generic canvas-app minimalism. It allows the shell to remain visible, informative and distinctive while keeping the viewport primary.

## 1.2 Museum Editor's current problem is not “too much chrome”; it is weak semantic ranking

The current shell puts domain (`Scene | Camera`), view (`Plan | 3D`), local mode (`Layout | Arrange`), armed tools and display controls close together. The P23.14 baseline already identifies this as control-weight flatness. Removing half the controls would make the screenshot cleaner without solving the conceptual problem.

Research suggests a better question: **what rank is each control expressing, how long does that state live, and what owns it?** Mature tools distinguish application/workspace context, view context, tool state, selection, properties and transient gesture state through placement, grouping, labels, surface hierarchy and persistence—not only through button fill.

P23.14 should therefore establish a visual grammar for rank before choosing a style.

## 1.3 Richness should come from meaningful layers, not ornamental density

The requested non-minimal direction is credible. Blender, Houdini, Unreal, Ableton, After Effects and GIS/engineering software all demonstrate that a professional tool can remain information-rich and recognizable. Their stronger patterns are not “show everything.” They use:

- stable surface hierarchy;
- compact repeated row rhythms;
- strong panel/section landmarks;
- typography that distinguishes labels from values;
- visible state and ownership;
- domain-appropriate iconography;
- selective semantic color;
- disclosure and filtering when the information set grows.

The useful goal is **structured richness**. Decorative cards, shadows, gradients or accent colors do not create professional depth if ownership and state are still ambiguous.

## 1.4 The shell should make selection coherence one of the product's signatures

Unreal's viewport ↔ Outliner ↔ Details relationship is a particularly strong precedent for Museum Editor: one object identity appears coherently in the scene, hierarchy and property surface. Museum Editor already has a stronger architectural reason to preserve this because one deterministic selection authority is a fixed contract and P24 will extend it to ordered multi-selection with a primary entity.

This can become a recognizable product behavior, not merely an implementation constraint:

> **Wherever an entity appears, selection looks related; wherever properties appear, their owner is obvious; switching views changes affordances, not identity.**

That principle also protects P26, where canonical selection must survive Plan/Section/Elevation/3D transitions.

## 1.5 Educational UX should move out of permanent property prose

Museum Editor currently spends prime Inspector space explaining the product. Ableton provides a useful opposite model: guided learning is a dedicated Learn View, while Info View supplies context-sensitive explanation for what the pointer is over. After Effects similarly separates a Learn workspace/panel from normal production panels.

The transferable lesson is not “copy a Help panel.” It is:

> **teaching should appear at the moment and scope where uncertainty exists, without permanently displacing the work.**

For Museum Editor that means favoring concise labels, reason-coded disabled states, focused tooltips, contextual help, empty-state teaching and optional deeper explanation. The Inspector should remain property-first.

## 1.6 Progressive density is better than progressive disappearance

The strongest dense-editor precedents manage growth through panel sections, filters, stacked/solo groups, optional columns, context tabs and search. They do not rely on hover-reveal for core state.

This matters directly for P24 material/light properties and P26 architectural properties. The Inspector needs a density grammar that can add capability without becoming either a scroll dump or a set of hidden mystery controls. Likewise the Navigator needs a hierarchy grammar that can distinguish entities, groups, relation metadata and search results without turning all rows into equivalent selectable objects.

## 1.7 Status is valuable when it is curated

Blender and VS Code both preserve status areas, but their strongest use is contextual: current tool hints, workspace/file state, progress, warnings and concise environment state. VS Code's own UX guidance explicitly warns against status-bar accretion.

Museum Editor's status bar should remain a useful persistent landmark, but current triplication of Grid/Snap/status facts across ribbon, canvas and status bar is the wrong kind of richness. A durable system needs **one authoritative home per fact, with at most one deliberately passive echo**.

## 1.8 Timeline should read as part of the Camera workspace grid, not as a bolted-on media widget

After Effects and DaVinci Resolve show that temporal surfaces feel integrated when panel edges, headers, hierarchy, selection language and transport logic belong to the same workspace grammar as the spatial/composition view. Museum Editor's Camera Timeline already has strong product ownership; P23.14 should use that ownership to make the dock structurally coherent with the viewport and side surfaces.

The no-flow, edge and sequence states should read as different contents of one Camera-owned surface, not as unrelated widgets. Visual density can adapt by scope; the semantic lane set remains a Camera decision.

## 1.9 P26 makes “nested context with a return path” a first-class shell problem

ArcGIS Pro's active-pane/contextual-tab system, Blender's editor/workspace distinction and several CAD/DCC patterns all show ways to expose context without pretending every context is a new document world. P26 specifically rejects permanent peer workspaces for Section, Wall Elevation and Ceiling Focus.

P23.14 should therefore avoid a shell primitive that means “every new view becomes another top-level tab.” It needs room for a **contextual instrument layer** subordinate to the durable Plan/3D distinction, with explicit entry, current context and return navigation.

P23.14 should design the grammar; P26 later decides the exact product presentation.

## 1.10 Professional, warm, educational and creative can coexist because they come from different mechanisms

These qualities do not need one compromise visual style.

- **Professional** comes from precision, stable ownership, readable density, explicit units, deterministic state and trustworthy feedback.
- **Warm** can come from neutral temperature, typography, shape character, humane copy and gentle surface/motion treatment.
- **Educational** comes from contextual explanation, meaningful labels, reason codes, previews and progressive disclosure.
- **Creative** can come from a distinctive surface vocabulary, controlled color, icon character, spatial composition and the relationship between shell and canvas.

Trying to make every button simultaneously “friendly + creative + technical” produces noise. Assign these qualities to the layers that can carry them best.

## 1.11 Most promising overall direction

Research does not justify one final aesthetic, but it does justify a product-system direction:

> **A visibly instrumented workbench: stable landmarks; strong semantic rank; compact but not hidden controls; an Inspector that edits rather than explains; hierarchy that distinguishes entities from metadata; contextual teaching; a state system richer than hue; and a controlled signature visual language framing the P23.13 architectural paper/ink canvas.**

The next design phase should explore substantially different aesthetic territories inside this system rather than “polishing the current UI.”

| **2. | **3. | **8. # 3. Precedent patterns

This section groups patterns by transferable idea rather than cataloguing applications.

## 3.1 Stable workbench, contextual contents

### Pattern

A persistent workbench defines **where kinds of work happen**. Selection, active tool or active pane changes the contents inside those regions.

### Why it works

- spatial memory survives context changes;
- users can predict where properties/hierarchy/status appear;
- visual density becomes learnable through repetition;
- new capability can enter an existing region instead of demanding a new shell.

Unreal is especially clear: Viewport, Outliner and Details have distinct roles; selecting an actor in either Viewport or Outliner synchronizes the other and populates Details. VS Code similarly preserves Editor, Side Bars, Panel and Status Bar. After Effects allows deep panel rearrangement but still uses a consistent panel grammar.

### Failure mode

Full workspace configurability can become a product of its own. Blender and Adobe support deep rearrangement because their expert audiences need it, but Museum Editor does not need arbitrary pane composition to gain their structural benefits.

### Adapt, do not copy

Adopt stable semantic regions and strong panel grammar. Do not adopt full “every panel can be anything” customization unless a later real workflow proves it necessary.

## 3.2 Selection synchronization as a trust mechanism

### Pattern

One selection appears simultaneously in the canvas, hierarchy and property surface.

### Why it works

The user learns a dependable loop:

`find → select → locate → inspect → edit → see result`.

The same pattern supports discoverability from either direction: find an entity in space and reveal it in hierarchy, or find it in hierarchy and reveal it in space.

### Failure mode

Some mature editors allow pinning/locking a property pane or independent selection contexts. Those are useful expert features but also create multiple simultaneous contexts. Museum Editor's fixed one-selection-authority contract means copying that flexibility would be harmful unless the architecture later explicitly changes.

### Adapt, do not copy

Make cross-surface continuity visually strong. “Pinned Inspector selection” should not be borrowed merely because Unreal/After Effects can lock viewers/panels.

## 3.3 Contextual command layers, not one infinite toolbar

### Pattern

Commands are organized by scope and current context. ArcGIS Pro makes this explicit with a stable ribbon whose visible tabs/groups can change with application/pane state. Blender separates Workspace, Editor, active Tool and tool settings. Sketch keeps a contextual toolbar while the Inspector changes by selection.

### Why it works

The interface communicates **why an action is present**. The user sees groups of related actions rather than a bag of buttons.

### Failure mode

A ribbon can become bureaucratic: many tabs, big labels and groups make the app feel like enterprise software rather than a spatial creative tool. A fully contextual toolbar can also shift too much, weakening muscle memory.

### Adapt, do not copy

Use rank and grouping logic, not a literal Office ribbon. Keep high-frequency control locations stable even if the available tool set changes.

## 3.4 Dense panels that shed complexity gracefully

### Pattern

High-information tools use multiple density controls at once:

- disclosure sections;
- search/filter;
- optional columns;
- stacked panels;
- solo/expand behavior;
- compact row patterns;
- advanced sections.

After Effects is a strong precedent: panels can group/tab/stack; stacked panels can solo; Timeline/Project columns can be shown, hidden, reordered and resized. Unreal Outliner supports search/filter/columns. Blender Properties uses context tabs and collapsible panels.

### Why it works

The information stays available without demanding equal prominence at all times.

### Failure mode

Over-disclosure creates “accordion archaeology”: users spend more time opening sections than working. Search can also become an excuse for weak information architecture.

### Adapt, do not copy

Museum Editor should decide a small number of durable Inspector sections and default-open priorities. Search/filter should serve genuinely large property/hierarchy sets, not compensate for a poor base order.

## 3.5 Contextual education instead of permanent tutorial chrome

### Pattern

Ableton separates learning into two scales: Learn View for guided instruction and Info View for short context-sensitive explanation. After Effects similarly offers a Learn panel/workspace without making it the normal production shell.

### Why it works

A beginner can ask “what is this?” without forcing an expert to repeatedly scroll past the answer. Teaching can follow the user's current target.

### Failure mode

Tooltips alone are insufficient for conceptual workflows; guided help everywhere becomes noise; tutorial cards inside every empty state become visual debt.

### Adapt, do not copy

Use a layered education model:

1. visible labels and meaningful grouping for core concepts;
2. hover/focus explanation for control meaning;
3. reason text for disabled/rejected states;
4. contextual empty-state guidance for first action;
5. optional deeper help for concepts such as wall hosting or camera flow.

This is particularly well suited to moving today's wall-first explanatory prose out of the Inspector.

## 3.6 Timeline as a workspace surface, not an accessory

### Pattern

After Effects and DaVinci Resolve treat timeline/composition surfaces as structural peers inside a media workspace. Their timelines share selection, headers, panel edges, density controls and terminology with the rest of the application.

### Why it works

Temporal editing feels like another dimension of the same project, not a mini-app pasted under the canvas.

### Failure mode

Media editors can become timeline-first. Museum Editor must not let the Camera Timeline dominate Camera Plan/3D when spatial authoring is the actual task.

### Adapt, do not copy

Align Timeline edges, header grammar, state language and typography with the shell grid. Preserve its Camera-only ownership and its 48/288 behavior. Let no-flow/edge/sequence scope change density inside the same framing.

## 3.7 Workspace identity without product fragmentation

### Pattern

DaVinci Resolve gives workflow pages strong identity, while Blender Workspaces give task-specific arrangements. Adobe applications share a family of panel behaviors even when individual tools differ.

### Why it works

Different tasks can feel purpose-built without teaching a second UI from scratch.

### Failure mode

If domain switching changes the entire visual metaphor, Scene and Camera start to feel like separate products. This would be particularly wrong for Museum Editor because the domain switch is attention-only and the world/document/history remain shared.

### Adapt, do not copy

Scene and Camera may have bounded context cues and different tool contents, but panel headers, row grammar, state semantics, selection presentation, typography and density should remain one system.

## 3.8 Strong state systems use redundant channels deliberately

### Pattern

Professional editors use combinations of contour, fill, handles, icons, labels, cursor, placement and color to distinguish hover, selection, tool activation, focus, disabled and error states. WCAG explicitly requires that color not be the only visual means for important information, and keyboard focus must be visible.

### Why it works

A state remains legible in different themes, with reduced color perception, and when multiple states overlap.

### Failure mode

The opposite failure is visual overload: every state adds another glow, badge and color. State channels should be assigned, not accumulated.

### Adapt, do not copy

Create a state precedence model and reserve visual channels by meaning. P23.13 already provides a good canvas precedent: physical wall mass survives selection while blue sits outside it; snap and invalid use separate semantic treatments; keyboard focus is distinct.

# 4. Visual-system dimensions

These are dimensions the designer should take a position on. They are **not token prescriptions**.

## 4.1 Hierarchy: establish a visible rank ladder

Museum Editor contains more semantic ranks than today's Row 2 presentation acknowledges. A useful design model is:

| Rank | Meaning | Lifetime | Examples | Visual implication |
|---|---|---|---|---|
| **A. Product / project** | What project and project-wide state am I in? | Long-lived | project identity, persistence, Undo/Redo, Preview/Publish/account | Stable frame; never visually confused with an authoring tool. |
| **B. Domain** | Which authoring concern has attention? | Session-scale | Scene / Camera | Strong landmark, but switching it must not look like loading another document. |
| **C. Primary view** | How am I looking/working spatially? | Task-scale | Plan / 3D | Strong but subordinate to domain; future-safe. |
| **C2. Contextual instrument** | What temporary derived precision context is open? | Task/subtask | future Section / Wall Elevation / Ceiling Focus | Must read as nested context with return path, not peer project mode. |
| **D. Workspace-local stance** | Which local operation family is active? | Task-scale | Layout / Arrange | Clearly subordinate to domain/view. |
| **E. Armed tool / momentary action** | What will the next gesture do? | Gesture/chain | Wall, Door, Move, Connect, Add Camera | Compact, repeatable tool grammar; armed state obvious. |
| **F. Selection / property context** | What entity/entities own the properties? | Selection-scale | selected Wall, Scene object, Camera | Cross-surface identity grammar. |
| **G. Transient / status** | What is happening right now? | Seconds | snap, preview, invalid refusal, saving, drag dimension | Near action point or status region; must not masquerade as persisted state. |

The exact composition is open. The need for distinct rank is not.

A likely failure is three nested segmented controls with different labels but identical geometry. Another failure is putting every rank into a different colored pill. Rank should come from **placement + grouping + type + shape + persistence + surface**, with color supporting rather than carrying the entire distinction.

## 4.2 Density: compact, legible, landmarked

Professional density works when the eye can chunk it quickly. Museum Editor should explore:

- compact rows with consistent baselines;
- predictable label/value alignment;
- section headers strong enough to scan but not larger than the work;
- indentation reserved for real hierarchy;
- disclosure used for advanced or secondary groups, not every three-row block;
- dividers/spacing that express ownership changes;
- stable row heights for repeated property controls;
- visible units and tabular numerics;
- limited badges and chips reserved for exceptional state;
- search/filter only where the content set actually warrants it;
- high-information states designed explicitly, rather than treating the empty two-room state as the canonical screenshot.

The target is not maximum compactness. It is **high information per visual decision**.

## 4.3 Typography: human labels, technical values

P23.13 already establishes a useful conceptual split inside Plan: human-readable labels and technical numeric/reference typography. The shell can echo that logic without literally reusing drawing type styles everywhere.

Explore a typography system with:

- a warm/humanist or neutral UI sans for navigation, entity names and explanatory text;
- tabular figures for measurements and transforms;
- optional mono treatment for compact references/technical identifiers where it improves alignment;
- clear differentiation between panel header, section header, property label, value, helper/reason text and status text;
- sentence case as the default for readable UI, with all-caps reserved—if used at all—for small structural eyebrows rather than every section title;
- no tiny low-contrast helper copy as the primary explanation of state.

A serious editor usually feels serious because its numbers, labels and ownership are disciplined—not because everything is condensed gray text.

## 4.4 Surfaces: use a small depth vocabulary

A rich editor can use layered surfaces without turning into card soup. Explore a small number of structural surface roles:

1. **application frame** — project/global context;
2. **workspace frame** — rails/ribbon/timeline chrome;
3. **panel content** — hierarchy/properties rows;
4. **canvas/work surface** — P23.13 paper in Plan, spatial viewport in 3D;
5. **transient overlay** — menus, numeric fields, refusals, previews.

Depth may come from tonal shift, edge treatment, inset/outset borders, shadows, texture or a combination. The important part is consistent semantic use.

Avoid giving every control its own rounded container. Large numbers of independent cards erase hierarchy because every local group claims equal visual importance.

## 4.5 Color: semantic first, character second, bounded context third

P23.13 already assigns meaningful Plan colors: graphite physical ink, selection blue, snap teal, invalid red and dark focus treatment. P23.14 should not create a shell where generic brand blue is used simultaneously for selection, active domain, active view, armed tool, focused field and primary CTA.

A durable color strategy should distinguish at least:

- **canonical selection**;
- **keyboard focus**;
- **snap/guide success**;
- **invalid/refusal**;
- **warning/standing issue**;
- **destructive**;
- **read-only/derived context**;
- **domain/context accent**, if adopted;
- **neutral active controls**.

Warmth can come from neutral surface temperature and restrained contextual accents rather than turning every surface beige. Creative identity can come from one or two distinctive accent relationships, not an unrestricted palette.

A promising precedent is Houdini's use of bounded context coloring in pane headers: context can be visible without repainting all controls. Museum Editor could explore a similar principle while remaining much simpler.

## 4.6 Iconography: optical coherence matters more than one source library

Museum Editor currently mixes Lucide-derived icons, owner-ratified custom Plan icons and repo SVGs. P23.13 correctly protects certain Plan tool silhouettes. P23.14 should not erase semantic decisions merely to achieve “one icon pack.”

Research suggests focusing on:

- optical stroke/fill weight at actual shell sizes;
- consistent bounding boxes and visual centers;
- stable metaphors for selection, move, rotate, scale, view and disclosure;
- labels beside ambiguous/high-rank concepts such as Scene/Camera or Plan/3D;
- custom icons where domain meaning genuinely needs them;
- state changes that do not rely on swapping to an entirely different metaphor.

The goal is **one visual family**, not necessarily one vendor source.

## 4.7 State language: reserve channels by meaning

A candidate state matrix for design exploration:

| State | Must communicate | Non-hue channel candidates | Color role |
|---|---|---|---|
| Hover | hittable / preselection | neutral contour, surface lift, cursor | secondary only |
| Selected | canonical entity identity | outer contour, row marker, handles, Inspector header | stable selection accent |
| Primary in multi-select | active member of selected set | stronger contour/marker, explicit primary indicator | same selection family, stronger value |
| Keyboard focus | keyboard target | dedicated focus ring/offset/shape | neutral/dark or dedicated focus token; never selection-only |
| Active domain/view | current context | placement, label weight, selected segment geometry | bounded contextual accent possible |
| Active local mode | stance | subgroup surface / inset segment / label | usually neutral-active |
| Armed tool | next gesture behavior | pressed/latched geometry, tool cursor, short state label | accent support, not only signal |
| Disabled | unavailable | reduced affordance + reason on hover/focus | low chroma; retain readable text |
| Invalid/refusal | proposed operation rejected | stop/error icon, boundary/marker, reason text | invalid semantic color |
| Warning | standing issue | warning icon/count, section marker | distinct from refusal color treatment |
| Destructive | irreversible/high consequence action | explicit label/icon, separated action region, confirmation where required | destructive semantic color sparingly |
| Temporary preview | not committed | ghost/dashed/translucent geometry, live readout | contextual neutral/accent |
| Snap winner | relationship will be applied | unique marker shape + guide + relation text | snap semantic color |
| Authored vs derived | canonical versus computed/read-only | row treatment, icon/label, interaction affordance | mostly structural, not color-only |
| Read-only context | visible but not editable here | muted interaction affordance, lock/context cue only when needed | lower emphasis without looking disabled if still selectable/revealable |

The designer should test overlapping states, e.g. selected + focused, selected + invalid gesture, multi-selected + primary + hovered, and read-only context + selected canonical entity.

## 4.8 Motion: explain change, do not decorate it

Useful motion roles:

- preserve where a panel/Timeline came from as it expands/collapses;
- show nested instrument entry/return without pretending a new document loaded;
- maintain selection continuity across Plan/3D/contextual views;
- acknowledge successful state changes or mode transitions;
- make reflow/disclosure comprehensible.

Avoid bounce, overshoot or ambient animation in measurement-heavy controls. Reduced-motion behavior must remain first-class.

## 4.9 Panel grammar: make the right and left rails cousins, not twins

A shared panel system should define common structure while preserving role differences.

**Navigator / left rail:** “what exists, where it belongs, and how to reveal it.” It needs hierarchy rows, group headings, search, selection markers, reveal actions and visibly secondary relation metadata.

**Inspector / right rail:** “what the current selection is and what can change.” It needs a strong selection header, compact property sections, units, mixed/inherited/shared states later, contextual actions and reasoned disabled/destructive actions.

Both can share:

- header height and typography;
- section-header treatment;
- row metrics;
- disclosure affordance;
- search/input grammar;
- badges/reason text vocabulary;
- keyboard focus treatment.

They should **not** share content simply because a component exists. The Inspector must not become inventory; the Navigator must not become a second property editor.

## 4.10 Canvas chrome: one utility grammar across Plan, 3D and future instruments

Current Plan and 3D place utilities differently. P26 increases the cost of leaving this unresolved.

Explore a unified rule for:

- orientation/axis affordance location;
- scale/units;
- grid/snap display state;
- view helper toggles;
- current instrument/context label;
- temporary selection readout when rails collapse;
- safe zones for anchored fields, snap labels and refusals.

This does **not** mean every view shows identical widgets. It means a creator learns where view-local utilities and status belong.

# 5. Professional + warm + educational + creative

These qualities can reinforce one another when each is expressed through appropriate mechanisms.

| Quality | Concrete mechanisms | Useful precedents | Failure extreme |
|---|---|---|---|
| **Professional / credible** | stable shell geometry; explicit units; aligned numerics; clear property ownership; deterministic selection; visible reasons; compact hierarchy; consistent commands | Unreal, Rhino, Blender, ArcGIS Pro | sterile gray control matrix; fake CAD complexity; tiny text mistaken for sophistication |
| **Warm / inviting** | humane type; warmer neutral frame; gentle surface transitions; clear empty states; readable labels; restrained corner/edge character; calm motion | Ableton's direct language, modern Sketch/Figma/Penpot clarity, creative-tool panel systems | oversized rounded cards; pastel consumer dashboard; cute copy during technical failure |
| **Educational** | visible labels for high-rank concepts; contextual Info/Help; reason-coded disabled/refused states; previews; guided first-use surfaces; progressive labels | Ableton Info/Learn View, After Effects Learn workspace, Figma optional property labels | permanent tutorial prose; tooltip dependence for core concepts; onboarding banners that never disappear |
| **Creative / recognizable** | controlled signature accent; distinctive surface/edge vocabulary; coherent custom spatial icons; domain framing; intentional relationship between architectural paper and shell; expressive but bounded state transitions | Ableton/Houdini/DCC identity, Adobe workspace coherence | decoration without semantics; arbitrary gradients; every panel becoming visually unique |

## 5.1 A useful identity opportunity: “architectural paper inside an instrumented studio”

P23.13 already gives Plan a strong material metaphor without literal skeuomorphism: cool paper, graphite architectural mass, restrained drafting ink, blue selection outside the physical band, teal snap and red invalid state.

P23.14 can either ignore that and wrap it in generic SaaS chrome, or use it as one ingredient in a broader identity. A promising research direction is to let the **canvas feel like the drawing/model surface** while the **shell feels like the instrument bench around it**.

That does not require fake metal, rulers or paper texture. It can be achieved through contrast in surface tone, edge treatment, numeric typography, icon character and measured use of color.

This should remain one design territory among several, not a preselected answer.

## 5.2 Warmth should not weaken refusal and destructive states

Friendly software is not software that avoids saying “no.” Museum Editor's architecture already requires invalid edits to be refused with reason. Warmth here means concise, human explanation and a clear next step—not softening an invalid state until it looks optional.

Likewise P24's destructive lighting reset should look intentionally consequential even if the rest of the shell is warm.

## 5.3 Educational does not mean beginner-only

The highest-value teaching features also help experts when context is unusual: why a placement candidate is rejected, why an action is disabled, which entity owns a mixed property, why an object is excluded from a future Section depth, or which tool will receive the next gesture.

Design education as **explainability of state**, not as a tutorial layer glued over the editor.

# 6. Anti-patterns

## 6.1 Generic minimal SaaS shell

**Symptom:** white/gray cards, large whitespace, one blue accent, icon-only actions, core state revealed only on hover.

**Why it fails:** authoring tools need persistent spatial/state memory. It also makes every semantic state fight for the same accent color.

## 6.2 “Canvas-first” interpreted as “hide the editor”

**Symptom:** rails auto-hide, mode labels disappear, properties become floating popovers, important state appears only under the pointer.

**Why it fails:** it improves clean screenshots while worsening orientation, keyboard use and dense workflows. Focus mode already provides an explicit way to collapse the shell when desired.

## 6.3 Flat editor chrome

**Symptom:** domain, view, local mode, tool and display toggle all use the same segmented-control/button style.

**Why it fails:** semantic rank disappears. Adding P24/P26 controls then produces toolbar accretion rather than hierarchy.

## 6.4 Cardification

**Symptom:** every Inspector section, toolbar group and status block becomes a rounded card with shadow.

**Why it fails:** the page becomes visually busy while structure becomes weaker; cards imply independent objects even when the content belongs to one continuous property surface.

## 6.5 Accent-color inflation

**Symptom:** the same bright color means selected object, active domain, current view, armed tool, focused field, primary action and link.

**Why it fails:** state collisions become inevitable. It also undermines P23.13's carefully assigned selection/snap/invalid language.

## 6.6 Mode ambiguity

**Symptom:** a creator cannot tell whether a highlighted control is a workspace, a persistent stance, an armed tool, a toggle or a momentary action.

**Why it fails:** the lifetime of the state becomes unpredictable. Museum Editor's `Scene`, `Plan`, `Layout`, `Wall`, `Grid` and `Preview` are not equivalent choices.

## 6.7 Panel clutter disguised as comprehensiveness

**Symptom:** every property visible, all sections open, repeated project summaries, permanent explanatory prose, many badges.

**Why it fails:** high density without hierarchy becomes exhausting. Progressive density should preserve access while ranking relevance.

## 6.8 Excessive disclosure

**Symptom:** almost nothing visible until the correct accordion, hover target or kebab menu is found.

**Why it fails:** experts cannot scan; learners cannot discover; keyboard paths get obscure. Disclosure is a density tool, not a substitute for information architecture.

## 6.9 Duplicated state

**Symptom:** Grid/Snap/save/selection facts rendered as independently interactive controls in several surfaces.

**Why it fails:** the user cannot tell which one owns the setting and implementation risks divergent state.

## 6.10 Inspector as dashboard or inventory

**Symptom:** project status, counts, tutorials and creation catalog all compete above selected-entity properties.

**Why it fails:** the property surface loses its contract. P24/P26 will make this much worse if not corrected before they add sections.

## 6.11 Hierarchy rows that lie about affordance

**Symptom:** relation text, counts and entity rows share identical row treatment even though only some are selectable.

**Why it fails:** the user forms the wrong mental model of what exists as an editable entity.

## 6.12 Theme as identity

**Symptom:** seven color themes are treated as the product's visual identity.

**Why it fails:** a durable identity should survive theme changes through type, geometry, hierarchy, iconography and state language. Theme is a variation layer, not the design system.

## 6.13 Literal CAD cosplay

**Symptom:** dense command ribbons, tiny glyph grids, technical jargon and monochrome panels are added because “professional tools look like that.”

**Why it fails:** Museum Editor explicitly targets creators without CAD/DCC training and is not a BIM system. Architectural credibility should come from the model, drawing language and precision—not unnecessary complexity.

## 6.14 “Friendly” consumer-app cosplay

**Symptom:** giant rounded buttons, cheerful illustration on every empty state, conversational copy in property rows.

**Why it fails:** it lowers information density and can make precise spatial editing feel unserious.

# 7. P24 / P26 pressure tests

P24 and P26 are used here only to test system durability.

## 7.1 P24 staging pressure

| Future pressure | Shell quality that must survive | Failure if P23.14 gets it wrong |
|---|---|---|
| Ordered multi-selection + primary entity | selection language must scale from one to set+primary without new authority | different highlight systems for viewport, tree and Inspector |
| Mixed property values | property rows need a clear “mixed” presentation distinct from disabled/empty/inherited | ad-hoc dashes and placeholder text that become ambiguous |
| Shared vs unique material values | property sections need relationship/status language without turning Inspector into inventory | material logic spawns a bespoke card system |
| Placement/support refusal reasons | one reason/refusal grammar must work near gesture and in property context | silent no-op or unique toast styles per feature |
| More assets and object hierarchy | Navigator needs compact entity/group/search grammar | endless flat rows or room-owned hierarchy that contradicts world-local Scene ownership |
| Lights/environment + destructive reset | destructive actions need deliberate placement and consequence language | destructive action looks like normal toggle/tool |
| More transform controls | tool groups must grow without flattening domain/view/local mode hierarchy | Row 2 becomes an icon strip with no conceptual rank |

P24 therefore argues for a shell that is **property-system rich and selection-system explicit**, not merely visually polished.

## 7.2 P26 spatial/instrument pressure

| Future pressure | Shell quality that must survive | Failure if P23.14 gets it wrong |
|---|---|---|
| Section / Wall Elevation / Ceiling Focus as contextual instruments | nested context + strong return path | hard-coded `Plan | 3D` pill requires replacement or ortho becomes fake peer workspace |
| Selection persists across Plan/Ortho/3D | selection identity must be view-independent | instrument-local highlights/IDs create apparent second selection system |
| Cut / projected / hidden / symbol streams | authored vs derived/read-only visual language | shell state colors collide with drawing stream semantics |
| Finite depth/crop + Reveal | reason/reveal action grammar | excluded entities silently disappear or a one-off “section UI” language appears |
| More architectural properties | Inspector density and section hierarchy | architectural properties become a scrolling wall of fields |
| Active precision near target | shell must support quiet surrounding chrome while active instrument is precise | everything remains equally loud during precision work |
| Instrument entry/exit | motion/context framing should preserve spatial memory | context switch feels like a new app/document |

P26 therefore argues most strongly against **hard-coded view inventory** and for a reusable **instrument context grammar**.

## 7.3 Cross-pressure conclusion

A shell that survives both P24 and P26 must be able to grow in two orthogonal directions:

- **more entities/properties/selection states** (P24);
- **more derived spatial contexts/instruments** (P26).

The reusable system should therefore be organized around ownership and state, not today's finite list of buttons.

# 8. Candidate design territories

These are deliberately different territories for designer exploration. None is selected. Each must still satisfy the fixed architecture contracts and P23.13 Plan language.

## Territory A — Instrumented Atelier

### Personality

Architectural studio / exhibition workshop: precise, crafted, calm, tactile without literal skeuomorphism. The Plan's cool paper and graphite feel intentional because the shell reads as the workbench around it.

### Hierarchy

Strong project frame; domain/view called out through clean labeled bands; local modes and tools sit in a more instrument-like secondary rail. Panel headers are explicit but compact.

### Density

Medium-high. Property rows remain compact, but section breaks and negative space are used selectively to create breathing landmarks rather than overall spaciousness.

### Surfaces

Warm or neutral shell frame; cooler canvas/paper; subtle inset/outset edge treatment; restrained shadow only where layers genuinely overlap. Panels feel continuous, not card-based.

### Typography

Humanist UI sans for names/navigation; tabular numerics; mono/technical accent for compact references and measurements.

### Color strategy

Graphite/neutral foundation, P23.13 semantic colors preserved, perhaps one muted warm product accent used for global/domain framing rather than selection. Scene/Camera difference could use narrow context cues rather than full recoloring.

### Interaction-state character

Selection remains crisp and technical. Armed tools feel latched through geometry and label, not glow. Focus has a strong neutral ring. Snap/refusal retain semantic color.

### Why it fits Museum Editor

It can connect architectural credibility to museum/creative craft without pretending to be BIM. It also gives a clear visual story for “paper/model surface inside a studio tool.”

### Risks

Can become tasteful-but-generic if the “atelier” idea is only beige neutrals. Can drift into faux-physical skeuomorphism. Needs a genuinely distinctive edge/icon/type vocabulary.

## Territory B — Technical Workbench

### Personality

Compact engineering instrument: high trust, high information density, crisp geometry, serious spatial software. Less warm at first glance, but made approachable through excellent labels and contextual explanation.

### Hierarchy

Very explicit structural framing. Global frame, workspace header, panels and canvas use strong separators and consistent grid alignment. Domain/view/local mode ranks are legible through placement and section framing rather than decorative color.

### Density

High. Inspector and Navigator optimized for scanning many rows. Numeric values align tightly; advanced properties collapse predictably; search/filter strong when needed.

### Surfaces

Dark or mid-tone shell framing a lighter Plan paper and rich 3D viewport. Low-radius or near-square geometry. Separation comes from value and edges more than shadow.

### Typography

Compact neutral sans plus strong tabular numeral treatment. Technical references can use mono more visibly than Territory A.

### Color strategy

Mostly neutral shell; semantic colors are vivid and scarce. Selection/snap/invalid become especially legible because little else uses saturated color.

### Interaction-state character

Precise contours, markers and state labels. Disabled states remain readable. Temporary gesture scaffolding feels like instrumentation.

### Why it fits Museum Editor

Highest ceiling for dense P24/P26 growth and serious architectural credibility. Makes ownership and numeric precision natural.

### Risks

Could become intimidating or sterile. If labels shrink too far it recreates CAD/DCC barriers. Needs warmth through type/copy/surface details rather than large cards.

## Territory C — Chromatic Studio

### Personality

Creative technical software closer in spirit to music/DCC tools: energetic, memorable, dense, expressive. Color creates spatial landmarks and context recognition rather than decoration.

### Hierarchy

Stable neutral frame with deliberately colored context bands/headers for major domains or instrument contexts. Common tools stay neutral; semantic states keep dedicated colors.

### Density

Medium-high to high. Compact, but color and panel framing help chunk information quickly.

### Surfaces

Layered mid/dark neutrals with localized chromatic headers, active strips or section markers. The Plan paper becomes a bright working field inside a richer shell.

### Typography

Crisp modern sans with highly legible values; possibly stronger weight contrast than other territories.

### Color strategy

A controlled palette with strict role assignment: product/domain accents live in bounded surfaces; selection/snap/invalid remain independent. No free-for-all colored buttons.

### Interaction-state character

Strong but disciplined. Context transitions can animate a band/header rather than repaint the whole shell. Hover remains neutral so it cannot compete with selection.

### Why it fits Museum Editor

Could establish a recognizable identity and creative energy while retaining professional density. Particularly compatible with Scene/Camera differentiation if accents remain bounded.

### Risks

Highest risk of color overload and accessibility failure. Domain color must never become sole state signal. Themes become harder because semantic and expressive colors must remain stable.

## Territory D — Editorial Control Room

### Personality

Spatial direction/editing suite: deliberate, cinematic, structured, with stronger emphasis on authoring phases and temporal/spatial coordination. Inspired by professional media workspaces rather than CAD.

### Hierarchy

Project/domain framing becomes visually strong. Camera gains a naturally integrated Timeline zone; Scene and Camera share the same panel grammar but can have visibly different workspace headers/tool runs.

### Density

Medium-high. Major regions are visually obvious; within them controls can be compact. Timeline and Inspector feel like first-class docked systems.

### Surfaces

Clear horizontal/vertical zones, strong grid alignment, darker frame around canvas, timeline aligned exactly with viewport/panel boundaries. Fewer floating pieces.

### Typography

Professional editorial sans; strong section labels; numeric/camera values receive tabular treatment.

### Color strategy

Mostly neutral with selective context accents. Camera could receive a restrained temporal/cinematic cue without a second design system.

### Interaction-state character

Transitions between spatial and temporal attention are smooth; collapsed Timeline still reads as the same surface. Transport state has its own grammar distinct from selection/tool state.

### Why it fits Museum Editor

Camera is unusually important compared with conventional CAD. This territory makes Direct/cinematic authoring feel native rather than bolted onto an architecture editor.

### Risks

Can overstate Scene/Camera separation and make the domain switch feel like separate applications. Must preserve attention-only semantics and common selection/property grammar.

## Territory E — Guided Spatial Desk

### Personality

Professional spatial authoring with unusually strong explainability. More label-forward and approachable than classic DCCs, but still compact and serious.

### Hierarchy

High-rank concepts use explicit text labels and stable placement. Ambiguous icon-only controls are rare. A small contextual help/status surface can explain focused/hovered controls without occupying property space permanently.

### Density

Medium. More labels remain visible by default, but repeated property rows stay compact. Advanced sections collapse; teaching content appears only when useful.

### Surfaces

Light or medium warm neutral frame with clear panel zones and a highly legible canvas. Empty states are informative but bounded.

### Typography

Friendly, highly readable sans; technical values remain aligned/tabular. Helper/reason text has clear hierarchy rather than tiny gray captions.

### Color strategy

Calm neutral surfaces; semantic colors do most of the work. Product personality comes more from typography, iconography, edge shape and motion than a broad palette.

### Interaction-state character

Every unavailable or rejected action can explain itself. Tool state includes short text when ambiguity would otherwise require memorization. Focus states are especially strong.

### Why it fits Museum Editor

Directly supports the target creator who wants architectural credibility without CAD/DCC training. It also offers a disciplined destination for today's Inspector prose: explanation remains available but no longer blocks properties.

### Risks

Can become verbose and less expert-efficient if labels/help do not compress gracefully. Could look like a productivity app unless paired with a distinctive spatial/editor visual identity.

# 9. Questions for designer exploration

Research does not justify one answer to the following. A strong designer should take explicit positions and test them against P23.14 screens A–F plus P24/P26 pressure cases.

1. **What is the signature visual relationship between shell and P23.13 Plan paper?** Does the shell frame the paper through contrast, continuity, or deliberate material opposition?
2. **How should Scene vs Camera be visible at a glance** without making the domain switch look like switching applications?
3. **What visual primitive expresses domain, view and local mode rank** if three identical segmented controls are rejected?
4. **Where can color safely express product identity** without colliding with selection, snap, invalid and focus semantics?
5. **How dense should default Inspector sections be at ~300 px width?** What remains always visible, what collapses, and what is “advanced”?
6. **What is the minimum selected-entity header** that still anchors identity, reference, multi-selection/primary state and contextual actions?
7. **How should entity rows differ from group headings and relation metadata** in the Navigator before P26 adds more structure?
8. **What does a reason surface look like across scales?** Tooltip for disabled action, inline property reason, transient gesture refusal, standing warning count.
9. **How should focus mode preserve selection identity** when both side rails collapse?
10. **What is the common canvas-chrome grammar** for Plan, 3D, Camera and future orthographic instruments?
11. **How much of Row 2 should remain positionally stable** when switching among the four current domain/view cells?
12. **What is the correct visual home for Grid, Snap, unit and other view-display state** so each fact has one owner?
13. **How should Timeline headers/lanes align with the shell grid** in expanded and collapsed states, including no-flow?
14. **How should Camera-specific transport state differ from generic active-tool state?**
15. **What contextual-help mechanism can replace permanent Inspector prose** while remaining keyboard-accessible?
16. **How should destructive actions live inside a property surface** without becoming normal property rows or oversized warning cards?
17. **How does the system distinguish authored, inherited/shared, mixed and derived/read-only values** when P24/P26 need them?
18. **What does contextual instrument entry look like conceptually** when P26 arrives: subordinate strip, header takeover, breadcrumb, inset frame, or another grammar? P23.14 should demonstrate that the system can host the answer without choosing P26's exact product decision.
19. **How much motion is useful for context continuity** before it slows expert work?
20. **Which visual traits must survive all themes** so product identity is not reduced to palette choice?
21. **How does coarse-pointer/touch acquisition coexist with desktop density** without globally inflating every control?
22. **What is the high-density stress state?** Designers should show a real dense Navigator + Inspector + warning + active gesture state, not only an empty or two-room hero screen.

# 11. What this research does not decide

This document intentionally leaves open:

- final shell composition;
- whether panels visually dock, float or hybridize;
- exact Row 1/Row 2 replacement geometry;
- final typeface, radius, elevation or color tokens;
- final icon family;
- exact P26 instrument navigation presentation;
- P24 material/light/multi-selection product behavior;
- any change to Camera timeline semantics;
- any P23.15 geometry policy;
- implementation/component structure.

The next design phase should use these findings to produce **clear, competing shell concepts** that take positions on hierarchy, density, identity and education, then stress each concept against the current six canonical review states and the P24/P26 pressure tests. The research ceiling should be used to challenge the current composition, not merely reskin it.
