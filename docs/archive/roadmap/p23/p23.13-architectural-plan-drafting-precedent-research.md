# P23.13 — Architectural Plan drafting precedent and product research

**Date:** 2026-09-15  
**Status:** research artifact — informs later P23.13 design; not an implementation plan  
**Scope:** P23.13 Architectural Plan drafting finish  
**Primary roadmap authority:** `docs/plans/2026-09-14-P23-remaining-roadmap-reconciliation.md`  
**Related P23 context:** `docs/plans/2026-09-07-P23-layout-depth-minimum-build.md`, `docs/plans/2026-09-08-P23.6-architectural-drafting-visual-pass.md`, P23-H2 snapping/selection/guide harvest, P23.10 direct Wall/Junction editing, and the final P23.11/P23.12 contracts when they land.

---

## Research intent

P23.13 should not be treated as a cosmetic pass over the current Plan renderer. Its product outcome is a 2D architectural surface that reads and behaves like a credible small-plan editor while remaining substantially simpler than full CAD/BIM.

This report therefore studies established architectural drawing conventions and mature editor interaction patterns, then separates them into four classes:

1. **Established architectural / technical-drawing convention** — broadly understood visual language worth respecting where Museum owns the necessary meaning.
2. **Common professional-editor convention** — interaction patterns repeated across mature CAD/BIM/modeling tools.
3. **Tool-specific design choice** — useful precedent, but not an industry truth.
4. **CAD/BIM baggage** — complexity that exists for construction-document, building-model, standards, layer, story, family, material or annotation workflows that Museum Editor does not currently own.

The goal is not to make Museum look like AutoCAD. The goal is to take the strongest, most transferable ideas from mature tools while keeping Museum direct, calm, learnable and truthful to its authored model.

This research intentionally does **not** constrain recommendations to current component seams. Existing implementation is orientation evidence only. Architectural authority, Layout/Scene ownership, one selection/history path, and one compiled geometry authority remain hard product constraints.

# 1. Executive findings

## 1.1 Separate physical geometry from drafting ink

This is the most important visual direction.

Architectural plans use a graphic hierarchy rather than a single stroke rule. Geometry cut by the plan plane — especially Walls and Columns — normally receives the strongest profile/poché. Objects and edges seen below the cut use lighter treatment. Dimensions, grids, guides and surface information are lighter again.

Museum should therefore stop treating these ideas as one thing:

```text
physical Wall thickness
= screen stroke width
= visual hierarchy
```

The higher-ceiling model is:

```text
physical Wall band / footprint
        ↓
drafting ink / outline / poché
        ↓
transient interaction overlay
```

A 200 mm Wall remains a 200 mm physical band regardless of zoom. Readability can receive screen-space ink assistance without inflating physical geometry.

### Current Museum implication

The current SVG wall presentation derives a thick stroke from physical thickness and clamps it to a minimum screen width. That was a useful drafting baseline, but P23.13 should treat the rule as a design assumption to challenge rather than an invariant.

At distant zoom, a minimum *ink* width may be appropriate. A minimum *physical Wall band* width is not.

**Expected value:** very high. This decision affects joins, Openings, selection, dense-plan readability, semantic zoom and 2D/3D coherence at once.

---

## 1.2 Add automatic semantic zoom instead of scaling one representation forever

Mature tools simplify what they show as scale changes.

Revit varies Wall detail with view detail/scale; coarse views can suppress compound detail that would become unreadable. SketchUp LayOut similarly offers draft/simplified rendering modes while navigating or working with complex views.

Museum does not need user-facing `Coarse / Medium / Fine` controls. It does need automatic presentation regimes:

### Far / overview

- topology and silhouette clarity dominate;
- Wall mass remains readable but detail simplifies;
- Junctions and handles disappear;
- Door/Window symbols collapse to simple meaningful marks;
- Room labels reduce or suppress;
- passive Scene context fades strongly;
- only major grid information remains.

### Normal architectural reading

- full Wall band and proper join/cap treatment;
- clear Door/Window cuts;
- Room name/reference/area where space permits;
- LayoutObjects readable but subordinate;
- grid and passive Scene context remain quiet.

### Near / edit

- direct-edit handles;
- Junctions where actionable;
- curve controls;
- Opening handles;
- working dimensions;
- snap source and guide feedback.

Presentation LOD must never change topology, snap result, hit truth, authored value, canonical identity or history.

**Expected value:** very high. Semantic zoom gives one coherent answer to many current “how much detail should remain visible?” problems.

---

## 1.3 Reopen the decision against exact in-canvas precision during creation

The current P23.6 direction deliberately keeps Wall drawing simple:

```text
click start
→ preview candidate + passive live length
→ click commit
→ exact length/angle edits later in Inspector
```

That is defensible, but precedent suggests a higher ceiling is possible without inheriting command-line CAD.

Revit uses temporary dimensions during creation and selection. AutoCAD Dynamic Input places distance/angle fields near the pointer. SketchUp permits immediate keyboard numeric entry during ordinary drawing/move operations. The important shared pattern is not “CAD command input”; it is **precision at the locus of attention**.

A modern Museum version could be:

```text
click start
→ move pointer
→ preview actual Wall + live length / angle
→ optionally type exact value
→ click or Enter
→ continue
```

Users who do not need precision never touch the numeric entry. Users who do need precision avoid a draw-then-select-then-Inspector correction loop.

This research therefore recommends that the future P23.13 designer explicitly reconsider the passive-only numeric decision rather than inherit it by default.

**Expected value:** high.  
**New durable semantics required:** no.

---

## 1.4 Keep Door representation truthful even when that means less-standard symbolism

A door leaf plus swing arc is one of the most familiar architectural-plan conventions. However, that symbol encodes real semantics:

- hinge side;
- leaf orientation;
- swing direction / side;
- often opening direction relative to adjacent space.

Museum currently does not author those semantics. Therefore a standard swing arc would be visually familiar but semantically false.

Current P23 direction is correct to use a neutral Door representation:

- Wall cut / opening void;
- jambs;
- restrained threshold or Door-specific cue;
- no inferred leaf;
- no inferred swing arc;
- no inferred inward/outward relationship.

A slightly less conventional symbol is preferable to a precise lie.

### Door-swing deferral ratification

The provisional roadmap deferral is research-supported:

- Door swing is safe to defer from P23.13;
- it does not require prerequisite architectural work before P23.13;
- the existing Wall-hosted Opening model is a suitable conceptual base for future hinge/side data;
- P23.13 must not infer swing/handing from Room side, Wall direction, opening offset or renderer convenience;
- future swing presentation should remain derived through canonical geometry/compiler/render-model output rather than become SVG-owned authored meaning;
- on curved Walls, the future hinge location must be resolved on the actual opening edge using Wall/opening arc-length geometry, not by a center-tangent visual shortcut;
- the Door leaf should remain a rigid straight leaf rotating about the resolved hinge unless a future product feature explicitly adds non-rigid/folding Door semantics.

The research does **not** ratify an exact future schema. In particular, future design must still decide how authored hinge side and swing side remain stable under Wall canonical direction, splitting, reshape and other topology-preserving edits.

## 1.5 “Defines room boundary” is Museum-specific model behavior, not an architectural Wall type

Museum’s canonical distinction between room-bounding and non-room-bounding Walls is useful product semantics, but it does not map cleanly to a standard drafting category.

It does **not** mean:

- exterior vs interior;
- structural vs non-structural;
- permanent vs movable;
- masonry vs stud;
- full-height vs partial-height;
- hidden/overhead geometry.

Professional BIM tools frequently hold room-boundary behavior independently from basic physical Wall appearance. Revit’s Room Bounding behavior is a good example: it affects spatial computation without creating a new universally recognizable Wall line style.

Museum should therefore keep both as one physical Wall family. The non-room-bounding state may receive a subtle secondary treatment, especially on selection or hover, but should not hijack familiar technical-drawing conventions such as dashed hidden lines.

**Strong direction:** same contour/thickness language, with quieter body density/tone or a context-only role cue.

---

## 1.6 Architectural drawing and interaction feedback should be two perceptual layers

Mature editors generally distinguish:

- the drawing/model itself;
- preselection/hover;
- committed selection;
- snap target;
- snap relation/guide;
- transient draft;
- invalid state;
- direct-edit controls.

Vectorworks is especially useful precedent: preselection, snap-source highlighting, SmartCursor extension lines, current snap marker and selected-object feedback are distinct concepts. Rhino SmartTrack similarly keeps tracking guides temporary rather than turning them into model geometry.

Museum should preserve that separation:

### Resting layer

Calm, mostly neutral architectural drawing.

### Active interaction layer

More vivid, transient state using accent color, halo, marker shape, guide line, dimensions and handles.

Selection should not recolor so much base geometry that the architectural drawing disappears under “blue editor mode.”

A useful design principle:

> **Neutral ink explains architecture. Accent explains interaction.**

---

## 1.7 Rooms should use adaptive derived labels, not a BIM annotation subsystem

Professional BIM often separates Room model objects from Room Tags. That gives enormous annotation flexibility, but it also creates a second annotation lifecycle: authored tag placement, leaders, visibility, family styles and view-specific behavior.

Museum does not need this for P23.13.

A better fit is derived presentation from existing Room metadata:

```text
Gallery A
R-A3 · 42.6 m²
```

Suggested hierarchy:

1. authored Room name;
2. compact stable reference;
3. derived area.

At lower space/zoom budgets, area disappears first, then secondary reference, then eventually label entirely. Selection can temporarily reveal full identity even when the resting label is suppressed.

No persistent Room-tag object is necessary.

---

## 1.8 Column / Platform / Plinth visuals are limited by current product semantics

P23.5 deliberately defines `Column`, `Platform` and `Plinth` as creation presets over ordinary LayoutObjects:

- Column → ordinary cylinder;
- Platform → ordinary box;
- Plinth → ordinary box.

No preset-specific durable metadata survives creation. Therefore P23.13 cannot truthfully inspect an arbitrary cylinder and know it is an architectural Column, nor inspect an arbitrary box and know it is a Platform or Plinth.

This matters because mature tools give durable architectural entities highly specific symbols. Archicad Columns, for example, can receive dedicated plan markers because a Column is a persistent semantic object.

Museum has two legitimate directions:

### P23.13 presentation-only direction

Render ordinary LayoutObject footprints beautifully from geometry, without inferring architectural role.

### Future semantic expansion

If special persistent Column / Platform / Plinth plan treatment proves valuable enough, introduce explicit durable architectural-role semantics in a later slice.

That would be a product-model change, not “visual polish.”

# 3. Topic-by-topic research

## 3.1 Wall representation, thickness, joins, caps and intersections

### Established architectural convention

Walls cut by a floor-plan plane usually receive the strongest graphic hierarchy. Common approaches include:

- dark/heavy profile lines;
- filled or lightly filled Wall body (poché);
- clean intersections without duplicated interior seam lines;
- free Wall endpoints rendered as intentional caps;
- lighter treatment for objects seen beyond/below the cut.

The exact appearance varies by office and drawing purpose, but hierarchy is stable: architectural cut matter reads before annotation and furniture.

### Common professional-editor convention

Mature tools make joined Walls read as connected physical geometry rather than independent thick lines crossing through each other.

Useful recurring behavior:

- L/T/X joins resolve into one clean visual mass;
- interior cleanup lines disappear when they do not convey useful construction information;
- free endpoints remain visible;
- curved and straight segments belong to the same Wall visual vocabulary;
- edit reference lines can exist without being the resting representation.

### Tool-specific choices

AutoCAD Architecture exposes justification/reference lines and detailed Wall cleanup diagnostics. Archicad can display Wall reference lines as an editing aid. Revit suppresses many internal join edges by default so the plan reads as connected Wall mass.

These tools prove a valuable distinction:

```text
editable reference geometry
≠ resting architectural representation
```

### CAD/BIM baggage to avoid

Do not import merely to gain attractive Walls:

- compound Wall skins;
- material priorities;
- core vs finish layers;
- wall wrapping;
- cleanup groups;
- configurable cleanup radii;
- renovation states;
- construction-phase graphics.

Museum does not need those semantics for a credible Plan.

### Transfer to Museum

At normal zoom, Wall should read as a continuous physical band with deliberate outline/poché rather than only as a widened centerline.

Desired visual result:

- physical thickness remains geometrically honest;
- connected Junctions have coherent mass;
- shared Wall renders once;
- openings remove the Wall band at the actual hosted interval;
- free endpoints have clean cap treatment;
- selection/hover adds an overlay rather than changing physical interpretation.

At far zoom, simplify the drawing instead of indefinitely widening thin Walls in screen pixels.

## 3.2 Boundary vs non-room-bounding Wall hierarchy

### Established architectural convention

There is no widely understood floor-plan convention for “physical Wall that does not participate in this application’s semantic Room face extraction.”

Dashed line, lighter Wall, poche differences and patterned fills already carry other meanings in architectural/technical drawings, depending on context.

### Common professional-editor convention

Spatial computation properties can be independent from Wall visual identity. Room-bounding behavior in BIM systems is frequently a model property rather than a new Wall species.

### Tool-specific choice

Some editors expose debug/reference overlays that reveal spatial or topology behavior only when users need to understand it.

### CAD/BIM baggage to avoid

Do not reinterpret Museum `role` as:

- exterior/interior;
- structural/nonstructural;
- load-bearing/non-load-bearing;
- temporary/permanent;
- hidden/overhead.

### Transfer to Museum

Both roles should remain recognizably physical Walls.

Good candidate treatments for non-room-bounding Wall:

- same contour, slightly quieter body fill;
- same contour, subtle interior pattern that does not resemble hidden-line drafting;
- role indicator revealed on selection/hover;
- tiny contextual icon/label only when role is actively inspected.

Do not use hue alone, and do not make non-room-bounding Wall look provisional or invalid.

---

## 3.3 Straight and curved Walls

### Established architectural convention

A curved Wall is still a Wall. Its lineweight, body, openings and Room relationship use the same architectural vocabulary as straight Wall geometry.

### Common professional-editor convention

Mature tools hide control geometry until editing becomes relevant.

- resting curve: clean final geometry;
- selected curve: endpoints / shape controls appear;
- active control: guides/tangency information appear only as needed.

### Tool-specific choices

Archicad’s contextual “pet palette” and Rhino’s point-editing modes are useful examples of revealing control power only after selection.

### CAD/BIM baggage to avoid

Museum does not need:

- arbitrary NURBS degree/knot editing;
- tangent constraint networks;
- fillet/trim/extend tool families;
- always-visible control polygons;
- general curve-curve topology repair.

### Transfer to Museum

Curved Wall resting representation should be the straight-Wall visual language bent through authored geometry.

Edit state should distinguish function by handle shape, not merely color:

- Junction = topology/connectivity control;
- curve control = shape control;
- Opening handle = hosted interval control.

A designer should test whether curve-control guides remain visible only during drag or persist while the curved Wall is selected.

---

## 3.4 Doors and Windows in Plan

### Established architectural convention

Doors commonly use Wall opening + jamb + leaf + swing arc. Windows commonly use Wall opening + jambs + lighter parallel frame/glazing lines.

### Common professional-editor convention

Hosted Openings visually cut their Wall. They are not usually drawn as decorative marks over an intact Wall body.

### Tool-specific choice

Archicad is useful precedent for allowing a symbolic floor-plan representation to differ from literal 3D projection, provided the symbol is driven by real authored semantics.

### CAD/BIM baggage to avoid

P23.13 should not create:

- Door family types;
- leaf construction;
- handing/swing direction;
- fire ratings;
- window sash configurations;
- reveal/wrapping rules;
- schedule marks;
- sill/head annotation systems.

### Transfer to Museum

#### Door now

- clean Wall void;
- jambs;
- subtle Door-specific threshold/center cue;
- no hinge;
- no leaf;
- no arc.

#### Window now

- clean Wall void;
- jambs;
- two or three lighter parallel frame lines;
- no unsupported glazing/sash semantics.

#### Far zoom

Door and Window should remain distinguishable through simplified shape, not through text labels everywhere.

Possible far form:

- Door: clear Wall break + single threshold mark;
- Window: Wall break + single/twin center frame mark.

#### Future Door swing

Deferral is ratified as described in §1.4. The future feature should add authored semantics first, then standard swing symbolism.

---

## 3.5 Columns / structural-support-like objects

### Established architectural convention

A structural Column cut by the plan plane typically receives strong cut weight comparable to Wall mass.

### Common professional-editor convention

Dedicated Column entities get specific plan display and edit semantics.

### Tool-specific choice

Archicad supports several Column marker symbols, including plain, slash, X or crosshair-type display options.

### CAD/BIM baggage to avoid

Do not pull in structural-analysis meaning, material, load path, core/veneer or column-wall wrapping just to obtain a familiar symbol.

### Transfer to Museum

P23.13 cannot assume every cylinder is a Column. Therefore:

- Column **creation tool icon/ghost** may look column-like;
- committed cylinder should use generic LayoutObject footprint grammar unless durable semantics say otherwise;
- selected generic cylinder can expose geometry controls without structural decoration.

If user research strongly favors persistent Column plan identity, log that as future semantic scope rather than infer it visually.

---

## 3.6 Platforms, plinths and raised architectural regions

### Established architectural convention

Horizontal surfaces below cut are normally lighter than Wall cut geometry. Raised slabs/platforms may be expressed with boundaries, fill, steps or elevation annotation depending on drawing purpose.

### Common professional-editor convention

When a product has a true slab/platform entity, its plan outline and surface fill can be tailored to that semantic type.

### Tool-specific choice

Archicad slab display supports explicit outline and cover-fill treatment because slab is a durable model entity.

### CAD/BIM baggage to avoid

Do not add:

- storey systems;
- slab composites;
- structural deck layers;
- finish-layer semantics;
- level datum infrastructure

merely to make a box preset appear architectural.

### Transfer to Museum

Current Platform/Plinth are ordinary boxes after creation. Therefore use generic geometry-driven presentation:

- lighter contour than Wall;
- restrained fill;
- readable footprint;
- selected state may expose authored height/elevation information if that value already exists canonically.

A true persistent “raised architectural region” would be new semantics and should be scoped separately.

---

## 3.7 Generic LayoutObjects, furniture-like objects and passive Scene footprints

### Established architectural convention

Furniture and fixtures shown in plan normally sit below cut Walls in visual hierarchy.

### Common professional-editor convention

Context used for alignment/tracing is often muted or halftoned relative to active editable geometry.

### Tool-specific choice

Revit halftone/reference-style display is useful precedent for contextual information that must remain visible without competing with authored architecture.

### CAD/BIM baggage to avoid

Museum does not need a general layer/class visibility system merely to express hierarchy.

### Transfer to Museum

Recommended three-tier hierarchy:

```text
Architecture
Walls / Openings / Rooms

Editable Layout context
LayoutObjects

Passive context
Scene footprints in Layout mode
```

#### LayoutObject

- medium/light footprint;
- normal edit highlight when selected;
- geometry-derived representation;
- no implied Room ownership.

#### Passive Scene footprint

- low opacity or no fill;
- muted outline;
- dash can remain useful because here it denotes contextual/non-authoritative projection rather than hidden architecture;
- no resting handles;
- no Layout hit authority;
- stronger suppression during active Wall/Opening editing or dense-plan overview.

## 3.8 Rooms: names, references and area

### Established architectural convention

Room names and area values are common floor-plan information, but offices differ on exact tag layout.

### Common professional-editor convention

Information hierarchy matters more than ornamental badges. Room information should be stable and readable but subordinate to Wall geometry.

### Tool-specific choices

Revit separates Room semantics from Room Tag annotations. RoomSketcher uses a much simpler in-space label model with optional area/dimension display.

### CAD/BIM baggage to avoid

P23.13 should avoid:

- authored Room Tag instances;
- tag family/type systems;
- leader authoring;
- view-specific tag state;
- schedule integration.

### Transfer to Museum

Use existing P23.12 display identity as source:

```text
Gallery A
R-A3 · 42.6 m²
```

Possible hierarchy:

- Name: strongest;
- reference: compact secondary;
- area: quiet derived numeric value.

Semantic zoom / density behavior:

- large/normal Room: name + ref + area;
- medium: name + compact ref;
- small/far: name only;
- tiny/congested: suppress label;
- selected Room: reveal full identity in local presentation even if normal label is hidden.

Do not shrink labels indefinitely to fit small faces.

## 3.9 Dimensions and measurement treatment

### Established architectural convention

Dimension graphics are normally lighter than cut geometry and use extension/witness lines, ticks/markers and numeric text.

### Common professional-editor convention

Working dimensions and construction-document dimensions are separate concerns.

Temporary dimensions support:

- creation;
- direct edit;
- precise placement;
- offset/clearance feedback.

They disappear when the interaction ends.

### Tool-specific choices

Revit temporary dimensions are a particularly good model for active editing. AutoCAD Dynamic Input keeps measurements near the pointer. SketchUp lets numeric input refine ordinary direct manipulation.

### CAD/BIM baggage to avoid

P23.13 should not add:

- persistent dimension chains;
- dimension-style managers;
- architectural/engineering unit-format systems beyond existing project needs;
- print-scale annotation sizing;
- authored witness-line placement.

### Transfer to Museum

Working dimension contexts worth designing:

- live Wall length during drawing;
- Wall length/angle during direct edit;
- Opening width during resize;
- Opening offset / available clearances during slide;
- rectangle width/depth;
- object move delta or useful clearance;
- Junction coordinate only where genuinely helpful.

Research recommends testing in-canvas editable numeric entry rather than keeping every value passive.

Dimension placement rules should prefer:

- outside Wall/body when possible;
- stable side choice during a gesture;
- text moved outward when span is too short;
- suppression rather than overlap with core geometry.

## 3.10 Line-weight hierarchy, fill, hatch, contrast and negative space

### Established architectural convention

The dominant hierarchy is usually:

1. cut architecture;
2. visible objects/edges;
3. annotation/information;
4. reference/grid/context.

Negative space is important. A credible plan does not require filling every Room with color.

### Common professional-editor convention

Lineweight/detail changes with scale and purpose.

### Tool-specific choices

LayOut exposes explicit line styles. Revit suppresses internal detail at coarse scales.

### CAD/BIM baggage to avoid

Do not add hatches just to make the Plan “look professional.” Hatch implies meaning such as material, cut, finish, phase or surface.

### Transfer to Museum

Recommended perceptual stack:

```text
A. Architectural cut
   Wall band/profile

B. Seen editable geometry
   Openings, LayoutObjects, platform-like footprints

C. Information
   Room labels, working dimensions

D. Context
   grid, passive Scene footprints

E. Transient interaction overlay
   hover, selection, snap, draft, invalid, direct-edit controls
```

Room fill should be extremely restrained or absent in resting state. Selection can introduce a temporary region tint.

## 3.11 Selection, hover, focus and direct-edit handles

### Common professional-editor convention

Hover/preselection and committed selection are different states. Snap-source highlighting is different again.

### Tool-specific choices

Vectorworks gives preselection, snapped-object and selected-object separate appearances. Rhino exposes control points only when editing them.

### CAD/BIM baggage to avoid

Avoid an AutoCAD-style forest of grips and context menus on every selected entity.

### Transfer to Museum

Recommended state hierarchy:

#### Rest

Architectural drawing only.

#### Hover

- thin outer halo or contrast bump;
- no full handle set;
- enough to tell user what click would target.

#### Selected

- stronger outline/halo;
- minimal primary handles.

#### Direct edit

- relevant handle subset;
- working dimension;
- active snap/guide;
- potential baseline/original geometry ghost if needed.

#### Keyboard focus

Dedicated focus ring/shape distinct from selection.

#### Invalid

Color plus non-color grammar: broken/dashed preview, blocked marker, error glyph or pattern.

### Handle vocabulary

Designer should deliberately use shape to encode function. Candidate language:

- Junction: filled diamond/circle topology node;
- curve control: hollow round control point;
- Opening width edge: small square/tick handle;
- object resize: corner square;
- rotation: ring/arc if rotation editing already exists.

Exact shapes remain design work, but “every handle is the same blue dot” should be rejected.

---

## 3.12 Snapping, guides, alignment and invalid states

### Common professional-editor convention

Good snap feedback answers:

1. **where** the candidate point resolves;
2. **what** source/reference caused it;
3. **what relation** is active.

### Tool-specific choices

AutoCAD uses different snap marker shapes and optional tooltips. Vectorworks SmartCursor highlights reference geometry and shows extension lines. Rhino SmartTrack uses temporary reference points and tracking lines.

### CAD/BIM baggage to avoid

Museum should not display every enabled candidate or expose dozens of snap modes as first-class UI.

### Transfer to Museum

Current H2 winner-only direction should remain.

Minimal strong grammar:

```text
winning marker
+ optional source emphasis
+ optional single guide / extension line
+ short relation label when needed
```

Examples:

- Endpoint
- Midpoint
- Intersection
- Perpendicular / orthogonal
- Opening edge
- Grid

Grid should generally be quieter than semantic geometry snaps.

### Invalid draft

Do not make rejected geometry simply disappear.

Show:

- attempted candidate;
- unmistakable invalid styling;
- local failure reason;
- affected source highlight when useful.

This teaches the rule and lets user correct the gesture without guessing.

## 3.13 Creation workflows and in-progress geometry

### Common professional-editor convention

Mature tools preview enough of the final result that the user can predict the commit.

### Transfer to Museum — Wall creation

The high-ceiling interaction is:

```text
click start
→ move a preview of the actual final Wall band
→ acquire snap / guide
→ inspect live length / angle
→ optional type-to-enter exact value
→ click or Enter to commit
→ continue
```

The preview should communicate:

- actual thickness;
- likely cap/join result;
- snap result;
- Room closure cue;
- valid/invalid state;
- live dimensions.

Do not make an abstract centerline the primary visual if the final Wall mass can be previewed truthfully.

### Opening insertion

On Wall hover while Door/Window tool is active:

- reveal candidate host clearly;
- show insertion marker/ghost cut;
- preview actual Wall void and symbol;
- show width and useful host offsets;
- reject invalid fit before commit.

### Curved Wall creation/edit

Preview final Wall band, not merely a control polygon. Control geometry is secondary edit scaffolding.

### Cancellation

All draft/guide/control presentation must vanish immediately on cancel/tool change/commit and create no history.

## 3.14 Zoom-dependent detail and semantic simplification

A useful starting matrix:

| Element | Far | Normal | Near / edit |
|---|---|---|---|
| Wall | simplified physical band/silhouette | full physical band + proper profile | band + edit/reference overlays |
| Door | opening break + small Door cue | gap + jamb + threshold | full neutral symbol + handles/dimensions |
| Window | simplified slot | gap + frame lines | frame + handles/dimensions |
| Junction | hidden | hidden unless context | visible when actionable |
| Room | none/name only | name + ref + area where fit | full selected identity/context |
| Dimension | hidden | selected/active only | active/selected precision |
| LayoutObject | simplified footprint | normal footprint | edit handles |
| Scene footprint | strongly reduced | muted | still passive |
| Grid | major only / potentially hidden | major + useful minor | detailed enough for precision |

Use hysteresis or stable thresholds around LOD transitions so labels/handles do not flicker during small wheel-zoom changes.

---

## 3.15 Dense-plan behavior and label suppression

### Common professional-editor convention

When information no longer fits, mature documentation systems reposition or suppress lower-value annotation before obscuring core geometry.

### Transfer to Museum

Priority should remain roughly:

1. active selected/edit target;
2. invalid diagnostic;
3. active snap / precision dimension;
4. Room identity;
5. editable LayoutObject context;
6. passive Scene context.

A bounded derived label placer can reasonably:

- seek safe interior Room positions;
- reserve space around active handles/dimensions;
- prefer no leaders;
- hide area before name;
- maintain placement stability across tiny pan/zoom changes;
- reveal full selected identity when normal label is suppressed.

This need not become a general annotation solver or persistent layout document.

Visual stability is more important than mathematically optimal packing every frame.

---

## 3.16 Iconography and toolbar representation

Tool icons should communicate the action being armed. Canvas symbols must communicate what the authored model truthfully owns. Those are related but not identical obligations.

### Wall

Use a recognizable thick/double-edge Wall glyph, not a generic single line.

### Curved Wall / bend

If a separate curve action exists, use the same Wall-band vocabulary bent into a curve. Avoid generic Bezier pen icon unless the action truly edits arbitrary curves.

### Door

Use Wall opening/jamb icon without directional swing if the product cannot author swing.

### Window

Use Wall slot with two/three lighter parallel lines.

### Junction / Add Junction

Show Wall node/intersection with a small node or `+` at the connection point.

### Room

Enclosed region + small label motif.

### Column preset

Circular/square cut-form icon is appropriate for **creation**. Do not infer persistent Column semantics after commit.

### Platform / Plinth preset

Raised slab/block icon is appropriate for **creation**. Again, avoid implying durable subtype once the result is an ordinary box.

### Generic LayoutObject

Use geometry/object iconography rather than architectural category names unsupported by durable metadata.

## 3.17 Light and dark theme behavior

Mature tools often treat interaction colors separately from drawing/model colors. Vectorworks, for example, allows distinct interactive appearance over different drawing backgrounds.

Museum has two credible product directions:

### A. Paper surface inside any shell theme

Plan stays a warm/light architectural “sheet” even if application shell is dark.

Strengths:

- very strong architectural familiarity;
- predictable ink hierarchy;
- keeps the document/workspace visually distinct from chrome;
- easier to prevent semantic colors changing across app themes.

### B. True dark drafting surface

Plan becomes dark and every drafting token is deliberately redesigned for that surface.

Strengths:

- consistent all-dark application experience;
- can reduce luminance for long sessions.

Risks:

- naive inversion destroys conventional lineweight hierarchy;
- dark fill/Wall mass can compete with selection colors;
- Room and passive-context contrast becomes harder.

### Recommendation

Keep paper-light as the default design baseline. If true dark Plan is pursued, design it as a separate semantic palette rather than mechanically invert colors.

Do not make seven shell themes individually reinterpret Wall, Door, snap and invalid semantics.

---

## 3.18 Accessibility and non-color differentiation

Important state cannot depend on hue alone.

Recommended channels:

- **selected:** accent + thicker/outer halo;
- **hover:** contrast + thin halo;
- **invalid:** color + dashed/broken preview + blocked/error shape;
- **snap family:** marker shape first, optional color second;
- **focus:** dedicated focus ring distinct from selection;
- **non-room-bounding role:** tone/pattern/context cue, not hue alone;
- **passive/read-only:** line style + opacity/contrast, not only gray hue.

Small direct-edit handles require a strong focus/hover enlargement or clear surrounding focus shape so keyboard/pointer targeting remains visible.

---

## 3.19 Keeping 2D visually coherent with corresponding 3D

2D architectural representation does not need to be a literal top-down render of 3D. Mature architectural tools deliberately use symbolic plan display.

The governing rule should be:

### Must correspond to physical/canonical truth

- Wall position;
- Wall thickness;
- curve path;
- accepted join/cap geometry;
- Opening position and width;
- LayoutObject footprint;
- Room boundary/topology;
- canonical identity.

### May be symbolic presentation

- outline weight;
- poché/fill;
- label placement;
- simplified Window frame marks;
- neutral Door threshold;
- selection/hover;
- snap guides;
- temporary dimensions;
- far-zoom simplification.

### Must not appear without authored semantics

- Door hinge/swing;
- structural Column classification;
- material hatch;
- overhead/hidden projection;
- storey/cut-plane meaning;
- load-bearing distinction;
- BIM classification.

This gives Museum a credible architectural Plan without turning Plan into either a debug view or a literal 3D screenshot.

# 4. Transferable visual language

A coherent Museum-specific Plan language can be summarized as follows.

| Entity/state | Resting Plan language | Active language | Rationale |
|---|---|---|---|
| **Room-bounding Wall** | physical-width band/poché + strong clean profile | selection halo + endpoint/Junction controls | primary architectural cut |
| **Non-room-bounding Wall** | same physical family, subtly quieter body/role cue | same selection grammar + explicit role context | same physical object, different Room behavior |
| **Curved Wall** | same Wall grammar | relevant curve controls only | curve is not separate object family |
| **Door** | gap + jambs + threshold/cue | host/position/width handles | truthful without swing fiction |
| **Window** | gap + jambs + thin frame lines | host/position/width handles | familiar and semantically safe |
| **Room** | quiet field + adaptive name/ref/area | restrained region selection emphasis | space remains behind Wall hierarchy |
| **Junction** | mostly invisible | topology node only when actionable | avoids node clutter |
| **LayoutObject** | medium/light footprint | ordinary object handles | seen/editable object, not cut Wall |
| **Scene footprint** | very quiet context footprint | no Layout edit handles | preserves ownership isolation |
| **Working dimension** | absent | light extension/tick + numeric value | precision without annotation subsystem |
| **Snap** | absent | compact marker + optional guide/source cue | transient relation |
| **Draft** | absent | ghost of actual final geometry | predictable commit |
| **Invalid** | absent | patterned/broken candidate + marker/reason | readable without color alone |
| **Keyboard focus** | absent | dedicated visible focus ring | distinct from selection |

Core product principle:

> **Resting Plan should look close to architectural drawing output. Editing scaffolding should appear when the user touches the model, then disappear again.**

# 5. High-ceiling redesign opportunities

Ranked by expected UX/product value, **not implementation cost**.

## 1. Replace “Wall as thick screen stroke” with physical Wall band + separate drafting ink

**Value:** highest.

Why:

- restores honest scale;
- makes joins/caps more architectural;
- gives Door/Window cuts a real physical host band;
- improves selected/hover overlay design;
- makes semantic zoom coherent;
- aligns 2D visual mass with 3D Wall geometry.

**New durable semantics:** no.

---

## 2. Introduce automatic semantic zoom / visual LOD

**Value:** very high.

Why:

- solves clutter systematically;
- lets overview remain calm while edit view remains powerful;
- keeps handles/Junctions/labels from becoming permanent noise;
- gives Door/Window representations graceful zoom behavior;
- improves dense-plan performance/readability.

**New durable semantics:** no.

---

## 3. Reopen type-to-enter precision during Wall and Opening creation

**Value:** high.

Why:

- reduces Inspector round-trip;
- makes Plan feel like a drafting tool rather than a visual toy;
- keeps precision optional;
- follows Revit/AutoCAD/SketchUp precedent without copying command-line UI.

**New durable semantics:** no.

---

## 4. Preview final architectural geometry during creation/edit

**Value:** high.

Why:

- user sees real thickness, opening cut and likely join before commit;
- invalid topology becomes understandable earlier;
- reduces gap between gesture and result;
- especially important for curved Walls and hosted Openings.

**New durable semantics:** no.

---

## 5. Define one explicit interaction-state grammar

Cover:

- rest;
- hover;
- keyboard focus;
- selected;
- direct edit;
- snap winner/source/guide;
- valid draft;
- invalid draft.

**Value:** high. Every current and future Plan tool becomes easier to understand.

**New durable semantics:** no.

---

## 6. Adaptive Room identity and stable derived label placement

**Value:** medium-high.

Why:

- lets P23.12 identity feel intentional rather than dumped onto centroids;
- greatly improves dense plans;
- keeps labels useful without becoming annotation objects.

**New durable semantics:** no.

---

## 7. Zoom-aware truthful Opening visual system

**Value:** medium-high.

Why:

- Door/Window appearance is a major part of “this reads like a floor plan”;
- neutral Door semantics can still look deliberate and polished;
- far/mid/near forms avoid clutter.

**New durable semantics:** no.

---

## 8. Rebuild LayoutObject / passive Scene hierarchy around architectural lineweight

**Value:** medium.

Why:

- makes Museum-specific staging context feel integrated with the architectural drawing;
- prevents passive Scene from competing with Wall authoring.

**New durable semantics:** no.

---

## 9. Add durable architectural roles for Column / Platform / Plinth

**Value:** potentially high later, but semantic expansion.

Would unlock:

- real Column poché/markers;
- persistent Platform/Plinth Plan identity;
- better Navigator language;
- consistent tool/icon/canvas semantics.

**New durable semantics:** yes. Future scope, not P23.13 visual inference.

---

## 10. Add authored Door hinge/swing semantics

**Value:** useful later, not required for P23.13.

Would unlock standard leaf + swing symbols and richer 3D/interaction behavior.

**New durable semantics:** yes. Safe to defer.

# 6. Risks and anti-patterns

1. **Do not use dashed Wall contour for `Defines room boundary = off`.** Dashed line already carries hidden/overhead/reference meanings.
2. **Do not preserve minimum screen Wall width as minimum physical geometry.** Keep readability ink separate from scale truth.
3. **Do not make selection replace architectural appearance.** Add overlay around the drawing.
4. **Do not show every Junction or curve control permanently.** Reveal by context.
5. **Do not show every snap candidate.** Keep H2 winner-only policy.
6. **Do not add hatch merely to look CAD-like.** Hatch must mean something.
7. **Do not draw Door swing because users recognize it.** Recognition does not justify invented semantics.
8. **Do not infer Column from cylinder or Platform from box.** P23.5 deliberately removes durable preset identity.
9. **Do not adopt consumer room-first ownership models.** Museum canonical shared Wall/Junction/Openings remain authoritative.
10. **Do not copy Revit Room Tags, Room Separation Lines, levels, stories or family systems into P23.13.**
11. **Do not persist general dimension chains for drafting credibility.** Working dimensions provide most of the value.
12. **Do not let semantic zoom affect hit/snap/topology truth.** Presentation only.
13. **Do not let labels visibly jump every small pan/zoom step.** Stable placement matters.
14. **Do not let shell themes redefine semantic drafting colors arbitrarily.**
15. **Do not give generic entities special architectural symbols without durable semantics.**
16. **Do not import CAD command-line culture, hundreds of toggles or an exposed snap taxonomy.** Museum should keep professional precision and discard professional ceremony.
17. **Do not build a second Plan geometry/selection state merely to obtain prettier visuals.** Architectural presentation remains derived from canonical output.
18. **Do not let future Door swing become SVG-local state.** Authored meaning must live upstream and render as derived presentation.

---

# 7. Design tensions

| Tension | Research direction |
|---|---|
| **Physical thickness vs screen readability** | Preserve physical Wall band; add screen-space ink/LOD independently. |
| **Technical credibility vs simplicity** | Borrow line hierarchy, snapping and temporary precision. Reject layers/styles/composites/stories. |
| **Room-boundary role vs familiar drafting conventions** | Use subtle Museum-specific secondary cue; do not hijack dashed/structural symbols. |
| **Door familiarity vs semantic truth** | Truth wins. Neutral Door now; standard swing only after authored data exists. |
| **Persistent labels vs clean canvas** | Adaptive hierarchy: name > reference > area; selected identity may override suppression. |
| **Direct-edit power vs dense-plan calm** | Reveal handles/Junctions only by context and zoom. |
| **Curves easy vs curves powerful** | Expose only P23.11’s meaningful controls; avoid general NURBS freedom. |
| **Working precision vs low-friction creation** | Show values by default; exact typing optional; no modal dialog or command-line ceremony. |
| **Plan output vs editor UI** | Resting state should approach presentation drawing; edit overlays appear on demand. |
| **Light paper vs dark app shell** | Treat Plan surface as its own semantic drawing environment; paper-light is safest baseline. |
| **2D symbolism vs 3D coherence** | Symbolic graphics are fine; symbolic semantics require authored truth. |
| **Nice Column/Platform visuals vs generic LayoutObject model** | P23.13 beautifies geometry; persistent special identity needs future semantics. |
| **Collision avoidance vs visual stability** | Prefer deterministic stable label placement over constant optimal rearrangement. |
| **Consumer friendliness vs CAD power** | Hide precision complexity until useful, but do not force users through Inspector for basic exact drafting. |

12. Which temporary dimensions appear automatically versus only after selection?

## Openings

14. What neutral Door symbol reads unmistakably “Door” without implying hinge or swing?
15. How far can Window symbolism go before it implies sash/glazing construction Museum does not own?
16. How should Door and Window simplify at far zoom while remaining distinct?
17. If Door swing becomes future scope, what stable authored reference frame should survive Wall direction/split/reshape?

## Rooms and density

18. What exact typography hierarchy should Room name/reference/area use?
19. Which label field disappears first under space pressure?
20. Should a selected Room always force its full identity onto the canvas even if it overlaps passive context?
21. How much movement can a derived Room label make during zoom before it feels unstable?
22. Should Room selection use fill tint, boundary emphasis, or both?

## LayoutObjects and passive Scene

23. Should generic cylinders/boxes receive only geometry-driven Plan treatment?
24. Is durable Column/Platform/Plinth identity valuable enough to justify a future semantic expansion?
25. How quiet should passive Scene footprints become during active Wall/Openings authoring?
26. Should passive Scene labels ever appear in Layout mode, or only on cross-owner hover/selection context elsewhere?

## Theme and accessibility

27. Should Plan remain a light paper surface inside dark shell, or should a full dark drafting surface be designed?
28. What non-color channel distinguishes every important state in grayscale?
29. What focus treatment stays obvious over Wall poché, Room fill and selection overlay?
30. How should invalid state remain strong for red/green color-vision deficiencies?

## Overall product feel

31. Should resting Plan look close to final architectural drawing output, with editor controls revealed on demand?
32. Where should Museum sit between RoomSketcher’s calmness and Vectorworks’ precision feedback?
33. Which conventions make Museum feel credible immediately, and which merely make it feel like legacy CAD?
34. Which P23.13 visual decisions must remain presentation-only, and which findings justify explicit future product-semantic proposals?

# 9. Recommended product direction for later design exploration

The research points toward a clear high-level target:

> **Architectural drawing when idle; precision editor when touched.**

In that target state:

- Wall is real physical plan mass rather than an indefinitely fattened screen stroke;
- drafting ink communicates cut hierarchy independently from geometry;
- connected joins read as one architecture system;
- Door/Window symbols are familiar only as far as authored semantics allow;
- Room labels are adaptive and derived;
- Junctions and curve controls stay quiet until actionable;
- LayoutObjects remain subordinate to architecture;
- passive Scene footprints remain useful context without stealing Layout authority;
- zoom removes detail deliberately instead of letting visual clutter scale forever;
- snap feedback shows one winning relation clearly;
- invalid draft remains visible and explanatory;
- precision can stay near the user’s eye/pointer instead of requiring an Inspector round-trip;
- all temporary interaction scaffolding disappears when the gesture ends.

Most current P23 product boundaries survive precedent review and should remain:

- one primary Wall concept;
- canonical Wall/Junction/Opening/Room ownership separate from Scene content;
- passive Scene context in Layout mode;
- quiet Junctions;
- neutral Door until swing semantics exist;
- one canonical selection/history path;
- derived Room labels rather than annotation ownership;
- no BIM taxonomy, stories or construction-document subsystem.

The three assumptions most worth challenging during P23.13 design are:

1. **Wall-as-thick-stroke presentation**;
2. **lack of a coherent semantic-zoom system**;
3. **passive-only precision during creation.**

If P23.13 only changes colors, icons and spacing while leaving those assumptions untouched, it can become prettier but will leave much of the available product ceiling unused.

# 11. Research disposition summary

### Ratify / carry forward

- one physical Wall concept;
- truthful neutral Door until swing is authored;
- Window as neutral hosted frame/cut symbol;
- quiet/contextual Junctions;
- passive Scene footprints in Layout mode;
- one selection/history path;
- snap winner rather than candidate cloud;
- derived Room labels and area;
- temporary dimensions rather than persistent annotation system;
- SVG/render presentation remains derived from canonical geometry, never a topology authority;
- Door swing safely deferred; future swing derived upstream, including correct curved-Wall arc-length hinge geometry.

### Strongly challenge in P23.13 design

- Wall as a physically thick screen stroke with readability clamp;
- one visual representation across all zoom levels;
- every architectural entity sharing near-identical handle grammar;
- precision restricted to post-selection Inspector edits when in-canvas optional typing could remain simple.

### Future semantic questions, not P23.13 presentation hacks

- durable Column / Platform / Plinth architectural roles;
- Door hinge/handing/swing;
- true raised-region/floor-feature semantics beyond ordinary box geometry;
- materials/hatches;
- construction-document annotation;
- storeys / cut planes / BIM classification.

This report should be used as precedent/product evidence when the P23.13 designer starts after P23.12. It should not be converted mechanically into an implementation checklist; the designer still needs to resolve the open visual language and interaction questions against the final landed P23.11/P23.12 behavior.
