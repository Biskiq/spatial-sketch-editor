## 1. Brief objective

Make the 2D Layout surface read and behave like a **credible small architectural plan**
rather than a debug visualisation of the wall engine — while remaining substantially simpler
than full CAD/BIM.

Concretely, P23.13 must deliver a coherent Plan drafting visual language covering:

- wall thickness / joins / caps / boundary-vs-partition distinction;
- legible authored Door/Window cuts with neutral technical-plan symbols;
- Room name / reference / derived area presentation;
- dimensions (working only — see §8);
- zoom-stable line weights and handles;
- selection / hover / focus / direct-edit / curve precedence;
- snap / draft / invalid feedback;
- label collision / suppression;
- empty and dense-plan states;
- representative-theme and zoom review.

The outcome is judged the way the research frames it: **architectural drawing when idle;
precision editor when touched.** Resting Plan should approach presentation-drawing calm;
editing scaffolding appears when the user touches the model, then disappears again.

This brief explicitly permits a **substantial rethink of the Plan drafting visual language**.
Proposals are not constrained to the current SVG/component structure (see §7). What they may
not do is re-decide product semantics, ownership, or identity (see §3).

## 2. Current-state summary (what exists after P23.12)

### 2.1 P23.12 identity — shipped, consume it, do not redesign it

- **Canonical IDs remain the only identity/connectivity authority.** Junction IDs alone define
  connectivity. Nothing derives connection from coordinates.
- **Display identity is presentation only** and never becomes an identity, connectivity,
  selection, history or persistence key, and never depends on document order.
- **Vocabulary (final contract, implemented):**
  - Rooms: **required authored name** (existing `planRoomMetadataUpdate` path, Inspector-only
    rename, duplicates allowed, auto-named `Draft Room N` / `… copy`) + stable compact
    reference (`R-…`).
  - Walls / Openings: **bounded optional authored name** (`planWallMetadataUpdate` /
    `planOpeningMetadataUpdate`; clear = `name: null`; blank rejects; no-op rejects) +
    stable compact reference (`W-…` / one shared `O-…` family regardless of Door/Window).
  - Junctions: **reference only** (`J-…`), no authored names in the P23 minimum.
  - References: family prefix + hyphen + short opaque suffix, **max six visible characters**
    (e.g. `W-7K3M`), unique within the Layout document, never recycled, never truncated /
    wrapped / shrunk, no encoded order / location / ancestry / kind / geometry, no lineage
    suffixes (`W-12.1` prohibited). Quiet monospaced text, no pill/border/button styling.
  - Raw canonical IDs survive as secondary/debug detail: Inspector **Technical details**
    (collapsed, copyable, `Copy ID`), search `ID match: …` explanations, relationship
    messages. Search indexes names + references + raw IDs **and** existing kind/role terms
    ("door" still matches).
  - Named entities lead with name, reference secondary. Unnamed entities lead with the
    reference — no placeholder names. Duplicate names keep distinct references; no warnings
    or forced suffixes. Name-equals-reference shows once in compact surfaces.
  - **Name inheritance (locked):** split survivor keeps its name, genuinely new fragments
    start unnamed; explicit duplicate/repeat copies optional names with new references;
    retired references never transfer; Undo restores exact identities.
  - **Rename ownership (locked):** exactly one rename authority per kind (Inspector field).
    No inline Navigator rename, no second context-menu rename path.
- **Where identity appears today:** Navigator identity line (name + complete reference) with
  an optional context line only when distinguishing (`Door · on W-7K3M`); Inspector unified
  header + Technical details; search with visible-match highlighting; Plan uses
  name/reference for **selected-target feedback only — P23.12 adds no permanent field of
  reference labels.** Room references support selected-target identification and
  duplicate-name disambiguation; **their spatial presentation is P23.13's problem.**
- **Visitor rule (C11):** the visitor does not consume, render, mutate or import editor
  display-identity logic. Inert metadata in released data is allowed; no publish stripping.

### 2.2 Plan rendering and canvas — the starting point you may visually rethink

- **Pipeline (locked):** `CompiledLayoutGeometry → PlanRenderModel → SVG` is the only Plan
  path. No SVG-owned geometry, topology or selection state. Presentation is derived; it never
  defines topology.
- **Current wall presentation (assumption to challenge, not invariant):** thick stroke derived
  from physical thickness, clamped to a minimum screen width. Joins of connected walls are
  standalone square-mitered masses that legitimately touch at shared Junctions; junction-correct
  seams are P23.15 rendering work, not P23.13 scope.
- **Canvas chrome:** X/Z rulers in meters, segmented scale bar, X/Z axis key, toggleable
  major/minor grid (0.25 m plan step). Pan = middle-drag, zoom = scroll, Shift = angle snap.
- **Paper in every theme:** `--editor-plan-*` tokens are never overridden per theme; selection
  is the same blue in all seven shell themes. Current invariant: **hover must never look
  selected; selection is blue.** Whether the paper-light Plan surface itself survives is a
  genuine P23.13 question (see §5.8) — the *token mechanism* is locked, the *surface
  direction* is not pre-decided beyond the research recommendation.
- **Empty state (P23.13 owns the copy):** dashed ghost blueprint `DRAW YOUR FIRST ROOM` /
  `Use Rectangle Room or Polygon Room in the toolbar above` / `10.0m × 8.0m`. It names
  Rect/Poly Room only, mismatches toolbar labels ("Rect"/"Poly"), and never mentions the Wall
  tool.
- **Single-target only.** No marquee, no selection sets (deferred post-P23). Scene 3D
  Shift-click additive selection is a separate shipped Scene capability, not a Plan precedent.

### 2.3 Direct editing, curves, snaps — shipped behavior, P23.13 polishes the language

- **P23.10 direct manipulation (shipped):** drag Junction handle = move Junction; drag Wall
  body = rigid move; drag Wall endpoint = same Junction move; context menu `Add junction here`
  = subdivide (requires resolved click distance). Pointer and Inspector-numeric paths converge
  on one canonical candidate or nothing; gesture renders proposal geometry, validates once on
  release. 4 px drag threshold.
- **P23.11 curves (shipped):** `LayoutWall.centerline` is `line` or a cubic chain; Inspector
  Curved toggle (the only straight⇄curve convert), bend-point count + exact X/Z edits, remove /
  add-at-midpoint; Plan curve controls on the *selected* curved Wall; Bend command
  (`⌘`-drag macOS / `Alt`-drag elsewhere) inserting a bend at grabbed arc distance; context-menu
  twin; commit-time render-safe validation (Issue #6 class) that refuses without committing.
  One evaluator feeds Plan/3D/visitor. **Bend discoverability is an open design question** with
  no on-canvas affordance today beyond the menu twin.
- **Snapping (shipped):** explicit ribbon toggle mirrored in status bar; canonical snap-owner
  model (grid / Junction / Wall intersection / angle); screen-constant markers; only a honored
  snap reports snapped; **winner-only** — never a candidate cloud. PR #56 re-derives anchor
  drags at release, so release truth can differ from pointermove preview.
- **Invalid (shipped, three channels):** refused styling on proposal geometry + `role="status"`
  mutation message in the Inspector selection block + Topology diagnostics accordion /
  Geometry warnings alert list with 6 px diagnostic markers. Nothing auto-repairs.
- **Labels today:** Room authored names on faces with legibility floors (face ≥ 1 m²,
  scale ≥ 6 px/m, 24 px suppression radius vs dimensions/selection/diagnostics/accepted labels,
  document order breaks ties); Junction handles culled below 6 px/m. **No Room area on Plan**
  (area/perimeter live only in the selected Room Inspector). No Wall/Junction/Opening ID is
  drawn on Plan except selected-target feedback. Snap markers ~5 px (semantic) / ~3 px (grid);
  `+15°`-style yaw feedback during rotation gestures.
- **State tokens today:** passive/context muted-or-dashed; hover `#55a1ff` thinner/softer, no
  handles; selected `#2f8cff` + mode-allowed handles; dedicated invalid tokens; Navigator row
  hover/selected/disabled treatments; shared 1 px accent + 2 px soft-ring focus treatment.

### 2.4 Shell, Navigator, Inspector — context you must respect but not restructure

- **Shell truth:** 36 px Project Row / 32 px Workspace Ribbon / 24 px Status bar; left rail
  `minmax(15rem, 300px)` = **240–300 px**, collapsible to 0 with focus restored to viewport.
  Build tools live in the ribbon (`Select | Wall | Rect Room | Poly Room | Door | Window |
  Column | Platform | Plinth`, `Snap 0.25m | Grid | Tour`, contextual `Cancel`).
  `Scene | Camera` is the domain axis; `Plan | 3D` is the view axis; Scene-Plan carries the
  local `Layout | Arrange` mode. Camera Plan authors camera nodes over read-only architecture.
- **Navigator (Scene domain only):** page navigation with bounded back stack; global search
  (direct → one-hop related → nested dependents → topology counts); Roots
  `Rooms / ARCHITECTURE: Walls, Openings, Junctions / PLACED CONTENT: Layout Objects, Scene
  Content`; Opening home under host Wall; Room page with boundary-order walls, hosted Openings,
  collapsed `Boundary Junctions (n)` and `Assigned Layout Objects (n)`; expanded Room Wall rows
  show a non-selectable `Ends <j> · <j>` relation row (the density problem P23.14 owns —
  preferred default is removal, not a second selection surface). Reveal-or-pinned-strip
  behavior; emphasis bridge reuses Plan hover vocabulary. **Navigator state is UI-only** —
  never selects, mutates, or records history.
- **Inspector:** summary `dl` → Place accordion → Objects inventory → Topology diagnostics
  (only when issues > 0) → single-entity Selection editor → Geometry warnings. Deliberately not
  a document browser. Rename lives here; context menus deliberately omit Rename ("omit, don't
  dummy"); disabled items carry visible reasons.
- **Known gaps owned by P23.14 (do not solve here):** status-hint contrast (#34), axis tokens
  in number fields (#35), context-menu arrow-key navigation (#38), tablist behavior (#39),
  Project Row popover coordination (#40), Document menu focus lifecycle (#41).
- **Scene/Camera placement:** canonical wall-first Scene and Camera content is **world-local**
  and never moves implicitly with Layout edits. Scene footprints in Layout Plan are passive
  context: muted, non-authoritative, no Layout hit authority, no resting handles.

## 3. Locked product/architecture constraints

These are invariants. A proposal that requires breaking one needs an owner decision — it is
not a design choice. (Tags: **[C]** = constraint.)

1. **[C] Wall-first ownership.** Walls exist once between two Junctions; Junction identity is
   the only connectivity truth; Rooms are persistent semantic faces reconciled over derived
   boundary faces (never re-derived from scratch, never point-in-polygon inference); Openings
   are hosted by exactly one Wall via meter offset from the canonical Wall start. No second
   geometry, selection, history or topology system.
2. **[C] Canonical IDs are data identity; P23.12 names/references are presentation.**
   Display identity never becomes a key, never affects connectivity, never depends on
   document order. The name-inheritance and rename-ownership rules in §2.1 hold.
3. **[C] Separate documents.** `LayoutDocument` (architecture + document-level Layout objects)
   vs `SceneDocument` (models/primitives, lights, materials, Camera graph). Layout edits never
   move world-local Scene/Camera content implicitly. Scene footprints stay passive in Layout
   mode; Camera Plan reuses architectural context without gaining Layout authority.
4. **[C] One geometry/compiler pipeline.** `compileLayoutGeometry()` output feeds
   Plan/3D/visitor; one curve evaluator; no consumer-local resampling; no flatten-on-save.
   Invalid candidates never enter history. Rendering never broadens the valid topology set.
5. **[C] Deterministic selection/history.** One canonical Layout selection slot; one shared
   chronological tagged history; every durable intent is one transaction producing exactly one
   Layout history result or none, restoring exact identities and coordinates. Rejected edits
   install nothing; cancelled/transient derivation consumes no allocation and leaves no trace.
6. **[C] No invented semantics.** No storeys/levels/site/building hierarchy, no structural
   analysis meaning, no material/layer/style/family/category systems, no BIM classification,
   no automatic wall ownership, no fake Door handing/swing/leaf/direction, no inferred Column
   from cylinder or Platform/Plinth from box, no overhead/hidden projection, no
   load-bearing/hidden distinctions, no schedule/tag/family/annotation objects. Familiar
   symbols are allowed only as far as authored semantics reach.
7. **[C] Navigator is UI state, not authority.** It never selects, mutates, dirties or records
   history. The `Ends` relation must not become a second Junction-selection surface.
8. **[C] Visitor/editor isolation is absolute.** `/museum` and `/p/:publicationId` stay
   visitor-safe; editor hierarchy/selection/history/gizmo code never enters visitor chunks.
   P23.12's C11 rule holds for everything P23.13 adds.
9. **[C] One action surface per command; omit, don't dummy.** No competing mutation paths, no
   inline Navigator rename, no second context-menu mutation path, no Room-owned vertices,
   no marquee/multi-select (deferred post-P23, Issue #28).
10. **[C] Plan labels consume the P23.12 contract.** No raw-ID formatting in the renderer, no
    new naming fields, no authored Junction names, no document-order ordinals, no lineage
    suffixes, no pill/border reference styling. Room rename path is reused, not duplicated.
11. **[C] P23.14 owns the broader shell.** Toolbar/ribbon structure, Navigator density/IA,
    Inspector grouping/headers, context-menu/popover keyboard behavior, status-hint contrast,
    tablist/focus architecture, and the `Ends`-row final call are P23.14 decisions. P23.13 may
    state requirements *of* those surfaces (e.g. "Plan needs a place for X") but must not
    restructure them.

## 4. Research/convention synthesis (preserve the four classes)

The precedent research studied architectural drawing conventions and mature editor patterns
and deliberately separated them into four classes. **Do not flatten these into generic
recommendations** — the class determines whether a precedent is adoptable, adaptable, or
forbidden.

### 4.1 Established architectural / technical-drawing convention (respect where we own meaning)

- **Cut hierarchy:** geometry cut by the plan plane (Walls, Columns) gets the strongest
  profile/poché; seen-below edges are lighter; dimensions/grids/guides/surface info are
  lightest. Resting order: cut architecture → seen editable geometry → information →
  context → transient overlay.
- **Joined walls read as one mass:** L/T/X joins resolve into continuous physical bands;
  interior seam lines disappear; free endpoints get intentional caps; openings remove the
  wall band at the actual hosted interval.
- **Door/Window truthfulness:** Doors = wall opening + jambs + leaf + swing arc;
  Windows = opening + jambs + lighter parallel frame/glazing lines. **Adopt only the part we
  own** (see §4.4 for the Door consequence).
- **Room information:** names + areas are normal plan content, but exact tag layout varies by
  office — hierarchy matters more than ornament.
- **Dimensions:** lighter than cut geometry, with extension/witness lines, ticks and numeric
  text.
- **Negative space:** credible plans do not fill every room with color; Room fill is
  restrained or absent at rest.

### 4.2 Common professional-editor convention (interaction patterns worth adopting)

- **Temporary/working dimensions:** Revit-style temp dimensions during creation/selection,
  AutoCAD Dynamic Input near the pointer, SketchUp immediate keyboard entry — the shared
  pattern is **precision at the locus of attention**, not command-line CAD.
- **Distinct interaction states:** resting drawing vs hover/preselection vs committed selection
  vs snap target vs snap relation/guide vs transient draft vs invalid vs direct-edit controls
  are separate perceptual concepts (Vectorworks precedent; Rhino SmartTrack keeps guides
  temporary, never model geometry).
- **Snap grammar:** good feedback answers *where* it resolves, *what* source caused it, and
  *what relation* is active — with one winning marker + optional source emphasis + optional
  single guide/extension line + short relation label. H2 winner-only policy holds.
- **Semantic zoom / LOD:** Revit coarse/medium/fine and LayOut draft modes simplify with
  scale automatically (no user-facing detail switch): far = topology/silhouette, normal = full
  architectural reading, near = edit affordances. Presentation LOD never changes topology,
  snap, hit truth, values, identity or history.
- **Creation previews:** mature tools preview enough final result to predict the commit —
  actual thickness, likely join, snap, closure cue, valid/invalid state, live dimensions.
- **Dense-plan triage:** reposition or suppress lower-value annotation before obscuring core
  geometry; active selection/edit target outranks everything.

### 4.3 Tool-specific precedent (useful, not industry truth)

- AutoCAD Architecture justification/reference lines and cleanup diagnostics; Archicad
  reference-line edit aids and pet-palette contextual editing; Revit halftone/underlay for
  passive context, Room Bounding as *model property* rather than wall species, temp-dimension
  styling; Vectorworks SmartCursor/extension lines and interactive-appearance separation;
  SketchUp inference + keyboard precision without ceremony; Rhino control-point disclosure on
  demand; RoomSketcher calm resting readability with simple name/area labels; Archicad
  symbolic plan display driven by real semantics (the *mechanism* is precedent, the symbols
  must be ours).
- The recurring lesson: **editable reference geometry ≠ resting architectural representation**,
  and **tool icons arm actions while canvas symbols report authored truth** — related but
  separate obligations.

### 4.4 CAD/BIM baggage to avoid (complexity we do not own)

Do not import any of the following merely to gain attractive walls or familiar symbols:

- Compound wall skins, material priorities, core/finish layers, wrapping, cleanup groups/radii,
  renovation/phase graphics; stories/levels/composites/site/building systems; structural
  priorities, load paths, column-wall wrapping; layers/styles/command-line culture, hundred-item
  snap taxonomies; families/categories/tags/leaders/schedules, Room Tag instances, Room
  Separation Lines; dimension chains/style managers, print sheets/scale output, DXF/PDF export,
  construction documents; NURBS degree/knot editing, tangent networks, fillet/trim/extend
  families, always-visible control polygons, general curve repair; slab composites, finish
  layers, level datums; Door family types, leaf construction, handing, fire ratings, sash
  configurations, reveal rules, schedule marks, sill/head systems; persistent annotation
  objects, view-specific state, general layer/class visibility.
- Specifically for P23.13: **no hatch to look CAD-like** (hatch must mean something); **no
  dashed contour for non-room-bounding walls** (dash already means hidden/overhead/reference);
  **no minimum-screen-width preserved as minimum physical geometry**; **no Door swing drawn
  from recognition**; **no Column/Platform/Plinth inference from generic geometry**;
  **no consumer room-first ownership models** (Planner 5D-style); **no second Plan
  geometry/selection state for prettier visuals**.

### 4.5 Research positions P23.13 inherits (already ratified — design within them)

- **Physical band vs drafting ink (§1.1, highest value):** stop equating physical thickness =
  screen stroke = hierarchy. Model: physical band → drafting ink/outline/poché → transient
  overlay. A 200 mm wall stays 200 mm at any zoom; readability gets screen-space ink help
  without inflating geometry. The current thick-stroke-with-clamp is a design assumption to
  challenge.
- **Semantic zoom (§1.2, very high value):** automatic presentation regimes (far/overview,
  normal reading, near/edit) per the research matrix; hysteresis so nothing flickers on small
  wheel steps.
- **Precision at locus (§1.3, high value):** explicitly reconsider the P23.6 passive-only
  numeric decision (draw → select → Inspector round-trip). In-canvas optional type-to-enter
  length/angle/offset/width during creation/edit is now an open design question requiring no
  new durable semantics.
- **Truthful Doors (§1.4):** neutral Door now (clean void + jambs + restrained threshold cue;
  no hinge/leaf/arc/inward-outward). **Deferral ratified:** swing is safe to defer, needs no
  prerequisite architecture, wall-hosted offset + tangent/normal/yaw already expose what a
  future glyph needs, future glyph stays derived compiler output (never SVG-owned), curved
  hinge resolves at the opening edge's arc-length position with a rigid straight leaf. The
  research does **not** ratify an exact future schema — hinge/side stability under
  direction/split/reshape is still open (see §6.9).
- **Boundary role is Museum-specific (§1.5):** `boundary | partition` is spatial-computation
  behavior, not exterior/interior, structural, or material meaning. One physical wall family;
  non-bounding gets a subtle secondary treatment (quieter body/role cue, never hue alone, never
  provisional/invalid-looking), especially on selection/hover.
- **Two perceptual layers (§1.6):** neutral ink explains architecture; accent explains
  interaction. Selection must not drown the drawing in "blue editor mode".
- **Derived Room labels (§1.7):** no BIM tag subsystem. Hierarchy: authored name →
  compact reference → derived area; area drops first under pressure, then reference, then the
  label; selection can reveal full identity while suppressed.
- **Column/Platform/Plinth limit (§1.8):** P23.5 presets are ordinary cylinder/box after
  creation with no surviving role metadata — presentation-only beautification of footprints is
  allowed, architectural-role inference is not. Durable roles would be a future semantic
  expansion, not visual polish.
- **2D/3D coherence rule:** must correspond (position, thickness, curve path, accepted
  join/cap, opening position/width, footprints, Room boundary, identity); may be symbolic
  (weights, poché, label placement, simplified frames, neutral threshold, overlays, guides,
  temp dimensions, far simplification); must not appear without semantics (swing, Column
  class, hatch, overhead, storey, load-bearing, BIM class).

## 5. P23.13 design problem areas

Each area ends with the concrete decisions the two designers must each answer.challenge the
current answers freely; the locked constraints in §3 are the only immovable parts.

### 5.1 Wall grammar: band, joins, caps, mixed thickness

Resting walls must read as continuous physical bands with deliberate outline/poché, shared
walls rendered once, connected junctions coherent, free ends capped, hosted openings cutting
the real interval. Decide: resting wall body (dark poché vs neutral fill vs white-with-profile
vs zoom-dependent hybrid); join treatment for L/T/X and mixed thickness/height; cap language;
how the same grammar bends through curved walls; the far-zoom simplified form; where the
screen-space ink floor lives so distant thin walls stay readable without lying about geometry.
*Decisions: body treatment; join/cap rules; mixed-thickness policy; far-form threshold.*

### 5.2 Boundary vs partition distinction

Same physical family, perceptibly different Room behavior, without hijacking dashed hidden-line
language and without hue-alone encoding. Decide the secondary cue (body density/tone, interior
pattern, context-only role mark) and when it appears (always vs selection/hover vs inspected).
*Decisions: resting cue; emphasis cue; grayscale-safe channel.*

### 5.3 Door and Window symbols (neutral, zoom-aware)

Doors: unmistakably "door" with only void + jambs + threshold cue — no hinge/leaf/arc. Windows:
void + jambs + two/three lighter frame lines, stopping before implied sash/glazing construction.
Both need far/mid/near forms that stay mutually distinct without text labels everywhere
(candidate: door = break + threshold mark; window = break + center frame mark). Decide exact
geometry, weights, and simplification thresholds.
*Decisions: normal-zoom symbols; far symbols; near/edit additions; Window frame limit.*

### 5.4 Room labels: name / reference / area

Hierarchy name → reference → area from P23.12 identity; area is derived (new on Plan).
Decide typography scale/weight/color roles; interior placement that seeks safe positions and
reserves space around handles/dimensions (bounded placer, no leaders preferred, stability over
optimal packing); suppression order and thresholds; selected-room override (reveal full identity
even when resting label suppressed); duplicate-name disambiguation in situ; fill-vs-boundary
selection emphasis. Never shrink-to-fit indefinitely.
*Decisions: type hierarchy; placement/suppression rules; selection override; duplicate handling.*

### 5.5 Dimensions and in-canvas precision

Working dimensions only (no chains, no authoring, no style managers). Contexts: live wall
length/angle during draw and direct edit; opening width/offset/clearances during slide;
rectangle width/depth; move deltas; helpful junction coordinates. Placement: outside wall/body
preferred, stable side per gesture, text pushed out on short spans, suppressed rather than
overlapping. The open question from §1.3: optional type-to-enter exact values during
creation/edit (wall length/angle, opening width/offset) without command-line ceremony — who gets
it, when does the field appear, is it clickable/editable/keyboard-focused/passive-until-typing,
and which dimensions appear automatically vs after selection.
*Decisions: auto-vs-selected dimension set; placement rules; type-to-enter scope and trigger.*

### 5.6 Handles, Junctions, curves: a shape-encoded grammar

"Every handle is the same blue dot" is rejected. Candidate language (adopt/adapt/replace with
reason): Junction = filled topology node; curve control = hollow round point; opening edge =
square/tick; object resize = corner square; rotation = ring/arc if rotation editing exists.
Decide the final shape set; when Junctions appear (selected wall only / hover / active wall
tool / combination); how much curve scaffolding persists (drag-only vs while-selected);
whether baseline/reference geometry ever shows during edits; opening vs curve vs topology
control disambiguation at shared points.
*Decisions: handle shape system; Junction reveal rule; curve-scaffolding persistence.*

### 5.7 Interaction-state grammar

One explicit system over: rest, hover, keyboard focus, selected, direct-edit, snap
winner/source/guide, valid draft, invalid draft. Resting layer calm and neutral; active layer
vivid and transient (accent, halo, marker shape, guide line, dimensions, handles). Selection
adds overlay without replacing architectural appearance. Focus gets a dedicated ring distinct
from selection. Invalid gets color **plus** non-color grammar (broken/dashed preview, blocked
marker, glyph/pattern, local reason). Snap gets marker-shape-first encoding with optional
source emphasis, single guide, short relation label (Endpoint/Midpoint/Intersection/
Perpendicular/Opening-edge/Grid). Decide exact treatments and the precedence stack when states
coincide (Room vs Wall vs Opening vs Junction vs curve control vs Scene footprint vs Arrange
owner).
*Decisions: per-state treatment; precedence order; invalid and focus non-color channels.*

### 5.8 Zoom, density, empty states, themes

Automatic LOD matrix (far/normal/near per entity class) with stable thresholds; label
collision/suppression with priority (selected/edit target → invalid diagnostic → active
snap/precision → Room identity → LayoutObject context → passive Scene); passive Scene fading
under active authoring and overview; grid detail per regime; empty-state copy and naming
consistency (fix the Rect/Poly vs Rectangle/Polygon gap, mention the Wall tool honestly);
dense-plan behavior without label jitter. Theme direction: paper-light Plan as default baseline
vs a fully designed dark drafting surface (never mechanical inversion; never seven themes
reinterpreting drafting semantics). Decide LOD thresholds, suppression priority, empty copy,
and the theme direction with its semantic palette.
*Decisions: LOD matrix; suppression priority; empty-state copy; paper vs dark direction.*

### 5.9 Creation and edit previews

Every creation/edit gesture previews the actual final geometry, not an abstract centerline:
real thickness, likely cap/join, snap result, Room-closure cue, valid/invalid styling, live
dimensions. Wall draw (click → move → optional type → commit → continue); opening insertion
(host highlight → ghost cut → void+symbol preview → width/offsets → pre-commit fit rejection);
curved creation/edit (final band primary, control polygon secondary scaffolding); cancellation
(all scaffolding vanishes immediately, no history). Decide preview composition per tool and the
Room-closure cue.
*Decisions: per-tool preview content; closure cue; cancel behavior.*

### 5.10 LayoutObjects, Columns/Platforms, passive Scene

Three-tier hierarchy: architecture → editable LayoutObjects → passive Scene footprints.
LayoutObjects get medium/light geometry-driven footprints with normal edit highlight and no
Room-ownership implication. Committed cylinders/boxes keep generic grammar (creation
tool icon/ghost may look column-/slab-like; the committed result must not claim role).
Passive Scene: very quiet (low opacity/no fill, muted outline; dash acceptable *here* as a
non-authoritative-context signal), no handles, stronger suppression during active authoring,
no Layout hit authority. Decide footprint weights/fills, suppression levels, and whether
passive labels ever appear in Layout mode.
*Decisions: LayoutObject grammar; passive Scene treatment per regime; label policy.*

### 5.11 Iconography

Tool icons arm actions; canvas symbols report truth. Wall = thick/double-edge glyph (never a
single line); curved/bend = same band bent (never a generic Bézier pen unless arbitrary curves
are edited); Door = opening/jamb icon **without** swing; Window = slot + parallel lines;
Junction/add-junction = node at connection; Room = enclosed region + label motif;
Column/Platform/Plinth presets = cut-form/slab icons **for creation only**; generic
LayoutObjects = geometry icons, never architectural category names. Decide the icon set
consistent with the chosen canvas language.
*Decisions: per-tool icon geometry; creation-vs-committed distinction.*

## 6. States and edge cases the design must cover

The proposal is incomplete unless each item below has an explicit resting **and** active
treatment. Prefer a state × entity matrix over prose where it clarifies.

1. **Zoom regimes:** far overview / normal reading / near edit for every entity class; LOD
   transition thresholds with anti-flicker behavior on small wheel steps.
2. **Selection/hover/focus collisions:** hovered-vs-selected, focused-vs-selected, two
   co-located candidates (e.g. Junction under Opening edge, curve control over snap source),
   selected entity under active snap, Arrange-owner vs Layout-owner overlap.
3. **Direct-edit set:** Junction drag, rigid Wall move, endpoint reshape, add-junction
   subdivision, bend insert/drag/remove, curve-toggle regions, Opening slide/resize/insert —
   each with handles, working dimensions, snap/guide and invalid variants.
4. **Snap/invalid:** each snap family (endpoint, midpoint, intersection, perpendicular /
   orthogonal, Opening edge, grid) with winner marker + source + guide + label; each refusal
   class with broken-pattern preview + marker + local reason + affected-source highlight.
5. **Openings:** Door vs Window at three zooms; min-width hosts; openings near wall ends,
   junctions and each other; invalid-fit pre-commit state; arched profiles (rectangular /
   rounded / pointed) without implying construction beyond the authored profile.
6. **Curves:** resting curved wall vs selected (controls shown) vs control-drag (guides shown);
   bend-point dense chains; sub-6 px/m culling behavior; tangent-adjacent straight/curve joins.
7. **Rooms:** large / medium / small / tiny faces; duplicate names adjacent; suppressed-label
   selected room; area-first-drop suppression sequence; Room selection fill vs boundary choice;
   shared-wall participation visible without a second selection surface.
8. **Density:** representative small, angled, shared-wall, curved and dense plans legible at
   supported zooms; no accepted geometry invisible; labels never obscure core geometry;
   placement stability across tiny pan/zoom.
9. **Non-room-bounding walls:** resting, hovered, selected and inspected treatments that read
   as physical walls with different Room behavior — never provisional, hidden or invalid.
10. **LayoutObjects and Scene:** generic cylinder/box/sphere resting vs selected; Column-like
    vs Platform-like footprints without role claims; passive Scene footprints at three zooms,
    during active Wall/Opening authoring, and in dense plans; cross-owner hover/selection
    context without Layout hit authority.
11. **Empty / sparse / broken:** first-run ghost; toolbar/empty-copy naming agreement; sparse
    single-wall plans; compiler-flagged geometry (diagnostic marker rank vs labels); legacy
    internal-dependency smoke paths (no new behavior, just non-broken rendering).
12. **Theme/accessibility:** all seven shell themes with the chosen Plan surface; grayscale
    legibility of every state; red/green-deficient invalid and focus treatments; keyboard-only
    path to every handle/dimension shown (visual focus ring, enlarged targets); status-hint
    legibility requirement stated for P23.14 without solving it here.
13. **Unresolved research questions the designer must judge (not inherit silently):**
    resting wall body treatment; non-bounding cue in grayscale; LOD thresholds and far forms;
    handle shapes and Junction reveal rule; baseline-geometry visibility; curve-scaffolding
    persistence; type-to-enter scope and trigger; auto vs selected dimensions and their
    editability; neutral-Door exact geometry and Window frame limit; far Opening distinction;
    Room type hierarchy, drop order, selection override, label travel tolerance, selection
    emphasis; generic-vs-durable Column/Platform treatment and whether to propose future
    semantics; passive Scene quietness and label policy; paper vs dark surface; focus ring over
    poché/selection; invalid for color-vision deficiency; resting-near-drawing vs
    editor-scaffolding balance; RoomSketcher-calm vs Vectorworks-precision position; which
    decisions stay presentation-only vs justify future semantic proposals. (Source: research
    §8, questions 1–34.)

## 7. What the designer is explicitly free to rethink

Within §3, everything visual and interactive about the Plan drafting surface is open —
including challenging current implementation structure. The renderer is an implementation
detail; propose the right language and let the later child plan map it onto the pipeline:

- Entity representation and line hierarchy: wall band vs ink, poché/fill/profile, join/cap
  geometry, boundary cue, curved-wall bending of the same grammar.
- Selection/hover/focus language: halo shapes, overlay vs recolor, precedence stack,
  keyboard-focus distinction, "blue editor mode" avoidance.
- Handles and controls: shapes, sizes, reveal rules, curve scaffolding, opening ticks,
  rotation affordances, touch/keyboard target treatment.
- Guides and feedback: snap markers/shapes/labels, extension/tracking lines, source emphasis,
  temporary dimensions and their placement, invalid pattern/marker/reason composition.
- Creation states: preview composition, live values, optional typing, closure cues, host
  highlighting, ghost cuts, cancel clearing.
- Room/Wall/Opening/Junction presentation: labels, type roles, area treatment, reference
  placement (consuming — never replacing — the P23.12 vocabulary), duplicate handling.
- Curves: resting simplicity vs edit power, control disclosure timing, bend communication.
- Columns/Platforms/LayoutObjects: footprint grammar, creation-ghost vs committed distinction,
  hierarchy vs architecture, passive Scene quietness regimes.
- Zoom/density: full LOD matrix, collision/suppression/priority rules, stability guarantees,
  empty/dense variants.
- Drafting-related iconography: the complete tool icon set in the canvas language.
- The three high-value research challenges in particular: **wall-as-stroke → band+ink**,
  **one-representation-forever → semantic zoom**, **passive-only precision → optional
  in-canvas typing**. Leaving all three untouched while only recoloring is a valid proposal
  only with written justification for why the ceiling was declined.

## 9. Expected designer deliverables and comparison criteria

### Deliverables (per designer, independent)

1. **Resting-state Plan system:** wall band/ink/poché, joins/caps, boundary cue, Door/Window
   symbols, Room label hierarchy with area, LayoutObject/passive-Scene tiers, grid/rulers/scale
   treatment — shown on at least: small rectilinear, angled/shared-wall, curved-wall, and dense
   plans at three zooms.
2. **Active-state grammar:** hover / focus / selected / direct-edit / snap-winner-source-guide /
   valid-draft / invalid-draft treatments with the precedence stack made explicit; handle shape
   system with reveal rules; working-dimension set with placement rules; invalid pattern +
   marker + reason composition.
3. **Creation/edit previews:** per-tool preview composition (Wall draw, Opening insert/slide/
   resize, bend/curve edit, rectangle presets) with live values, closure cues and cancel
   behavior; type-to-enter position argued explicitly (adopt with trigger design, or decline
   with written reason).
4. **Zoom/density system:** LOD matrix per entity class with thresholds and anti-flicker rule;
   label collision/suppression/priority specification; selected-override rule; empty-state copy
   proposal; dense-plan specimen.
5. **Openings and Rooms specifications:** neutral Door vs Window geometry at three zooms with
   the Window frame-limit position; Room typography/placement/suppression/duplicate/selection
   rules.
6. **Iconography sheet:** tool icons in the canvas language with the creation-vs-committed
   distinction for presets.
7. **Theme/accessibility annex:** Plan surface direction (paper default vs designed dark
   alternative) with the semantic palette; grayscale proof of every state; focus and invalid
   non-color channels; keyboard reachability of shown controls.
8. **Boundary log:** what was deliberately left to P23.14 / P23.15 / future semantics, and any
   research-ratification disagreement (especially Door swing) with supporting analysis.
9. **Open-question register:** every §6.13 question answered, deferred with reason, or
   explicitly left to implementation tuning — no silent inheritance.

### Comparison criteria (how the two proposals are judged against each other)

- **Architectural credibility at rest:** does an untouched plan read as architecture, with cut
  hierarchy, calm negative space and truthful openings — closer to RoomSketcher calm than to
  engine debug view?
- **Precision power when touched:** can exact work happen at the locus of attention, with
  predictable previews, clear snap winners and local dimensions — closer to
  Revit/Vectorworks clarity than to Inspector round-trips?
- **Truthfulness:** does every mark correspond to authored semantics, with Door neutrality,
  generic-geometry honesty and no BIM fiction? Is the 2D/3D correspondence rule respected?
- **Zoom/density coherence:** does one LOD + suppression system explain far, normal and near
  without clutter, flicker or invisible geometry?
- **State legibility:** are hover/focus/selected/edit/snap/invalid instantly distinguishable
  without hue alone, with selection as overlay rather than recolor?
- **Constraint respect:** are §3 invariants held (identity, ownership, pipeline, history,
  isolation, P23.14 boundary) with no scope creep into deferred work?
- **Research fidelity:** are the four precedent classes preserved — conventions respected,
  editor patterns adapted, tool choices borrowed consciously, baggage refused with reasons?
- **Completeness under §6:** does the proposal cover every listed state and edge case, or name
  its omissions honestly?
- **Implementability honesty:** is the visual ambition mappable onto one derived
  presentation pipeline without implying a second geometry/selection authority or new durable
  semantics? (Designers do not write the mapping — but must not require forbidden architecture.)
- **Independence:** do the two proposals represent genuinely different judgments on the open
  questions (especially §1.3 precision, §5.8 theme, wall body treatment) rather than two
  skins over one answer?
