# P23.12 designer brief — architectural names and stable display identity

**Slice:** P23.12 — Architectural names and stable display identity.
**Status:** direction only. No implementation-ready child plan exists yet; the
roadmap is [`docs/plans/2026-09-14-P23-remaining-roadmap-reconciliation.md`](../../plans/2026-09-14-P23-remaining-roadmap-reconciliation.md) §P23.12.

designer, grounded in the current UI. It does not propose visual design and does
not specify implementation.

does not create one. Every Room always shows *some* authored name — often a
machine-generated one.

### 1.2 Wall / Opening / Junction identity **[current]**

- `LayoutWall`, `LayoutWallOpening` and `LayoutJunction` have **no `name` field**
  (`layout-wall-first-types.ts`). Their identity is their `id` plus their endpoint
  Junction IDs (Walls) or host Wall ID (Openings).
- Canonical IDs are allocator-produced strings such as `wall-chain-1`,
  `junction-chain-1`, `opening:door:1`, plus split-derived IDs; imported documents
  may carry arbitrary strings.
- There is **no** `W044` / `J022` / `D007`-style reference facility anywhere in
  code. P23.6e Gate 1 recorded it as unavailable and deliberately fell back to
  formatted IDs.

### 1.3 Where identity text appears today **[current]**

**One shared label derivation.** `formatPlacementLabel(id)`
(`apps/editor/src/lib/editor/editor-outliner.ts`) trims the ID, splits on
`-`, `_` and whitespace, and title-cases each part. So `wall-chain-1` renders as
**`Wall Chain 1`**. It is used by every label path below.

**Caution — the formatter only understands `-`, `_` and whitespace.** Real
allocator IDs use other separators, and those survive verbatim into the label:

| Real canonical ID | Source | Rendered label today |
|---|---|---|
| `wall-chain-1` | Wall chain authoring | `Wall Chain 1` |
| `wall-chain-1.b`, `wall-chain-1.b.2` | Wall split fragments (`allocateId(…, `${seed}.b`)`) | `Wall Chain 1.b` |
| `junction-chain-2` | Junction chain authoring | `Junction Chain 2` |
| `junction-chain-1.2` | Noding/duplicate-derived uniqueness suffix | `Junction Chain 1.2` |
| `opening:door:1`, `opening:window:3` | `nextWallFirstOpeningId` → `` `opening:${kind}:${index}` `` | `Opening:door:1` |
| `wall-chain-1:knot:1` | Curve bend point (`layout-wall-centerline.ts`) | `Wall Chain 1:knot:1` |

So the current primary label for an Opening is literally `Opening:door:1`, and a
split Wall fragment reads `Wall Chain 1.b`. Any reference scheme must be judged
against these inputs, not against a hand-written `W044`.

### 1.4 Current Navigator density and legibility **[current]**

Confirmed density/legibility problems in the real rail (§2 of the baseline
records that the "268 px" figure in the roadmap is not a code constant; the
shipped rail is 240–300 px):

1. **`Ends` relation rows.** Expanding a Room Wall row renders
   `<p>Ends Junction Chain 1 · Junction Chain 2</p>` — two long formatted IDs in
   a single non-selectable line at `0.68rem`. It is the *deepest* text in the
   page: Room title → `Boundary` section → Wall row → its children, where each
   `.hierarchy-children` nesting level adds `margin-left: 0.85rem` +
   `padding-left: 0.62rem` (~1.47 rem per level) on top of the row's own padding
   and the 1.7 rem chevron column. This is the concrete case the roadmap calls
   "materially noisy".
2. **Label + meta collision.** Row labels and secondary meta are both single-line
   `text-overflow: ellipsis` (`tree-row__label` / `tree-row__meta`), with the meta
   right-aligned by `margin-left: auto`. A label like `Wall Chain 1.b` plus a meta
   like `▸ 2 openings` competes for the same ~200 px of usable text width, and
   either can be truncated independently — including the half that carries the
   identity. Labels are also the longest they will ever be today (§1.3 table:
   `Opening:door:1`, `Junction Chain 1.2`).
3. **Row height budget.** Entity rows are `min-height: 2rem` with a `1.7rem`
   chevron column; section rows `1.8rem`, relation rows `1.6rem`. Adding a
   persistent second identity line would change the rhythm of every page.
4. **Raw ID only discoverable by hover.** The only place the raw ID is readable in
   the rail is the row `title` (a tooltip), and the pinned strip's `title`. There
   is no visible route to the raw ID, and hover is unavailable on touch.
5. **Pinned strip pressure.** Two stacked lines plus a right-aligned action button
   must fit the same narrow rail; the action label is a full phrase
   (`Show in Walls ›`).
6. **Search exposes IDs but not by design.** Because search matches the raw
   canonical ID, a user can find `wall-chain-1` — but the result row *displays*
   `Wall Chain 1`, so the match is invisible and looks arbitrary.

### 1.5 Selection / reveal / search behavior relevant to identity **[current]**

All of this is landed P23.6e behavior that P23.12 changes the *words* of, not the
mechanism:

- **Representation, not visibility**, drives reveal: a row under a collapsed
  ancestor or outside the viewport is still *represented*. Absence from the
  projection (wrong page, active filter, active search with no match) is what pins.
- Reveal on Plan selection: represented → scroll + highlight (auto-disclosing the
  ancestor chain); not represented → the neutral pinned strip with one reason
  (`Not in <Room name>` / `Outside active filter` / `Not in search results` /
  `Not on this page`) and `Show in <Home> ›`.
- Opening a page never selects; Back never selects; entering a page never scrolls.
- Row hover/focus drives Plan emphasis (the existing Plan hover vocabulary) — no
  second renderer, no selection.
- Search **replaces** the rendered surface without changing the page; selecting a
  result leaves the query in place.
- Row accessibility: the row button's accessible name is its **visible text** —
  the label plus the right-aligned meta when present (`Wall Chain 1 ▸ 2 openings`)
  — never the raw ID, which is only a `title`. Disclosure chevrons carry their own
  `aria-label="Expand/Collapse {label}"`, so the same label text is repeated into
  several accessible names per row. The tree is `ul[role=tree]` with
  `li[role=treeitem]`; `aria-selected` is set only for entity rows.
- Wall-first Room rename has exactly one authority (the Inspector field). Room
  selection is preserved across a successful rename.

## 2. Fixed P23.12 requirements

These are settled by the roadmap. They are inputs to design, not questions.

1. **Authored Room name remains the existing authority** — same field, same
   mutation path, same Inspector surface. P23.12 must not add a second Room naming
   field or path.
2. **Walls and Openings gain optional authored names** as Layout metadata, written
   through one canonical metadata planner/adapter/transaction, edited in the
   selected entity's Inspector panel.
3. **Junctions remain reference-only** — no authored Junction names.
4. **Walls, Openings and Junctions each get a stable compact reference**, and the
   one display-identity contract is consumed by Plan, Navigator, search and
   Inspector. **Whether Rooms also receive a compact reference is not stated in the
   roadmap** — Rooms already have an authored name, and the exit criterion for
   Rooms is only "a concise, accessible, unambiguous label everywhere it appears".
   Treat "does a Room need a reference too?" as an open question for the child
   plan, not as a settled requirement.
5. **Authored name is primary where one exists.**
6. **The compact reference remains available as the unambiguous secondary
   identity** where a name is primary.
7. **Unnamed entities use the compact reference as the primary label.**
8. **Raw canonical IDs remain available as secondary / debug detail** — never the
   only label, never removed as an escape hatch.
9. **Search indexes authored names, compact references and raw canonical IDs.**
10. **Rename stays Inspector-owned.** No inline Navigator rename, no context-menu
    rename, no second mutation surface.
11. **Display identity never replaces canonical identity or connectivity.** Names
    and references are presentation; canonical IDs remain the identity and
    connectivity authority, and references must never depend on document order.
12. **Stability:** references survive reorder, deletion, insertion, split,
    Save/Load and Undo/Redo; renaming never changes topology, selection identity or
    Scene/Camera; duplicate names are legal and must not break identity.

**Not yet decided and therefore an open question, not a requirement to satisfy:**
the *mechanism* of the compact reference. The roadmap requires the future child
plan to ratify either persisted presentation metadata or a deterministic
collision-safe derivative of the canonical ID, and explicitly forbids
document-order ordinals. A designer should treat the *shape* of a reference as
unknown (not necessarily `W044`) and design for a short, stable, non-sequential
token.

## 3. Design decisions needed

Nine decisions. For each: what is being decided, the concrete current UI state it
affects, and what is already fixed. **No answer is proposed here.**

### D1 — Named vs unnamed presentation

- **Decide:** how a *named* Wall/Opening reads versus an *unnamed* one, such that
  the two states are distinguishable without one looking like an error state, and
  such that a Room's machine-generated `Draft Room 2` name reads as a real name
  rather than a placeholder (it is a real authored name — the codec rejects empty).
- **Current state:** unnamed Wall rows show `Wall Chain 1` in the rail and
  `Wall wall-chain-1` in the Inspector; Room rows show `Draft Room 2`.
  Nothing marks whether those strings are authored or generated.
- **Affected:** every Navigator row (`HierarchyRow.svelte`), every Inspector
  selected-entity block (`EditorInspector.svelte` ~1915–2163), Plan Room labels
  (`plan-overlays.ts` `room-name`).
- **Fixed:** unnamed entities must use the compact reference as the primary label;
  named entities must lead with the name; raw IDs stay reachable.

### D2 — Name + reference hierarchy

- **Decide:** the reading order and visual weight of name → reference → raw ID in a
  one-line context (rail row, Inspector header). Which of the three is visible by
  default, which is revealed on demand, and how the secondary tier is visually
  subordinated without becoming illegible.
- **Current state:** the rail shows one label + one right-aligned meta; the
  Inspector shows a bold header plus one or more plain `<span>` lines. Raw ID
  visibility differs per surface today (§1.3), which makes the tiering inconsistent
  before P23.12 even starts.
- **Affected:** `HierarchyRow.svelte` `.tree-row__label` / `.tree-row__meta`;
  Inspector `layout-selected-room` block header.
- **Fixed:** all three tiers must exist and be retrievable; the name is primary
  where present; the raw ID is secondary/debug, not primary.

### D3 — Navigator row treatment

- **Decide:** the final row composition for named and unnamed architecture —
  whether a reference shares the label line, occupies the meta slot (which today
  carries relationship facts like `▸ 2 openings` / `3 walls` / `also in Gallery B`),
  or earns its own line; and what happens when identity and relationship facts
  compete for the same width.
- **Current state:** a label slot (`Wall Chain 1`, `Wall Chain 1.b`,
  `Opening:door:1`) plus an optional right-aligned meta slot (`▸ 2 openings`,
  `3 walls`, `also in Gallery B`), both single-line `text-overflow: ellipsis`;
  `min-height: 2rem` rows; Rooms / Walls / Openings / Junctions / Room pages all
  reuse the same row component.
- **Affected:** `HierarchyNavigator.svelte`, `HierarchyRow.svelte`,
  `hierarchy-page-projection.ts` secondary-text builders.
- **Fixed:** the row must stay a single canonical selection surface keyed on
  canonical IDs; the `Ends` relation row's final fate is a P23.14 decision
  (roadmap's preferred default is removal from normal Room Wall disclosures) — do
  not pre-empt it here, but do not design a row treatment that *depends* on the
  `Ends` row surviving either.

### D4 — Inspector selected-header treatment

- **Decide:** one consistent selected-entity header pattern across Room, Wall,
  Opening, Junction and Layout object, including where the editable **Name** field
  sits and how editability is signalled for Wall/Opening (new) versus Room
  (existing) versus Junction (never editable).
- **Current state:** four different patterns coexist —
  `{name}` + `{id}` (Room), `Wall {id}` (Wall), `Junction {id}` (Junction),
  `{kind} opening` + `Opening: {id}` + `Wall: {id} · …` (Opening),
  `{kind} object` + `{id}` (Layout object).
- **Affected:** `EditorInspector.svelte` selected-entity blocks (~1915–2163) and
  the existing Room `Name` field.
- **Fixed:** rename is Inspector-owned; Room's rename path and field stay as they
  are; Junctions never get a name field. Grouping/ordering of the rest of the
  Inspector is P23.14 — this decision covers the header and identity fields only.

### D5 — Search-result treatment

- **Decide:** how a result conveys *why* it matched when the match was a reference
  or a raw ID that is not otherwise visible in the row, and how authored names and
  references are presented inside the existing `Direct matches / Related /
  Topology` grouping.
- **Current state:** results are grouped by category (`Rooms`, `Walls`, …) then by
  match kind; direct rows show label + facet or a host secondary
  (`Door on Wall Chain 1`); Openings pages/results carry a `Show in Walls ›` action.
  A query for `wall-chain-1` returns a row reading `Wall Chain 1` with no visible
  reason for the match.
- **Affected:** `hierarchy-search.ts` blocks/groups, `HierarchyRow.svelte`,
  `HierarchyNavigator.svelte` search surface.
- **Fixed:** search must index names, references and raw IDs; the bounded
  retrieval shape (direct → related → nested dependents → summarized topology →
  stop) is unchanged.

### D6 — Plan label treatment *insofar as P23.12 sets the identity hierarchy*

- **Decide:** which identity tier the canvas is allowed to show for architecture
  that has no label today (Walls, Openings, Junctions, and Room references), and
  how that intent is expressed as a constraint for P23.13. **P23.12 does not
  place or style Plan labels** — final placement, collision, zoom behaviour and
  line weights are P23.13.
- **Current state:** Plan draws Room names only; Room-name labels already lose to
  dimension readouts at low zoom; Junction handles are culled below 6 px/m;
  Room labels are suppressed within 24 px of any higher-priority label/marker.
  A selected Opening adds one fixed top-left screen-space label
  (`door · 0.90 m × 2.10 m`).
- **Affected:** `layout/plan-overlays.ts`, `lib/layout/plan-render-model.ts`
  label styles, `layout/LayoutPlanViewport.svelte` selection label.
- **Fixed:** all architecture labels must consume the P23.12 identity contract
  rather than formatting raw IDs in the renderer; labels stay derived, never
  persisted annotations; the SVG render pipeline is unchanged.

### D7 — Truncation, overflow and compact-reference legibility

- **Decide:** the minimum legible footprint of a reference and the truncation rule
  when name + reference + relationship meta exceed the rail width — including
  whether a reference may ever be truncated (it is the unambiguous identifier, so
  truncating it may defeat its purpose), and how that interacts with the existing
  single-line ellipsis behaviour.
- **Current state:** label and meta are independently ellipsised; the pinned strip
  ellipsises both lines; the row tooltip is the raw ID; sentence-length generated
  names already exist (`Draft Room 10`, `Gallery A copy 2`) and will lengthen once
  Wall/Opening names are authored.
- **Affected:** `HierarchyRow.svelte` (`.tree-row__label`, `.tree-row__meta`),
  `HierarchyNavigator.svelte` (`.hierarchy-pin__*`, `.tree-nav__page`),
  Inspector `relation-links` / `object-room-meta` value spans.
- **Fixed:** the raw ID must remain reachable even when other tiers truncate.

### D8 — How raw IDs appear when exposed

- **Decide:** the consistent home for the raw canonical ID (tooltip only, a
  secondary line, a collapsed "detail" disclosure, the Inspector, search) and its
  typography, so it reads as technical detail rather than a competing label — plus
  how it is exposed on touch/keyboard, since a `title` attribute is neither.
- **Current state:** raw IDs are surfaced today by row `title`, pinned-strip
  `title`, Inspector `<span>` lines, `Boundary walls:` lists, endpoint buttons,
  hosted-Opening buttons, the Align dropdown labels, Objects accordion rows,
  topology diagnostics rows, and status messages — inconsistently and mostly
  without visual differentiation from authored names.
- **Affected:** all surfaces in §1.3.
- **Fixed:** raw IDs remain a secondary/debug tier and are searchable; they are
  never the primary label.

### D9 — Dense-state treatment, accessibility, contrast and readability

- **Decide:** how dense architecture reads once every entity has two identity tiers
  (e.g. a Room page with many boundary Walls each carrying a name, a reference and
  an opening count), what is suppressed first, and the accessibility/contrast
  expectations for the secondary tier — remembering the status bar's own hint
  contrast is a known defect (issue #34, owned by P23.14).
- **Current state:** dense cases today are the Room boundary list, the Walls page
  with the `In multiple rooms` filter (rows gain participation text), and the
  expanded Room Wall disclosure. Secondary meta uses `--editor-text-muted` on
  `--editor-bg-panel`; the selected row switches meta to
  `--editor-text-primary`. The Navigator tree is `role="tree"` with
  `aria-selected` on entity rows; chevrons have their own `aria-label`.
- **Affected:** `HierarchyRow.svelte`, `HierarchyNavigator.svelte` styles,
  `styles/tokens.css` text ramp, `EditorInspector.svelte`.
- **Fixed:** contrast must hold; accessibility work changes semantics and focus, not
  camera graph, persistence or authored ownership; multi-select is not a tool for
  solving density here.

## 5. Constraints — do not redesign

1. **Canonical IDs and topology.** IDs remain the identity and connectivity
   authority. Display identity never becomes an identity, connectivity, selection
   or history key, and never depends on document order.
2. **Reference-generation mechanism.** Whether references are persisted
   presentation metadata or a deterministic derivative of canonical IDs is an
   implementation decision the child plan ratifies. Do not design against a
   specific mechanism (e.g. do not assume `W044` numbering), and do not rely on
   document order, row index or insertion sequence.
3. **Transaction / history architecture.** Naming is Layout metadata through one
   canonical transaction; a rename is one history entry or none; Undo/Redo restores
   it. No bespoke naming pipeline.
4. **Room reconciliation.** Room identity stays reconciliation-owned; naming must
   not change how Rooms are created, split, merged or retired.
5. **Selection authority.** One canonical Layout selection slot; one Navigator.
   Identity presentation must not create a second selection surface — this is
   explicitly why the `Ends` row must not become a Junction picker.
6. **Navigator IA beyond identity presentation.** Page set, history/back, search
   shape, filters, reveal and pinning semantics are landed. Extending the IA
   (new pages, relationship explorers, inline editing) is not P23.12.
7. **P23.13 drafting visuals.** Wall grammar, joins/caps, Door/Window symbols,
   dimensions, line weights, handles, snap/invalid feedback, label collision and
   zoom/density rules are P23.13. P23.12 only fixes the identity *hierarchy*.
8. **P23.14 shell / Inspector restructuring.** Navigator density/disclosure polish,
   Inspector grouping and action placement, enabled/disabled explanation patterns,
   context menus, status hints, keyboard/focus and accessibility remediation are
   P23.14. P23.12 may define the header/identity pattern; it may not restructure the
   panel.
9. **Multi-select** (issue #28, post-P23).
10. **Tags / taxonomy / classification / aliases / localization.**
11. **Authored Junction names** — not in the P23 minimum.
12. **BIM / storey / site / building hierarchy.**
13. **Inline Navigator rename** — the Inspector remains the only rename authority.
14. **Camera, visitor and Scene-identity surfaces** — Camera keeps its own labels;
    visitor output gains no editor identity vocabulary.

### 6.2 Mismatches between current code and the roadmap

1. **The `Ends` row is more prominent than the roadmap implies.** The roadmap
   describes it as one row inside an expanded Room Wall disclosure; that is
   accurate, but its label is a *single sentence-length line built from two
   formatted IDs* (`Ends Junction Chain 1 · Junction Chain 2`) inside an already
   indented child block. Screenshots should show it at the real rail width.
2. **Search can match an ID it does not display.** The roadmap lists raw-ID search
   as a P23.12 addition to preserve; raw-ID search **already exists**
   (`hierarchy-search.ts` matches `wallId`/`openingId`/`junctionId`), and today it
   produces results whose visible label does not explain the match. P23.12's job is
   therefore partly to make an existing capability legible, not only to add one.
3. **"Unnamed" is not a supported Room state.** The roadmap's presentation contract
   speaks of "unnamed architecture"; for Rooms the codec requires a non-empty name
   and auto-generates `Draft Room N`. Only Walls/Openings/Junctions can be unnamed.
4. **The rail width figure is unverified.** Roadmap and P23.6e directive say
   268 px; code has 240–300 px. Confirm the intended width before judging density.
5. **The Inspector already exposes raw IDs in more places than "debug detail"
   suggests** (Boundary walls list, endpoint/hosted-Opening buttons, Align dropdown,
   Objects accordion, diagnostics rows). Any tiering decision has to cover these or
   explicitly leave them.
6. **The current fallback label is worse than "formatted raw ID" implies.** The
   roadmap's shorthand (`W044`, `J022`, `D007`) reads like a tidy token; the shipped
   formatter only splits on `-`, `_` and whitespace, so real allocator IDs surface
   as `Opening:door:1`, `Wall Chain 1.b` and `Junction Chain 1.2` (§1.3 table).
   P23.12 is not just adding a reference — it is replacing a fallback that is
   currently illegible for a whole entity family.
