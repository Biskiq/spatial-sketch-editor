## 1. Purpose

P23.14 is the shell and visual-system slice. It exists because P23.0–P23.13 finished
the *substance* of the architectural Build phase — wall-first topology, canonical
curves, direct editing, display identity, the Plan drafting visual language — while
the shell around that substance settled only far enough to be functional.

**The outcome P23.14 is now accountable for (owner review, 2026-09-17):** establish a
coherent, extensible editor-shell **visual system and interaction grammar** with a high
enough ceiling that future P24, P26 and later capability can normally enter through the
*same language* without requiring a new shell redesign:

> a durable shell and visual system that (a) reads as one product across Scene/Camera and
> Plan/3D, (b) can host **P24** staging workflows and **P26** spatial/orthographic view
> concepts *without a shell rewrite or a second visual language*, and (c) does not freeze
> today's temporary P24/P26-sensitive content into permanent information architecture.

**P23.14 owns the visual operating system, not speculative future functionality.** It may
substantially revise: shell presentation; hierarchy; layout composition; control grouping;
density; typography; iconography; surfaces; borders and elevation; visual state treatment;
panel composition; timeline integration; and the canvas/chrome relationship. It also
owes the reusable grammar other surfaces inherit — property sections and rows, toolbar
groups, segmented selectors, mode/tool treatment, panel headers, status/warning/refusal
treatments, contextual instrument framing, selection/focus/hover/disabled states,
hierarchy rows, menu/popover grammar, Timeline shell grammar, and the spacing/type/icon/
token systems. Architecture and ownership contracts are preserved (§9). **[D]** in scope,
**[V]** in treatment.

**P23.14 does not implement** P24 multi-selection capability, material/light/environment
workflows or placement/support semantics; P26 Section, Wall Elevation, Ceiling Focus or
crop/depth/reveal behavior; P23.15 junction geometry; or speculative future view controls.
Those capabilities must have a *clear extension path* through the selected visual system —
which is not the same as shipping an implementation of them (§14).

**What this document is not.** It does not propose a visual direction, pick a style,
prescribe CSS or a component library, or optimize around current Svelte component
boundaries. Current styling is explicitly **not** authoritative (§10).

**Declared slice scope** (roadmap reconciliation, 2026-09-14; re-scoped by owner review
2026-09-17): P23.14 is registered as *"Editor Shell & Visual System Foundation"* —
formerly *"Build shell, Navigator and Inspector finish"* with a bounded polish scope. That
bounded work is **retained inside** the larger outcome rather than dropped, and it still
absorbs six open issues: **#34** status-bar hint contrast, **#35** canonical axis tokens in
number fields, **#38** shared context-menu keyboard navigation, **#39** editor tablist
keyboard behaviour, **#40** Project Row popover coordination, **#41** Document menu focus
lifecycle. It also owns the P23.6e Navigator-density follow-up. Source:
`docs/plans/2026-09-14-P23-remaining-roadmap-reconciliation.md` §P23.14. **[D]**

**Concurrent P23 slice, already merged (not P23.14's scope, but it lands beside it).** The
Junction-dissolve / Wall-join slice — **merged to `main` through PR #57** (`2716f61`,
implementation `e43ecf4`, 2026-09-17) and consuming no tracker P-number, per the child-plan
exception — replaces a degree-2 Junction with one joined Wall. Its shipped entry point is
**Delete/Backspace on a selected degree-2 Junction in the Plan**, with the transaction
reporting success or a per-code failure in the status message. Its *optional* entry points
were explicitly deferred to P23.14's shell finish: an **Inspector** action, a
Navigator/tree row action, and a Plan context-menu item. So P23.14's Inspector surface must
be able to host a **reason-coded destructive action** (`Delete junction` / join walls)
beside property sections, and must be able to show a refusal reason rather than a silent
no-op. None of those follow-ups may become a second eligibility authority — the core
planner owns every eligibility decision. **[D]**

## 2. Product mental model

### What Museum Editor is **[D]**

A browser tool for creators who want to author an interactive 3D museum, exhibition or
walkthrough — architectural space, placed objects, camera navigation — and publish it as
a visitor-facing web experience. It is explicitly **not** a BIM system, a DCC
replacement, Figma/Canva, or a game engine (`docs/north-star.md`).

Authoring is phase-based, not a waterfall: **Build** (spatial/architectural) → **Stage**
(objects, materials, lighting) → **Direct** (camera and route) → **Experience** (visitor
journey). P23 shipped Build; P24 is Stage; P26 deepens Build's spatial/vertical depth;
P25 is Experience. Phase names are authoring vocabulary, not UI labels. **[D]**

### Who it is for **[D]**

An individual creator (architect, exhibition designer, museum technologist, or an
artist building a portfolio space) working alone in a browser, who needs *credible
architectural authoring* and *credible camera direction* without CAD or DCC training.
Product authorization is single-user project ownership today. No teams, permissions or
collaboration exist.

### Core authoring workflows **[D]**

```text
Scene → Plan → Layout    draw Walls / Rooms / Door / Window / Column / Platform /
                         Plinth, select, reshape, inspect, refine
Scene → Plan → Arrange   place and move Scene objects (own pipeline)
Scene → 3D               verticals, materials, lights, object placement in space
Camera → Plan / 3D       authored camera nodes, connections, paths, framing
Save / Preview / Publish  (Row 1 + Publish surface)
```

Undo/Redo is **one** chronological stack for Spatial, tagged per document (Scene vs
Layout), exposed in Row 1. **[D]**

### Scene vs Camera **[D]**

`Scene | Camera` is the **domain** axis. **Scene** is the physical space (Layout
architecture + placed Scene content). **Camera** is guided cinematic camera navigation
— "Camera" always means a cinematic `PerspectiveCamera` route, never a webcam. Camera
owns the timeline and the node/connection graph. A domain switch is **attention-only**:
it never changes the document, history or the world, and never snaps the view.

### Plan vs 3D **[D]** with a P26 caveat **[P26]**

`Plan | 3D` is the **view** axis, orthogonal to domain. All four cells exist and are
reachable today:

| | Plan | 3D |
|---|---|---|
| **Scene** | the Build surface (`Layout` mode) and `Arrange` | spatial 3D of layout + scene |
| **Camera** | camera-graph authoring over a read-only architectural backdrop | camera authoring in 3D |

Boot is **Scene → Plan**. Camera → Plan is *not* a second layout editor: it authors
camera nodes over read-only architecture, with its own toolbar and Inspector.

**The P26 caveat is load-bearing for shell design:** Plan/3D is durable as a *top-level
distinction*, but P26 introduces **contextual orthographic instruments** (Section, Wall
Elevation, Ceiling Focus/reflected plan) that are explicitly *not* peer workspaces.
P26 lists the presentation question — `Plan|3D + Open Section` vs `Plan|Ortho|3D` vs a
breadcrumb takeover — as an **open design problem for external proposal**. A shell that
hard-codes exactly two view slots will need surgery in P26. See §13.

### Scene Plan local modes **[D]**

Scene → Plan carries a workspace-local mode presented as `Layout | Arrange` (internal
value is still `staging`; the user-facing word is **Arrange**). This is a *mode inside a
view inside a domain*, one level below the two global axes. **[?]** How a third level of
locality should be signed visually is an open design question (§17).

### Camera Timeline ownership **[D]**

The Timeline mounts in the **Camera domain only** and is Camera-owned in both Plan and
3D. It is collapsed `48px` / expanded `288px`, user range `240–300px`, with expansion
state persisting verbatim and **never** auto-expanding on a domain switch. Lanes:
Camera Path, Shots, FOV, Look At, Roll. Collapsed chrome is an integrated 48px temporal
mini-player (not a second playback bar). Expanded chrome has a fixed 36px header.

**The lane set is not static, and it can be absent entirely.** Lanes resolve from preview
scope: with **no camera flow** there is no *sequence*, so the dock keeps its header (or its
48px transport strip when collapsed) and renders an **empty body** — no lane surface, no
ruler — while the scope chip reads `No sequence yet`. The surface is still there; only its
lane body is empty.
A single placed camera node does not create a flow, so it produces no lanes either.
Selecting a **connection** gives the five *edge-local* lanes; a real flow (≥2 connected
nodes) gives the full sequence lane set. §3 and §7 carry the measured detail, and **no
screenshot in §4 shows a populated lane set** — the lane surface is currently specified in
words only. **[D]** for scope-dependence; **[V]** for lane presentation.

### How the surfaces relate **[D]**

```text
viewport      primary work surface — one shared Plan|3D axis, never unmounted, only
              collapse/clip; direct-manipulation fixtures live here
row 1         project identity, persistence, project modes, undo/redo, preview,
              theme, account — global scope
row 2         domain · view · mode · contextual tools — the authoring grammar
left rail     Selection/outline surface (Hierarchy|Assets in Scene; the Camera sidebar
              in Camera) — "what exists" and "what is selected"
Inspector     owned property surface for the *current selection context* — "what this is"
timeline      Camera-owned temporal surface, mounted in Camera only
status bar    persistent, informational: cell, selection, save state, hints, grid/snap
overlays      transient: previews/ghosts, snap markers, invalid refusals, focus ring
```

**There is one deterministic selection authority**, and viewport, left rail and Inspector
are *consumers* of it — not three independent selections, and **not** "exactly one selected
entity" as a permanent contract. Current Layout editing may remain single-target; future
Scene staging (P24) may hold an **ordered selection set with one primary/active entity**
that every surface resolves identically. Marquee and layout multi-select do **not** exist
today (deferred, issue #28), and the shell must not imply them yet. **[D]** as one
authority; **[P24]** for set/primary semantics.

returned to the viewport). *Correction carried forward:* planning prose described a
canonical **268px** Navigator rail, but there is no such constant in code; the roadmap's
own figure was corrected to the real **240–300 px** range (including the 240 px minimum) on
2026-09-17. `docs/plans/P23.6e-directive.md:141` and the P23.12 designer briefs still say
`268`. Design to 240–300 px regardless. **[D]**

### Surface-by-surface

#### Row 1 — Project Row `[D]`
- **Purpose:** project scope and everything global. `‹ Projects` (back to Project Hub),
  an inline-editable project-name field, a location/session chip (`Local Session` for a
  guest, cloud state when authenticated), a save-state control (`Save to Cloud`, whose
  disabled reason explains any blocker), a Document menu (`⋯`) holding per-document
  JSON import/paste/copy/download/reset plus Layout status and invalid-import feedback,
  the `Spatial | Publish` project-mode pair, Undo/Redo, Visitor `Preview`, a theme menu,
  and account/sign-in.
- **Must stay coherent with:** the save-state control aggregates **scene and layout
  dirtiness**; Undo/Redo binds the one tagged Spatial history stack; Document-menu focus
  lifecycle and popover coordination are open P23.14 issues (#40, #41).
- **Content durability:** **[D]** in role; **[P24]** in that Staging adds more
  document-level operations, and **[P26]** in that non-Spatial surfaces must *defer* the
  undo slot rather than share a universal cross-workspace undo.
- **Current tension:** `Spatial | Publish` reads as a 2-tab mode switch, but Publish is a
  project-level supporting **surface** (and `Experience` is a third, future, primary
  mode — P25). Flat 2-tab treatment will not scale. Flagged, not prescribed.

#### Row 2 — Workspace Ribbon `[D]` in role, **[P24]/[P26]** in content
Right side is stable across all four cells: `Snap` (value dropdown, e.g. `0.25 m`),
`Grid` toggle, and a panel-visibility group (`collapse left rail`, `collapse right
rail`, `Focus` — collapse both, `\`). Centre-left is **entirely cell-dependent**:

| Cell | Mode/scope segment | Tool group |
|---|---|---|
| Scene · Plan | `Layout \| Arrange` | Layout: Select, Wall, Rect Room, Poly Room, Door, Window, Column, Platform, Plinth + `Tour` viewport option |
| Scene · 3D | — | Select, Move, Rotate, Scale, Add Asset, `Local \| World` |
| Camera · Plan | — | Select, Add Camera, Connect, View |
| Camera · 3D | — | Select, Move, Rotate, Add camera, Path, Frame, View, `Observer \| POV` |

- **Purpose:** the authoring grammar — domain, view, mode, active tool, and the view's
  authoring actions.
- **Must stay coherent with:** the pre-P21 note that contextual/floating toolbars
  *relocate into Row 2* (P21+ target), leaving viewports with direct-manipulation
  fixtures only. Today's ribbon already satisfies this; the leftover floating toolbar
  concept should not be resurrected.
- **Durability:** **[D]** as a location and as a grammar (a segmented axis pair + a
  contextual action run). **[P24]** for the Scene 3D `Move/Rotate/Scale/Add Asset/
  Local|World` group and for any staging action that P24 adds or reorganizes.
  **[P26]** for the `Plan|3D` pair and for any future view-local display control.

#### Left rail `[D]` in role, **[P24]/[P26]** in content
- Scene domain: a `Hierarchy | Assets` segmented header; a breadcrumb (`‹ Back` +
  current page label); a search field ("Search Rooms, Walls, Openings…"); then grouped
  counts with expandable rows — `Rooms (n)`, `ARCHITECTURE` → `Walls / Openings /
  Junctions`, `PLACED CONTENT` → `Layout Objects`, `Scene Content`; and a footer
  selection summary with a reveal action (`Show in Walls ›`).
- Camera domain: the four-section **CameraSidebar** — `ENVIRONMENT` (read-only),
  `SEQUENCE INSPECTOR` (+ `Preview Sequence`), a **drop target** for an unsequenced
  camera ("Drag a connected Unsequenced camera here to start"), and connections with a
  component-local flat accordion.
- **Must stay coherent with:** canonical selection routing — Navigator is a *consumer*
  of selection identity, never a rename or mutation authority; page/history/reveal
  state is preserved (P23.6e).
- **Durability:** **[D]** as "what exists + what is selected" with reveal. **[P24]** for
  staging rows (rooms→objects→materials hierarchies will deepen). **[P26]** for its
  grouped taxonomy — Columns, Platforms, Ceilings and orthographic-relevant structure
  will add rows/groups.
- **Known current problem:** expanded Room→Wall disclosures can render a
  **non-selectable** `Ends <junction> · <junction>` relation row per Wall ("Boundary
  Junctions (n)" remains the Room-context Junction inventory). This is a real density
  and affordance defect with a stated preferred fix: remove the relation row from normal
  disclosures. It also caps how much this surface can be relied on to teach topology.

#### Inspector (right) `[D]` in role, **[P24]/[P26]** in content
Single-selection property surface. Today it renders, in order: a title + context line
("Layout Plan editing · preview-only"); a **read-only summary block** (Project / Source
/ Status / Rooms / Objects / Issues) followed by several lines of prose explaining
wall-first semantics; then collapsible sections — `Place` (Door, Window, Box, Cylinder,
Sphere, Column, Platform, Plinth as a 2-column grid), `Objects`, `Selection` (identity,
reference, then typed fields such as Name, Fixed endpoint, Length, Angle, Thickness).
With nothing selected it shows a short instruction plus a `NO SELECTION` explainer. **The two domains differ today:** the Scene Inspector leads with that summary + prose; the Camera Inspector omits it and goes straight to a selection prompt — so the same 300px column opens very differently depending on the cell.
- **Must stay coherent with:** the Inspector is **not** a document inventory; it shows
  only the one selected entity, and selection authority is deterministic across
  viewport/rail/Inspector.
- **Durability:** **[D]** as an owned property surface. **[P24]** for `Place`, material
  and light sections. **[P26]** for every architectural section that will grow
  (opening sill/head/arch-rise, wall-top profile, ceiling/section parameters).
- **Known current problem:** the default state spends its most prominent area on
  documentation prose, and the summary block occupies the top of every state. See §8.

#### Viewport `[D]`
- Plan is an **SVG** canvas (`CompiledLayoutGeometry → PlanRenderModel → SVG`); 3D is a
  WebGL canvas. Both occupy the same box and are collapsed/clipped — never unmounted.
- Plan carries in-canvas chrome: a `Draft layout · dirty` status chip, a coordinate
  ruler on both axes (metres), a grid, room fill and wall mass, dimension text,
  endpoint/curve handles, a `.focus-ring` keyboard instrument (P23.13), an axis gizmo
  **bottom-right**, and a footer strip with counts ("1 rooms · 0 objects · 0 geometry
  warnings · Selected: …") plus a `2 m` scale bar.
- 3D carries an **orientation/navigation box top-right** and its own armature.
  **[P23.15]** the architectural Wall/Junction **mesh** appearance inside that canvas —
  today's joins, seams, gaps and overlaps — is evidence of current state, not the final
  visual baseline (§12.1).
- **A selected camera node already has a finite-frustum representation in 3D.**
  `EditorCameraFramingHelpers.svelte` builds `EditorSelectedVirtualCameraFiniteFrustum` — a
  1px blue perimeter plus a translucent (~9%, scene-occluded) fill, depth-clamped to the
  authored target distance — and it is governed by the ribbon's `Frame` helper toggle.
  During playback it yields to exactly one moving visitor-camera frustum
  (`EditorCameraRig.svelte`), and visitor preview suppresses both. Tokens:
  `--editor-camera-frustum-line` / `--editor-camera-frustum-fill`. **Camera Plan
  deliberately renders no frustum, FOV cone or look-target** — Camera Plan has no framing
  authoring. **[D]** in role, **[V]** in treatment; §15 screen E exercises it.
- **Must stay coherent with:** the viewport is the primary work surface; the canvas is
  never unmounted; focus mode collapses the shell *around* it; Plan and 3D consume the
  same compile, and no consumer resamples curves or reinterprets opening topology.
- **Durability:** **[D]** as primary surface. **[P24]** for 3D staging affordances
  (gizmos, footprints, placement ghosts). **[P26]** for Plan itself — Plan will gain
  contextual orthographic siblings and derived display streams (cut/projected/hidden/
  symbol) that need their own visual grammar over the same canvas. **[P23.15]** for the
  architectural mesh itself — 3D joins and gaps are that slice's to fix with geometry, not
  the shell's to mask with presentation.

#### Timeline `[D]` in role, **[V]** in presentation
Camera-owned dock in both Camera views, two sizes: collapsed `48px`, expanded
`store.timelineHeight` (default `288px`, user range `240–300px`). **The lane surface is
scope-dependent and can be absent entirely.** Three verified states (component-verified
2026-09-17; the empty states are also visible in §4 screenshots 3 and 4):

| Preview scope | Expanded body | Collapsed body |
|---|---|---|
| **No camera flow** (zero nodes, or one unsequenced node) | header + **empty body** — no ruler, no lanes; chip reads `No sequence yet`; the dock still occupies its full `288px` | header-style **48px transport strip** (scope chip, edge-flip, transport, `POV \| Observer`, Observer tools, More, chevron) with **no scrubber** |
| **Edge** (one connection selected or previewed) | ruler + five **edge-local** lanes | 48px mini-player with scrubber |
| **Sequence / idle** (a real flow exists) | ruler + the full five-lane surface | 48px mini-player with scrubber |

- **The five lanes** — label column `7.5rem`, then ruler `28px` and lanes `44 / 48 / 34 /
  34 / 32` on a board that is `min-width: 42rem` and horizontally scrollable: **Camera
  Path** (transition bars + numbered node diamonds), **Shots** (per-node shot blocks with
  hold labels), **FOV** (degree-labelled keys; framing-envelope bands and handles in 3D
  only), **Look At** (target keys), **Roll** (constant `0°` at both ends).
- **Two lanes are paint-only in some states.** `Roll` is a fixed `0°` constant in *every*
  scope, and in Edge scope `Shots` reads `Quiet for Edge scope` / `No independent shot
  data` — yet each still holds `32px`/`48px` of a `288px` dock. This is §16's trust test in
  lane form (see §8 #14). Flagged, not prescribed.
- **Authority boundary on lanes.** A designer may freely challenge **visual weight,
  grouping, collapsing order, density and presentation** of these lanes. **Removing a lane,
  or changing what the Camera timeline means, is a Camera product decision** — not shell
  freedom — and requires separate Camera reconciliation (§10). **[V]** presentation,
  **[D]** which lanes exist.
- **Reachability defect behind the two unpopulated states (recorded 2026-09-17).** In a
  *canonical* project — every project created by **New Project** since P23.3 — **no
  camera node can be placed at all**: placement acceptance still requires membership of a
  room registry that a wall-first document deliberately leaves empty. Only the no-flow
  row above is reachable there, which is why the Edge and Sequence rows cannot be
  produced — or captured — in a new project. Diagnosis, evidence and the P24 handoff:
  [`../tech-debt/README.md`](../tech-debt/README.md) TD-1. Treat this as a **defect, not
  a design choice**: do not design the dock around the missing nodes as if empty camera
  authoring were intentional.
- **Must stay coherent with:** Camera-domain ownership; never auto-expand on domain
  switch; scrubbing belongs to the expanded ruler/lanes, not a second playback bar.
- **Known current problem:** the collapsed mini-player is **narrower than the viewport**
  (measured 760px inside a 980px viewport; the collapsed frame is
  `min(47.5rem, calc(100% - 2rem))` centred, while the expanded frame is full width), so it
  does not align with either the canvas edges or the status bar — a visible shell
  fragmentation. **[V]**

#### Status bar `[D]`
24px, always present: cell badge (`Scene • Plan`), selection summary, save state,
contextual navigation hints (`X/Z Grid`, `Orthogonal Wall`, `Snap Angle`, `Middle + Drag
pan`, `Scroll zoom`, `Shift angle snap`, `\ Focus`), and right-side grid/snap/metric
indicators. **Issue #34 (status-bar hint contrast) is P23.14's.** **[V]** for treatment,
**[D]** for its role.

#### Overlays and transient surfaces `[D]`
Preview ghosts and live dimension readouts during a gesture; snap markers; guides;
`invalid` refusals as a toast above the status bar (e.g. *"Wall rejected: Chain legs must
have non-zero length"*); the P23.13 keyboard focus ring; the Plan empty-state ghost and
its dismissible card; the numeric entry field anchored to a handle. Distinct from
committed state, and separate from the Inspector.

#### Collapse / focus mode `[D]`
`collapse left rail`, `collapse right rail` and `\` → grid `0 1fr 0`, CSS only, panels
`inert`, focus restored to viewport. Requests during an active pointer gesture defer to
one coalesced pending config; external resizes cancel the gesture.

## 6. Canonical workflows

Described so the shell is designed around *work*, not around screens. **[D]**

1. **Start and frame.** Boot → Scene · Plan · Layout, empty plan, viewport focused.
   Intent: get out of the way; make the first architectural act obvious.
2. **Draw architecture.** Pick a tool → drag → commit. Tool stays armed for a chain;
   Escape/select clears. During the gesture: live dimension, snap markers, guide, and a
   refusal toast if the placement is invalid.
3. **Reshape.** Select a Wall → endpoint handles appear → drag a handle (moves the
   Junction) or type into an anchored numeric field. Curved walls add a bend/curve-point
   control to the same group.
4. **Refine by exact value.** Keyboard: select → `Enter` enters the control group →
   arrows traverse → `Enter` opens the numeric field on the focused control → type →
   commit. Escape unwinds one level at a time. The readout announces role, position,
   owner reference and current value with units. (P23.13's A5 contract; see §11.)
5. **Place content (Staging).** In `Arrange` (Plan) or 3D: place from the Inspector's
   `Place` grid or the asset library, then move/rotate/scale in `Local` or `World`.
6. **Inspect.** Selection is routed, so the rail and Inspector both follow the viewport
   and vice versa; the rail offers `Show in …` to reveal off-page entities.
7. **Direct a camera.** Switch domain to Camera (attention-only) → author nodes in Plan
   or 3D → expand the Timeline to scrub the sequence and read the five lanes.
8. **Save, preview, publish.** Row 1 shows dirtiness and blockers; `Preview` opens the
   visitor takeover; Publish shows saved-vs-published and one action.

**Cross-cutting intent:** a creator should always be able to answer *which document am
I editing*, *what is selected*, *what is my active tool/mode*, *is this saved*, and
*which of these surfaces owns the value I am changing*.

## 9. Fixed product/architecture contracts

Engineering invariants translated into designer-readable constraints. A shell proposal
that violates one of these cannot be accepted, regardless of how good it looks. **[D]**

1. **Two domains, one document world.** `Scene | Camera` stays a domain switch. It never
   changes the document, history or world, and never snaps the view.
2. **One view axis, extensible.** `Plan | 3D` are top-level distinctions. **P26 may add
   contextual orthographic instruments** — they must *extend* the existing shell grammar,
   not create a second navigation or camera system or a set of peer workspaces.
3. **Plan and 3D are not two products.** Both consume one compile
   (`compileLayoutGeometry()`); no surface may own or duplicate geometry, and no consumer
   reinterprets opening topology.
4. **Visitor/editor isolation.** `/museum` and `/p/:publicationId` stay visitor-safe;
   editor-only hierarchy, selection, history and gizmo code never enter visitor chunks.
   A visitor surface is not a shell state.
5. **One navigation system** and **one camera-motion system** for the whole product. No
   dual nav graph, no second motion authority.
6. **Camera Timeline is Camera-owned**, in both Plan and 3D, collapsed/expanded with
   persistent state and no auto-expansion on domain switch.
7. **Separate document ownership.** `LayoutDocument` (architecture) and `SceneDocument`
   (models/primitives/lights/materials/cameras) are distinct. **Layout edits never move
   world-local Scene/Camera content implicitly.** This is the single most important
   architectural fact for design work.
8. **Room-local transforms, canonical world coordinates.** Scene placement is
   world-local; do not design shell affordances that imply Room-relative object ownership.
9. **Deterministic selection, history and Undo/Redo.** **One** selection authority consumed
   by viewport, rail and Inspector — never parallel selection truth, and never "exactly one
   selected entity" as the contract. Current Layout editing may remain single-target; P24
   staging may hold an ordered selection set with one primary/active entity that every
   surface resolves the same way. One chronological tagged Spatial history stack.
   Selection identity belongs to canonical entities, **not to a view** — a view switch may
   change handles, never identity.
10. **Selection-scoped Inspector.** The Inspector is the property authority for the
    *current selection context*; it is not a document inventory and never becomes one by
    accretion. Today it edits one selected entity; under P24 it may present multi-selection
    and mixed values **while the one selection authority is unchanged**.
11. **Authored state must never migrate into presentation-only UI state.** Derived
    display (footprints, dimensions, fills, section streams, previews) is read-only and
    never becomes an input to architecture. Conversely, nothing a designer invents as a
    purely visual layer may become required document state.
12. **Invalid input is refused with a reason** — never auto-repaired, never silently
    dropped. A silent no-op is a defect, not a style choice (problem #12 in §8 is exactly
    this).
13. **One mechanism per question.** No second solver, no second placement path, no second
    snap engine, no second compiled-geometry authority. A shell that needs "a small
    parallel system" to express a concept has found an architecture problem, not a design
    solution.
14. **The viewport stays the primary work surface.** The shell may be quiet or present,
    but the canvas is not a preview pane.
15. **Derived-state exclusions must be reasoned, never silent.** (P26 direction, already
    a P23 habit: a refused wall says why.)

## 10. Explicit design freedom

**Current presentation is not authoritative.** Existing CSS, tokens, component
structure and screenshots must **not** be treated as visual constraints merely because
they exist. The designer may challenge or replace any of the following: **[V]**

- panel styling, borders, corner geometry, elevation, tonal surface hierarchy;
- docked vs visually floating treatment **where ownership remains intact** (ownership is
  §9; geometry and float are free);
- spacing, density, control geometry, sizing, alignment rhythm;
- typography (family, scale, weight, casing, tabular figures);
- iconography (family, weight, optical size, metaphor consistency) — noting that the icon
  set is currently mixed: a Lucide-based set, a handful of owner-ratified custom Plan
  icons, and repo-SVG Plan icons added in P23.13;
- borders, dividers, elevation, shadow, color system, accent policy, semantic color use;
- toolbar visual grouping, labels, headers, section headings, disclosure affordances;
- affordance treatment (what looks clickable, and how strongly);
- hierarchy treatment in the rail (grouping, indentation, disclosure);
- Inspector composition and section ordering;
- Timeline presentation — visual weight, grouping, lane density, and the collapsed/expanded
  treatment of lanes. **Camera ownership, the lane set and the collapsed/expanded behaviour
  survive**; removing a lane or redefining Camera timeline semantics is Camera product
  reconciliation, not shell freedom (§3, §8 #14);
- supported desktop responsive behaviour;
- the *presentation* of Row 2's four semantic ranks — the ranks themselves are fixed by
  §2, the visual grammar is not.

**Also in scope:** replacing or restyling the in-canvas chrome; unifying Plan and 3D
canvas utility placement; giving the refusal/toast, empty-state and disabled surfaces a
system rather than one-off treatments; and proposing a signature visual trait.

**Out of scope for the designer's authority:** anything in §9; the P23.13 settled Plan
visual language (§11); P24 or P26 feature design; the view-taxonomy decision itself
(P26 owns it — the designer's job is to make the shell *able* to host the answer); P23.15's
junction geometry (the shell may not compensate for current wall/junction mesh appearance —
§12.1); and any change that requires a second navigation, camera, selection or geometry
authority.

## 11. P23.13 baseline

Treat as **settled**. P23.13 merged to `main` on 2026-09-17 (PR #58, `368a799`). Do not
reopen unless current docs mark a row unresolved. **[D]**

- **Plan visual language.** Wall mass/thickness/joins/caps; boundary vs non-boundary
  distinction; legible Door/Window cuts as neutral technical symbols; Room
  name/reference and derived area; dimensions; zoom-stable line weights and handles;
  selection/hover precedence; snap/draft/invalid feedback; label collision/suppression;
  empty and dense Plan states; representative-theme and zoom review.
- **Door/Window neutrality.** Opening symbols represent only authored semantics. Swing,
  handing, opening direction, leaf type are **not** inferred and must not be invented
  visually. Plan may not imply data the document does not have.
- **Passive Scene content.** Scene footprints are passive ink in Plan, with no fill and a
  CSS-hook-isolated presentation, so Camera Plan keeps its own vocabulary.
- **Handles and the focus instrument.** Direct-edit and curve affordances; endpoint and
  curve-point controls; a visible `.focus-ring` overlay for the keyboard control group.
- **Keyboard contract (A5).** `Enter` on a selected entity enters its control group;
  arrows traverse and wrap; `Escape` unwinds one level; a second `Enter` opens the
  numeric field on the focused control; the readout announces role, position, owner
  reference and **current value with units**. Arrows must **not** enter the group, and
  pointer focus is not group entry.
- **Semantic zoom / density.** As zoom leaves, dims shed first, then secondary edges, then
  labels, then handles — silhouette last. Dense plans must not pile up labels.
- **Display identity (P23.12).** Every Wall, Opening, Junction and Room has a concise
  unambiguous label everywhere it appears: authored name primary, stable compact
  reference as secondary, raw canonical IDs as debug detail only. **References never
  depend on document order.** Naming is Layout metadata; rooms keep their existing rename
  path. This is the contract the rail, search, Plan labels and Inspector all consume —
  a shell redesign must not invent a second labelling scheme.
- **Icons.** Wall, Rect Room, Poly Room, Door, Window keep their owner-ratified originals
  (byte-identical, silhouette-pinned); everything else uses repo-SVG assets. The 2026-09-17
  ruling superseded only the *icon* wording — the in-drawing Door **cue** (three-dash
  perpendicular, with its displaced sub-8px fallback) is **still** spec, and the two
  decisions share the word "Door" across documents. Do not read the ruling as weakening
  the cue. **[?]** Flagged because it has already been misread once.

## 12. Forward compatibility — the slices that land after P23.14

Two neighbours press on the shell and neither is P23.14's to design: **P23.15**, the next
P23 slice, which owns derived 3D architectural geometry; and **P24**, Scene staging depth.
(P26 is §13.) P23.14's obligation to each is to leave a **path**, not to build them (§14).

### 12.1 P23.15 — junction-correct wall-first 3D **[P23.15]**

P23.15 owns **junction-aware wall tessellation** for all and only the Junction
configurations canonical P23 topology already accepts — a deterministic miter/bevel/bridge
policy across mixed thickness and straight/curved tangent cases, with editor/visitor 3D
geometry parity and visible-gap/overlap/degeneracy validation. Unsupported topology stays
rejected upstream; rendering never broadens the valid set. Source:
`docs/plans/2026-09-14-P23-remaining-roadmap-reconciliation.md` §P23.15.

**What this means for shell design:**

- The current 3D shell **structure** is valid evidence — one canvas, orientation box,
  armature, framing helpers, selection frustum, grid. None of it is expected to change
  because of P23.15.
- The current architectural **Wall/Junction mesh appearance is not the final visual
  baseline**. Today's joins, seams, gaps and overlaps are precisely what P23.15 exists to
  correct.
- **P23.14 must not compensate for current 3D geometry through shell presentation** — no
  seam-hiding scrims or chrome "corner caps", no heavier 3D selection outlines sized to
  cover a gap, no density or color choice justified by today's welding defects.
- **[P23.15]** is carried on the 3D-facing claims and captures in this file: §3 Viewport,
  §4 capture 5, §5 durability map, §15 screen C.

**Do not broaden P23.14 into P23.15's geometry work** — no tessellation, junction or mesh
policy decisions belong here. §16 test 10 is the check.

### 12.2 P24 — Scene staging depth **[P24]**

Enough P24 direction to stop the shell freezing today's staging workflows. **Do not
redesign P24 and do not pull P24 features into P23.14.** Sources:
`docs/plans/2026-09-08-P24-scene-staging-depth-umbrella.md`,
`docs/plans/2026-09-10-P24-minimum-child-plans.md`.

**What P24 is:** Stage work over one project/Scene system, split into **P24A** asset
supply + canonical ingest and **P24B** rich 3D staging. Implementation-ready children
run `P24.0 → P24.5`:

| Child | Outcome | Shell surfaces it pressures |
|---|---|---|
| P24.0 | canonical Stage reachability, roomless entities, flat groups, ordered selection; **switching views cancels an unfinished operation first** | rail rows without a Room parent; selection ordering; a **view-switch cancellation** contract the shell must disclose |
| P24.1 | approved static supply + authoritative delivery; frozen 12-asset corpus; canonical material IDs; footprint proxies | library/asset surfaces; replacement of built-in supply; attribution output |
| P24.2 | shared floor placement and honest transforms; Floor/Keep-on-Floor, resolution reasons; Local frozen at drag start; uniform scale only | `Place` entry, transform group, ghost/preview language, **refusal reasons for unsupported/unresolved** |
| P24.3 | bounded material authoring: instance tint + metric tile override, mixed values, Edit Shared vs Make Unique | **Inspector material section**, mixed-value state, shared/unique disclosure, choice dialog |
| P24.4 | authored lights + one environment + Gallery reset; absent vs explicitly-authored mode; session-only assist light | light Inspector, environment section, helper visuals, destructive-reset confirmation |
| P24.5 | minimum acceptance and P25 handoff | no new UI |

**Selection-model reconciliation (2026-09-17).** P24.0's ordered selection with one
primary/active entity is why §2, §5 and §9 say **one selection authority** rather than
*one selected entity*: the shell must be able to present a set with a primary, and mixed
values are a *presentation* of that set — never a second selection truth. The current P24
toolbar, hierarchy, transform, asset, Inspector and staging controls are **not permanent
information architecture**; P23.14 designs the system they inhabit, while P24 owns the
actual staging capability, material/light/environment workflows, placement and support
logic, multi-selection semantics, mixed-value product behavior and Stage-specific feature
decisions.

**Design implication, stated plainly:** P24 will add *controls and sections* into
already-crowded places (the Inspector most of all), and will introduce at least three
state classes the shell has no precedent for — **mixed values**, **reasoned refusal of a
support candidate**, and **destructive reset of authored lighting**. The shell must offer
a path for these. Treat every Scene-3D transform/asset control and
every Inspector staging section as **placeholder content, not permanent IA**. **[P24]**

**Explicitly not P24's (deferred there or elsewhere):** a giant asset store; marketplace,
teams, collaboration; wall/ceiling support, physics, packing; a graph/UV/slot material
editor; a second Scene store or a Room-owned Scene hierarchy.

## 13. P26 forward-compatibility

Enough P26 direction to show how future spatial/view capability presses on the shell.
**Do not invent P26 behavior beyond current docs.** Source:
`docs/Deep-research/P26-research/P26-architectural-spatial-depth-synthesis.md`.

**What P26 is:** one canonical wall-first model acquires **controlled vertical structure**
plus a **precise orthographic surface** for authoring it. Plan stays horizontal
authority; a contextual **Orthographic** family (Section, Wall Elevation, Ceiling Focus)
becomes the vertical precision instrument; 3D proves the space. All edit one
`LayoutDocument`. No Levels, sheets, families or documentation system.

| P26 concept | Shell implication |
|---|---|
| **Orthographic as one shared instrument family**, parameterized by an explicit view kind | A third spatial view concept must enter the shell as a *contextual instrument*, not a peer workspace — the model of "four peer workspaces" is explicitly rejected |
| **View kind is explicit instrument state** (transient-first, pinnable later; never architectural truth) | Entering/leaving an instrument is a shell state question the designer owns; kind must never appear as document state |
| **Plan itself gains derived display streams** (cut / projected / hidden / symbol) with a **single membership stage** that emits **reason codes** for exclusions | Overlay/scene-graph legibility; a "reveal what was excluded" affordance model |
| **Cut hierarchy** `CUT > NEAR > FAR > passive > hidden-absent`; flat poche fills, no hatch engine | A visual grammar extension of P23.13's Plan language, not a replacement |
| **Active precision only around the target** (handles + temp dims + one snap + guide + proposal; scaffolding hides on commit) | Reinforces a canvas-first, quiet-shell direction — and directly pressures the current "everything visible at once" ribbon/status/canvas-triplication |
| **Identity: selection belongs to canonical entities, not a view**; no section-local identity; no merging on selectable streams | The rail/Inspector selection contract must survive view switches and new views |
| **Opening interaction resolves from hosted semantic relations, not boolean faces** | If openings are selectable in orthographic views, the shell's selection affordance must work from the host→opening relation |
| **Plane/span/look, finite depth + lateral/vertical crop, Reveal for exclusions** | A whole new control cluster with no current shell precedent |
| **Contextual navigation risk** ("return navigation must excel — the known weakness of contextual models") | A directly named shell design problem |
| **Workspace/navigation presentation is explicitly an open design question**: `Plan\|3D + Open Section` vs `Plan\|Ortho\|3D` vs a breadcrumb takeover | The single most important P26 item for P23.14: **do not hard-code two view slots** |

**The test to design against:**

> If P26 introduces two or three meaningful new spatial/view concepts, can they enter
> through the existing shell grammar without requiring a second visual system or a shell
> rewrite?

**Not P26's:** IFC/BIM classification, documentation sheets, far-field fading design,
cut-only interaction, gable/shed handle grammar, temp-dimension rules — those remain
open designer territory inside P26, which is *not* P23.14's to design.

## 14. Future capability pressures / reusable design vocabulary

States and extension needs the selected P23.14 visual system must have a **plausible path
for** — a vocabulary for thinking in systems rather than in fixed screens. **[V]** as
treatment.

**P23.14 does not need to ship primitives solely for capabilities that do not yet exist.**
It should not produce fake mixed-value UI, fake Section controls or unused Reveal controls
to claim future-readiness; those states arrive with the capability that needs them. What
must be true at P23.14's exit is that a new state or action can **enter through this
grammar** instead of creating a parallel UI language — and that a genuinely *new* primitive
requires explicit justification rather than becoming the default.

## 16. Future-pressure tests

Every future P23.14 concept should survive all of these. **[D]**

1. **P24 test — staging extensibility.** Can P24 add or reorganize staging controls
   (mixed values, reasoned refusals, a destructive lighting reset, material sections) and
   introduce ordered multi-selection with a primary entity, without breaking shell
   hierarchy, control ranking, or the **one-selection-authority** contract?
2. **P26 test — view extensibility.** Can two or three new spatial/view concepts
   (Section, Wall Elevation, Ceiling Focus) enter through the existing grammar without a
   second interaction language, a second navigation system, or a shell rewrite?
   **Do not hard-code two view slots.**
3. **Density test.** Can the shell serve both a two-room sketch and a 21-room / 48-wall
   plan without becoming noisy — and does it degrade by *shedding* rather than by
   overflowing or hiding essentials?
4. **Ownership test.** Can a creator always tell which surface owns the value they are
   changing (canvas gesture, rail, Inspector, Row 1) — and is every fact shown in exactly
   one authoritative place, with at most one passive echo?
5. **Canvas test.** Does the viewport remain the primary work surface — i.e. is the shell
   quieter than the canvas in the working states, not louder?
6. **Cross-workspace test.** Do Scene/Camera and Plan/3D feel like one product with two
   axes rather than four unrelated tools — same primitives, same state semantics, same
   selection identity, differentiated only where domain ownership genuinely differs?
7. **Trust test** *(added from P23.13's residue)*. Does every visible control do something
   the user can see, or explain why not? No mute controls, no silent no-ops, no
   documentation prose standing in for a property.
8. **Identity test.** Does the design introduce **zero** new labelling/naming schemes
   beyond the P23.12 display-identity contract?
9. **Remove-the-viewport-collapse test.** Does the shell still work when both side panels
   are collapsed to `0 1fr 0` — is selection still legible, and is the way back obvious?
10. **P23.15 test — derived-geometry honesty** *(added 2026-09-17)*. Does any part of the
    design depend on today's Wall/Junction mesh appearance being final, or try to hide
    current 3D seams through shell presentation? P23.15 owns that geometry; the shell must
    still read correctly after it changes.
