## 2. Final presentation recommendations

### References

- Family prefixes **R / W / O / J**, hyphen, short uppercase suffix.
- **Maximum six visible characters**, including prefix and hyphen; for example `W-7K3M`. This specifies a footprint, not an allocation algorithm.
- Avoid ambiguous characters within suffixes. No encoded order, location, ancestry, kind or geometry.
- Quiet monospaced text at readable contrast, with **no pill, border or button styling**.
- Never truncate, wrap or shrink a reference. Budget six character cells at the normal utility-text size.
- References are unique within the Layout document and non-editable. Do not recycle retired references for different entities.

The proposals’ opaque-token concern is valid, but fabricated sequence or ancestry is worse. Keep tokens short; names carry memorability.

### Navigator

**Identity line:** name first, complete reference beside it. Unnamed entities show the reference once.

**Optional context line:** relevant kind/relationship, such as `Door · on W-7K3M` or `Also bounds Gallery B`.

Do not repeat `Wall · Boundary` beneath every Wall or force every row into two lines. Reserve that space for information that helps distinguish or understand the entity.

Room references remain visible in Navigator identity rows. Use the same presentation in search and pinned selection. A shared Wall retains exactly the same identity in every Room context.

### Inspector

- Unified header: **name or reference**, with reference secondary when named; kind stated separately.
- Room retains **Name**. Wall/Opening gain **Name (optional)**. Clearing an optional name restores reference-led presentation.
- Full names can wrap in the header and remain editable in the field.
- **Technical details** starts collapsed, opens by keyboard/touch, and exposes a selectable full canonical ID with **Copy ID**. Preserve disclosure state while inspecting different entities.
- Provide **Copy reference** in the Inspector, without making Navigator references look actionable.
- Relationship controls and normal messages use names/references, not allocator strings. Keep existing panel grouping and rename authority.

### Search

- Match name, reference, raw ID, and existing kind/role terms.
- Highlight visible matching text.
- When a hidden canonical ID explains the result, add `ID match: …` with the matching portion visible; full ID remains available in Technical details.
- Preserve Direct / Related / Topology distinctions. Relationship context must explain related results.
- Exact reference matches must be prominent **within their existing result group**.
- Selecting a result preserves the query and existing selection/reveal behavior.

### Plan

- Room names remain the normal semantic labels.
- Existing selected-target feedback uses name/reference instead of internal selection terminology.
- Wall/Opening/Junction identity is available through selection; P23.12 adds no permanent field of reference labels.
- Room references support selected-target identification and duplicate-name disambiguation. P23.13 determines their spatial presentation.

### Long names, duplicates and density

- Under pressure: remove redundant metadata → abbreviate relationship summaries → ellipsise name. **Reference survives intact.**
- Full name remains available through selection in Inspector, not hover alone.
- Duplicate names retain distinct references; no automatic renaming.
- If a name exactly equals its own reference, show that string once in compact presentation; Inspector still distinguishes Name from Reference.
- Validate at **240–300 px**, including nested rows, selection pins and dark/light themes. Do not shrink text to preserve the current row composition.

## 3. Decisions that must be settled

Only **name inheritance on creation operations** needs an explicit product lock beyond the synthesis. Recommended defaults:

- **Wall split:** surviving Wall keeps its name; genuinely new fragments start unnamed.
- **Explicit duplicate/repeat:** copy optional Wall/Opening names unchanged, with new references.
- **Rooms:** preserve existing required-name and reconciliation behavior.
- **Retired entities:** their references never silently transfer to replacements; Undo restores them.

With these defaults accepted, no further product-design round is necessary. Reference storage/generation and collision handling belong in implementation planning, subject to the six-character footprint and stability guarantees.

## 4. Final P23.12 design contract

> Every Room, Wall, Opening and Junction has a stable, document-unique compact reference. Rooms retain required names; Walls and Openings support optional names; Junctions remain reference-only.
>
> Named entities lead with their name and retain a readable reference. Unnamed entities lead with the reference. Kind and relationships remain separate context. Raw canonical IDs appear in accessible, copyable Technical details and relevant search-match explanations.
>
> References use R/W/O/J families, occupy at most six characters, never truncate, and encode no mutable properties or topology lineage. Existing references never change because of renaming, reordering, unrelated edits or property changes. New entities receive new references; retired references are not reassigned. History and persistence restore exact identities.
>
> Navigator, Inspector, search, existing Plan identity feedback and architecture-related messages consume one identity vocabulary. Names may truncate in compact surfaces; references may not. Search preserves name/reference/ID and kind/role retrieval.
>
> Rename remains Inspector-owned. Split and duplication follow the name-inheritance rules above. No automatic fragment names, inline rename, Junction names, new navigation structure, permanent Plan label system or Inspector restructuring enters P23.12.
