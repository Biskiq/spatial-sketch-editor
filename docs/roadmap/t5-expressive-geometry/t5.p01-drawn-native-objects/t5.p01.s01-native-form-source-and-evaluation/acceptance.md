### Golden determinism

`corpus.ts` built its regular rings with runtime trigonometry. ECMAScript does not specify
transcendental results bit-exactly, so a golden produced from `Math.cos`/`Math.sin` output is a
property of the runtime, not of the kernel. The reviewer's failures isolate that path without
relying on their machine: every failing source is generated by `regular()`, while every literal
source passed, and runtime trigonometry is the only engine-dependent operation in the generator.
The local runtimes happen to agree with each other on arm64 — macOS and Linux, Node 20/22/24/26 —
which is why the defect did not reproduce here; agreement on one architecture is not a
cross-platform guarantee. The fix removes the dependence rather than assuming one architecture.

The fix does not touch canonical output:

- `__fixtures__/regular-ring-units.json` pins each required ring as shortest round-trip decimal
  literals of the reference doubles. Multiplying them by 2, 40 or 0.45 is exact IEEE multiplication.
- `regular()` refuses a count with no pinned table instead of falling back to trigonometry; the
  `star-5` fixture and the `too-many` invalid case no longer call it.
- `geometry-core-boundary` now applies its forbidden-arithmetic scan to the fixture directory as
  well as `packages/geometry-core/src`, so a future ring cannot silently reintroduce the defect.
- All 48 digests were compared before and after the fixture change and are identical; **no pinned
  value was regenerated or overwritten.**

Verified locally:

| Environment | Result |
| --- | --- |
| macOS arm64, Node 26.7.0 | `profile-corpus` 125/125, `geometry-core-boundary` 6/6 |
| Linux arm64, Node 20.20.2 and 26.12.1 | 131/131 each (the two files) |
| Linux arm64, Node 22.23.4 and 24.22.1 | `profile-corpus` 125/125 each |

**Not verified:** a real Linux x64 runtime. The local x64 emulation is numerically unusable
(`2 * 0.5` returns `0`, `Math.PI` returns `3`), so no result from it is evidence. The structural
fix removes the only engine-dependent operation from the golden inputs; a real x64 CI or developer
run is still the remaining external confirmation and is not claimed here.

## Criterion 6 — not met, owner decision required

The plan's criterion 6 is: *"Stage, Plan and Preview draw and select the same form result."*

**Drawing** is met through one renderer: Stage and Preview dispatch `kind: 'form'` to the same
`EntityForm.svelte`, and the Plan lens is a camera reading of that same Stage. The form was
observed in both the 3D and Plan readings.

**Selection is not met, and cannot be completed inside S01 without widening into T1/T2 work.**
Verified in the current tree and in the running editor:

- `buildPlanSceneFootprintProjection` has no production caller; only
  `plan-scene-form-footprint.test.ts` consumes it. The Plan form ring is an exposed, unit-tested
  seam, not a production Plan surface.
- `resolvePlanSceneHit` / `resolvePlanSceneHitAtZoom` have no production caller; only the same test
  imports them.
- No adapter registers `StageAdapterBinding.hitProvider`. The Stage's production hit path resolves
  compiled **Layout** fragments only, so an adapter-provided Scene hit cannot claim the pointer.
- There is no 3D Scene entity-picking path (no raycaster or renderer pick registry). In the running
  editor, clicking the visible form selected the **room floor** and opened its Card; the form has
  no Index row or Find entry, and Find reported "No matching subjects".
- The Index groups are derived from `planView.membership`, which is Layout membership; Scene
  entities are absent from the locator in this base.
- Because nothing can select a form, the product cannot invoke move, turn, duplicate, delete or
  size on it. Those planner paths are library-tested only, which is not end-to-end selection.

A resolution would need all of:

1. Scene subject projection into the Index/Find and semantic selection (T1 host + T2 Scene).
2. A Scene Plan hit provider built on the existing footprint seam, plus selection mapping and
   priority against Layout hits (T2, with T1 review).
3. A 3D Scene picking path: a renderer/entity pick registry or analytic equivalent, a Stage ray
   hand-off and selection installation (T1/T2 architecture; a new Stage capability).
4. The Agent E2E selection journey and its accepted evidence.

### Occlusion cost

The reviewer measured ~5 ms per pointer event for floor-support resolution alone at 60 forms of
128 smooth anchors. The local reproduction uses the same shape count, three workloads, 200 rays
and five measured rounds after warm-up; the timer covers `supportOccluders` + `floorSupport`, the
two calls the adapter makes per pointer event. Before = `7b49728a`; after = `a1ded6a3`.

| Workload (60 forms × 128 smooth anchors) | Triangles | Before, per event | After, first event | After, steady state |
| --- | --- | --- | --- | --- |
| Scattered 0.7 m rings | 61 200 | 2.05 ms | 1.16 ms | **0.011 ms** |
| 40 m rings | 122 640 | 2.77 ms | 1.89 ms | **0.76 ms** |
| Dense overlapping 40/8 m star (synthetic worst case) | 491 280 | 7.47 ms | 4.89 ms | **3.58 ms** |

Causes and fixes:

- **Per-form triangle loop:** a ray that misses the form's canonical local bounds cannot hit a
  triangle. The local AABB test is conservative (expanded by the triangle test's epsilon), so it can
  only skip provably missed bodies and never change a hit.
- **Allocation in the triangle test:** the Möller–Trumbore loop allocated two `Vec3` tuples and
  three more per triangle; the scalar form performs the same operations in the same order without
  the allocations.
- **Occluder construction per event:** `supportOccluders` evaluated each form's canonical key and
  allocated its occluder list on every pointer move. The adapter now retains the list per immutable
  accepted snapshot and excluded subject in a `WeakMap`; a new accepted revision naturally misses.

Hit semantics were checked against the previous implementation on 5 000 random rays over 24 forms
(square, concave, smooth and pentagon outlines, rotated and varied extent): 0 differences in
`FloorSupport` values, including occluder identity and distance.

**Not measured:** browser/GPU frame time and the reference-laptop workload. These are CPU
microbenchmarks of the same functions the pointer path calls; a passing correctness suite is not a
browser performance claim. The dense synthetic case still costs ~3.6 ms per event because every
form covers the ray; that is a bound on an adversarial scene, not a representative one.
