# PR6 proposal · How Biskiq agents should find the right evidence

**Draft for owner review · 26 November 2026 · baseline after #421**

Give agents a short way to find three things: what the creator should experience, which product boundaries their change must preserve, and what observation would prove the work succeeded. Let them choose the implementation. The largest change proposed here is to stop publishing implementation progress and completed plans as permanent repository knowledge.

Pilot this on one Appearance surface, one ordinary fix and one engineering planning question before changing the rest of the repository. Keep the current gate, owner holds and approval rules in force while the pilot is evaluated. The companion audit reconstructs the failures, compares three revisions with post-PR5 main, and distinguishes research results from practitioner advice. [Evidence and sources](../../broad-research/repository-context-evidence.md)

## The decision

Approve three changes in direction together.

1. Give each approved visual target a directly reachable, revision-specific identity and use it in the implementing PR. Keep the feature's visible composition and interactions there. Shared shell prose should explain only cross-feature obligations that still apply.
2. Move routine work coordination to the work item. Keep durable technical knowledge with the code, experiment or approved design that gives it meaning. Delete spent instructions as part of the change that spends them.
3. Delegate reversible engineering choices to the implementer. Preserve an owner's right to change direction and require a decision for actual changes to agreed boundaries, product promises or exposure. Use a short experiment to determine whether any optional planning skill earns its place.

A rewrite focused on wording alone would leave two U5 failures possible: an older document could still define the Library differently, and a reviewer could still accept a functional substitute without seeing the approved interaction. The original U5 also contained worthwhile work. Keeping its real inspection and write paths made forward recovery possible. ### Alternatives

| Approach | What it buys | Cost or risk | Judgment |
| --- | --- | --- | --- |
| Keep the current architecture, shorten the guides, run the gardener more often | Familiar navigation and low migration risk | Preserves separate surfaces for scope, progress and permission. Archive-only gardening cannot stop new paperwork from entering the active tree. | Use a wording correction for an isolated defect. Decline as the system-wide answer. |
| Use almost exclusively code, tests and a task prompt | Very cheap cold start for ordinary repairs | Current code cannot tell an agent that an approved Library should behave differently or why an alternative topology lost. Knowledge in a single chat disappears for the next contributor. | Use as the lower bound in a cold-start comparison if the pilot still feels heavy. |
| Adopt a full specification and evaluation platform | Traceable requirements, screenshot baselines, skill telemetry and maturity dashboards | More synchronized representations, model-specific upkeep, frequent approval work and goldens vulnerable to WebGPU, font and fixture variation. | Consider a targeted component golden or a check for a repeated failure. The whole platform has no demonstrated return here. |
| **Keep a small entry point, scoped visual targets and executable domain constraints** | A reviewer can check the intended change, and agents can find the reason for a boundary without reading a program history | Requires usable specimens, judgment about what to retain, and a real comparison while developing visual work | **Recommended.** Run it on a recoverable slice and reverse any deletion that measurably impairs the work. |

## Which source can decide which question?

| Question | Source to use | What it may decide |
| --- | --- | --- |
| What work is authorized now? | The owner's current task and any explicit active hold, with the live issue or PR for coordination | Scope, delegated decisions and deliverable. A merged plan records the decisions it actually approved. A milestone or research finding alone cannot release work. |
| What does the product do today? | The running entry point, owning implementation, boundary tests and observed journeys at a revision | Facts about present behavior, including bugs. CI results are evidence for the path and inputs exercised. |
| What should this creator see and be able to do? | The latest explicit approval for that surface and state, linked to the visual artifact and any subsequent scoped ruling | Composition, labels, hierarchy, actions, responsive states and intentional omissions. Unspecified regions use the existing shell. |
| What must remain true across implementations? | The owning semantic contract and its executable witness where available | Ownership, identity, coordinate frames, security, formats, history and isolation. Tests demonstrate covered failure classes. Rationale states obligations that a finite test cannot exhaust. |
| Why pursue this direction, or why was a plausible approach rejected? | A short product intent, measured study, counterexample or experiment with its limits | Rationale and evidence for exploration. A successful spike earns the next engineering decision. |

Two apparent conflicts often resolve immediately. An approved change to a dock key applies across tools when the approval names that scope, as D12 did. A prototype that simulates editing a Finish using local state specifies a preview experience. The implementation can realize it with a render-only draft, one writer and one Undo. If an invariant genuinely prevents an approved action, show the smallest failing case, the user-visible consequence and viable options to the owner. Continue independent work. Existing CSS, a plan omission and a test that freezes an old label each warrant investigation by the implementer. None alone warrants a new approval. ### One credible entry point

The following is an example of what the entire root guide could say after migration. The links point to working destinations in today's tree. The pilot tests whether those destinations suffice.

> Follow the owner's current task and [explicit holds](../../focus.md). Work within the authorized scope. Commit when asked and omit agent attribution.
>
> For a visible change, open the approved state for that surface and compare the running product with it. The [design catalogue](../../prototypes/README.md) identifies the relevant decisions and shell defaults.
>
> Layout, Scene, Camera and Experience each own their authored facts. Preserve the canonical compiler and evaluators, saved-data boundaries and visitor isolation. Read the [owning contract](../reference/architecture.md) when a change touches one of those seams.
>
> Verify the affected behavior through its normal entry point. The [test guide](../../apps/editor/tests/README.md) identifies local and integration checks, including the DB-backed API suite. Run and setup commands live in the [development README](../../README.md#development).
>
> Make reversible choices and explain material departures. Bring changes to protected boundaries, approved experience or production activation to the owner.

The five current instruction files need different treatment. The two useful reminders for an API contributor are authenticated ownership/conditional Save and how to obtain a real database test. Keep that local route. Put Studio integration and the relevant entry contract beside the feature. Prototype isolation and run commands belong in the catalogue and packages. Start the pilot with no separate editor, generic packages or prototypes boilerplate beyond any irreducible local gotcha identified during migration. Link the area explicitly from the task when working from root. Keep personal preferences and client tool instructions in their existing user or client scope.

## What design implementation would look like

Use an ordinary catalogue entry and implementation PR. The **approved revision plus explicitly scoped amendments** identifies the target. Keep the decision itself in one place and link to it. The catalogue may point to an HTML state, a screenshot, a short recording or a board. A semantic mock is sufficient if it exposes the design decisions people need to review.

| --- | --- |
| Target and scope | At #399, open the recommended app in the walnut preset with Materials, Paint-pick intent and Oak detail. Use the responsive board for desktop and iPad portrait. Use the subsequent #408 ruling for coexistence with an open Index at 1024 px. Index redesign, alternate concepts and the future brush stay outside this change. | Target a visible failure before polishing | Place the same Library invocation beside its running implementation, with a comparable selection, detail, viewport and pointer. Compare position against the Stage and dock, nested families, sample shape, information hierarchy and availability of a separate detail action. Use actual visual evidence in the PR. An overlay, pair of pictures or brief recording is enough to expose the specific difference. |
| Exercise the interaction | Activate the card in Paint, then separately activate detail. Observe the armed choice and unchanged project/history. Exercise Shift-keep-open and keyboard activation. For a draft, cancel back to the invoking control, then apply an eligible edit and Undo once. Use the real Stage and write path. Compare material appearance under a named lighting setup only when that appearance is at issue. |
| Resolve disagreement in the owning PR | If the Index blocks a click at 1024 px, show that state, describe whose action becomes unavailable, and apply the existing scoped ruling. Adapt the implementation freely to respect it. A new, material departure needs an owner decision with the picture and consequence attached. A nonvisual patch to a satisfied writer uses its ordinary behavioral tests. |

Core parity belongs to the implementation that claims to deliver the surface. A reviewer should be able to fail an attractive screenshot whose card performs the wrong action, and fail a passing interaction test whose sheet hides the Index. The owner retains final manual acceptance. Matching a design proves fidelity to the decision. When ease of use is the open question, let a creator try the task from a cold start and observe where they hesitate or choose the wrong target. That result can reopen the design. A new approval replaces the applicable catalogue pointer and obsolete design details in the same change. Keep past targets reachable by revision for comparison. There is no need to transcribe the board into a pixel table or generate a second target from production.

## Repeat the valuable part of T1 and T2 planning

For difficult work, ask for a creator journey, the capability it requires, the consequential uncertainty and the cheapest observation that could change the decision. Show which pieces can be reused, the prerequisite order, how a slice could fail, and which choices are delegated. Write that in the draft PR in whatever form helps reviewers decide. One worked example can teach this better than an always-loaded planning method.

Take a creator enlarging a round gallery after a neighbour has acquired a window. First ask which identity and opening relationship must survive. Try resizing at a value that should work and one that makes the neighbour too short. Compare the whole candidate, refusal, unchanged history and exact radius. Only then plan the kernel/codec and integrated editor steps that depend on the result. The designer can explore a direct handle, precise entry or both without committing the engine to the first sketch. The S2 wrong-corner example and S8 inspection host are suitable examples of a probe changing the architecture and a capability enabling several presentations. [Connected-curve spike](./t1-spatial-world/next-batch/spikes/s1-connected-curves.md) · [S2 counterexample](./t1-spatial-world/next-batch/spikes/s2-space-conversion.md) · [Appearance foundation](./t2-look-atmosphere/s8-professional-material-foundation/pr-e7-report.md)

Separate the engineering and final-design decisions **when their uncertainties differ**. An engineering PR can demonstrate a renderer or planner through a fixture, disposable control or vertical slice. Its controls acquire production design authority only through explicit approval. A designer can sketch early enough to expose a missing affordance, then try the real latency, refusals and data before final approval. If a sketch shows that a creator needs to change one of three surfaces independently, feed that requirement back to the domain owner. Avoid freezing either the model or the UI to achieve a clean handoff. For a known gesture over a proven planner, ship one ordinary end-to-end PR.

## Preventing accumulation during ordinary work

- **A new instruction needs a consumer.** Identify the surprising decision it enables and who would otherwise get it wrong. If a tool can enforce the constraint reliably, use the existing owning check. If one task needs it, put it in that task. A matter of taste may live in a scoped design or remain delegated.
- **Change the consumer in the same diff.** When a command, approval or format changes, search for its name and old behavior in scopes, skills, tests and examples. Update the authoritative instruction and remove the obsolete route. The reviewer can ask which actual task would still need the old text. A global registry of rules or expiry dates would itself require maintenance.
- **Close at the source.** A PR or issue can retain debate, progress and acceptance evidence. The last consumer of a temporary plan either points the remaining work to a live item or removes it. A unique observation needs its inputs, environment, expected result and limits. A conclusion like “Gate B passed” is disposable once the PR records it.
- **Retire by example.** Preserve the S1 fixture and its exact subdivision/refusal observations, S2's failed representation, E7's failed lighting recipe and R217's bounded owner acceptance. Remove a merged C3 resume checkpoint once its successors and obligations are accounted for. Keep T4 prepared release and the unimplemented T5 design available as future choices. Moving every old file into another directory recreates the problem. ### A bounded test of the recommendation

Use three task prompts, two fresh runs per prompt, six runs total. Keep the model/version, harness, tool permissions, base code, fixture and task wording identical within each pair. Run the current guides in one copy and pilot guidance in the other. Alternate order. Give both agents the same access to approved evidence. Give the runners the problem and allowed source artifacts. Keep answer-bearing issue text, historical patches, scoring notes, prior chats and the other run out of their brief. Use identical isolated checkouts without remote or commit-history lookup for replays, and record any solution already visible in the supplied tree. Use disposable worktrees and no production accounts. These runs are proposed experiments. The audit's repository probes are the baseline observations available today.

| Task | Outcome scored by a reviewer who did not implement it |
| --- | --- |
| **Ordinary repair** · A Paint dropper shows pressed when idle. Supply a local reproduction based on #415. | Through a mounted control, idle and armed states are distinguishable and change correctly. Existing reads/writes remain sound. Note unnecessary permission requests and unrelated plans or updates. [Issue #415](https://github.com/Biskiq/spatial-sketch-editor/issues/415) |
| **Approved visual change** · On identical disposable trees seed a U5-style regression: render the Library over the Index and make the primary card open detail in Paint mode. Include a case with the Index open at 1024 px. | Score the desktop/constrained state, choosing versus inspecting, focus restoration and no write when arming. Inspect prototype and production captures with matched intent. Mix the pre-fix pair with a corrected control and ask the reviewer to identify the discrepancy without seeing the branch label. Apply the #408 amendment when scoring. |
| **Engineering decision** · A creator wants to enlarge a connected gallery without losing a neighbour's opening. Give the S1 fixture and earlier research as available starting evidence. Ask for the smallest next decision on a *different* fixture with the neighbour opening near its limit. | The plan identifies the owning semantic fact, predicts an acceptance and a refusal, distinguishes simulated from production behavior and sequences the integration test that could disprove the prediction. Give credit for a better representation with equivalent evidence. A replay establishes retrieval and transfer to a near case only. |

Count the evidence available in an ordinary transcript: task checks satisfied on first review, material deviations and subsequent fix rounds, unnecessary versus necessary owner decisions, documents/bytes actually read before the first relevant action, and elapsed time to an acceptable result. Use input/output token counts if the client exposes them. Otherwise label byte and tool-call counts as proxies. Include the injected instructions in both conditions when measurable. Record runtime waits separately from agent effort. A short wrong result scores as a failure.

**Decision rule for this small sample.** Require all protected semantic and visual outcomes in the pilot, including rejection of the planted visual defect. Proceed only if at least two task pairs also improve context read or avoid an unnecessary intervention without extra corrective rounds. Compare the third pair explicitly. If quality falls, identify the lost piece of knowledge and restore its narrowest effective route. If outcomes tie and effort differences are ambiguous, keep the current behavior for that area and repeat only the disputed case once. Six runs can expose a bad design and support a reversible local choice. They cannot establish a general productivity effect.
