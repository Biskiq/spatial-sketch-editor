## 1. The defect, stated once

A Room-duplicate / repeat operation and an import can both **admit** geometry that the canonical
topology gate later **rejects**. Concretely: a curved (cubic-chain) Wall copied into a position whose
**Bézier bows cross** another Wall while their **endpoint chords stay disjoint** is admitted, because
the duplicate batch gate classifies Wall pairs with the chord-exact `classifyWallIntersection`
(`packages/layout-core/src/layout-wall-topology.ts:129`) and never calls the sampled crossing gate
`detectWallCurveTopologyCrossings` (`packages/layout-core/src/layout-wall-first-precision.ts:1964`).
The next document-wide sampled gate then rejects — including for edits that have nothing to do with the
crossing — and the rejection is attributed to the *new* edit rather than to the pre-existing geometry.

```text
ONE RULE, FOUR SCOPES (F-C7 / Q5):
  enforced  validateWallFirstTopology (layout-wall-first-precision.ts:1732, gate at :1790)
  enforced  validateChainTopology (layout-wall-chain.ts:982) — Wall-chain / rectangle authoring
  ABSENT    validateWallFirstLayoutDocument (layout-wall-first-codec.ts:164)  → import admits (F-C6)
  ABSENT    validateBatchWallTopology (layout-duplicate.ts:201)               → duplicate admits (F-C1)
  INTRA-ROOM ONLY  the compile (layout-geometry-validation.ts:128/138)        → inter-Room crossing OK
The gate is the same function the duplicate path failed to call, so the two verdicts disagree by
construction, not by a numeric tolerance (F-C4).
```

**Impact is UNKNOWN, mechanism is established.** No repository evidence exists that any live exported
payload actually carries an inter-Room curved crossing (harvest UN-9). Whether the omission at
`layout-duplicate.ts` was a deliberate P23.4 scope choice or an oversight is also **UNKNOWN** (harvest
UN-8) — though the doc comment there claims parity with the canonical bar, which it does not hold.

**How Option E re-reads this defect.** The four-scope table above describes the rule's *enforcement* gap.
Option E (§2.10) changes the rule's *subject*: the gate keeps failing on geometric intersection, but only
between entities in the SAME connected group, so the intended behaviour of a crossing between independent
groups stops being "rejected" and starts being "permitted geometry". The enforcement gap matters either
way — under E, a path that omits the group-scoped gate still cannot distinguish a permitted independent
overlap from a genuine intra-group violation. **The delivered model is in §2.11, traced from source at
`7c3d392a` rather than inherited from these anchors.**

## 2. The decision

> **Which validity policy governs curved Walls whose Bézier geometry crosses another Wall, and what
> happens to documents that already contain such a crossing?**

Four bounded options were presented in P23B.1 §8 (PO-1) and are reproduced here with the consequences
each one has on the surfaces this record is required to cover. **No option is recommended. This record
exists so the owner can rule, not so an implementer can infer.**

### Option A — reject at ingress (one rule, every surface)

Every surface — duplicate/repeat, authoring, import — applies the single sampled-curve validity rule, so
an invalid document can never be created **or admitted**.

| Surface | Consequence |
|---|---|
| Authoring / Room duplication | Room duplicate gains `detectWallCurveTopologyCrossings` on its batch path; a chord-disjoint but curve-crossing copy is refused **before** any history entry, identity mint or install. Duplication becomes consistent with Bend/knot/chain authoring. |
| Import of an already-invalid document | **Refused at ingress.** The codec (or the import seam) gains a topology rule it does not have today. An exported payload carrying such a crossing stops importing. |
| Editing / repairing an admitted-invalid document | The state becomes unreachable *through the product*, so no repair path is required for new documents. **But** it remains reachable from payloads already imported before the change and from any hand-edited file: the ruling must say what happens to an already-open document that fails the new gate. |
| Diagnostics, identity, history | Cheap and clean: one verdict, one code, one attribution. No new severity state, no identity semantics, no history semantics. |
| Existing exports | **The real cost.** Compatibility breaks for any payload containing a curved inter-Room crossing. Needs a decision on whether a migration/repair hint is offered, and whether the break is silent or explained. |

*Surfaces touched:* `validateBatchWallTopology` (or its replacement call), the codec or the import path,
any fixture/import-compatibility expectation. *Evidence:* F-C1, F-C3, F-C6.

### Option B — admit with an explicit invalid state

The document may exist and render, is **visibly marked invalid**, and later Wall operations report the
**pre-existing** cause rather than a fresh rejection.

| Surface | Consequence |
|---|---|
| Authoring / Room duplication | Duplication may still admit the crossing — but no longer silently: the result carries an explicit invalid state. Requires a decision on whether duplication is also *warned* up front. |
| Import of an already-invalid document | Import continues to admit; the document is marked invalid on arrival. Needs the vocabulary to exist before import can express it. |
| Editing / repairing an admitted-invalid document | The document is editable in the sense that it loads, but a *repair path* is implied: an invalid document must be repairable or the state is a trap. Whether "repair" means user-managed or assisted is a further call (it shades into Option C). |
| Diagnostics, identity, history | **The expensive option.** Requires a severity/vocabulary decision (`invalid` as a first-class document state vs. an issue list), attribution that names the pre-existing crossing Walls rather than the touched Wall, and a history semantics decision: does the invalid state participate in undo/redo, and does a repair produce a history entry? Identity is unaffected (no new entities), but *entity-level* attribution must survive the document-wide scan. |
| Existing exports | **Best compatibility.** Existing payloads keep importing; the product's honesty improves instead of its strictness. |

*Surfaces touched:* the issue/severity vocabulary, the Plan/3D invalid-rendering path, message
attribution in `validateWallFirstTopology`. *Evidence:* F-C2, F-C5.

### Option C — provide repair (offer an explicit resolution)

When an operation would produce a crossing, the system offers an explicit resolution — separate, nudge
or noding — instead of silently rejecting.

| Surface | Consequence |
|---|---|
| Authoring / Room duplication | Duplication of a crossing-producing Room becomes a **guided interaction** rather than a refusal. |
| Import of an already-invalid document | Still needs an answer; C does not decide ingress. C pairs with A or B. |
| Editing / repairing an admitted-invalid document | This IS the repair path — the option whose purpose is the third surface. |
| Diagnostics, identity, history | Substantial: the planner result vocabulary gains an "offered resolution" outcome; the gesture gains a UI affordance; the resolution itself is an edit and therefore must produce deterministic selection/history behaviour. Choosing "noding" specifically interacts with the landed noding path and with Wall identity (whether a split creates entities). |
| Existing exports | Unaffected by itself (it adds capability, not strictness). |
| **Nature of the change** | **This is CAPABILITY, not cost.** It adds an authoring affordance the product does not have. P23B's umbrella scope is explicitly cost, not capability (`no new architectural capability, view, mode, document...`; "P23B adds no view, no document, no schema"). |

*Surfaces touched:* the planner result vocabulary, the editor gesture UX, history. *Evidence:* F-C5,
F-C3. **Scope flag:** adopting C requires an explicit scope decision — it is not a P23B optimization and
should probably not live in P23B at all.

### Option D — leave as-is, document it

Behaviour is unchanged; the situation is documented.

| Surface | Consequence |
|---|---|
| Authoring / Room duplication | A successful operation can still create geometry a later, unrelated operation rejects. |
| Import of an already-invalid document | Still admitted (F-C6). |
| Editing / repairing an admitted-invalid document | Still blocked by the pre-existing crossing, still misattributed to the new edit. |
| Diagnostics, identity, history | Unchanged — including the misattribution. |
| Existing exports | Fully compatible. |
| Depth | The defect is intentionally kept, and the misleading **code comment** at `layout-duplicate.ts:196-200` (which claims a bar the gate does not hold) should be corrected as part of closing, or the state is actively misleading to the next reader. |
| Interaction with M-2 | **Blocking.** If D is chosen, the synthesis's verdict-reuse half of M-2 is inadmissible (§8.6 AB-3): you cannot cache a negative verdict whose existence the product does not acknowledge. |

*Surfaces touched:* documentation only. *Evidence:* F-C1, F-C5, F-C6.

### 2.10 Option E — independent spatial placement; explicit topological connection (OWNER-DIRECTED)

**This is the owner's requested direction for revised planning. It is recorded as direction, not as a
ratified implementation:** no acceptance criterion, delivery scope or delivery slot is settled by
recording it, and §4.1 still requires the owner to name a delivery path.

The defining principle:

> Spatial overlap is not topological connectivity. Rooms and disconnected Wall groups may occupy
> overlapping coordinates without automatically becoming one architectural structure. Joining them
> requires a deliberate creator action.

**E is not B, and E is not D.** B admits the document and carries a *marked-invalid* state — the overlap
is still an error, merely a tolerated one. D keeps the existing defect and documents it. Under **E the
intersection between INDEPENDENT groups is intentionally permitted geometry**: not an error, not a
defect, and not something a later operation must repair.

What E replaces is narrower and more precise than "the crossing rule": F-C7's *one rule, four scopes*
stays one rule — but its **subject** changes from "all Walls in the document" to "Walls in the same
connected group".

```text
REQUIRED BEHAVIOUR (owner statement)
  · an independent Room can be MOVED across another Room
  · a Room can be DUPLICATED at exactly the same coordinates as its source
  · different independent Room groups may have crossing or coincident Wall geometry
  · the operation does NOT automatically create or share Junctions, split Walls, merge Rooms, create
    portals, or alter either group's identity
  · Wall and Junction ids remain DISTINCT unless an explicit connection operation establishes shared
    topology
  · associated objects and hosted Openings remain with their owning Room/Wall
  · a geometry-alignment or snap suggestion does NOT itself authorize a topological join
  · any two Rooms that need to connect must be deliberately joined by the creator
  · future collision warnings may identify overlapping entities, but stay NON-BLOCKING and must not
    automatically repair, node, join or alter geometry

THE BOUNDARY OF THE POLICY (not negotiable in planning)
  valid WITHIN a connected structure   vs   overlap BETWEEN independent structures
  E relaxes EXACTLY ONE class — geometric intersection between entities that are not in the same
  connected group. Everything intrinsic stays rejected: self-intersecting Walls, malformed Room
  boundaries, illegal relationships inside an intentionally CONNECTED group, zero-length Walls, Room
  boundary closure and role, and the existing intrinsic invariants.

NOT IN SCOPE
  no vertical stacking semantics. Same-position X/Z overlap is in scope for the POLICY definition;
  floor/elevation authoring is a separate product capability and is not opened here.
```

### 2.10.1 Concern matrix (what E directionally decides, and what it defers)

| Concern | Option E direction |
|---|---|
| Independent spatial overlap | **Permitted** geometry, for entities not in the same connected group |
| Automatic connectivity from overlap | **Forbidden** — no junction adoption, no noding, no merge, no portal creation |
| Intrinsic Wall/Room validity | **Preserved** — unchanged rejection set (see the boundary block above) |
| Explicitly connected group topology | **Validated within its applicable connectivity scope** — the group, not the document |
| Deliberate joining | **Explicit creator operation** — interface and invariants defined at planning level, UI/commands/modes deferred |
| Collision warnings | **Deferred and non-blocking** — must not repair, node, join or alter geometry |
| Import compatibility | Once E ships, existing independent overlaps must **not** be rejected solely for their spatial intersection |
| Selection and visual overlap | **Separate acceptance requirements** — no implied mesh union, no visual stacking system, no automatic occlusion or renderer-ordering fix |

### 2.11 Verified current behaviour — the topology ownership model (source-verified at `7c3d392a`)

Traced BEFORE designing anything, because Option E's whole question — *can independence be distinguished
from coincidence without a schema change?* — is answerable only from the model. All anchors are symbols,
re-resolved at this HEAD; P23B.1's line numbers are discovery anchors only.

```text
Q1 — HOW ARE CONNECTED WALL/ROOM GROUPS REPRESENTED TODAY?
  There is NO group record and NO persisted relation. Connectivity is DERIVED, and its authority is
  the Junction:
    · layout-wall-first-types.ts — "Junction IDs are the only normal-authoring connectivity authority";
      "Junction ID equality *is* connectivity". LayoutDocumentWallFirst carries junctions · walls ·
      rooms · openings · objects · an optional identity ledger, and NOTHING ELSE: no group, no parent,
      no cluster, no cluster id.
    · connectedRoomIds (layout-room-isolation.ts) — the RIGID-CONNECTIVITY graph. It builds
      junction→rooms from each Room's boundary Walls' endpoints and takes the transitive closure from
      the anchor Room; its own doc says it "subsumes shared Walls, since a shared Wall shares its
      endpoints". Deterministic: anchor first, then members in document order.
    · resolveIsolatedRoomGroupSubgraph (same module) materialises that group as ONE rigidly movable
      unit — the "CONNECTED ROOM GROUP" layout-room-move.ts calls the movable unit. A Room with no
      shared boundary Junction is a group of one, "discovered rather than special-cased".
  ⇒ THE DISCONNECTED-GROUP DISTINCTION OPTION E NEEDS ALREADY EXISTS. It is connectedRoomIds's notion
    of a group. No group id is required, and none should be added.

Q2 — ARE EXPLICIT IDS + ROOM BOUNDARY REFERENCES SUFFICIENT TO DERIVE CONNECTIVITY?
  Yes for Wall/Room connectivity: a Room's boundary: OrientedWallRef[] resolves to Walls, whose
  startJunctionId/endJunctionId give Junction identity.
  Portal relations are NOT a second authority. validateWallFirstPortalRelations (layout-portals.ts)
  requires a door's connectsRoomIds pair to be exactly the two physical Rooms whose reconciled boundary
  references the hosting boundary Wall, and its doc is explicit: "the relation never creates adjacency
  by itself — this set derives purely from Room boundaries". A portal is a DEPENDENT relation validated
  against derived adjacency (fail-closed at Save), never an input to group membership.

Q3 — DOES A SHARED WALL, SHARED JUNCTION OR PORTAL MAKE TWO ROOMS ONE TOPOLOGY GROUP?
    shared Junction  → YES, rigidly
    shared Wall      → YES, by the subsumption above (two Rooms referencing one Wall share its Junctions)
    portal relation  → NO — validated against adjacency, never constitutive of it

Q4 — WHICH VALIDATORS CONFUSE COORDINATE COINCIDENCE WITH SHARED IDENTITY?
  Five, with a precise and consistent confusion: they treat GEOMETRIC INTERSECTION as a topology error
  without ever asking whether the two entities are in the same connected group.
    1. validateWallFirstTopology (layout-wall-first-precision.ts) — THE one canonical gate.
       Document-global pairwise classifyWallIntersection over EVERY Wall pair (WallIntersectionKind =
       none · shared-explicit-junction · endpoint-on-interior · proper-crossing ·
       collinear-endpoint-touch · collinear-overlap · invalid). Every outcome other than `none` /
       `shared-explicit-junction` is a hard failure. Group membership is never consulted. It also
       rejects `duplicate_junction_point` for ANY two Junctions within JUNCTION_COINCIDENCE_EPSILON
       (1e-9) ANYWHERE in the document.
    2. detectWallCurveTopologyCrossings (same file) — the sampled curve authority, equally document-
       global; returns the FIRST crossing in document.walls order.
    3. validateChainTopology (layout-wall-chain.ts) — the same bar via the same two functions, per its
       own doc: "every wall pair must relate only through explicit shared junctions (or be disjoint)".
    4. validateBatchWallTopology (layout-duplicate.ts) — the same bar, chord-exact, whole-document.
    5. validateLayoutRoomGeometry (layout-geometry-validation.ts) — the compile, which is INTRA-ROOM
       ONLY (validateLayoutDocumentGeometry loops floors → rooms → per-Room validation). A crossing
       between two Rooms is invisible to it. This is F-C2, and it is the OPPOSITE asymmetry from 1–4:
       the compile and the topology gate disagree by construction.

Q5 — WHICH OPERATIONS AUTOMATICALLY ACQUIRE CONNECTIVITY OR PERFORM NODING?
  Exactly one production path: planWallChain (layout-wall-chain.ts). It is the only non-test caller of
  planWallCrossing, planWallSplit and planWallSplitAtPoint, and it applies two automatic fixes:
    · ADOPTION — an existing Junction whose point coincidesAsJunction (1e-9) is ADOPTED
      ({ kind: 'adopt', keepJunctionId, duplicateJunctionIds }), so a new Wall drawn to an existing
      group's Junction REUSES its id instead of minting a parallel one;
    · SPLITTING — straight crossings are resolved by planWallCrossing / planWallSplitAtPoint, which
      insert the shared Junction and split the host Wall.
  Both produce shared Junction ids: AUTOMATIC CONNECTIVITY FROM GEOMETRIC OVERLAP. The single exception
  is the curved crossing, which REJECTS instead of auto-noding — "any curve crossing that would need
  automatic curved noding rejects the whole authoring command".
  Room duplicate and Room move do NOT node. They validate and reject.

Q6 — WHICH EXISTING CONTRACTS INTENTIONALLY DEPEND ON DOCUMENT-GLOBAL TOPOLOGY VALIDITY?
    · validateWallFirstTopology — the one canonical gate, shared by the P23.1 precision planners,
      Room-move and the chain path. Document-global BY DESIGN; four callers depend on that scope.
    · validateChainTopology — "the P23.9 plan forbids un-noded visual crossings in committed data".
    · validateBatchWallTopology — "every wall pair must relate only through explicit shared junctions".
    · the codec (validateWallFirstLayoutDocument) — explicitly EXCLUDES topology: "P23.8's topology
      validity rules (noding, crossings, enclosure, correspondence) are out of scope here". That is the
      ingress hole F-C6, and the reason duplicate and import admit what the gate later rejects.
    · the compile — depends on topology only INTRA-Room.
  ⇒ FOUR contracts must change scope together for E. The codec's exclusion is NOT one of them: E does
    not require the codec to start validating geometry.

GATE ASYMMETRY, RESTATED AS THE DEFECT'S SHAPE (this is what makes F-C1 and F-C6 possible):
  operation             gates that run                                       curve crossing checked?
  Room duplicate        isolation → codec → validateBatchWallTopology(chord)   NO  → admits (F-C1)
  Room move             codec → validateWallFirstTopology(full) → portals     YES → rejects
  Wall chain authoring  auto-adopt/auto-node → validateChainTopology(full)     YES; rejects the curved case
  import                codec only                                            NO  → admits (F-C6)
  compile               per-Room boundary geometry                            NO  → blind  (F-C2)
```

#### 2.11.1 The hard cases, verified against the model

| Hard case | What the code does TODAY | Consequence for Option E |
|---|---|---|
| Exactly coincident independent Junctions | `duplicate_junction_point` rejects ANY two Junctions within 1e-9, document-wide. Every authoring path that resolves a coincident endpoint ADOPTS the existing Junction rather than minting a second (`planWallChain`). | **The one case the model cannot express.** Two distinct Junction ids at the same point are not representable today — see §2.11.2. |
| Crossing and collinear overlapping Walls between independent groups | Rejected: `proper-crossing` / `collinear-overlap` / `endpoint-on-interior` via `validateWallFirstTopology`; curve crossings via the sampled gate. | In scope for E. Needs the group-scoped SUBJECT, not new representation. |
| An independent Wall touching another group's endpoint | Chain authoring ADOPTS the coincident Junction ⇒ the two become ONE group. Without adoption the same coordinates are rejected as `duplicate_junction_point`, and a genuine T is rejected as `endpoint-on-interior`. | Today "touching" ⇒ "joining". E requires distinct identity, so this is a real behaviour change — and it is the same 1e-9 question as the first row. |
| Two Rooms with a DELIBERATELY shared Wall | Already representable and already correct: `connectedRoomIds` makes them one rigid group; `resolveIsolatedRoomGroupSubgraph` moves them together (an interior shared Wall travels exactly once); `validateWallFirstPortalRelations` requires a portal pair to match the two Rooms adjacent to the hosting boundary Wall. | **Preserve unchanged.** This IS E's "explicitly connected group", and it already works. It is the containment proof that E's restriction must not break. |
| A disconnected standalone Wall intersecting a Room boundary | Rejected by the document-global gates (rows above); the compile is blind to it (F-C2). | In scope for E as permitted overlap; the compile question is separate and belongs to P23B.9's cross-Room cases (G3). |

#### 2.11.2 The one missing representation (stated, not invented)

**Everything Option E requires is expressible today EXCEPT exact coordinate coincidence between two
independent Junctions.**

What is NOT missing: a group id, a cluster relation, a parent pointer. Connectivity is already derived
from Junction identity, `connectedRoomIds` already computes exactly the group E needs, and "these two
entities are independent" is already decidable — they share no Junction id. **E therefore requires no
schema change, no persisted relation and no new identifier.** This record adds none, and no implementer
may add one to make the plan look complete.

What IS a genuine architectural question, and belongs to the owner rather than to an implementer:

> **Does coordinate coincidence still imply Junction identity?**

The 1e-9 rule is documented as "an identity tolerance, not a screen-space acquisition radius and not a
geometry/intersection tolerance. It only absorbs numerical noise that cannot express a separate authored
node" (`layout-junction-identity.ts`). Two of E's stated requirements — "a Room can be duplicated at
exactly the same coordinates as its source" and independent Walls with identical endpoint coordinates —
land squarely on that documented assumption: at the same coordinate there is, by construction, only ONE
node.

Three bounded answers, with what each costs. None is chosen here:

```text
(a) KEEP the rule and SCOPE E's coincidence requirement
      Coincidence still means shared identity; E permits overlap and distinct-but-NOT-identical
      endpoints. Cost: two of the owner's stated requirements become the weaker "coincident within
      tolerance but distinguishable", which is a different product statement than the one written.
(b) RELATE the rule to GROUP MEMBERSHIP
      Two Junctions may coincide only when they belong to different connected groups; within one group
      coincidence stays an error. Cost: the identity tolerance becomes membership-dependent, so the
      same two coordinates are "one node" or "two nodes" depending on unrelated document state. It
      must then be PROVEN that Junction identity stays deterministic across move, duplicate and
      undo/redo — a new invariant the model does not have today.
(c) MAKE identity purely EXPLICIT
      Coordinate coincidence never implies identity; only an explicit join does. Cost: the largest
      change. It interacts with planWallChain's adoption fix, with snap acquisition and with every
      existing test that relies on adoption, and it is a schema-semantics decision well beyond a
      validator scope change.
```

This record does not choose. It records the question, names it **decision D-9**, and notes that **(b)
and (c) are the only answers that literally satisfy the owner's stated requirement** — (a) does not, and
must not be presented as if it did.

### 2.12 External precedent for the decision (P23B.2 §D — context, not authority)

P23B.2 researched validity policy specifically for this defect and reached the same four alternatives,
independently and without endorsing any of them. Its precedents are recorded here because they describe
what each option COSTS structurally, which is exactly what a ruling needs:

| Precedent | What it shows | Relevance to our options |
|---|---|---|
| OpenPlan3D `roomDetection.ts` inserts intersection vertices into a DERIVED planar graph, leaving source Walls untouched and source ids attached (**SV**) | normalization can happen during derivation rather than by refusing input | a fifth shape between our B and C — but it means *permitting* intersecting architectural Walls, which is a product position, not a defect fix. Its own validation record notes unresolved collinear overlaps |
| FreeCAD `BRepCheck_Analyzer` with optional, explicitly expensive deeper checks (**SV**) | geometric validity can have LEVELS, not one boolean | supports a policy where cheap structural validity and deep geometric diagnosis are distinct — the distinction our codec-vs-topology gap lacks |
| CGAL exposes BOTH a boolean self-intersection check AND a collection of intersecting primitive pairs (**DOC**/**SV**) | multi-level checking can also be more DIAGNOSTIC, not just more expensive | directly supports retaining the OFFENDING WALL IDENTITIES, which is how a failure is attributed to pre-existing geometry rather than to the current edit |
| IfcOpenShell separates schema validation from geometric validation and documents the limits of the former (**DOC**) | structural/shape validity ≠ geometric validity | the closest external analogue of our exact gap, and a precedent for stating the scope of each check rather than implying one covers the other |

P23B.2's product-policy table is the same A/B/C/D set presented here, and its research conclusion is this
record's position verbatim: **"External precedents support separating structural validation, geometric
diagnostics and repair. They do not select Museum Editor's policy. That decision remains with the owner."**
It adds one implementation constraint for whichever option is chosen, which this record adopts:

```text
"A repair operation must also preserve deterministic entity identity, history and atomicity. Silent
 geometry changes during import or validation could violate those expectations."
```

⇒ Under option C (repair), the repair must be an explicit, attributable edit that produces a
history entry — never a silent geometry change during import or validation.

### 4.1 Delivery slot and authorization path (the ruling needs an implementation owner)

plan, not in the product.

**Owner of the work the ruling authorizes:** **UNASSIGNED.** This is a distinct second decision and this
record will not infer it. The owner must name a slot together with the policy.

critical-path effects inside P23B:

## 6. Option E acceptance-test design (planning level — NOT authorized to implement)

Concrete tests for the revision contract's §9, split by whether they can be written **today** or only
**after E ships**. Nothing here is green, and no future-policy test may be presented as passing before
its implementation exists. Each row names the behaviour it pins so the split is checkable.

```text
EXECUTABLE AGAINST CURRENT BEHAVIOUR — these PIN today's shipped verdicts and are the regression net
  for any later policy change. Each asserts a REJECTION today.
  T1  duplicate a curved Room onto ITSELF (delta 0,0): expect a rejection, with the code the chord gate
      produces (collinear overlap of the clone), and NOT a claim about connectivity
  T2  move Room A through Room B: expect a rejection from move's full document-global gate; assert
      document, selection, history and preview are UNCHANGED (atomicity, RT-1 R-b)
  T3  two independent Walls whose endpoint coordinates are identical: expect that authoring ADOPTS the
      existing Junction — assert the resulting SINGLE Junction id, which is today's evidence that
      touching IS joining
  T4  two independent curved Walls crossing: expect rejection from the sampled crossing authority
  T5  collinear overlap between two independent groups: expect `collinear-overlap` rejection
  T6  two Rooms with a DELIBERATELY shared Wall: expect ACCEPTANCE and a single rigid group —
      connectedRoomIds returns both, resolveIsolatedRoomGroupSubgraph moves them together, and an
      interior shared Wall travels exactly once. THIS TEST MUST PASS BEFORE AND AFTER E
  T7  self-intersection or an invalid boundary INSIDE one group: expect the applicable rejection to
      SURVIVE E — this is the containment proof
  T8  a genuinely invalid operation rejected ATOMICALLY: document, identity, history and preview
      unchanged
  T9  save/import round-trip: identity and relationships preserved exactly
  T10 undo/redo: the exact placement is reproduced, with no stale artefact served
  T11 Plan, 3D and visitor consume equivalent canonical geometry (existing parity suites)
  T12 repeated vs scoped validation: identical outcomes AND identical diagnostic ordering for the SAME
      ordered input (the corrected G2 — order-PRESERVING, not order-invariant)

FUTURE OPTION E — these may only be written when E ships, and each MUST fail before it does
  F1  duplicate a curved Room onto itself: SEPARATE ids, no automatic connectivity, both groups
      independently editable
  F2  move Room A through Room B: both remain independently editable; no merge, no noding
  F3  independent Walls with identical endpoint coordinates: NO implicit shared Junction
  F4  two independent curved Walls crossing: no new Junction and no Wall fragments
  F5  collinear overlap between independent groups: permitted
  F6  import of a document carrying an independent-group overlap: admitted once E ships, and NEVER
      rejected solely for its spatial intersection
  F7  a snap or alignment suggestion at an overlapping coordinate does not authorize a join
  F8  deliberate join is the ONLY way to create shared topology, and it is explicit and attributable
```

**Two design constraints these tests encode, so neither is lost:**
1. **T3 and F3 are the D-9 question in test form.** Today's T3 asserts a single Junction id; F3 asserts
two. They cannot both pass, which is precisely why D-9 is a decision rather than an implementation
detail — and why D-9 must be answered before any Option E slice is planned in detail.
2. **Collision warnings stay non-blocking.** `LayoutGeometryIssue.severity` already models
   `'warning' | 'error'` and `hasBlockingLayoutIssues` already ignores `severity !== 'warning'`, so the
   vocabulary for a non-blocking warning EXISTS and is honoured by the blocking predicate. It has **no
   production producer today** (no non-test site emits a warning severity). A future collision warning is
   therefore a *producer* to add at warning severity, not a new mechanism — and it must not repair, node,
   join or alter geometry.
