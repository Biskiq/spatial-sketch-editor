## 3. Review checkpoints and commit shape

```text
Every slice:  implement → focused tests → applicable regression suites → measure where relevant →
              commit → report/review → fix and re-review until accepted → slice-closeout on the SAME
              branch → self-check → next slice.
One branch (`p23b`), one PR (#82). No child PRs. Slice boundaries preserved in Git; a merge commit is
preferred over a squash at the end.

REFERENCE-FIRST ORACLE RULE (binds every slice; a commit that violates it is rejected at review)
  Wherever a mechanism's oracle needs that mechanism's own code, it takes TWO commits, not one:
    1. FREEZE THE REFERENCE — commit TODAY'S behaviour as executable expectations. Green on landing,
       because it asserts code that already exists; it fails loudly from then on if a later change
       diverges, which is the alarm that matters.
    2. LAND THE MECHANISM WITH ITS COMPARISON — one commit introduces the mechanism AND the assertion
       comparing it against commit 1's frozen reference.
  An oracle written as "new path ≡ old path" CANNOT be green before the new path exists; demanding that
  is a sequencing bug, not a standard to relax. The converse is equally forbidden: a mechanism whose
  oracle arrives in a later commit. Every mechanism has a green oracle IN ITS OWN COMMIT, and no oracle
  may require code that does not yet exist.
  Applied: P23B.4 S1/S2 (frozen per-consumer samples · shared derivation) · P23B.7 S2/S4 (frozen
  whole-document verdicts · gesture-scoped preflight) · P23B.5 S2/S4 and P23B.6 S2/S3 already had the
  reference step first and needed no correction.
  ALSO APPLIED TO THE POLICY SLICE — WITH ONE DIFFERENCE THAT MATTERS. Its commit 1 FREEZES the
  PRE-POLICY verdicts (T1–T13 as they ship today, INCLUDING T3's single-id adoption), and its commit 2
  lands the group-scoped gates TOGETHER with the POST-POLICY assertions. T1–T5 and T3 are cases the
  policy INTENTIONALLY changes, so the frozen pre-policy results become HISTORICAL COMPARISON EVIDENCE
  and are REPLACED as active assertions in the implementation commit — they are NOT kept green alongside
  their incompatible successors, because demanding both verdicts is demanding a contradiction.
  What must remain green AFTER the change: T13 (within-group adoption) and T6–T8 (the containment set).
  The frozen pre-policy run is what proves the change went exactly as far as ruled and no further.

GATE 0 (BINDING — D-11 =      the umbrella scope amendment AND the §SEQUENCE insertion AND the policy
        ARRANGEMENT 1, so this slice's plan and acceptance criteria are approved BEFORE that slice
        gate ALWAYS applies)   starts. The ARRANGEMENT-2 alternative does not exist: the policy slice is
                               in-phase and in this PR. The slice's acceptance criteria include the
                               dedicated D-12 oracle (§4.2.2), which must PASS BEFORE its acceptance.
GATE 0b (BINDING)              owner confirms the POST-POLICY baseline is recorded, that NO expectation
                               was committed against a ruled-but-unlanded policy, and (since the
                               policy has now shipped) that the fixture ledger's CLASS 3 entries have
                               been RE-BASED to the shipped verdicts rather than left future-only
                               (P23B.0 §2.1). It precedes GATE A.
GATE A (after P23B.0-durable)   owner confirms the fixtures are authoritative and the baselines recorded.
GATE B (after P23B.4)           owner reviews the key grammar + OR-1/OR-2/OR-3 evidence BEFORE P23B.5
                                generalizes the grammar. This is the point where a wrong key would
                                propagate furthest.
GATE C (after P23B.5)           owner reviews the invalidation graph + guard/refusal evidence before
                                P23B.6 reuses it for meshes.
GATE D (after P23B.7)           owner reviews interaction semantics (no gesture/history change) before the
                                P23B.8 decision is taken against the post-P23B.7 code.
GATE E (P23B.9)                 the full gate; a failure returns to the owning slice.
GATE F (P23B.10)                merge + closure decisions (both owner-only).
```

```text
CRITICAL PATH (strictly sequential — each removes a confound for the next):
  ruling D-1 (policy) ┐
                      ├─► P23B.0-dur ─► P23B.4 ─► P23B.5 ─► P23B.6 ─► P23B.7 ─► P23B.8 ─► P23B.9 ─► P23B.10
  ruling D-7 (slot)  ┘
                      └─► (what the verdict-bearing fixture PINS; M-2b admissibility)

THE RULING IS TWO DECISIONS, AND THE CHAIN NEEDS THE THIRD THING TOO (decision record §4.1/§4.2):
  D-1 policy        — RULED: Option E. Consumed first by the policy slice, then by P23B.0-dur (fixture
      polarity, RE-BASED on the shipped post-policy validator) and P23B.4 (M-2b).
  D-7 delivery slot — RULED AND STAGED: **P23B.3a**, the ARRANGEMENT-1 in-phase policy slice, placed AHEAD
      of P23B.0-dur. The owner authorized the §SEQUENCE amendment and the slice's staging commit has
      LANDED; this map does not restate the sequence, and the amended block's preservation contract is
      P23B.10 MR-10. That slice's acceptance criteria include the DEDICATED D-12 oracle (§4.2.2), which
      passes before acceptance rather than later.
  THE SHIPPED BEHAVIOUR — what the two consumers are ACTUALLY keyed to. A ruling does not change the
      validator, so the fixtures pin the behaviour SHIPPED when they are frozen and M-2b is judged against
      the CURRENT FULL validator. Because P23B.3a lands BEFORE P23B.0-durable, that shipped behaviour IS
      the post-policy behaviour; the fixtures are frozen once, against it, and never relabelled. Naming
      D-7 unblocks the DECISION; only landed code changes what may be asserted. Anti-pattern to refuse in every shape: an implicit
      fix, or a ruling-shaped assertion, arriving inside whichever slice next touches the crossing scan
      or the preflight.
  THE OPTION E PATH — RULED, and it RESTRUCTURES this chain (decision record §4.1/§4.2, D-11):
      ARRANGEMENT 1 is SELECTED: a dedicated, narrowly scoped topology-policy slice sits AHEAD of
      P23B.0-dur, so the chain gains a leading edge and P23B.0-durable moves behind it. The
      pre-optimization baseline is therefore POST-POLICY by construction (synthesis §7.4), and the D-12
      reconciliation proof (OR-D12-1…6) PASSES AT THAT SLICE'S ACCEPTANCE — it does not wait for P23B.4
      or P23B.9. ARRANGEMENT 2 is NOT selected; PATH 1(b) stays withdrawn.
      Revised chain:  [policy slice] ──► P23B.0-dur ──► P23B.4 ──► … ──► P23B.10
```
