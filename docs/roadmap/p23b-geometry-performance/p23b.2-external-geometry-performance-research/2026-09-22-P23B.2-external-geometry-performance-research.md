# P23B.2 — External Geometry Performance Research

**Research date:** September 22, 2026  
**Scope:** Geometry performance and correctness in Museum Editor’s existing wall-first pipeline.  
**Method:** Broad external discovery, followed by selective remote source inspection.

## A. Executive synthesis

P23B.1 identifies two separate problems: repeated geometry work during editing, and inconsistent enforcement of curved-crossing validity.

The research must preserve that distinction. Faster validation cannot justify weaker validation, and caching must preserve the compiler’s existing geometric results.

The relevant external precedents fall into five mechanism families:

1. **Shared geometric representations:** derive a curve once, then reuse its sampled or tessellated representation across compatible consumers.
2. **Spatial broad-phase filtering:** eliminate impossible intersection pairs before running the existing narrow-phase predicate.
3. **Dependency-aware recomputation:** identify which changed inputs can affect which derived outputs and validation results.
4. **Derived-artifact reuse:** preserve unchanged geometry and rendering resources across baseline and candidate states.
5. **Execution isolation:** move suitable CPU work off the main thread without introducing another geometry authority.

These are research candidates, not accepted implementation decisions.

The measured P23B.1 baseline remains approximately 41.8 ms p50 and 49.3 ms p95 for accepted Bend releases on the clean 40-curved-Wall fixture. The approximately 280 sampling calls are source-derived, not directly measured. The fixture also lacks durable serialized identity, so those values cannot yet serve as a reproducible post-change comparison.

The strongest distinction from the outset: a spatial index can reduce candidate pairs, but it cannot establish curved-intersection correctness by itself. Likewise, a dirty-node system can limit recomputation, but it does not establish that document-wide invariants remain valid.

### Important finding: Pascal Editor

Authentic upstream is `pascalorg/editor`; multiple similarly named forks exist. Its public repository describes dirty-node processing, and actual source confirms it. The public README also distinguishes the hosted Pascal Next preview from capabilities already released in the open-source editor. <Cite refs={["turn0search7","turn0search2"]}/>

The most useful inspected implementation is `packages/viewer/src/systems/wall/wall-system.tsx` at commit `bcc2020`.

It implements three relevant mechanisms:

- Dirty Walls grouped by level; changed Walls rebuilt while unrelated Walls avoid that rebuild path.
- Adjacent-Wall rebuilding deferred during active dragging, with pending work subsequently flushed.
- Progressive rebuilding with work limits to avoid concentrating large batches in one frame.

Its `level-miter-cache.ts` also provides a particularly relevant Q7 precedent: a cache keyed by level identity, guarded by explicit comparison of the actual geometric inputs rather than a generic whole-document hash.

**Applicability:** These mechanisms demonstrate ways to distinguish affected geometry, unchanged geometry and dependent geometry. They do not prove that Museum Editor can copy Pascal’s scheduling, because Museum Editor currently requires a single canonical accepted-geometry result across Plan, editor 3D and visitor.

### Important finding: OpenPlan3D

Its September 9 curved-room implementation uses the same 16 quadratic facets for Room detection and web 3D Wall geometry. Its crossing-room implementation inserts intersections into a derived graph without modifying source Walls. <Cite refs={["turn0search10"]}/>

The pinned implementation also uses `sceneSignature.ts` to exclude non-rendered fields from a JSON-based scene identity, while conservatively retaining fields that might affect rendering.

This provides two distinct precedents:

- Common geometric approximations can prevent different consumers from interpreting the same curve differently.
- A derived-output signature can use a documented dependency projection rather than blindly serializing unrelated data.

Neither establishes that Museum Editor's current sampling consumers are equivalent. That remains an explicit proof obligation.

## C. Mechanism dossiers

### Q1 — Shared canonical curve representation

**Diagnosis:** One accepted release independently samples the same curved Walls during topology precheck, face extraction, topology postcheck and compilation. Opening processing adds another consumer when Openings exist.

#### External mechanisms

**OpenPlan3D — shared faceted path.** Its `roomDetection.ts` uses `wallPathSpans()` to construct graph segments. The implementation retains source Wall IDs when generating facets. Its curved-room validation record confirms shared facets across Room detection and 3D Wall geometry. <Cite ref="turn7search4"/>

Source: [roomDetection.ts, lines 18–44](https://github.com/laanlabs/openPlan3D/blob/d68cadf703578f2cd3a7c77f820e18d342580c32/src/lib/utils/roomDetection.ts#L18-L44).

Evidence: SOURCE-VERIFIED.

**Bezier.js — reusable parametric curve operations.** `Bezier.reduce()` decomposes a curve into simpler subcurves. `curveintersects()` subsequently processes pairs of overlapping reduced curves, while `pairiteration()` recursively subdivides candidate pairs.

Source: [bezier.js, `reduce` and `curveintersects`](https://github.com/Pomax/bezierjs/blob/4e767299184ab4079dc8d7c970020103db14f431/src/bezier.js#L835-L900) and [utils.js, `pairiteration`](https://github.com/Pomax/bezierjs/blob/4e767299184ab4079dc8d7c970020103db14f431/src/utils.js#L796-L838).

Evidence: SOURCE-VERIFIED. This demonstrates reusable curve-processing structure, not a verified equivalent of Museum Editor’s sampling semantics. <Cite ref="turn1search7"/>

**IfcOpenShell — common geometry-processing entry point.** Its geometry iterator supports bulk processing, element filtering, caching, and output as triangulated geometry or OpenCASCADE representations. <Cite refs={["turn0search0","turn0search1"]}/>

Evidence: DOCUMENTED. The exact internal representation-cache key was not established.

#### Museum Editor applicability

A candidate is an ephemeral, compiler-owned derived representation of each Wall centerline, shared with consumers whose sampling requirements match.

That representation could carry:

| Field | Purpose |
|---|---|
| Source Wall ID | Preserve architectural identity |
| Source input identity | Distinguish changed curve geometry |
| Ordered samples | Preserve existing traversal |
| Sampling configuration | Prevent incompatible reuse |
| Parameter values | Preserve association with the underlying Bézier |
| Segment bounds | Support broad-phase queries |
| Derived cumulative length | Support consumers requiring arc length |

This is an applicability inference, not an accepted data schema.

**Critical proof:** Same curve does not automatically mean same sampling result.

Before reuse, compare the existing consumers for sample count, approximation rule, orientation, endpoint inclusion, traversal reversal, numeric tolerance and any consumer-specific simplification.

A shared cache keyed only by Wall ID would be unsound. A cache keyed by geometry but not sampling options could also be unsound.

A safer research distinction is between sharing canonical source geometry, sharing compatible sampled data, and sharing consumer-specific derived results. These have different equivalence requirements.

Verification requires differential tests comparing existing and candidate outputs across straight, quadratic/cubic, reversed, highly curved, near-degenerate and multi-segment cases. Compare topology verdicts, intersection identities, Room polygons, Opening positions and compiled geometry—not just visually similar meshes.

**Remaining unknown:** P23B.1 UN-5. The existing consumers' actual sampling configurations have not yet been compared.

### Q2 — Curved-topology broad phase

**Diagnosis:** The existing topology gate checks document-wide Wall pairs. Endpoint chords can miss crossings between bowed curves, so chord-only filtering cannot replace the sampled crossing check.

#### Competing mechanisms

| Mechanism | External precedent | Actual guarantee | Limitation |
|---|---|---|---|
| Dynamic R-tree | RBush | Finds indexed bounding boxes overlapping a query | Requires index updates and valid bounds |
| Static packed R-tree | Flatbush | Queries an immutable indexed collection | Rebuild needed after input changes |
| Bounding-box pair filtering | CGAL | Removes impossible candidates before geometric predicates | Box overlap alone proves no intersection |
| Recursive curve subdivision | Bezier.js | Narrows overlapping curve pairs through subdivision | Different numeric and geometric semantics |
| Derived faceted intersections | OpenPlan3D | Finds intersections on sampled Wall facets | Approximation-dependent; some overlap cases unsupported |

RBush implements `search`, `collides`, `insert` and `remove` in `index.js`. Flatbush implements construction through `add`/`finish`, followed by bounding-box queries; its packed data can also be transferred between threads. <Cite refs={["turn3search1","turn3search0"]}/>

Pinned sources: [RBush `index.js`](https://github.com/mourner/rbush/blob/e59712716a84dda2e31f9b471b32faa178d8056f/index.js) and [Flatbush `index.js`](https://github.com/mourner/flatbush/blob/bb12071743bfeaf1b11d232b0a07b7857cabfdf8/index.js).

CGAL’s self-intersection implementation uses box-intersection machinery with geometric intersection predicates. This is a useful source-level precedent for separating broad-phase pair discovery from the actual intersection decision. <Cite ref="turn4search3"/>

Source: [CGAL `self_intersections.h`](https://github.com/CGAL/cgal/blob/4abd208f2fa7295c0ef118579c4b30ba560dca5f/Polygon_mesh_processing/include/CGAL/Polygon_mesh_processing/self_intersections.h).

#### Applicability and proof

The useful architectural distinction:

```text
Canonical Wall geometry
       ↓
Conservative spatial bounds
       ↓
Candidate Wall pairs
       ↓
Existing crossing predicate
       ↓
Canonical topology verdict
```

The index generates candidates; it does not decide validity.

For the current sampled-polyline predicate, bounds enclosing every sampled segment are sufficient for broad-phase coverage. Analytic Bézier bounds are another candidate, provided they enclose the curve with any necessary tolerance margin.

The broad phase must not omit a pair the existing narrow phase would reject.

A conservative box can produce false positives. Those cost extra narrow-phase work but do not change the verdict. False negatives are unacceptable.

A spatial index also does not resolve an already-invalid document. Existing invalid pairs must either remain represented in the validation result or be handled under an explicit product policy.

**Research trade-off:** RBush supports dynamic changes. Flatbush supports compact static snapshots. A simple per-Wall AABB scan may have lower maintenance cost for Museum Editor’s current document sizes. No evidence yet establishes an R-tree as the faster choice for the measured 40-Wall fixture.

Verification should compare indexed and exhaustive candidate sets using curved crossings, touching endpoints, shared Junctions, nearly tangent curves, reversed Walls, multiple Rooms and degenerate boxes.

### Q3 — Affected-subset validation

**Diagnosis:** Single-Wall pointer gestures currently perform document-wide preflight. Yet validity must still cover crossings with Walls belonging to other Rooms.

#### External precedent

FreeCAD models dependencies between document objects. Its `DocumentObject` exposes touched state, recomputation requirements and lists of dependent objects. `Document::recompute()` processes dependency-ordered objects and propagates recomputation through recorded dependency edges. <Cite ref="turn1search3"/>

Pinned sources:

- [DocumentObject.cpp, `touch` and `mustRecompute`](https://github.com/FreeCAD/FreeCAD/blob/cacc86b3ffdebf08aa4a4b4e367bc2f8357d35bc/src/App/DocumentObject.cpp).
- [Document.cpp, `recompute`](https://github.com/FreeCAD/FreeCAD/blob/cacc86b3ffdebf08aa4a4b4e367bc2f8357d35bc/src/App/Document.cpp#L2900-L3000).

Evidence: SOURCE-VERIFIED.

Pascal independently demonstrates dirty-entity tracking and propagation to dependent geometry, including adjacent Walls. Its Door system documents parent-Wall invalidation when an Opening changes.

Evidence: SOURCE-VERIFIED at the pinned Pascal revision.

#### Applicability

FreeCAD’s dependency graph and RBush’s spatial index solve different parts of Museum Editor’s problem:

- Dependency tracking identifies which derived outputs may change.
- Spatial indexing identifies which other geometric objects may interact with changed geometry.

Neither alone is enough.

The candidate investigation should distinguish:

1. Changed canonical entities.
2. Entities geometrically dependent on those changes.
3. Existing geometry that might intersect their changed bounds.
4. Derived Rooms, Openings and compilation results affected by the change.

**Equivalence requirement:** Scoped validation must produce the same canonical validity result as exhaustive validation, including cross-Room intersections.

An important distinction arises for already-invalid baselines.

If an exhaustive baseline is known valid, an incremental gate can investigate changed geometry against the relevant unchanged geometry, subject to complete dependency tracking.

If the baseline contains unresolved invalid pairs, checking only newly changed pairs cannot establish whole-document validity. The existing violations still exist.

Therefore, any affected-subset proof must specify its baseline-validity precondition or preserve the pre-existing issue set. The product decision about what edits to permit remains open.

Verification should include a valid baseline, an invalid baseline, one changed Wall, Room duplication, changes to connected Junctions, Opening edits and operations that modify multiple Walls through reconciliation.

Use exhaustive validation as the differential oracle.

### Q4 — Incremental compilation and pre/post validation

**Diagnosis:** Structural and topology validation run before and after Room reconciliation. Compilation itself contains the largest measured stage.

#### External mechanisms

**FreeCAD — ordered recomputation.** Its document graph distinguishes touched objects from objects that must execute, then propagates changes through dependencies.

**Pascal — dirty processing plus deferred dependents.** The dragged Wall rebuilds during interaction; adjacent Walls may remain pending until the drag settles. Its source contains separate pending-work state and progressive batch processing.

**IfcOpenShell — filtered bulk processing.** The geometry iterator accepts an `include` set, allowing selected elements to be processed without necessarily processing every geometric element. The documentation explicitly limits filtering granularity to whole elements. <Cite ref="turn0search1"/>

These are SOURCE-VERIFIED or officially documented precedents for work scoping. None directly proves how Museum Editor should reconcile Rooms.

#### Applicability

A potentially reusable intermediate result must have an explicit dependency contract.

For example, a Wall’s sampled centerline may remain unchanged while its compiled physical mesh changes because an adjacent Junction moves or an Opening changes.

Similarly, reconciliation may leave Wall geometry unchanged while modifying Room relationships or another structural output.

The central proof obligation is not simply whether an entity was directly edited. It is whether every input capable of changing that derived artifact is represented in invalidation.

The pre/post validation pair is particularly sensitive:

- Pre-validation establishes candidate validity before reconciliation.
- Reconciliation can change document structure or geometry.
- Post-validation establishes the validity of the reconciled result.

The second pass cannot be removed merely because the first passed.

Candidates for P23B.3 investigation include reusing unchanged intermediate checks, tracking reconciliation’s actual changes, and validating only the post-reconciliation consequences when that affected set can be proven complete.

The existing full validator should remain the correctness oracle throughout that investigation.

**Unknown:** The harvest does not establish a sufficiently complete reconciliation change contract to justify selective post-validation today.

### Q5 — Derived mesh caching

**Diagnosis:** Museum Editor already caches downstream artifacts by compiled-geometry object identity. A fresh candidate compile creates a new object, so the candidate misses those caches even when much of its geometry matches the baseline.

#### External precedent

Pascal rebuilds affected Wall geometry rather than indiscriminately rebuilding every Wall. Its source also explicitly disposes replaced geometry.

Sweet Home 3D’s `Wall3D` separates `updateWallGeometry()` from `updateWallAppearance()`. This is a useful precedent for separating geometry invalidation from appearance invalidation, although it uses a different rendering architecture.

Source: [Sweet Home 3D `Wall3D.java`](https://github.com/keich/SweetHome3D/blob/825635f774a531773bc001b7a5c8231740a9ffd4/src/com/eteks/sweethome3d/j3d/Wall3D.java#L176-L190).

Blueprint3D provides a contrasting implementation: its floorplan-update callback removes existing 3D Floors and Edges, then reconstructs them. It demonstrates why merely having a source-to-renderer separation does not establish incremental rendering.

Source: [Blueprint3D `src/three/floorplan.ts`](https://github.com/furnishup/blueprint3d/blob/cac8b62c1a3839e929334bdc125bf8a74866be9e/src/three/floorplan.ts).

Evidence: SOURCE-VERIFIED.

#### Cache ownership and lifetime

Three distinct reuse opportunities require separate evaluation:

| Layer | Reusable artifact | Required identity |
|---|---|---|
| Compiler | Compiled Wall/Room geometry | Complete compiler-relevant inputs |
| Mesh preparation | Vertex/index/material-group data | Complete mesh-builder inputs |
| Three.js adapter | `BufferGeometry` and associated resources | Stable mesh artifact and ownership |

These layers must not be conflated.

Three.js explicitly requires disposal of geometry when it is no longer used, and its resource model permits geometry, materials and textures to be shared between objects. <Cite refs={["turn1search1","turn5search1"]}/>

For a candidate that changes one Wall, a cache should not reuse another Wall’s mesh merely because its source Wall ID remains unchanged. It must account for connected geometry, hosted Openings, dimensions, material groups and every other mesh-building dependency.

Likewise, changing a Wall’s appearance should not force unrelated geometric calculations unless the actual implementation requires them.

**CPU and GPU costs remain separate.** Reusing compiler output may avoid CPU compilation. Reusing prepared mesh data may avoid CPU mesh construction. Reusing a Three.js geometry object may avoid adapter allocation and subsequent resource creation.

No source establishes that all three improvements would occur automatically from one cache.

The P23B.1 presentation gap remains unresolved, so a mesh-cache investigation must measure synchronous mesh preparation, adapter construction and first-use rendering separately.

Verification should include stable geometry identity, stable adapter identity where applicable, explicit disposal on final release, and repeated edit/undo/redo cycles without retained-resource growth.

### Q6 — Candidate-versus-baseline reuse

**Diagnosis:** Baseline restoration and accepted-compile reuse already work. The missing opportunity is reuse of genuinely unchanged sub-artifacts while compiling a new candidate.

#### External precedent

Pascal’s `level-miter-cache.ts` stores a miter solution per level and reuses it when its relevant Wall inputs compare equal.

The associated tests verify reuse across distinct arrays, invalidation when a Wall moves, separation between levels and cache clearing on remount.

Source: [level-miter-cache.ts](https://github.com/pascalorg/editor/blob/bcc20203dc1376fcc5eafe396a0f394f6601eab1/packages/viewer/src/systems/wall/level-miter-cache.ts) and [level-miter-cache.test.ts](https://github.com/pascalorg/editor/blob/bcc20203dc1376fcc5eafe396a0f394f6601eab1/packages/viewer/src/systems/wall/level-miter-cache.test.ts).

Evidence: SOURCE-VERIFIED.

This is a concrete precedent for reuse between distinct input objects without relying solely on reference equality.

#### Applicability

Museum Editor’s baseline/candidate relationship suggests three independent identity questions:

1. Does the source entity remain the same entity?
2. Does the derived artifact have exactly the same inputs?
3. Does the artifact remain valid in the candidate’s surrounding topology?

The third condition prevents naive Room-local or Wall-local caching.

An unchanged Wall centerline may be reusable for sampling. Its physical boundary mesh may not be reusable if its connected Junction, adjacent Wall or hosted Opening changes.

Candidate reuse therefore requires a complete invalidation graph, not just structural sharing.

The research also identifies a useful lifetime distinction: an artifact may be retained by the accepted baseline, temporarily referenced by a candidate, and later become unreferenced after acceptance or rejection.

That lifecycle must be explicit if CPU or GPU resources are shared.

**Proof strategy:** Compare full compilation and candidate-reuse compilation on identical document inputs. Verify numerical geometry, topology results, Room membership, mesh material groups and cross-view output. Include a rejected candidate followed by restoration to confirm baseline resources remain intact.

No external source establishes that Museum Editor currently has the immutable snapshot or artifact-ownership guarantees required for this mechanism. That requires repository verification during P23B.3.

### Q7 — Compile-input identity

**Diagnosis:** Accepted-compile reuse currently uses canonical whole-document JSON equality. This is effective and measured at roughly 0.1–0.2 ms on the reported 40-Wall case, so it is not a leading performance suspect.

The research question concerns alternative identity mechanisms, not replacing a demonstrated working optimization without evidence.

#### Competing approaches

| Approach | Precedent | Guarantee and limitations |
|---|---|---|
| Canonical full-input equality | Museum Editor current behavior | Strong value comparison, with serialization cost |
| Explicit relevant-field comparison | Pascal miter cache | Exact for the fields compared, if dependency coverage is complete |
| Projected-input serialization | OpenPlan3D `sceneSignature` | Omits fields excluded from the output’s dependency contract |
| Generation-based invalidation | Bonsai | Cache validity depends on complete mutation notification |
| Content hashing | General candidate | Hash equality alone does not prove input equality unless collision handling or a stronger contract exists |
| Reference identity | Existing Museum Editor caches | Sound for the exact object instance, not automatically across equivalent candidate objects |

OpenPlan3D’s [sceneSignature.ts](https://github.com/laanlabs/openPlan3D/blob/d68cadf703578f2cd3a7c77f820e18d342580c32/src/lib/utils/sceneSignature.ts) excludes background images and other non-3D-rendered fields from scene identity. Its source explicitly retains remaining fields conservatively to account for possible future render dependencies.

Bonsai’s [wall.py](https://github.com/IfcOpenShell/IfcOpenShell/blob/b6bc951dd398694fa6115e3d0983ba14e21eea00/src/bonsai/bonsai/bim/module/model/wall.py#L2757-L2798) provides a different mechanism: its wall gizmo cache is cleared on refresh and invalidated when a geometry-generation counter changes.

Bonsai’s [test_wall_topology_cache.py](https://github.com/IfcOpenShell/IfcOpenShell/blob/b6bc951dd398694fa6115e3d0983ba14e21eea00/src/bonsai/test/bim/module/model/test_wall_topology_cache.py) also verifies generation-based invalidation and distinguishes cached predicate kinds.

Evidence: SOURCE-VERIFIED.

#### Applicability

The key question for Museum Editor is the smallest input set that completely determines a particular output.

A compiler-wide identity may need the whole document. A Wall-centerline identity may need only that Wall’s curve and endpoints. A Room-mesh identity may require boundary Walls, Junction relationships, Openings and relevant compilation settings.

A revision counter is not equivalent to content identity unless every relevant mutation increments it correctly. Import, undo/redo, reconciliation, aliasing and candidate creation all matter.

A content hash is useful as an index key but cannot silently replace equality as a correctness proof.

**Assessment:** Field-level identity and generation-based invalidation are established external patterns. Whether either is appropriate for Museum Editor’s compile input remains unproven. The current JSON check is inexpensive enough that replacement requires a measured reason.

### Q8 — Worker isolation

**Diagnosis:** The acceptance compile is the largest measured individual stage. Running CPU-heavy geometry off the main thread could improve responsiveness, but may not reduce total computation or end-to-end acceptance latency.

#### External mechanism

The browser Worker API supports structured-cloned messages and transfer of supported resources. ArrayBuffer transfer moves ownership, leaving the sending side unable to use its former buffer. <Cite refs={["turn1search0","turn1search4"]}/>

`Worker.terminate()` stops a Worker immediately, without letting its current operation finish. <Cite ref="turn6search0"/>

These are documented browser guarantees. They do not establish that Museum Editor’s current compiler is Worker-compatible.

#### Candidate stage assessment

| Stage | Isolation potential | Main constraint |
|---|---|---|
| Canonical geometry compilation | Plausible | Pure transferable input/output and accepted-result integration |
| Topology validation | Plausible | Same canonical predicate and deterministic issue ordering |
| Face extraction | Plausible | Must remain part of the authoritative pipeline |
| Mesh preparation | Plausible if CPU-only | Separate from Three.js resource ownership |
| Svelte state installation | Main-thread responsibility | Reactive editor state ownership |
| Threlte scene integration | Existing renderer responsibility | Geometry adapter and scene lifecycle |
| GPU upload/presentation | Not solved by compiler Worker | Separate rendering measurements |

A Worker should execute the same canonical implementation, not a separately maintained approximation.

A candidate result also requires an acceptance identity. Consider the following ordering:

```text
Baseline B
   ↓
Candidate A starts
   ↓
Candidate C supersedes A
   ↓
Result A arrives
   ↓
Result A must not replace C
```

That requirement follows from asynchronous execution regardless of Worker library choice.

A result should be associated with the document revision and candidate transaction that produced it. Superseded results must not overwrite current state, install stale geometry, create history entries or alter selection.

Cancellation is another distinct question. Ignoring an obsolete result prevents stale installation but does not necessarily stop its CPU computation. Terminating a Worker stops that computation but may also discard reusable Worker state.

Transfer cost, Worker startup, serialization and main-thread installation remain part of the interaction latency.

**Applicability assessment:** Worker isolation is a credible later experiment, not an established first optimization. The source-backed redundant work and whole-document preflight should be evaluated independently before introducing asynchronous acceptance semantics.

## D. Curved-crossing validity precedents

The current Museum Editor defect is not merely a numeric approximation problem. Different operation paths enforce different scopes of an existing rule.

External projects demonstrate several ways of treating geometric validity, but their choices cannot be adopted without considering Museum Editor’s own product contract.

### D1. Normalize crossings in derived geometry

OpenPlan3D’s `roomDetection.ts` inserts intersection vertices into the derived planar graph. Source Walls remain unchanged and source IDs remain attached to generated segments.

This permits Room reconstruction from crossing Walls.

The project’s validation record explicitly notes unresolved collinear overlaps and other ambiguous geometries. <Cite ref="turn7search4"/>

This is a precedent for normalization during derivation, not proof that Museum Editor should permit intersecting architectural Walls.

### D2. Distinguish validation from ordinary rendering

FreeCAD’s Check Geometry implementation uses `BRepCheck_Analyzer` and can run additional Boolean-operation checks when enabled. The source explicitly treats additional analysis as potentially expensive. <Cite ref="turn5search0"/>

This shows that geometric validity can have multiple levels of checking and diagnostics.

It does not prove any particular Museum Editor import or recovery policy.

### D3. Detect and report invalid geometric relationships

CGAL exposes both boolean self-intersection checks and collection of intersecting primitive pairs. The latter provides more diagnostic detail than a single validity boolean. <Cite ref="turn4search0"/>

For Museum Editor, retaining offending Wall identities is relevant to distinguishing a failure caused by the current edit from one caused by pre-existing geometry.

### D4. Separate file/schema validity from geometric validity

IfcOpenShell exposes IFC schema validation, including type and attribute checks. Its documentation explicitly describes limitations of those checks. Schema validation should not be mistaken for a complete geometric-validity guarantee. <Cite ref="turn4search2"/>

This distinction closely matches Museum Editor’s current codec-versus-topology gap.

### Product-policy alternatives

| Policy | Invalid authoring | Invalid import | Later edits | Principal consequence |
|---|---|---|---|---|
| A. Reject at ingress | Reject invalid candidate | Reject invalid document | Operate on valid documents | Existing exported invalid documents may become unimportable |
| B. Explicit invalid state | May admit with diagnosed invalidity | Admit with diagnosed invalidity | Depends on recovery contract | Requires persistent, visible issue attribution |
| C. Explicit repair | Refuse or offer repair | Diagnose and support repair | Permit defined repair operations | Introduces additional authoring behavior |
| D. Retain current behavior | Inconsistent gates remain | Import remains permissive | Unrelated edits may reject | Existing admitted-but-uneditable class remains |

These are alternative contracts, not an ordered recommendation.

A repair operation must also preserve deterministic entity identity, history and atomicity. Silent geometry changes during import or validation could violate those expectations.

**Research conclusion:** External precedents support separating structural validation, geometric diagnostics and repair. They do not select Museum Editor’s policy. That decision remains with the owner during P23B.3.

### Research limits

No external source establishes a complete, ready-made replacement for Museum Editor’s pipeline.

Those guarantees must be verified against Museum Editor itself.

### Final research finding

P23B.2 establishes external precedent for reducing repeated geometric work while retaining a canonical result. It also establishes that correctness, invalidation and resource lifetime require their own explicit guarantees.

The unresolved decisions are now separable: sampling equivalence, spatial-index economics, dependency completeness, candidate artifact ownership, Worker latency and curved-crossing product policy.

Those findings form the evidence input for P23B.3, where Museum Editor’s actual implementation can be reconciled against them.
