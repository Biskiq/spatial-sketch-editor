## 1. Problem, and the evidence that motivates it

```text
1.1  MESH PREPARATION IS A REAL, MEASURED CPU COST: candidate mesh prebuild 4.9/5.7 ms (E1) and
     7.4/9.5 ms (E3); isolated 3D wall-mesh construction 4.6/4.8 ms (E1); 3D wall meshes 6.1/6.9 ms (E2).
     It is re-derived whenever the compiled geometry object changes, i.e. for every candidate (F-P9).
1.2  MESH BUILD DOES NOT RESAMPLE (F-P4). `buildRoomWallMesh` consumes the compile's own samples; there
     is no `wallCenterlineSamples` call in either mirror. So mesh cost is NOT duplicate sampling — it is
     geometry construction. Do not "optimize" it as if it were sampling work.
1.3  PLAN RENDER MODEL IS STRUCTURALLY CHEAP (F-P11): a pure projection of compiled geometry, ≈0.1 ms in
     both passes, and the Plan SVG string was 0.3/0.4 ms (E2, summed across polylines). Neither is a
     leading suspect — but both are re-generated on every reactive invalidation, and the reactive cost
     itself is UNMEASURED (UN-2).
1.4  THE PRESENTATION GAP IS UNCLOSED (PM-1 §9.2): the untagged derive/install gap, the reactive
     re-render, the CPU `BufferGeometry` construction vs the Svelte flush, GPU first-use upload and a
     presented frame are all UNMEASURED (UN-1/UN-2/UN-3).
1.5  THE EXISTING FLUSH MARK IS MISLABELLED BY ITS NAME (harvest correction): `p2311:3d-mesh-flush-latency`
     starts at the adapter build and ENDS at `tick()` — it measures Svelte flush latency and is neither
     GPU upload nor a painted frame. Treating it as either is a measurement error.
1.6  THE 64–314 ms BROWSER LONG TASKS ARE NOT GEOMETRY (PM-1 §9.3). They include unrelated
     browser/session work and must never be folded into a geometry total.
```

## 2. Scope, non-goals, dependencies

```text
IN
  · CONSUME the P23B.0-durable presentation measurements and state which cost class actually dominates
  · CPU-side reuse of unchanged per-Room / per-Wall mesh and adapter artefacts (M-3 applied to meshes,
    using P23B.5's identity⇒equality rule)
  · adapter rebuild avoidance for unchanged meshes, with dispose discipline preserved
  · GPU-upload / presented-frame measurement, and work in that area ONLY if it is measured to matter
  · Plan-side cost verification (render model + SVG attribute generation) — almost certainly a
    verification rather than a change
OUT
  · any change to wall-mesh GEOMETRY (bevel/jamb/reveal/topology) · any LOD/approximation
  · a second mesh pipeline, a second mesh builder, or divergence between the editor/museum mirrors
  · changing materials, lighting, or the visual system
  · changing what Plan/3D render (parity is correctness)
  · Worker/WASM · any schema/persisted change · any budget
  · ANY MESH UNION OR VISUAL STACKING SYSTEM. Independent overlapping groups may produce SEPARATE
    meshes; nothing here may merge them, claim they are one structure, or introduce a mesh-union,
    occlusion, depth-sorting or renderer-ordering mechanism to hide the overlap (Option E revision;
    decision record §2.10.1). Collision warnings are deferred and, when they exist, must be NON-BLOCKING
    and must not repair, node, join or alter geometry
  · COLLAPSING THE FOUR OWNERSHIPS. Source document ownership · compiled geometry · prepared mesh data
    (`IndexedWallMesh`) · adapter resource (`BufferGeometry`) stay distinct layers with distinct identity
    requirements (M-3m D-2). Option E changes none of them: two independent groups simply own their own
    source, their own compiled output and their own meshes
DEPENDENCIES
  hard  P23B.0-durable's PM-1 measurements. WITHOUT them this slice must NOT change rendering behaviour:
        it would be optimizing an unmeasured claim.
  hard  P23B.5's identity rule (for reuse) and P23B.4's key grammar (one grammar, one owner)
  met   the RECONCILIATION IDENTITY PRECONDITION (D-12, decision record §4.2.2): the mesh key assumes
        PERSISTENT Room identity across an overlapping edit. Option E lands BEFORE this slice
        (D-11 = ARRANGEMENT 1), so the policy slice has already discharged OR-D12-1…6 — this slice
        CONSUMES that proof rather than re-deriving it. The mesh-dependency negative matrix (G15) must
        include the case where overlap alone changes NO key input, so a mesh is NOT rebuilt merely
        because another independent group now overlaps it. Distinguish SOURCE identity from COMPILED
        sub-artifact equality: sharing a source Wall object is not the same claim as a compiled input
        object being `===`
```

## 4. Proposed mechanism, and the alternatives

```text
M-3m  SUB-PART REUSE, GATED ON A COMPLETE DEPENDENCY CONTRACT AND ON A KEY THAT IS NOT COMPILED
      OBJECT IDENTITY.
     A per-Room / per-Wall mesh may be reused across a candidate when a reuse key DERIVED from the
     mesh-builder's COMPLETE traced input set matches, the reuse guard can refuse, AND that input
     contract is traced as complete. This does not replace the geometry-keyed `WeakMap`; it lets the
     candidate's REBUILD skip parts the candidate did not touch.
     D-0  THE PREMISE THAT MUST NOT BE INHERITED (CORRECTED — it was wrong, not merely imprecise).
          An earlier draft of this mechanism stated the reuse condition as "its compiled input is the
          SAME object (EQ-5's shared-by-reference fact)". That conflates two different identities, and
          both halves are load-bearing:
            · EQ-5 IS A SOURCE-DOCUMENT FACT, NOT A COMPILED ONE. What P23B.1's EQ-5 establishes is that
              `spliceWallFirstArchitectureCandidate` shares UNAFFECTED Walls and centerlines BY
              REFERENCE with the baseline (`centerline ? … : wall`, `point ? … : junction`). That is
              what makes a SOURCE-object-keyed cache reachable, and it is why P23B.5's SAMPLE reuse is
              admissible. It says nothing whatsoever about compiled geometry.
            · COMPILED IDENTITY IS NOT SHARED, AND THE CANDIDATE'S COMPILED GEOMETRY HAS NO MEMO. P23B.1
              F-P9 establishes the opposite of the inherited premise: a release compiles a NEW
              `CompiledLayoutGeometry` for the candidate, so the two geometry-keyed WeakMaps
              (`wallSnapIndex`, `derivedWallMeshes`) MISS for it and are repopulated; they hit only when
              the frozen baseline is RE-INSTALLED (`restoreLayoutPreviewSnapshot` →
              `installWallMeshes`). The harvest records compiled geometry's memo state as
              `none (new object per compile)`.
          ⇒ CONSEQUENCE, STATED AS A REQUIREMENT. A mesh reuse may NOT be justified by a compiled-input
          object being `===`. The key must be DERIVED from the traced inputs (D-1) and evaluated against
          the baseline's SOURCE document, and the guard must be a real comparison — not an identity check
          that can only ever answer `false` for a candidate.
          ⇒ WHY THIS IS A CORRECTNESS PROBLEM AND NOT A STYLE PROBLEM. An identity-keyed implementation
          would never hit for a candidate, so it would sail through every equivalence oracle in §5 while
          delivering nothing — a false green that costs the slice its entire justification. S3 must
          therefore measure HIT COUNTS, not only equality; a reuse with zero observed hits on the
          committed fixtures is a FAILED mechanism, whatever OR-5 says.
     D-1  THE CONTRACT IS THE GATE (NEW, from P23B.2 §Q5 — a SOURCE-VERIFIED precedent carrying an
          explicit warning): reuse must not follow from a Wall id match, because the mesh builder's
          inputs also include CONNECTED GEOMETRY (Junctions and adjacent Walls), HOSTED OPENINGS,
          DIMENSIONS and MATERIAL GROUPS. The research states it directly: "a cache should not reuse
          another Wall's mesh merely because its source Wall ID remains unchanged." The slice must
          TRACE that input set from `wall-mesh-builder.ts` (both mirrors) and a negative test must show
          a change to each input DEFEATS the reuse. If the contract cannot be traced and tested, mesh
          reuse is NOT admitted (synthesis AB-9).
     D-2  THREE LAYERS, THREE IDENTITIES (NEW, from P23B.2 §Q5). Compiler output · prepared mesh data
          (`IndexedWallMesh`) · adapter resource (`BufferGeometry`) are separate reuse opportunities with
          separate identity requirements, and "no source establishes that all three improvements would
          occur automatically from one cache". This slice must state which layer it is reusing, and
          measure it separately.
     D-3  THE SEPARATION TO COPY / THE CONTRAST TO AVOID (NEW, from P23B.2 §Q5). Sweet Home 3D's
          `updateWallGeometry()` / `updateWallAppearance()` split (**SV**) is the precedent for keeping
          geometry invalidation distinct from appearance invalidation; Blueprint3D's remove-and-rebuild
          `redraw` (**SV**) is the contrast that shows a source-to-renderer separation alone does not
          imply incremental rendering. This slice changes GEOMETRY invalidation only — never appearance.
     Alternatives:
       (i)  reuse the whole mesh set keyed on the document — REJECTED: the candidate is always a new
            document, so it never hits where the cost is (F-P9).
       (ii) cache `BufferGeometry` instead of the indexed mesh — REJECTED as the first move: the adapter
            output is GPU-facing state whose lifetime is owned by the `$effect`; caching it outside that
            ownership creates the disposal hazard RL-5 names. Adapter-level avoidance is a SEPARATE,
            measured step (S4) with its own dispose proof.
ADAPTER (S4, measurement-gated).
     Reuse the existing `BufferGeometry` for meshes whose input mesh object is unchanged; rebuild and
     dispose exactly as today for the rest. Requires an explicit dispose proof, because the current code
     disposes per change and a reuse path must not skip a dispose nor share a buffer one surface mutates.
PLAN SIDE.
     Verify the render model and SVG attribute cost on the committed fixtures. Expected finding: not a
     suspect (F-P11). If verified, RECORD it as verified and change nothing.
WHAT IS NOT PROPOSED
     no geometry simplification, no draw-call/material restructuring, no instancing, no GPU-side work —
     none of these is justified by current evidence, and several would move the ENFORCED three-*
     estimates.
```

## 5. Correctness invariants and equivalence proof obligations

```text
INV-1  Compiled geometry unchanged; mesh GEOMETRY unchanged (same vertices, indices, groups, count).
INV-2  Plan/3D/visitor parity holds: the same compiled result drives all three surfaces.
INV-2b (Option E revision) Overlapping independent groups keep parity WITHOUT being merged: each renders
       from its own compiled output, and no surface may present the overlap as a single joined structure,
       nor adopt a different layer count or material grouping to resolve it.
INV-3  The editor/visitor mesh-builder mirrors stay byte-identical (`layout-mesh-parity.test.ts` green) —
       any change lands in both or the slice fails.
INV-4  `three-{object,material,draw-call,triangle}-estimate`, `svg-node-count`, `compiled-memory`
       (ENFORCED) are unchanged or explained; never re-recorded to pass.
INV-5  No mesh/BufferGeometry leak: every replaced artefact is disposed exactly once, and a reused
       artefact is never disposed by a still-owning consumer.
INV-6  No shared mutable GPU-facing object between two consumers.
INV-7  No reuse is justified by compiled-input OBJECT IDENTITY (D-0). The key is derived from the traced
       mesh-builder inputs and compared against the baseline's SOURCE document. A guard that can only
       answer `false` for a candidate is not a guard, and a reuse that never hits is not an optimization.
OR-5   identity⇒equality + refusal for mesh/adapter reuse: the reused mesh must be compared against a
       from-scratch build of the same room/wall (P23B.5's oracle, extended to render artefacts).
       EXTENDED by D-0: identity here means the DERIVED KEY's equality, never compiled-object `===`, and
       the reuse must be observed to HIT (see S3) as well as to refuse.
OR-8   lifecycle: after geometry change, document replacement, unmount and baseline restore, no stale
       mesh/BufferGeometry is rendered and nothing leaks (observable via dispose counts).
OR-9   (NEW, from D-1) MESH-DEPENDENCY NEGATIVE MATRIX: for each traced mesh-builder input — connected
       Junction moved, adjacent Wall moved, hosted Opening changed, Wall dimension changed, material
       group changed — the reuse must be observed to REFUSE. This is the oracle that makes M-3m
       admissible at all.
OR-10  (NEW, from P23B.2 §E) CPU/GPU ATTRIBUTION: the reported numbers must separate compiled-geometry
       reuse, prepared-mesh reuse, adapter construction and first-use GPU/presented-frame cost. A claim
       that "rendering is faster" must name the layer.
OR-11  (NEW, from P23B.2 §E) RESOURCE-RETENTION LOOP: repeated edit/undo/redo over the committed
       fixtures with no growth in retained GPU/CPU resources.
INV/OR-7  visitor bundle gate + `test:arch` boundaries.
MEASUREMENT ORACLE (this slice's distinguishing fact)
       the CPU construction cost, the Svelte flush and the GPU upload/presented frame are reported as
       SEPARATE numbers, using P23B.0-durable's marks. A claim that "rendering is faster" must name which
       of the four cost classes moved.
```

## 6. Implementation steps (each independently committable and reviewable)

```text
S1  CONSUME THE MEASUREMENTS (no production change)
    Report the four cost classes on the committed fixtures. If GPU/presented-frame cost is unmeasurable
    or the dominant class is elsewhere, RECORD THAT and let it constrain the rest of the slice.
S2  PIN CURRENT RENDER BEHAVIOUR (tests only)
    Equivalence tests for mesh build + adapter construction on the committed fixtures, so any reuse is
    measured against a real from-scratch control.
S3  M-3 FOR MESHES
    Reuse unchanged per-Room/per-Wall meshes across a candidate, keyed on the DERIVED input set (D-0),
    never on compiled-object identity. Tests: OR-5 + OR-8 + the watertight matrices
    (`wall-mesh-watertight-matrices`) + the mesh parity suite. MANDATORY ADDITION: an observable HIT
    COUNT on the committed fixtures — a candidate reuse whose hit count is zero has failed, and the
    slice must say so rather than report a passing equivalence oracle.
S3b MESH-DEPENDENCY CONTRACT + NEGATIVE MATRIX (OR-9) — LANDS WITH OR BEFORE S3
    Trace the mesh builder's inputs from both mirrors, record the contract, and land the negative
    matrix that proves each input change defeats reuse. S3 may not merge without it (AB-9).
S4  ADAPTER REBUILD AVOIDANCE (only if S1 shows CPU adapter construction matters)
    Key-based reuse of `BufferGeometry` for unchanged meshes — keyed on the same DERIVED inputs and the
    mesh identity, with an explicit dispose proof and a leak test. `BufferGeometry` object `===` is not
    available as a key for the same reason D-0 gives (a candidate's meshes are freshly built). If S1 does
    not show it matters, DO NOT IMPLEMENT — record the measurement and stop.
S5  GPU / PRESENTED-FRAME WORK (only if measured)
    Address whatever the measurement names, and nothing else. If the presented frame is dominated by
    browser/session work (the 64–314 ms long tasks), record that and change nothing.
S6  PLAN-SIDE VERIFICATION + RECORD
    Verify render model / SVG cost; record the finding.
```

## 8. Regression and resource-lifetime risks

```text
R-1  DISPOSE HAZARD (RL-5). Reused GPU-facing objects owned by an `$effect` must not be disposed by a
     sibling effect nor leaked when replaced. Needs an explicit dispose proof + leak test.
R-2  SHARED-MUTATION HAZARD. Two consumers sharing one `BufferGeometry` that one of them mutates.
R-3  MIRROR DIVERGENCE. The editor and museum mesh builders must stay byte-identical; a change in one
     copy alone passes locally and breaks the parity test (or worse, silently diverges the visitor).
R-4  ENFORCED-ESTIMATE DRIFT. Reuse that changes mesh grouping or material grouping can move
     `three-*-estimate` (object/material/draw-call/triangle). Those are ENFORCED; a real movement must be
     explained, not re-baselined.
R-5  VISITOR BUNDLE. Adapter/mesh code is shared with the visitor path; a "shared fast path" must not
     pull editor-only code into visitor chunks (umbrella invariant, `visitor-import-boundary`).
R-6  MEASUREMENT PERTURBATION. The flush mark (`p2311:3d-mesh-flush-latency`) ends at `tick()` and must
     not be reinterpreted as GPU upload or a presented frame. New marks must be DEV-gated and must not
     perturb the frame they measure.
R-7  PARITY. A rendering change that alters what one surface shows is a correctness failure, not a
     performance result.
R-8  Reactive cost (UN-2) may dominate the CPU-side work this slice optimizes; if so, record it rather
     than optimizing the smaller term.
```
