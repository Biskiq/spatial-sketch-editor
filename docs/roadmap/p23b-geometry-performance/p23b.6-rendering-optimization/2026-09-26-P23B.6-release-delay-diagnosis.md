## Named cause (PROVEN in node only)

The curved wall-chain release delay is the wall-chain commit's **whole-document Room-correspondence
proof**. `buildCorrespondenceComponents` (`packages/layout-core/src/layout-room-reconciliation.ts`,
pair loop at its `faces × predecessorRoomIds` block) runs unconditionally for every boundary-role
chain (`packages/layout-core/src/layout-wall-chain.ts`, the block where `planWallChain` commits),
and its self time is dominated by `distanceToPolygonRing` / `pointStrictlyInsidePolygon` /
`polygonsShareInteriorArea` (`layout-face-extraction.ts`): ~92 % of plan time, ≈776 ms node DEV of
an ≈885 ms plan on all-curved-40 — 10 candidate faces × 10 predecessor rooms = 100 pair tests over
2,560 face vertices, each running vertex probes, an edge-crossing loop and ear-clipping interior
derivations. A single independent segment in a clear gap, creating no face and touching no room,
still pays the full 100-pair proof. Zero `p2311Measure` marks exist in the wall-chain /
correspondence / face-extraction path, which is why the block sat in the unattributed interval.

```text
planWallSegment (boundary p50, node DEV)   straight 11.9 · all-curved 790.0 · owner 256.0 ms
full node commit path (plan+compile+mesh)  ~34      · ~820          · ~300 ms
browser release p50 (S6, same fixtures)     47      · 2,147         · 711 ms
```

The gap reproduces in node, so the planner — not mesh, adapter or flush — carries it. Browser
absolute is ≈2.6× node; the browser/node difference has **no established cause** (DEV-browser, snap,
history and instrumentation overhead are possible contributors, but no browser profile was taken).
The tool is `wall-chain` (boundary role): an early `partition`-role probe did not reproduce.

Non-causes confirmed: `curve-sampling` (~40 ms total), `finite-thickness` (~0), `snap-resolution`
6–7 ms, `preview-compile` ~30 ms, `mesh-prebuild` ~20 ms. The `$state`-proxy hypothesis was tested
and rejected (the planner clones the document first, escaping the proxy after one pass; ~1.0–1.3×).

**This does NOT explain the final S6 before/after increases** (all-curved whole-Room bridge 73.4 →
493.4 ms p50; Wall authoring 2,147 → 3,601 ms p50). Those deltas remain unresolved and are not
attributed to DEV overhead or to this bottleneck.

Secondary (minor): `commitWallChain` / `commitWallSegment` pass no `acceptance` to
`deriveInstallBundle`, so every boundary commit compiles twice (~26 ms),
`finalizeWallGeometryCandidate` threads its acceptance compile through `applyWallFirstDocumentPlan`
but the wall-chain path never adopted that.

## Required, redundant, avoidable

```text
required    Room correspondence itself — P23B.3a (Option E, D-12) and the P23.8 correspondence
            engine require an exact proof that independent components cannot claim each other's
            rooms (`unionAuthorized`); the verdict must stay exact
redundant   running the WHOLE-DOCUMENT 100-pair proof for operations whose affected extent is one
            new wall and zero changed faces — P23B.7 S3 already derives per-move affected extents,
            but that machinery serves the gesture preflight only; `planWallChain` never consults it
avoidable   no broadphase bbox reject before the O(a·b) probes, no cross-commit memoization on the
            same baseline, no scoping — the algorithm, not the requirement, is the cost
```

## Routing (owner-routed as P23B.11)

The recommendation was a NEW named slice consuming P23B.7's affected-extent contract and P23B.4's
extent-scan precedent without reopening either closed slice, with D-12 / Option-E verdict equality
as the acceptance bar — and explicitly NOT P23B.8 (nothing needs Workers/WASM; the win is
algorithmic: fewer pairs). The owner routed it as P23B.11 on 2026-09-26
([umbrella](../p23b.11-wall-chain-release-delay/2026-09-26-P23B.11-wall-chain-release-delay-umbrella.md)).
The follow-up's first step is ONE browser profile to confirm the split before any saving is promised.

Fix options recorded (expected gain and risk only, NOT implemented):

```text
1  scope correspondence to the operation's affected extent; whole-document fallback on refuse
   ≈776 → ~10–30 ms node correspondence on clear-gap authoring; medium risk (needs the S4-style
   proof that out-of-extent pairs cannot change the verdict)
2  broadphase bbox reject before the exact predicates ≈776 → ~100–200 ms; low risk (pure filter,
   verdict unchanged by construction; touching boxes still go exact)
```
