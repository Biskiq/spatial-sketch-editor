# P23B.0 (durable) — W7 budget policy record

TYPE:     policy record (W7)
STATUS:   recorded; implementation-review-ready, not accepted
SLICE:    P23B.0-durable — measurement foundation completion
EFFECT:   no numeric threshold is added, changed or removed by this slice

## 1. What the slice adds

Seven advisory interaction metrics and six bounded editor paths, all DEV/`__P2311_PERF__`-gated:

| metric | meaning |
| --- | --- |
| `interaction-input` | the pointer/wheel input boundary of one bounded action |
| `interaction-release` | the release of one bounded action, classified by its outcome (accepted distributions contain only accepted actions) |
| `interaction-reactive` | Layout preview derivation/install work scheduled by that input |
| `interaction-plan-apply` | the canonical planner/apply call the Plan viewport makes for an edit |
| `interaction-adapter` | editor adapter CPU work that rebuilds render geometry (the Three adapter; unavailable where no geometry adaptation happens) |
| `interaction-svelte-flush` | Svelte `tick()` flush completion after the input |
| `interaction-browser-frame` | the next `requestAnimationFrame` boundary after the input |

Paths: `selection`, `plan-drag-edit`, `bend-knot-edit`, `wall-authoring`, `plan-pan-zoom`,
`guided-3d-navigation`. Boundaries that do not apply to a path, or that the browser cannot observe here,
are recorded as `unavailable` with a reason; they are never estimated.

**Timing semantics (method v5).** `input`, `release`, `plan-apply`, `adapter` and `reactive` are
synchronous `[call start, call end]` boundaries; `svelte-flush` and `browser-frame` are deferred and start
where the synchronous input **ended**, so a frame encloses its own flush and is never additive with it.
`plan-apply` and `adapter` are separate boundaries: the canonical planner call is never reported as
adapter CPU work. Every action is classified by the outcome it reached — `accepted`, `setup`, `rejected`,
`suppressed` or `unclassified` — and only accepted, warm-up-excluded samples form an accepted
distribution, so a chain-start click or a refused attempt can never sit inside one.

**Fixture coverage (method v5).** Interaction capture covers three hosted fixtures in one browser session:
the owner workload and the size-40 straight and all-curved matrix cells. The size-40 pair is compared on
equivalent targets at one shared px/m viewport so a size or curvature reading cannot silently also be a
zoom reading. The comparison is advisory in exactly the same sense as the timings it produces.

## 2. Which metrics are enforced today (unchanged)

`ENFORCED_BUDGET_METRICS` (`apps/editor/src/lib/bench/bench-types.ts`) remains exactly:

```text
compiled-memory · cache-key-code-units · svg-node-count
three-object-estimate · three-material-estimate · three-draw-call-estimate · three-triangle-estimate
```

All seven are deterministic structural metrics recorded through the existing recorder and checked
fail-closed by `bench-report.ts`. `npm run test:perf` is green on the recorded method-v5 baseline; the
per-tier Chopin budgets in `g3-baseline.json` carry their original values and reasons (only the P23B
sections were added by the measurement recordings, at v4 and then v5). No re-baselining was used to
silence a failure.

Each deterministic tier records 15 metrics; the sampling is 2 warm-up + 5 measured samples for
`chopin`/`small`/`medium` and 1 warm-up + 3 measured samples for `large`. (An earlier record said
"15 samples each", which confused metric count with sample count.)

## 3. Which metrics are advisory

Wall-clock timing metrics recorded and budgeted for reference but not enforced
(`ADVISORY_BUDGET_METRICS`): `layout-compile`, `plan-render-build`, `wall-mesh-build`, `hit-test`,
`snap-query`. They depend on machine load and on a fixture set that is not a stable CI machine.

New in this slice and advisory by construction — no budget recorded for any of them
(`ADVISORY_INTERACTION_METRICS`): the interaction metrics in §1, across the six paths. The recorded
baseline carries their sample counts and p50/p95 and no target or fail bound. The method-v5 recording in
fact made the advisory reading *worse*, not better (an accepted Wall authoring commit is ≈693 ms on the
owner workload and ≈1,985 ms on the all-curved 40-Wall cell), and it changed nothing about enforcement:
advisory means advisory.

## 4. Standing policy for this slice

1. **No new enforced threshold.** This slice proposes none and adds none. Any later enforcement of a
   curved-authoring wall-clock budget requires a separate owner decision after these baselines, per the
   ratified plan's Deferred section.
2. **No weakening and no silent rebaselining.** Existing assertions, budgets and their reasons are
   untouched. Re-recording a budget to make a red test green is forbidden.
3. **One writer.** `bench:record` (through the recorder's validated browser-report import) remains the
   only writer of `g3-baseline.json`. The default test suite never rewrites a checked-in baseline:
   verified by re-hashing the baseline after the full `npm test` run (unchanged,
   `5534926e3a2dbceed9e0383da5914f95ff2824d0d90a760ca48f859b56ec5a8d`).
   The recorder's evidence gates *fail closed* on an inadmissible interaction capture (a missing accepted
   sample, a non-settled session, a dropped boundary, a missing warm-up exclusion, an unrecorded fixture
   reset, or hosted fixtures measured at different px/m). That is a feature of this policy, not an
   obstacle to it: an owner-supplied capture that fails those gates is reported as owner evidence and
   kept out of the baseline (W6 §7) rather than being admitted by weakening a gate.
4. **Advisory numbers are reported, not asserted.** Interaction results appear in the W6 record with their
   sample counts, warm-up, session and environment, and with the mark-nesting rule stated (nested P23.11
   marks are listed separately and are never summed into a P23B boundary).
5. **No product effect.** The marks stay behind the existing DEV + `__P2311_PERF__` gate; with the flag
   off, no mark is recorded and control flow is unchanged. Nothing here reaches a persisted schema, a
   visitor bundle, or a non-DEV build.

## 5. Owner decisions reflected here

- The preview browser is approved as the measurement browser (2026-09-24): native is the stronger
  environment, so the preview-browser result is transferable. The environment difference is stated as a
  limit in the W6 record, not as a waiver.
- `guided-3d-navigation` sampling is deferred by owner decision (2026-09-24) because the reported
  slowdown is in the 2D Plan paths. The deferral text travels inside the baseline
  (`deferredInteractionPaths`), so the missing samples stay auditable instead of looking like an
  omission. Capturing that path later removes the deferral; it does not change this policy.
- The owner's manual samples are complementary evidence beside the capture, not an authoritative second
  measurement, and remain outside the baseline JSON.
- Owner direction 2026-09-25: the reported problem is extreme slowness on **every** fixture, including the
  40-straight-wall control, so curvature stays a suspected amplifier rather than an established cause; the
  interaction capture was extended to the straight and all-curved controls on equivalent targets, the
  owner's own three-fixture manual capture is recorded as owner-supplied evidence, and further scripted
  capture is not required. Timing remains advisory: this direction changes no threshold and enforces
  nothing.
