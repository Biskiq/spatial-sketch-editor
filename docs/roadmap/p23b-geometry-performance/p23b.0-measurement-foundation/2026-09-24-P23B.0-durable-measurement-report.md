## 6. Bottleneck ledger (mark nesting stated, never summed)

The baseline's `nestedMarks` lists 39 existing P23.11 measures that can nest inside a P23B path/boundary
measure, with the recorded note: their distributions are listed separately and must not be summed.
Read together with the table:

- The Svelte flush and the next browser-frame boundary dominate every pointer-driven 2D path: flush p50
  ≈ 240–280 ms and browser-frame p50 ≈ 280–330 ms for selection/drag/bend, with browser-frame p95
  ≈ 1.0 s on drag and bend. Plan pan/zoom shows a lower flush (p50 ≈ 116 ms) with a higher frame
  p50 (≈ 652 ms).
- The measured editor adapter CPU work per accepted edit is small by comparison (p50 ≈ 50–57 ms,
  p95 ≤ 63 ms) — the cost observed here is not in the canonical planner call itself.
- `reactive` samples are dominated by sub-threshold, no-op prefixes (p50 0.0 ms) with a long tail
  (p95 ≈ 230–250 ms), which is why the boundary's median cannot be read without its p95.
- Wall-authoring shows the opposite shape at the input boundary (p50 0.2 ms — the chain click itself is
  trivial) and the whole cost at the release/accepted boundary (p50 ≈ 95 ms, p95 ≈ 774 ms) plus a
  browser-frame p95 ≈ 1.4 s.
- No boundary in this record attributes cost to GPU upload, driver execution or painted presentation.

## 8. Environment limits and UNKNOWNs

Environment limits for every claim in this record:

1. All numbers come from one developer machine (Apple M2, 16 GB, DPR 1) running the Freebuff preview
   browser (Chromium 130 / Electron 33.4.11), not native Chrome 153.0.8010.54. Owner-approved as a
   measurement browser on transferability grounds; cross-engine absolute differences are not resolved by
   this record.
2. The browser-frame boundary is a `requestAnimationFrame` callback, measured in a single foreground tab.
   Chromium throttles rendering when the window is not painting: during preparation, `requestAnimationFrame`
   stopped firing entirely for a period (0 callbacks in 400 ms) and the capture was restarted only after
   rendering resumed. Frame-boundary values therefore describe a foreground, painting window.
3. The capture requires the DEV server to be running (`/dev/perf/p23b`); the server exited mid-preparation,
   which invalidated one capture attempt. Only the completed capture above is recorded.
4. `tick()` and `requestAnimationFrame` prove flush completion and a frame boundary, not GPU upload or
   painted presentation.
5. Interaction timings are wall-clock samples on a developer machine, reported with p50/p95, warm-up and
   sample count; they are advisory, single-session and not reproducible to the millisecond.
6. The deterministic Node-tier metrics retain their own recorder settings; only the browser tier and the
   interaction paths are affected by the above limits.

UNKNOWNs, each with what would close it:

- **U-1 Chromium 130 vs native Chrome 153 on this machine.** Close by repeating the same six captured
   paths in native Chrome 153.0.8010.54 and recording both reports side by side (the owner may run this
  from a step-by-step guide; it is not required for this record).
- **U-2 Presented-frame latency.** No measurement surface in the editor reports a presented frame. Close
   by adopting a browser measurement surface (for example the Event Timing / `PerformanceObserver` frame
   APIs) inside the DEV gate, or by accepting the frame-boundary proxy for the whole slice.
- **U-3 GPU upload and driver execution cost.** Not observable from JS in this harness. Close only with a
   GPU-tracing measurement path (deferred in the ratified plan).
- **U-4 Guided 3D navigation cost.** Owner-deferred; the reported slowdown is in the 2D Plan paths. Close
   by capturing the fixed `p23b-nav-edge` playback action and removing the deferral text.
- **U-5 Cost split inside the Svelte flush.** The 39 nested P23.11 marks are recorded but not decomposed
   into a per-mechanism attribution. Close by attributing the flush work to the specific nested measures
   per path (a bounded follow-up, not part of this slice).
- **U-6 Which edit kinds the drag/bend populations cover.** The recorded `plan-drag-edit` population is
   Wall/room-unit translation while `bend-knot-edit` covers knot/control bends; Junction moves and Opening
   drags share the drag path but are not sampled separately. Close by extending the fixed owner actions if
   a later slice needs per-gesture attribution.

## 9. Recording defects found and corrected during this slice

The measurement run surfaced real attribution defects, each fixed as an identifiable commit before the
baseline was recorded (so the recorded content hash matches the final sources):

- a sub-threshold Plan release was counted as an accepted drag/edit boundary — corrected to be the
  selection click it performed (`805fed25`, `14b48dc7`);
- a knot-control bend's preview work was filed under `plan-drag-edit` — the shipped `curve-control-move`
  and `wall-bend` gestures both report as `bend-knot-edit` (`41fd3f17`);
- a press boundary was named from a path guessed before the shipped handler ran, which double-counted
  selections as drags (or the reverse). A press on a Wall both selects it and arms a move, so its input,
  Svelte flush and browser frame are now timed first and named from the path the release reports
  (`a6d58af0`, `b9a492da`);
- the guided-camera transport is marked (`4bd41245`) and owner-deferred paths are recorded explicitly
  rather than silently omitted (`a82dfc76`);
- shipped Plan handlers stay under their own names so the instrumentation never rewrites product code
  (`6f0ccbf8`).
