## 0. The finding

**The editor is slow on every fixture, including the one with no curvature at all.**

Measured in one browser session, on the same machine, with the three hosted fixtures driven through the
same fixed targets at one shared `19.292586 px/m` viewport (§4):

| path | boundary | 40 straight Walls (0 curved) | 40 all-curved Walls | added by curvature |
| --- | --- | --- | --- | --- |
| selection | pointer input | 121.7 ms | 472.9 ms | +351.2 (3.9×) |
| selection | Svelte flush | 15.8 ms | 245.1 ms | +229.3 (15.5×) |
| drag/edit | accepted release | 208.4 ms | 459.2 ms | +250.8 (2.2×) |
| drag/edit | canonical planner call (`plan-apply`) | 31.7 ms | 94.1 ms | +62.4 (3.0×) |
| drag/edit | Svelte flush | 16.7 ms | 272.9 ms | +256.2 (16.3×) |
| Plan pan/zoom | Svelte flush | 22.4 ms | 343.2 ms | +320.8 (15.3×) |
| Wall authoring | accepted release | 262.6 ms | 1,984.8 ms | +1,722.2 (7.6×) |
| Wall authoring | reactive derivation | 12.7 ms | 38.8 ms | +26.1 (3.1×) |

Read as three separate claims, in order of how much they constrain P23B.4:

1. **A straight-wall layout is already slow.** With zero curved Walls, an accepted Wall authoring action
   costs **262.6 ms**, an accepted rigid edit **208.4 ms**, a selection click **121.7 ms**, and a Plan
   pan/zoom frame **22.4 ms**. Nothing about these numbers is caused by curvature.
2. **Curvature is an amplifier, not the root cause.** Curvature multiplies *the same* boundaries the
   straight control is already spending time in (Svelte flush / browser frame / release): the flush
   boundary rises 15.5× on selection, 16.3× on drag/edit and 15.3× on pan/zoom — while the canonical
   planner call rises only 3.0×. The mechanism curvature makes expensive is therefore the **Plan render
   and flush path**, not the planner.
3. **Plan pan/zoom proves it.** Panning and zooming compile nothing, plan nothing and install nothing —
   they only re-render the Plan SVG. Yet pan/zoom's flush is 22.4 ms straight and 343.2 ms curved, i.e.
   the single most curvature-sensitive boundary in the record, and it cannot contain any compile or
   planning cost at all. `plan-apply` is unavailable on that path by construction (§6).

This matches the owner's own observation and corrects the direction the v4 record implied: the recorded
cost is **not** "outside the canonical planner" because an adapter bucket happened to be small (§6.3) —
it is inside the Plan's reactive-render/flush path, on straight geometry as much as curved.

## 4. Fixed actions, one shared viewport (the protocol as code)

The fixed actions are unchanged in *kind* from the ratified protocol, and are now stated per hosted
fixture against a **relative** target so the three fixtures are comparable:

| path | fixed target | snap/grid |
| --- | --- | --- |
| selection | Select boundary Wall (room 0, boundary edge 0) in the Plan viewport | not applicable |
| plan-drag-edit | Grab boundary edge 1 at 25% of its chord and move one 0.25 m grid increment, then release | Snap 0.25 m on; grid on |
| bend-knot-edit | Bend boundary edge 0 at its knot by one 0.25 m grid increment, then release | Snap 0.25 m on; grid on |
| wall-authoring | Create a 4 m partition Wall in the fixture's own clear region | Snap 0.25 m on; grid on |
| plan-pan-zoom | Middle-button pan and wheel zoom, in the same px/m view as every other hosted fixture | not applicable |
| guided-3d-navigation | Play the existing `PerspectiveCamera` edge `p23b-nav-edge` | not applicable |

Per-fixture coordinates: the owner case selects/bends `wall-chain-1`, drags `wall-chain-1.2`, and authors
between `[24, 24]` and `[28, 24]`; both matrix cells select/bend `room-0:wall-0`, drag `room-0:wall-1`, and
author between `[14, 5]` and `[18, 5]`. Bend/knot is **not applicable** to `p23b-40-wall-straight-v1`
(every centerline is a straight segment, so no knot exists) and is recorded with that reason; the straight
control records zero bend samples and is never converted.

Equivalence is enforced, not asserted:

- **One shared viewport.** Each fixture is zoomed out past the viewport's own `[2, 2000]` px/m clamp and
  then up an identical count of fixed 1.12 steps, so all three land on `19.292586186549904 px/m` by
  construction rather than by coincidentally equal framing. Recorded centres are `[11.7718, 9.0032]`
  (owner), `[12, 2.5]` (straight) and `[12, 2.325]` (all-curved, lower by 0.175 m because its target box
  includes the knot the straight control does not have).
- **One sampling protocol.** 5 warm-ups excluded plus 25 accepted measured actions per path (41 for
  plan/zoom), Snap 0.25 m and Grid on, driven by the DEV harness's scripted driver
  (`src/routes/dev/perf/p23b/drive.ts`) so the counts do not depend on who operated the mouse.
- **Every action is verified and restored.** An action that did not reach its intended path is repeated
  (recorded as a retry); every action that mutated the document is put back through the editor's own undo
  before the next action, and each restore is recorded as a fixture reset.

Reading the table:

- The accepted distributions contain **only accepted actions**; the authoring path's setup clicks are
  recorded as `setup` counts and stay outside them (§6.2).
- The warm-up exclusion is 5 for every applicable path and is applied in code, not in prose.
- A retry count is recorded per path. On the authoring path it equals the setup-click count (25, 25, 25):
  the retry rule is "an accepted action that follows a non-accepted attempt", and the authoring protocol

  is the shape of the path, and it is why the field is reported beside the outcome tally instead of being
  read alone.
- `unclassified` actions are hovers: a pointer move with no press behind it is its own completed action
  that derives geometry without committing anything, so it has no accepted release to report.
- The straight control records zero bend samples and the deferred 3D path records zero samples on all
  three fixtures, both with recorded reasons rather than implied gaps.

## 6. Internal pipeline cost vs interaction latency

Three different things are reported separately and are never summed: **interaction latency** (input,
release), **internal pipeline cost** (`plan-apply`, `adapter`, `reactive`) and **deferred scheduling
boundaries** (`svelte-flush`, `browser-frame`).

### 6.1 The canonical planner call, on its own boundary

| path | `plan-apply` p50 | all-curved | owner | active adapter |
| --- | --- | --- | --- | --- |
| drag/edit | 31.7 ms | 94.1 ms | 49.8 ms | unavailable |
| bend/knot | not applicable | 88.7 ms | 53.5 ms | unavailable |

`plan-apply` is the canonical planner/apply call. It is 3–5× smaller than the flush that follows it, and it
cannot exist at all on `selection` or `plan-pan-zoom` — where the flush is still 245 ms (curved) — so the
recorded cost is not the planner's call.

### 6.2 Accepted-release classification (v4's inflated distribution)

| path | v4 record | v5 record |
| --- | --- | --- |
| wall-authoring (owner) | 40 releases for 20 authored Walls, p50 94.9 ms | 25 accepted commits + 25 setup clicks; accepted release p50 **692.8 ms**, p95 762.8 ms |
| plan-drag-edit (owner) | 20 releases, verdict unclassified | 25 actions, 25 accepted commits; release p50 235.1 ms |

The v4 median was a mixture of chain-start clicks, suppressed clicks and refused attempts; it was never an
accepted-Wall-commit latency. Classifying by outcome raises the owner authoring release from ≈95 ms to
**692.8 ms** and makes the all-curved cell's **1,984.8 ms** visible at all. The straight control's
authoring release is 262.6 ms — the same boundary, no curvature.

### 6.3 Attribution correction

The v4 record filed the canonical planner/apply call under `adapter`, then concluded the cost was "outside
the canonical planner". v5 separates the two, and the numbers confirm the correction: on the owner case the
v4 `adapter` bucket read p50 49.5 ms / 56.6 ms and the v5 `plan-apply` boundary reads **49.8 ms / 53.5 ms**
— the same work, correctly named. The Three adapter boundary is **unavailable on every 2D path** (it is
emitted by the 3D scene path only) and is recorded with that reason rather than being filled with planner
time.

### 6.4 Nesting, stated once

`input`, `release`, `plan-apply`, `adapter` and `reactive` are synchronous `[call start, call end]`
boundaries. `svelte-flush` and `browser-frame` are deferred and start where the synchronous input **ended**,
so a frame encloses its own flush and is never additive with it. 38 existing P23.11 marks are listed in
`nestedMarks` beside the P23B boundaries and must not be summed into them. The corrected origin rule is
visible in the data: flush p50 ≈ frame p50 on every path (e.g. straight selection 15.8 / 17.1 ms, all-curved
selection 245.1 / 246.6 ms), where v4 had pooled two different origins under one metric.

## 9. Environment limits and UNKNOWNs

1. **Preview browser, not native Chrome.** All numbers come from the Freebuff preview browser (Chromium
   130 / Electron 33.4.11) at DPR 1 on an Apple M2. The owner approved that browser as a measurement
   environment; approval permits the environment, it does **not** establish that a result transfers to
   native Chrome 153.0.8010.54, and no such transferability is claimed here.
2. **Frame boundary, not presentation.** `requestAnimationFrame` is a frame-boundary mark; `tick()` proves
   flush completion. Neither proves GPU upload or a painted frame. Chromium throttles a non-painting
   window, so the numbers describe a foreground, painting tab.
3. **Advisory only.** Every interaction number is wall-clock, single-machine, single-session and advisory.
   None is a budget, and no enforced threshold was added.
4. **One machine, one session.** Same-environment comparisons (straight vs all-curved vs owner) are
   supported by this record; cross-machine or cross-browser comparisons are not.
5. **The scripted driver drives shipped handlers with synthetic pointer/wheel events** and no-ops pointer
   capture (a synthetic pointer is never captured by the browser). Hit-testing and editing are the shipped
   ones; a driver-vs-human input difference is not separable from this record.

UNKNOWNs, each with what would close it:

- **U-1 Native Chrome 153 on this machine.** Close by repeating the three hosted fixtures in native Chrome
  and recording both reports side by side (optional for this record; not required for acceptance).
- **U-2 Presented-frame latency.** Close by adopting a browser measurement surface (Event Timing /
  `PerformanceObserver` frame APIs) inside the DEV gate, or by accepting the frame-boundary proxy.
- **U-3 GPU upload and driver cost.** Not observable from JS here; close only with a GPU-tracing path.
- **U-4 Guided 3D navigation cost.** Owner-deferred; close by capturing `p23b-nav-edge` playback.
- **U-5 What inside the flush dominates.** The record shows *where* the cost is (the Plan reactive
  render/flush path, scaling with curved Plan content) but not *which* mechanism inside it. Close by
  attributing the flush to the 38 nested P23.11 marks per path — the recommended first step of P23B.4.
- **U-6 Why the all-curved cell is slower than the fully curved owner case** (e.g. authoring release
  1,984.8 ms vs 692.8 ms). Both are fully curved, so "curvature count" alone does not order them; the
  candidates are the constructed cells' short 0.35 m bulges versus the owner payload's arcs, and their
  different room adjacency. Close by measuring a per-Wall arc-length/segment-count descriptor alongside the
  timing inputs.
- **U-7 Drag/bend gesture coverage.** `plan-drag-edit` covers Wall and room-unit translation while
  `bend-knot-edit` covers knot/control bends; Junction moves and Opening drags are not sampled separately.
