## 1. Why this slice exists

```text
1.1  THE WALL-CHAIN SHARE IS SETTLED; THE REST IS NOT (D1 · P2). P23B.11 attributed and removed the
     wall-chain share of the release (all-curved Wall-authoring 944.5 → 88.6 ms p50; correspondence
     828.7 → 0.2 ms p50), while P23B.6's final-capture increases (headless Chrome 152: all-curved
     Whole-Room 73.4 → 493.4 ms p50; Wall authoring 2,147.0 → 3,601.2 ms p50) remain UNRESOLVED and
     were not attributed to P23B.11's mechanism. S1's Electron capture (944.5 ms) does not stand in for
     them, and the S1/S7 planner ratio (1.00–1.03× browser/node) says the remainder lies OUTSIDE the
     planner without saying where.
1.2  THE OWNER-NOTICED OBJECT IS NOT THE PLANNER (P2). What a person actually feels is frame timing
     during the authoring gesture (the preview while dragging) and the wait from release to the next
     presented frame. Neither number exists today, on either runtime.
1.3  THE TWO RUNTIMES WERE NEVER MEASURED UNDER ONE PROTOCOL (D1 · P2). D1's increases came from a
     headless Chrome capture; S1/S7 captured in Electron. No cross-runtime statement is possible until
     the same protocol produces both legs in one session.
1.4  THE BUDGET-NEUTRAL RULE IS THE HARD CONSTRAINT. The accepted partial baseline (D13) covers
     synchronous press/move only and does not settle these questions; it is neither rewritten nor
     extended here. No threshold, no `bench:record`, no `reuse:record`, no budget metric.
```

     comparison against a differently-run capture.
3.2  FIXTURES. The three committed fixtures P23B.6 measured, in the harness order
     (`p23b-40-wall-straight-v1` · `p23b-40-wall-all-curved-v1` · `owner-40-curved-v1`), plus
     `connected-curved-grid-v1` LAST as advisory evidence that is NEVER recorded. A recorded connected
     case is a STOP (fixture leak).
3.3  PATHS AND CLASSES.

## 4. The instrumentation this plan asks for (two separable items)

```text
4.1  THE GAP IS RECORDED, NOT ASSUMED. The shipped harness reports requestAnimationFrame callback
     intervals and states in place that this is "not presented-frame latency or GPU work"
     (`+page.svelte`; the v5 baseline carries the same limitation), and its only rAF series is the IDLE
     class — idle callback intervals, not a pointer-bounded gesture series. So two of M1's objects
     cannot be read from today's capture: a per-tick GESTURE series during a drag, and release → next
     PRESENTED frame. What DOES exist for the release side is the `browser-frame` boundary, a proxy
     (§4.3(ii)) rather than presentation time.

4.2  ITEM (a) — GESTURE FRAMES, ATTACHED TO A REAL DRAG. The series runs over the DRAG workloads in
     §3.3 (the harness's pointer gesture: down · moves · up, on Plan `plan-drag-edit`, `bend-knot-edit`
     and `whole-room-move-bridge`), so what is measured IS the preview while dragging, correlated with
     the product's own `pointermove-rigid` / `pointermove-bend` marks. The tap-based `wall-authoring`
     class has no pointer movement between its taps and is explicitly NOT the workload for this row.

4.3  ITEM (b) — THE RELEASE SIDE, and which signal may be called what. One authorization covers two
     ADDITIONS; the decline consequence (§4.4) differs for each.
       (b1) PRESENTATION-GRADE — the only signal that may be reported AS presented-frame latency: a
            correlated presentation-time source for the release span (CDP frame-presented / display
            events over a tracing session, driven identically on both runtimes — Electron exposes CDP
            through its remote debugging port, so one method covers both legs).
       (b2) LONG-FRAME OBSERVER, its OWN row and never the latency row: a long-animation-frame
            observer reports only frames over 50 ms, and `startTime` / `duration` / `renderStart` /
            `styleAndLayoutStart` are not presentation times. Kept because it speaks to the
            owner-noticed lag; it requires this observer, so it is NOT MEASURED if (b) is declined.
       PROXY — AVAILABLE TODAY, no instrumentation: the release-side `browser-frame` boundary =
            `[synchronous call end, next requestAnimationFrame callback]` (`bench-types.ts`), scheduled
            per gesture by the interaction measure. It is the ONLY proxy this plan will report for the
            release row, it must be LABELLED a proxy (never presented-frame latency), and its COVERAGE
            must be reported (how many release samples carry it, out of how many releases). The idle
            rAF callback-interval series is NOT a release proxy and is not used for this row.
     Every reported row carries its SIGNAL DEFINITION and its COVERAGE (samples per release and the
     share of releases covered). Where no presentation-grade signal exists, or none that runs
     identically on both runtimes under one protocol, the row is recorded as PROXY or NOT MEASURED.

4.4  THE TWO ITEMS ARE SEPARATELY AUTHORIZED, and the fallback follows from that split:
       (a) gesture frames       DECLINED → the gesture row is NOT MEASURED. The idle-frames class is an
                                idle rAF-interval row and does not substitute for it.
       (b) release-side additions
                                DECLINED → the presented-frame row = the existing `browser-frame` PROXY
                                (labelled, coverage reported); the long-frame-incidence row = NOT
                                MEASURED.
     Declining (a) narrows the gesture row. Declining (b) narrows TWO rows differently: the
     presented-frame row falls back to the existing `browser-frame` PROXY (labelled, coverage
     reported) and the long-frame-incidence row is NOT MEASURED. M1 still delivers BOTH D1 rows on both
     runtimes, D7, the attribution classes and the release proxy; the narrowing is recorded in the
     acceptance record rather than papered over.

4.5  GUARD RAILS. DEV-gated like the existing harness, inert in production, no new dependency, and
     build/typecheck/bundle/perf evidence must stay green (`npm run check`, `npm run build`,
     `npm run verify:visitor-bundle -w @portfolio/museum`, the perf lane). If an item cannot be added
     without touching a production module, STOP and report rather than widening scope.
```
