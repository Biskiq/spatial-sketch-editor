## 1. Why this slice exists

```text
1.1  THE WALL-CHAIN SHARE IS SETTLED; THE REST IS NOT (D1 · P2). P23B.11 attributed and removed the
     wall-chain share of the release (all-curved Wall-authoring 944.5 → 88.6 ms p50; correspondence
     828.7 → 0.2 ms p50), while P23B.6's final-capture increases (headless Chrome 152: all-curved
     Whole-Room 73.4 → 493.4 ms p50; Wall authoring 2,147.0 → 3,601.2 ms p50) remain UNRESOLVED and
     were not attributed to P23B.11's mechanism. S1's Electron capture (944.5 ms) does not stand in for
     them, and the S1/S7 planner ratio (1.00–1.03× browser/node) says the remainder lies OUTSIDE the
     planner without saying where.
1.2  THE OWNER-NOTICED OBJECT IS NOT THE PLANNER (P2). What a person actually feels is frame timing
     during the authoring gesture (the preview while dragging) and the wait from release to the next
     presented frame. Neither number exists today, on either runtime.
1.3  THE TWO RUNTIMES WERE NEVER MEASURED UNDER ONE PROTOCOL (D1 · P2). D1's increases came from a
     headless Chrome capture; S1/S7 captured in Electron. No cross-runtime statement is possible until
     the same protocol produces both legs in one session.
1.4  THE BUDGET-NEUTRAL RULE IS THE HARD CONSTRAINT. The accepted partial baseline (D13) covers
     synchronous press/move only and does not settle these questions; it is neither rewritten nor
     extended here. No threshold, no `bench:record`, no `reuse:record`, no budget metric.
```

## 3. M1 — the one protocol (both runtimes)

```text
3.1  ONE PROTOCOL, TWO LEGS. The same fixtures, paths, marks, action counts, settle rule, viewport and
     restore discipline run on (a) headless Chrome and (b) Electron. The two legs are captured in the
     same session and reported side by side; a leg that cannot run the protocol is a STOP, never a
     comparison against a differently-run capture.
3.2  FIXTURES. The three committed fixtures P23B.6 measured, in the harness order
     (`p23b-40-wall-straight-v1` · `p23b-40-wall-all-curved-v1` · `owner-40-curved-v1`), plus
     `connected-curved-grid-v1` LAST as advisory evidence that is NEVER recorded. A recorded connected
     case is a STOP (fixture leak).
3.3  PATHS AND CLASSES. Authoring paths `wall-authoring` and `room-creation-commit`; attribution classes
     as the S1/S7 keyed projection already reports them (`chain-topology-gate` · `chain-canonical-gates` ·
     `face-extraction` · `correspondence` · `room-reconciliation` · `wall-chain-commit-install` ·
     `room-geometry-compile` · `mesh-prebuild` · `restore-mesh-install` · `preview-compile-reused` ·
     `authoring-release`), each in its own isolated, settled session with the slice's own prefix.
3.4  ACTION COUNTS AND WARM-UP. 25 accepted actions per path (`DRIVE_ACTIONS_PER_PATH`), with the leading
     five excluded as warm-up by the ledger; an action that does not reach its intended path is retried
     and the retry is recorded, never averaged in. Every mutating action is put back with the editor's
     own undo (a recorded fixture reset) so every action acts on the ratified fixture.
3.5  SETTLE RULE. Three frames after the action (the harness's `settleFrames(3)` in the S1 hosting and
     class runs). A capture that does not report `settled: true`, or that drops any deferred boundary,
     is a STOP — the session is re-run, never partially recorded.
3.6  CONDITIONS MATCHING D1. The Chrome leg reproduces the conditions recorded for the P23B.6 S1b
     final-head capture — DEV build, Plan-only, viewport 1500×1000 CSS px, devicePixelRatio 1, ONE
     harness tab, driver action guard 6000 ms, same 4 m Wall segment and 4×2 m Room drag — because D1's
     numbers came from exactly that shape. The Electron leg runs the same protocol in the same session.
3.7  PROVENANCE, PER CAPTURE. Runtime and full version · mode (DEV) · viewport · DPR · harness tabs ·
     action guard · commit SHA · protocol id and revision · date and machine · fixture order. The two
     legs get one record each, exported as their own JSON; nothing is merged across runtimes.
3.8  WHAT M1 MAY SAY. Only that both runtimes were measured under one protocol, with the numbers beside
     D1's and the planner ratio already ruled out. NO cause for the browser/node gap, no explanation of
     D1's increases, no attribution to a mechanism, no threshold.
```

## 4. The one instrumentation item (the only authorization this plan asks for)

```text
4.1  THE GAP IS RECORDED, NOT ASSUMED. The shipped harness reports requestAnimationFrame callback
     intervals and states in place that this is "not presented-frame latency or GPU work"
     (`+page.svelte`; the v5 baseline carries the same limitation). So M1's two objects cannot be read
     from today's capture: there is no gesture-frame series and no presented-frame latency.
4.2  WHAT IS ASKED. DEV-only instrumentation behind the existing DEV route, inert in production:
       (a) GESTURE FRAMES — a per-rAF-tick boundary series from pointer-down to release inside the
           Wall-authoring gesture, so the preview-while-dragging is a distribution rather than a total;
       (b) RELEASE TO NEXT PRESENTED FRAME — a `PerformanceObserver` long-animation-frame series
           (`startTime` · `duration` · `renderStart` · `styleAndLayoutStart`) as the primary measurement,
           cross-checked on a bounded subset with CDP frame-presented trace events where available.
4.3  FALLBACK IF DECLINED OR IMPOSSIBLE. M1 still delivers D1 (both runtimes), D7, and the gesture-frame
     rAF-interval series; the presented-frame row is then recorded as PROXY (rAF interval only) or NOT
     MEASURED — never labelled as presented-frame latency. Declining the instrumentation does not block
     the slice, it narrows one row, and that narrowing is recorded in the acceptance record.
4.4  GUARD RAILS ON THIS ITEM. It is DEV-gated like the existing harness, touches no product path, adds
     no dependency, and must leave build/typecheck/bundle evidence green (`npm run check`,
     `npm run build`, `npm run verify:visitor-bundle -w @portfolio/museum`, the perf lane). If it cannot
     be added without touching a production module, STOP and report rather than widening scope.
```
