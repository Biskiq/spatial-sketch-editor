## Outcome

A creator working in Layout Plan can directly edit one canonical straight Wall or Junction with predictable, CAD-like minimum behavior:

- drag a canonical Junction to reshape every incident Wall;
- drag a straight Wall body to translate both endpoint Junctions rigidly in X/Z;
- drag a Wall endpoint to perform the unambiguous straight-Wall reshape already represented by moving that canonical Junction;
- add a canonical Junction at a Wall span, splitting that Wall deterministically;
- use the landed exact Junction X/Z, fixed-endpoint Wall length/angle and subdivision fields through the same canonical geometry-finalization path as direct gestures;
- preview a complete canonical candidate, then commit exactly one Layout history entry or reject the candidate without changing the document.

Snapping proposes coordinates only. Junction IDs remain connectivity truth, Rooms remain persistent semantic faces, Openings remain document-global and Wall-hosted, and the canonical validators, Room reconciler and compiler decide whether a candidate is valid. No gesture mutates `SceneDocument`, Camera state or visitor navigation.

### Gap statement

The required canonical seam does not fully exist today. `finalizeCandidate` in `layout-wall-first-precision.ts` runs structural validation, `validateWallFirstTopology` and the compiler, but it does not extract/reconcile Rooms or explicitly validate portal relations. Calling the current P23.1 planners directly from a pointer gesture would therefore reproduce an incomplete acceptance path.

The smallest addition is a geometry-specific finalizer in the same core module, reused by Junction position, Wall length, Wall angle, exact rectangle dimensions, rigid Wall move and Wall subdivision. It must use the landed P23.8 reconciler and P23.3 portal validator. Leaving rectangle dimensions on the old finalizer would retain a second canonical Junction-coordinate acceptance path. Metadata/object precision operations can keep the existing generic finalizer; P23.10 must not force Room reconciliation onto unrelated operations.

## 2. Product and interaction contract

### Availability and targeting

- Direct architecture editing is available only in Layout mode, Plan view, Select tool, on a supported straight canonical Wall/Junction.
- Only a primary pointer may initiate a direct-edit gesture: `event.isPrimary` must be true and the mouse/pen button must be the primary button. A secondary click never captures the pointer, opens a Layout transaction or moves geometry; it remains available to the independent context-menu path.
- Arrange mode, 3D view, drawing tools and legacy Room-owned geometry keep their current behavior.
- Existing hit priority remains authoritative: a Junction/Wall endpoint and an Opening body/handle win over the Wall body. A door/window drag must never become a Wall move.
- Pointer-down selects the canonical target before beginning a possible gesture. A click that never crosses the existing editor drag threshold is selection-only and produces no history.
- Any unsupported geometry returns a stable `unsupported_geometry` rejection. P23.10 does not reinterpret a curve as a straight span.

### Junction move / endpoint reshape

- Dragging the one canonical Junction handle moves that Junction in X/Z and preserves its ID.
- Every Wall incident to that Junction follows through its endpoint reference. No incident Wall is detached or cloned.
- A Wall endpoint handle is the same canonical Junction gesture. It is not a Wall-private vertex and does not acquire separate state.
- For a degree-N Junction, the UI identifies that one Junction and indicates that N connected Walls follow. All N are validated together.
- The free endpoint drag is the bounded straight-Wall reshape. Existing exact length and angle fields remain the constrained numeric forms with an explicit fixed endpoint.

### Rigid straight-Wall move

- Dragging a physical Wall body away from an Opening or endpoint translates both of its endpoint Junctions by one identical X/Z delta.
- The selected Wall preserves ID, role, thickness, height, endpoint order, length and angle. Its hosted Openings preserve IDs, host ID, offsets, widths and vertical/profile fields.
- Walls incident to either moved endpoint reshape because their shared Junction IDs moved. Those neighboring Walls and their hosted Openings are part of validation.
- The operation never detaches shared endpoints. If the connected context makes the translated candidate invalid, the whole candidate rejects.

### Add Junction / subdivide Wall

- Primary direct entry: right-click a physical Wall span and choose **Add junction here**. The command uses the hit projection's physical distance from the canonical start Junction.
- Exact entry: the selected-Wall Inspector exposes **Add junction at distance from start (m)** and uses the same subdivision planner.
- The command is unavailable/disabled when mutations are blocked. At an endpoint, outside the open span or through an Opening interior, the canonical planner rejects and nothing changes.
- No double-click shortcut and no persistent Add-Junction tool are introduced in this slice.

### Feedback and atomicity

- A valid preview is the fully derived candidate: Walls, Rooms and Openings render from the candidate compiled geometry.
- An invalid candidate leaves/restores the canonical baseline preview and draws only a transient invalid intent outline/handle plus the canonical rejection message. Invalid geometry is never installed as document truth.
- A snapped candidate that fails topology stays visibly invalid; the editor does not silently fall back to the unsnapped point.
- One valid release commits one deterministic Layout history entry. Invalid, cancelled and no-op gestures commit none.
- Scene selection, Scene transforms, Camera pose/route and `SceneDocument` never move or acquire history entries as a side effect.

### Resolved Issue #29 interaction decisions

| Open question | Decision |
|---|---|
| Shared or separate planners? | Separate public Junction-move and rigid-Wall-move planners because their intent validation and invariants differ; one private coordinate-candidate/finalization path underneath. |
| Wall move versus resize handles? | Wall body drag is rigid translation. Either endpoint/Junction handle is a canonical Junction move and therefore free reshape. Exact length/angle retain the existing fixed-endpoint Inspector semantics. No axial resize handle or solver is added. |
| Add Junction entry? | Existing Wall context menu at the clicked span plus the existing Inspector distance field. No new tool or double-click path. |
| Multi-incident/rigid snap behavior? | Resolve against immutable baseline geometry while excluding every owner whose geometry changes. Junction move filters the uncommittable `'junction'` family before winner selection; rigid Wall move may still snap its captured grab point to a stationary Junction because it applies one translation delta and merges no endpoint IDs. Snap never merges, splits or detaches topology. |
| Preview lifecycle? | Capture once, restore baseline before every replan, install only complete valid candidates, render invalid intent transiently, and replan the actual release. Never commit the last valid intermediate candidate. |
| Selection after subdivision? | Keep the original selected Wall ID. Because it remains the start fragment, its new endpoint Junction is immediately exposed by existing selected-Wall handle rules. Do not auto-select the new Wall/Junction. |
| Validation seams? | Whole candidate: structural/topology/Opening checks, face extraction plus explicit 1→1 Room reconciliation, Room-identity assertion, final structural/topology/Opening/portal checks, then compiler acceptance. |

## 3. Proposed planner and API boundaries

### Core contracts

Keep the public operations in `packages/layout-core/src/layout-wall-first-precision.ts` so P23.1 numeric and P23.10 direct paths cannot drift.

```ts
type WallMoveIntent = {
  wallId: string;
  delta: LayoutVec2;
};

function planRigidWallMove(
  document: LayoutDocumentWallFirst,
  wallOrIntent: string | WallMoveIntent,
  deltaArgument?: LayoutVec2
): PrecisionPlan;
```

Add `'wall-move'` to `PrecisionOperation`. A successful rigid move reports both endpoint Junction IDs in canonical endpoint order and the deterministic union of all Walls incident to either endpoint in `changedWallIds`. It changes only the two Junction point tuples before reconciliation.

Refactor the private candidate handling into two paths:

```ts
finalizeCandidate(...)                 // existing metadata/object behavior
finalizeWallGeometryCandidate({
  baseline,
  candidate,
  operation,
  changedJunctionIds,
  changedWallIds,
  createdWallIds
})
```

`planExactJunctionMove`, `planExactWallLength`, `planExactWallAngle`, `planExactRectangleDimensions`, `planRigidWallMove` and `planWallSubdivision` call `finalizeWallGeometryCandidate`. Thickness, height and object operations stay on the existing generic path unless their existing tests prove they already need the same seam; broad refactoring is not a P23.10 deliverable.

The geometry finalizer must:

1. run the existing pre-reconciliation structural/topology gate, including its current Opening-set translation, so malformed references and invalid crossings/overlaps keep their canonical rejection rather than being misreported as Room correspondence failures;
2. derive candidate faces with `extractBoundaryCandidateFaces`;
3. build explicit Room lineage by Room ID from the operation-produced candidate boundary:
   - Junction, Wall and rectangle coordinate edits: the candidate Room has the same directed Wall cycle as its baseline Room;
   - subdivision: `planWallSplit` has already rewritten `W` to `[W, W2]` or `[W2, W]`, so that rewritten candidate boundary is the declared successor cycle;
4. call `reconcileRooms` with one predecessor Room and exactly one declared candidate face per component, plus a guarded allocator that records/rejects any attempted Room birth;
5. assert equal Room-ID sets, no retired IDs, one `preserved` lineage record per baseline Room, and no split/merge/created lineage;
6. run the final canonical gates in order: wall-first codec, `validateWallFirstTopology`, `validateWallFirstOpeningSet`, `validateWallFirstPortalRelations`, compiler plus blocking-issue check;
7. return the reconciled/validated document or a stable rejection without mutating the baseline.

This lineage is declared from authored IDs and the operation's own boundary rewrite, never selected by nearest polygon or pointer location. It therefore supports arbitrarily large valid coordinate moves without making geometry proximity identity truth.

Do not add a new topology rule. Existing gate failures should retain their canonical issue/message. Add only stable precision rejection codes needed to distinguish `room_identity_lost`, `opening_set_invalid` and `portal_relation_invalid`; callers must not parse messages.

### App adapters

In `layout-preview-state.svelte.ts`:

- keep `updateWallFirstJunction` and `subdivideWallFirstWall` as the sole adapters for those operations;
- add `updateWallFirstWallMove(state, wallId, delta)` as a thin `planRigidWallMove` adapter;
- install successful plans only through `applyWallFirstDocumentPlan`;
- preserve `createLayoutNodingAllocator` as the sole editor allocator for subdivision;
- return the planner's stable rejection code/message so pointer feedback and Inspector feedback agree.

No adapter begins or commits history. Numeric callers use `runLayoutMutationGuarded`; pointer callers use the existing viewport transaction callbacks.

For the shared context-menu model, extend only the existing Wall variant/action:

```ts
{ kind: 'wall'; wallId: string; splitDistance?: number }
addJunction?(wallId: string, splitDistance: number): void
```

The item builder exposes **Add junction here** only when both the action and a finite projected distance exist. A P23.6e hierarchy Wall target has no spatial projection, so its menu keeps the existing Delete behavior.

### Pure editor gesture helpers

Add a pure, Node-testable direct-edit candidate helper beside the existing Opening drag helpers in `layout-interaction.ts`. It should derive total delta from the immutable pointer-down values, not accumulate pointermove deltas.

```ts
type LayoutArchitectureEditGesture =

The complete document/geometry baseline stays in the existing `LayoutPreviewSnapshot`, not duplicated into interaction state.

## 4. Gesture lifecycle and state ownership

`LayoutPlanViewport.svelte` owns pointer capture and the `LayoutPreviewSnapshot`, matching the landed wall-first Room gesture. `LayoutInteractionState` owns only serializable transient intent/status. The preview store owns the installed candidate. The history controller owns the transaction. Selection remains in `LayoutInteractionState.selection`.

### Begin

1. Require Layout Plan + Select, an unblocked mutation state and a supported canonical target.
2. Require `event.isPrimary === true` and primary-button/contact semantics before any direct-edit transaction or pointer capture. Return without beginning a move for secondary clicks.
3. Resolve the target through the existing Plan hit result.
4. Select `{kind: 'junction', junctionId}` for an endpoint/Junction or `{kind: 'physicalWall', wallId}` for a body.
5. Capture pointer ID, world-space start pointer, baseline Junction/endpoints and (for a Wall) the hit projection as `baselineGrabPoint`.
6. Compute and freeze affected owner IDs from the baseline document.
7. Capture one complete `LayoutPreviewSnapshot`, begin one Layout history transaction and capture the pointer.
8. Do not install a candidate until movement crosses the existing editor drag threshold. Before that threshold the operation remains a click.

### Update

1. Convert the current pointer to world X/Z.
2. Compute raw total displacement from `currentPointer - startPointer`.
3. Resolve optional snapping against the captured snapshot's compiled geometry and its frozen exclusion set.
4. Derive the candidate point/delta from baseline values; never add to the previous preview.
5. Restore the captured baseline snapshot before planning.
6. Call `updateWallFirstJunction` or `updateWallFirstWallMove`, which invokes the same core planner as numeric editing.
7. On success, keep the full candidate preview installed and mark the gesture valid.
8. On rejection, keep/restore the baseline installed, retain the attempted point/delta in transient state, render it with existing invalid drafting tokens and show the planner reason.

### Release

Recompute the candidate from the actual release coordinate and the immutable baseline. Restore the baseline first and run the planner again. Do not trust either the current preview document or a remembered last-valid candidate.

- valid, non-no-op release: install the result and commit the open transaction once;
- invalid or no-op release: restore the snapshot and cancel the transaction;
- in both cases: release pointer capture, clear gesture/snap feedback and retain the canonical selection if its ID still exists.

### Cancellation and mode transitions

Escape, `pointercancel`, lost pointer capture, tool change, Layout/Arrange change, Plan/3D change, project/document replacement and component teardown restore the snapshot, cancel the open transaction and clear the gesture. Extend `hasLayoutTransientInteraction` and every existing transient-clear path so a direct architecture edit cannot survive a mode transition. `pointerleave` alone does not cancel while capture remains active.

Svelte implementation stays in existing Svelte 5 runes/event patterns. Do not introduce a parallel event bus or document-level mutable singleton.

## 5. Mutation, reconciliation and history flow

```text
immutable Layout baseline
  → derive exact pointer/numeric intent
  → optional snap coordinate (guidance only)
  → public precision planner
  → clone and edit canonical Junction coordinates, or call planWallSplit
  → extract candidate faces
  → explicit 1→1 Room lineage + reconcileRooms
  → assert exact Room identity preservation
  → wall-first structural/topology/Opening/portal/compiler gates
  → one complete candidate document
  → existing preview install
  → one Layout history commit, or atomic cancel
```

The affected geometry set used for diagnostics and snap exclusion is:

- Junction move/endpoint reshape: the moved Junction plus every Wall incident to it and Openings hosted by any of those Walls;
- rigid Wall move: both endpoint Junctions plus the union of Walls incident to either endpoint and Openings hosted by any Wall in that union;
- exact rectangle dimensions: the four candidate Junctions, every Wall incident to them and Openings hosted by any affected Wall;
- subdivision: the target Wall, retained/start fragment, new/end fragment, new Junction, every Room boundary referencing the target Wall, and Openings hosted by the target Wall.

Validation remains whole-document even when the affected set is smaller. In particular, Opening and portal checks cannot be scoped only to the selected Wall because shared-Junction deformation can invalidate a neighboring Wall or change derived Room adjacency.

Coordinate operations and subdivision are required to preserve every Room identity. If extracted faces cannot be placed in exact 1→1 correspondence, the operation rejects as unsupported/identity-losing. These direct edits do not authorize Room creation, retirement, split or merge. This also guarantees that `SceneDocument` references do not need remapping and prevents an architecture gesture from implicitly moving Scene entities.

History stores the exact accepted Layout snapshot. Undo restores the byte-equivalent predecessor identities/coordinates/order; Redo restores the exact planned candidate, including deterministic subdivision IDs and Opening host/offset rebasing. Redo must not rerun the allocator, snap resolver, face matcher or planner.

## 6. Selection and reveal behavior

- Junction move: keep `{kind: 'junction', junctionId}` during preview, after commit, after rejection and after no-op.
- Wall body move and fixed-endpoint numeric length/angle: keep `{kind: 'physicalWall', wallId}`.
- Subdivision from context menu first selects the clicked physical Wall. On success, keep that original Wall selected.
- `planWallSplit` retains the original ID on the canonical start fragment. Its new endpoint is the inserted Junction, so existing selected-Wall focus/LOD rules make the new Junction handle immediately available without selecting it automatically.
- The new end-fragment Wall and new Junction appear in P23.6e hierarchy/source projections by canonical derivation. Do not expand Navigator rows, alter back navigation or add a second reveal state merely because they were created.
- Invalid candidates do not change selection.
- Selection is not part of Layout Undo/Redo history. If a user selects a newly created Junction and then undoes the subdivision, existing `reconcileLayoutSelection` clears the missing ID. Redo restores the document ID but does not resurrect the prior selection.

## 7. Snapping rules

### Common rules

- Use `resolveLayoutSnap` and its existing priority/tie-breaking. Do not add a P23.10-specific ranking.
- Query the captured baseline compiled geometry for the entire gesture. A live candidate must never become its own snap authority.
- Grid and stationary authored targets remain eligible under existing P23.2 settings/tolerances.
- Snap output is only an X/Z point. It never joins IDs, creates/reuses a Junction, inserts a split, changes a Wall host or detaches topology.
- The canonical planner judges the snapped candidate. If it is invalid, show that snapped target as invalid and reject on release. Do not silently retry the raw candidate.
- Existing snap disable/modifier behavior remains available; P23.10 adds no constraint solver and does not activate the currently separate orthogonal-guide candidate generator.

### Junction move

The raw candidate is:

```text
baseline Junction point + (current pointer − pointer-down pointer)
```

This preserves the grab offset. Resolve snapping for that candidate point. Exclude:

- the moved Junction's own baseline point;
- every Wall incident to the Junction;
- every Opening hosted by an affected Wall.

Pass an explicit `allowedKinds` set containing the currently active P23.2 families except `'junction'` (`wall-intersection`, `wall-midpoint`, `opening-edge`, `wall-span`, object bounds edge/center and grid). Existing-Junction candidates—including endpoint candidates emitted by `spanSnapCandidates`—must be removed before winner selection. Because Junction merging is out of scope, honoring the highest-ranked Junction family would otherwise mask lower-ranked candidates with a target that duplicate-Junction validation can never accept.

This filter is specific to Junction move/endpoint reshape. It does not change global P23.2 ranking, and snapping to a Wall span/intersection still remains guidance: if the unchanged topology cannot accept the candidate, the planner rejects it.

### Rigid Wall translation

At pointer-down, retain the hit projection as `baselineGrabPoint`. The raw candidate target is that point plus total pointer displacement. Snap that one target, then calculate:

```text
candidate delta = snapped-or-raw target − baselineGrabPoint
```

Apply the identical delta to both endpoint Junctions. Never snap endpoints independently because that would rotate or resize the Wall. Exclude:

- the selected Wall;
- every Wall incident to either endpoint Junction;
- every Opening hosted by an affected Wall.

Do not apply the Junction-move `'junction'` family filter here. A rigid Wall's captured grab point may snap to a stationary Junction because that alignment translates two existing endpoint IDs and does not merge either one. This keeps the selected Wall exactly rigid while still allowing its grabbed point to align with stationary Plan features or grid guidance.

## 8. Subdivision identity rules

The landed `planWallSplit` contract remains authoritative:

1. Given oriented Wall `W: A → B` and split Junction `X`, retain `W` as `A → X`.
2. Allocate deterministic new Wall `W2` as `X → B` with the existing editor noding allocator.
3. Allocate one deterministic canonical Junction `X`; do not create it at an endpoint or silently merge it with another Junction.
4. Copy Wall role, thickness and height to `W2`; preserve the retained Wall's fields and canonical orientation.
5. Keep an Opening before the split on `W` with identical metrics. Move an Opening after the split to `W2` and subtract the split distance from its offset. Reject a split through an Opening interior. Preserve Opening IDs and all other fields.
6. Rewrite every Room boundary occurrence forward from `[W]` to `[W, W2]` and reverse from `[W]` to `[W2, W]` before reconciliation.
7. Reconcile the rewritten boundary to the same Room ID and metadata. Any Room birth/retirement/split/merge is a rejection.
8. Preserve the selected `W`; do not auto-select `W2` or `X`.
9. Record the accepted candidate once so Undo removes `W2`/`X` and restores exact Opening/boundary data, while Redo restores the same IDs without reallocating.

The context-menu offset and Inspector distance are both physical meters from canonical `W.startJunctionId`, independent of screen direction or boundary traversal direction.

- Room-owned polygon vertices or revival of legacy Room geometry as authority;
- automatic Junction detachment, endpoint duplication, ID merging or topology repair;

- automatic subdivision as a consequence of snapping or dragging;
- direct 3D Wall/Junction manipulation;
- Scene entity, placement-cluster or Camera manipulation redesign;
- moving Scene entities because a Room or Wall moved;

- performance infrastructure such as workers, a second preview compiler or new geometry cache without measured need.

## 12. Risks and stop conditions

These are implementation stop conditions, not invitations to broaden P23.10.

- **Room lineage contradicts the identity-preserving contract.** If coordinate edits or `planWallSplit` cannot map every baseline Room to exactly one extracted candidate face using unchanged/explicitly rewritten boundary IDs, stop and report the failing fixture. Do not fall back to nearest-face heuristics, allow Room births/retirements or invent a new topology rule.
- **Existing accepted precision edits change meaning.** If routing P23.1 Junction/length/angle/rectangle operations through reconciliation changes valid Room identities or Opening/portal semantics, stop and identify whether the existing operation was bypassing a canonical invariant. Do not preserve acceptance by skipping the gate.
- **Subdivision rewrite is insufficient.** If `planWallSplit`'s forward/reverse Room boundary rewrite cannot supply exact candidate lineage, stop at the P23.8 seam. Do not add Room-owned vertices or a separate subdivision reconciler.
- **Rigid move implies detachment.** If desired body-drag UX can only be achieved by separating a shared endpoint, stop: automatic detachment is explicitly outside the slice. The in-scope behavior is shared-Junction translation followed by canonical rejection when invalid.
- **Curved Wall reaches the planner.** Reject it as unsupported and leave it for P23.11. Do not flatten or partially edit it.
- **Compiler/render mismatch.** If a candidate passes the planner gates but the canonical compiler/mesh path cannot render it, treat that as a blocking canonical validation gap. Do not add a viewport-only fallback or commit unrenderable state.
- **Scene coupling appears necessary.** Coordinate edits and subdivision must preserve Room IDs. If code reality demands moving/remapping `SceneDocument` or Camera data, stop and escalate the violated ownership assumption instead of crossing document boundaries.
- **Context-menu projection cannot be retained.** Extend the existing physical-Wall target to carry its already-resolved projection/offset. If that is impossible without a second hit resolver, stop and repair the adapter seam rather than duplicating hit testing.
- **Full-candidate preview is measurably too slow.** Measure first. The permitted first mitigation is frame coalescing/throttling while retaining immutable-baseline replanning and mandatory canonical release validation. A worker, alternate compiler or relaxed preview validator requires a separate owner decision.
- **History cannot isolate one gesture.** If an existing reactive write produces extra Layout or any Scene entries, stop and fix transaction ownership before shipping. Never squash history after the fact or allow a last-valid intermediate candidate to commit.

P23.10 is complete only when the straight-Wall minimum above uses one canonical mutation/reconciliation/compiler/history path, every invalid candidate is atomic, and no excluded capability is required to make the acceptance matrix pass.
