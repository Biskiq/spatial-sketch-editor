# P23.9 — Wall-span topology regression

**Parent:** P23.9 Wall / Partition sketching  
**Status:** implementation complete — review PR pending  
**Trigger:** manual dense-plan reproduction after PR #48

## User outcome

A boundary Wall whose endpoint snaps to the interior of an existing straight
Wall always creates one explicit shared Junction and subdivides the host Wall.
A divider snapped between two host Walls therefore produces the supported
`1→2` Room split instead of either committing a visually connected dangling
Wall or rejecting with a spurious `2→3` correspondence component.

## Scope

- Preserve the current robust exact-orientation classifier for general Wall
  intersections.
- Normalize sub-nanometre endpoint-on-host numerical dust inside the canonical
  Wall-chain noding path, using the existing Junction identity tolerance.
- Ensure Room correspondence does not treat tolerance-sized boundary drift as
  positive-area overlap.
- Add regressions using oblique host Walls and the same projected-double shape
  produced by wall-span snapping.

Out of scope: changing screen-space snap acquisition, widening authored
intersection tolerances, inferring Rooms in the viewport, compatibility
migrations, direct-edit behavior, or visitor rendering.

## Existing authorities

- `layout-snap.ts` remains the sole snap resolver.
- `layout-wall-chain.ts` remains the Wall authoring and noding transaction.
- `layout-wall-topology.ts` remains the exact general intersection classifier.
- `layout-room-reconciliation.ts` and `layout-face-extraction.ts` remain the
  only candidate-face/Room correspondence path.
- `JUNCTION_COINCIDENCE_EPSILON` is the existing tolerance for coordinate dust
  that cannot express a distinct authored node.

## State and lifecycle

No serialized fields, UI state, props, dependencies, or mount/unmount behavior
change. One completed segment remains one Layout transaction. Rejection remains
atomic; Undo/Redo continues restoring the exact committed snapshot.

## Acceptance

1. A projected endpoint on an oblique host splits that host and reuses one
   Junction even when robust orientation of the rounded projection is nonzero.
2. A divider projected between two oblique host Walls splits both hosts and
   changes one predecessor Room into two candidate Rooms.
3. An endpoint genuinely more than the canonical identity tolerance away from
   a host remains disconnected.
4. Genuine unsupported correspondence components still reject atomically.
5. Existing Layout tests, editor checks, and both app builds remain green.

The regression matrix executes 1,310 independent candidate operations: 591
one-oblique-host dividers covering the reported `2→3` family, 591 two-oblique-
host dividers covering intermittent `3→4`/missed-face outcomes, and 128
open-space operations guarding the earlier `2→2` adjacency failure.

## Boundaries and rollback

The change is confined to `@portfolio/layout-core`; no editor-only helper enters
visitor code, and Scene/Camera authorities are untouched. If tolerant recovery
cannot be bounded to the existing Junction identity epsilon, roll back the
runtime change and keep the reproducing tests as skipped evidence for a future
snap-provenance API rather than weakening general topology classification.
