# P23.11 — Canonical Curved Walls, Exact Curved Splitting and Render-Safe Validation

**Parent:** [P23 — Layout Depth umbrella](2026-09-07-P23-layout-depth-minimum-build.md)

**Status:** **implementation-ready.** This revision supersedes the anchor-only revision of this plan. Verify exact symbols/call sites against current `main` before implementation.

**Scope authority:** [P23 remaining-roadmap reconciliation](2026-09-14-P23-remaining-roadmap-reconciliation.md).

> **P23.11 is not frozen.** Product direction changed after slices 1–5 and 6a/6b landed: direct, creative Wall shaping is now the primary curve-authoring UX, and exact curved-Wall splitting is now required. The landed anchor-only `auto-bezier` representation cannot support either without changing geometry, so this revision **replaces** the canonical representation rather than extending it.

**Issue:** #6 — Bézier Wall can pass commit validation but fail physical Wall mesh generation.

**Repository baseline:** P23.10 is landed and remains the authority for canonical Layout mutation, Room reconciliation, immutable-baseline gesture preview, selection and Layout history.

**Fresh-authority policy:** update the current canonical schema in place. No migration, backward decoding, compatibility shim or old-document support is required before Compatibility Baseline.

## Why this revision exists (evidence)

The previous revision's central claim was *"replacing Euclidean distance with arc length does not guarantee a shape-preserving auto-Bézier split"*, and it deferred curved subdivision. Investigation confirmed the claim and located the exact cause, which is a representation limit rather than a numerical one:

| Evidence | Location |
| --- | --- |
| The canonical anchor stores **positions only** — no handles exist anywhere on the canonical path | `layout-wall-first-types.ts:71–92`; `WALL_CURVE_ANCHOR_KEYS = ['id','point']` at `layout-wall-first-codec.ts:84`; `grep handleOut\|handleIn` over the canonical type/codec/adapter returns **zero** matches |
| The evaluator **re-derives** every handle from the neighbouring anchors, so the shape is a function of the whole ordered point sequence | `compileAutoBezierAnchors` (`layout-geometry-curve.ts:65`), `createAutomaticTangent` (517), `nearestDistinctPoint` (541), `centripetalInterval` (558), `LAYOUT_AUTO_BEZIER_ALPHA = 0.5` (8) |
| Endpoints get a **one-sided** tangent; interior points get a two-sided centripetal blend — so a split changes the tangent at the cut point *and* at its two neighbours, i.e. up to four cubics | same, `createAutomaticTangent` branches at `!previous` / `!next` |
| `planWallSplit` measures a **chord** and writes `centerline: { kind: 'line' }` on both fragments | `layout-wall-noding.ts:37–46`, `:139–145`, `:217–222` |

Measured on the current evaluator (original curve vs. the same anchors partitioned at an authored anchor; polyline deviation in both directions):

| Fixture | Original arc length | Δlength | Max deviation |
| --- | --- | --- | --- |
| 1 anchor on the chord (`planConvertWallToCurve`'s initial state) | 10.0000 m | 0.0000 | **0.0000** |
| 1 anchor, real bow `[5,3]` | 11.8299 m | −0.1680 | **0.3808 m** |
| 2 anchors, S-shape `[3,2],[7,−2]` | 13.1578 m | −0.1186 | **0.3135 m** |
| 3 anchors | 13.2070 m | −0.0776 | **0.2189 m** |

Only the collinear degenerate case is preserved. A 38 cm shape change is not an acceptable split, and no anchor placement fixes it: the representation has no free handle degree of freedom to express the sub-cubics.

**Conclusion carried into this revision:** the canonical Wall must persist the evaluator's own output — an explicit cubic chain — so subdivision becomes exact de Casteljau and insertion becomes identity-preserving.

## Outcome

Canonical wall-first Layout supports one bounded curved-Wall workflow:

* **bend a Wall directly** — Bend-hotkey + Wall-body drag inserts a bend point at the grabbed span position and drags it, converting a straight Wall to curved automatically and adding a bend point to an already-curved Wall;
* refine that shape with the visible bend controls;
* convert straight Wall ↔ curved Wall explicitly;
* add, move and delete bend points;
* move endpoint Junctions using existing canonical Junction editing;
* rigidly move curved Walls without changing shape;
* keep Wall-hosted Openings positioned by physical distance along the curved centerline;
* support simple curved Room boundaries;
* **split a curved Wall exactly** — `Add Junction` / Wall split subdivides the containing cubic and preserves the curve;
* reject curve candidates before commit when the canonical physical-Wall mesh cannot render them.

No legacy Room-owned curve authoring returns or gains authority.

## 2. New P23.11 decisions

### 2.1 Canonical Wall curve data — a split-preserving cubic chain

Replace the anchor-only centerline with an explicit cubic chain. Endpoint **positions** stay owned by the Junctions; the chain stores the interior bend points and **one control pair per cubic span**. There is no per-point or per-endpoint handle model.

```ts
/** One interior bend point. Position is the authored, user-facing value. */
export type LayoutWallCurveKnot = {
  id: string;
  point: LayoutVec2;
};

/**
 * Control pair for exactly ONE cubic span. `handleOut` leaves that span's
 * first point; `handleIn` arrives at the span's second point. Spans are
 * derived geometry, never a user-facing handle. One span evaluates to exactly
 * one cubic — there is deliberately no per-point handle model.
 */
export type LayoutWallCubicSpan = {
  handleOut: LayoutVec2;
  handleIn: LayoutVec2;
};

export type LayoutWallCenterline =
  | { kind: 'line' }
  | {
      kind: 'cubic-chain';
      /** Ordered interior bend points. May be empty (a single cubic). */
      knots: LayoutWallCurveKnot[];
      /** Exactly `knots.length + 1` cubic spans. */
      spans: LayoutWallCubicSpan[];
    };
```

**Evaluation contract.** With point sequence `P = [startJunction, ...knots, endJunction]`:

```text
spans.length === knots.length + 1

cubic i = (P[i], spans[i].handleOut, spans[i].handleIn, P[i + 1])
```

One span owns **both** of its own controls, so a span's index, its cubic and its
controls are never derived from each other. Nothing evaluates `spans[i + 1]` to
sample span `i`.

**Why this is split-preserving.** The evaluator consumes stored spans and never derives them, so subdividing span `i` reproduces that span exactly. De Casteljau on
`(P0, P1, P2, P3) = (P[i], spans[i].handleOut, spans[i].handleIn, P[i + 1])` at parameter `t`
yields the intermediate points `Q0 = lerp(P0,P1,t)`, `Q1 = lerp(P1,P2,t)`, `Q2 = lerp(P2,P3,t)`,
then `R0 = lerp(Q0,Q1,t)`, `R1 = lerp(Q1,Q2,t)` and `X = lerp(R0,R1,t)`. The two replacement spans are exactly

```text
left  = { handleOut: Q0, handleIn: R0 }   // cubic (P0, Q0, R0, X)
right = { handleOut: R1, handleIn: Q2 }   // cubic (X,  R1, Q2, P3)
```

with `X` on the original cubic by construction. A split is therefore a *span splice*, not a re-interpolation.

| Requirement | How the cubic chain satisfies it |
| --- | --- |
| endpoint positions owned only by Junctions | The chain stores no endpoint position — only per-span controls |
| expresses the current creative smooth curve behaviour | One canonical smoothness rule derives spans on the **write** path (see below); a chain built by it evaluates identically to today's `auto-bezier` spline |
| exact subdivision of any cubic span | De Casteljau on the stored span |
| preserves the original curve exactly after a split | Both halves are true subdivisions of the same cubic; nothing is re-derived or refit |
| deterministic bend-knot insertion at any physical arc position | Arc distance → containing cubic + parameter → subdivide → splice; one deterministic knot ID |
| one canonical evaluator/sampler | §2.2 |
| no tangent-handle UX | `spans` are never rendered, hit-tested, selected or exposed |
| no competing authority | The persisted chain is the **only** curve authority. `auto-bezier` is removed from `LayoutWallCenterline` entirely |

**Rules**

* endpoints remain owned only by `startJunctionId` / `endJunctionId`; the chain never stores an endpoint position;
* `knots.length === 0` is legal and means **one cubic** directly between the two endpoint Junctions — it is *not* flattening, and it is the shape a bend-knot deletion can leave behind;
* `spans.length === knots.length + 1` is a validated invariant, and one span is one cubic;
* knot order is persisted and deterministic; knot IDs follow the existing deterministic anchor-ID policy;
* knot identities, spans and their controls are hidden implementation geometry; the user-facing model is bend points only;
* `line` remains the straight variant; `cubic-chain` may express a straight cubic but the schema does not attempt to canonicalise between them;
* deleting a knot is a **merge**, not a refit: removing point `P[j+1]` replaces spans `j` and `j+1` with one span `{ handleOut: spans[j].handleOut, handleIn: spans[j+1].handleIn }`, giving the single cubic `(P[j], spans[j].handleOut, spans[j+1].handleIn, P[j+2])`;
* `kind: 'auto-bezier'` is no longer valid on a canonical Wall centerline; the codec rejects it.

**One authority, one derivation.** `createAutomaticTangent` / `nearestDistinctPoint` / `centripetalInterval` stop being evaluator internals and become a pure **write-path** constructor (`deriveChainSpans(points)`): used when a planner needs to derive the spans around a knot that is being authored or moved. The read path (`centerline → cubics → samples`) never calls it. That single rule is what keeps "explicit cubic geometry" from becoming a second authority alongside auto-generated anchors — there are no auto-generated anchors any more.

The same derivation remains the interpolation rule for **legacy** `DraftSegment` `auto-bezier` room-owned paths (`layout-types.ts:47–54`, parsed at `layout-wall-first-codec.ts:736–744`). Those are untouched.

Update the current schema/codec directly. Do not add version/migration machinery.

### 2.2 One canonical evaluator and sampler

`wallCenterlineSegment` (the single adapter, `layout-wall-centerline.ts:66–101`) keeps its contract — including the **required** `traversal: 'forward' | 'reverse'` argument, whose absence once caused a reverse walk to trace a different curve — but now expands the chain into explicit cubics instead of an anchor list.

To keep exactly one sampling implementation while the canonical path no longer produces `DraftSegment` anchors:

* extract the cubic-flattening core (`adaptiveParameters`, `buildSampledSegment`, distance/tangent helpers) inside `layout-geometry-curve.ts` so it is driven by a `CubicBezierShape[]` plus an id;
* `sampleSegment(DraftSegment)` (legacy `auto-bezier` and `line`) becomes a thin wrapper that compiles its anchors to cubics first;
* the canonical path calls the same core with the chain's cubics;
* an invariant test asserts that a curve expressible **both** ways produces identical samples from both entry points.

Do not duplicate curve evaluation, and do not introduce a second sampler.

### 2.3 Bend is a named editor command, not a key

The bend modifier is a **named editor command** with a temporary default binding. Interaction code consumes the resolved intent and never inspects a physical key.

New pure module `apps/editor/src/lib/editor/editor-command-intent.ts` (no Svelte, no DOM, no layout imports):

```ts
export type EditorCommandId = 'layout.wall.bend';
export type EditorModifierToken = 'meta' | 'ctrl' | 'alt' | 'shift';
export type EditorPlatform = 'mac' | 'other';
export type EditorModifierSnapshot = {
  meta: boolean;
  ctrl: boolean;
  alt: boolean;
  shift: boolean;
};

export type EditorCommandBinding = {
  command: EditorCommandId;
  /**
   * Exact modifier set required. The binding resolves only when the held
   * tokens are exactly this set — extra held modifiers never match.
   */
  hold: readonly EditorModifierToken[];
};

/**
 * Temporary defaults. Replaced by user settings once keybinding storage
 * exists; nothing outside this table knows which token a command uses.
 */
export const EDITOR_COMMAND_BINDING_DEFAULTS: Record<
  EditorPlatform,
  readonly EditorCommandBinding[]
> = {
  mac: [{ command: 'layout.wall.bend', hold: ['meta'] }], // ⌘ + drag
  other: [{ command: 'layout.wall.bend', hold: ['alt'] }] // Alt + drag
};

export function resolveEditorCommandIntent(
  snapshot: EditorModifierSnapshot,
  platform: EditorPlatform,
  bindings?: readonly EditorCommandBinding[]
): ReadonlySet<EditorCommandId>;
```

**Chosen input:**

| Platform | Default binding | Rationale |
| --- | --- | --- |
| **macOS** | **⌘ (Command) held during Wall-body pointer-down** | Free on a canonical Wall hit — audit below |
| Windows / Linux | **Alt held during Wall-body pointer-down** | Alt is the conventional modifier on those platforms and is equally free on a canonical Wall hit |

Held modifiers must match **exactly**: the macOS default is ⌘ **alone**. Holding Shift or Alt in addition to ⌘ does not resolve `layout.wall.bend`, and no token is implied by another.

**Keyboard-map audit for macOS ⌘.** Every existing ⌘ contract is a *keydown chord* or is scoped to a different hit kind, so a ⌘-held **pointer drag on a canonical Wall body** is unclaimed:

| Existing ⌘ meaning | Where | Why it does not collide |
| --- | --- | --- |
| ⌘Z / ⌘⇧Z / ⌘Y undo-redo, ⌘D duplicate, ⌘G group, ⌘A select-all-in-room | `shortcuts.svelte.ts` `keydown` cascade | Keydown-only; never read during a pointer drag; duplicate/group/select-all additionally require the scene viewport focus and `sceneMayMutate` |
| ⌘/Ctrl + click = toggle selection | `resolveArrangeSceneModifiers` (`layout-interaction.ts:719–728`), fed from `LayoutPlanViewport.svelte:1885–1887` | Consumed by the **scene-object pick** branch, not by a `physicalWall` hit. `layout.wall.bend` is consulted **only** inside the resolved `physicalWall` branch, so scene-object ⌘-click keeps its meaning |
| ⌘/Ctrl/Alt must be absent | `LayoutPlanViewport.svelte:3089–3090` | Keydown-only (scene delete) |

Shift is **not** available (Plan snap-bypass `LayoutPlanViewport.svelte:1518`, angle-constrain `:1595`). Alt carries editor-wide meaning (scene cycle-placements `EditorSelection.svelte:1057`; camera handle gating `:367`) which is why ⌘ is the macOS default while Alt is only the non-macOS default.

**Rules**

* the intent is resolved at **pointer-down** from a modifier snapshot and stored **into the gesture**; nothing re-reads modifiers afterwards, so releasing the key mid-drag does not change the gesture owner;
* the only impure part is platform detection, which happens once at the viewport boundary and is injectable for tests;
* the viewport builds a `EditorModifierSnapshot` from the pointer event and asks the resolver — it must not branch on `event.metaKey` / `event.altKey` as product logic;
* user-configurable keybinding UI and persistence are **deferred**, but the binding table is data, so later remapping requires no consumer change;
* **modifier matching is exact by default.** A binding resolves only when the held modifier set equals its `hold` list; extra held modifiers must not match. The macOS default `['meta']` therefore does not resolve while Shift or Alt is also held. A future binding that wants `⌘⇧` must list `['meta', 'shift']` explicitly — nothing is implied;
* no positional heuristic distinguishes move from bend. The command is the only discriminator.

### 2.4 Frozen Wall-body gesture contract

| Pointer-down intent | Resolved hit | Below drag threshold | Threshold crossed | Release |
| --- | --- | --- | --- | --- |
| plain primary drag | `physicalWall` | nothing planned; release is a plain click that selects the Wall | **P23.10 rigid translation** — both endpoint Junctions get one identical delta | one history entry, or exact baseline restore |
| `layout.wall.bend` held | `physicalWall` | nothing planned; release is a plain click that selects the Wall | insert one bend knot at the pointer-down Wall projection, then drag that knot | **one** history entry for insert + bend, or exact baseline restore |

* straight Wall + bend intent ⇒ becomes `cubic-chain` automatically; no prior "Convert to curve" step.
* already-curved Wall + bend intent ⇒ gains one more bend knot at the grabbed **physical arc position**.
* repeated bend drags at arbitrary span positions are the primary curve-authoring UX.
* the visible bend controls remain available for later refinement.
* a non-primary contact and a second contact during a live gesture are refused, exactly as the other direct edits already do.

### 2.5 Legacy `pendingWallBend` resolution

Today the same gesture means *bend* on a legacy room-owned wall (`pendingWallBend`, `LayoutPlanViewport.svelte:294`, `beginPendingWallBend` at `:1787`) and *translate* on a canonical Wall (P23.10). That contradiction is removed by **gating the legacy bend behind the same `layout.wall.bend` intent**: plain body drag no longer inserts a legacy interior anchor, and the Bend intent does so in both representations.

This is a deliberate, documented behaviour change in the legacy path. It introduces no new authority: the legacy writer (`insertLayoutWallInteriorAnchor` / `layout-editing.ts`) is unchanged, and legacy Room-owned curves are neither revived nor promoted — they remain a transitional representation to be retired post-P23.

### 2.6 Opening semantics

Opening meaning stays:

```text
offset = physical metres from canonical Wall start
width  = physical metres along Wall centerline
```

For curves, physical length, placement and reverse traversal use canonical sampled arc length. This is already true after slice 2's landed work and is representation-independent:

* `compileOpening` places an opening at `pointAlongSamples(sampled.samples, opening.offset + opening.width / 2)` (`layout-geometry.ts:903–917`);
* `wallFirstWallSpan` reports `sampled.length` (`layout-opening-set.ts:73–87`).

A curve edit does not rewrite Opening offset merely to preserve world position. If the edited curve can no longer host an Opening, reject the whole edit.

### 2.7 Exact curved-Wall split contract

`planWallSplit` (`layout-wall-noding.ts:98`) becomes representation-general. At physical split distance `d` measured along the canonical centerline from the Wall's canonical start:

1. resolve the split **once** through `resolveCubicAtArcDistance` (§2.7.1) — the single split-distance authority. No consumer recomputes a distance, a parameter or a partition;
2. **subdivide exactly** with de Casteljau — no refit, no flatten;
3. create or reuse exactly one canonical Junction `X` (existing allocation/reuse rule and `coincidesAsJunction` guard unchanged);
4. retain Wall ID `W` on `A → X`;
5. allocate the `X → B` Wall ID through the existing `NodingIdAllocator` policy (seed `${wallId}-b`);
6. build both fragments **from `ResolvedWallSplitResult.fragments.a` / `.b`**. Those partitions are the **sole** partition authority: `planWallSplit` consumes them directly and must not reconstruct chain indices, re-derive the split span, or recompute any knot or span range itself. Each partition already satisfies `spans.length === knots.length + 1`;
7. preserve `role`, `thickness`, `height` and endpoint order;
8. preserve Opening IDs and physical placement, rebased against the **resolved** distance (never the requested `d`): `offset + width ≤ resolvedDistance` stays on A; `offset ≥ resolvedDistance` moves to B with `offset -= resolvedDistance`; a straddling Opening rejects the whole operation (existing `rebaseOpenings` rule, `:358–388`);
9. Room boundaries rewrite with the existing forward/reverse rule (`rewriteBoundaryForSplit`, `:391–407`);
10. Room identity is preserved through the existing reconciler;
11. one accepted operation = one Layout history entry;
12. Undo/Redo restores exact pre/post-split chain data and IDs.

#### 2.7.1 One resolved split-distance authority

One pure resolver owns arc-length inversion and produces one canonical result:

```ts
type ResolvedWallSplit = {
  /** Index of the cubic span containing the split. */
  spanIndex: number;
  /** Local parameter within that span, `0 < t < 1`. */
  t: number;
  /** Point on the original curve at that parameter (or the promoted knot). */
  point: LayoutVec2;
  /** Resolved physical distance along the Wall from its canonical start. */
  distance: number;
  /** Set when the request resolved onto an existing interior knot (§2.7.2). */
  promotedKnotId?: string;
};

type ChainPartition = {
  /** Interior knots of this fragment, in persisted order. */
  knots: LayoutWallCurveKnot[];
  /** Exactly `knots.length + 1` spans of this fragment. */
  spans: LayoutWallCubicSpan[];
};

type ResolvedWallSplitResult = ResolvedWallSplit & {
  /** Exactly the partitions and metrics the planners consume. */
  fragments: { a: ChainPartition; b: ChainPartition };
};
```

Junction placement, chain partition, Opening rebasing, fragment metrics and every diagnostic consume **that same result**. Nothing may mix the requested `d`, a separately sampled distance and an independently recomputed cubic distance across consumers — that divergence is exactly how a split lands off-curve.

The numerical tolerance is explicit and confined to arc-length inversion: the containing span is bracketed from cumulative sampled arc length, then `t` is refined by bisection against that span's own arc length to a documented tolerance. **De Casteljau subdivision at the resolved `t` is exact** — the tolerance bounds only how faithfully `distance` maps to `t`, never the geometry of the two halves.

#### 2.7.2 Split rules

* `d` must lie strictly inside `(0, arcLength)`; the existing endpoint rejections apply;
* a split resolving within the canonical knot-identity tolerance of either **endpoint Junction** rejects — there is no meaningful fragment;
* a split resolving within the canonical knot-identity tolerance of an existing **interior knot** does **not** reject. The result carries that knot as `promotedKnotId`, and the knot is **promoted to become Junction `X`**: its position is used verbatim as the Junction point and as the resolved `point`, its arc distance becomes the resolved `distance`, it is removed from both fragments' interior knot arrays, and the existing spans are partitioned exactly around it. No subdivision is performed, geometry is unchanged, and no redundant near-zero span is created;
* a split leaving a knot-less fragment is legal (`knots: []`, one cubic) — it must **not** be converted to `line`.

`planWallSubdivision` (Add Junction) delegates to this path, so its previous straight-only rejection of curved Walls is removed. Exact Wall length and exact Wall angle remain out of scope and continue to reject curved Walls.

## 3. Core geometry flow

### Compiler

```text
LayoutWall + endpoint Junctions
→ canonical centerline adapter (chain → explicit cubics)
→ shared sampling core
→ CompiledPhysicalWall.samples
→ Opening / bounds / physical Wall compilation
→ Plan + editor 3D + museum
```

Straight Walls must preserve existing compiled behavior.

No curve-specific compiler is introduced.

### Rooms and topology

Graph connectivity remains Wall/Junction based.

For geometric face calculations, expand each oriented Wall boundary into its canonical sampled centerline before polygon area/centroid/containment work. Do not persist those sample points as Room vertices.

Reject:

* curved Wall self-intersection;
* straight/curve crossing away from an explicit shared Junction;
* curve/curve crossing away from an explicit shared Junction;
* overlap/crossing that would require automatic noding.

**Deferred:** general automatic curve/curve intersection discovery and unrestricted curve noding. `planWallCrossing` (`layout-wall-noding.ts:287`) derives its split distance from a chord (`distanceTo`, `:341`) and has no unambiguous arc-distance path, so it continues to **reject curved participation** in P23.11. The representation change means enabling a straight/curve crossing later needs no schema work.

## 4. Canonical curve operations

Add canonical planners alongside the existing wall-first precision/edit planners:

```ts
planConvertWallToCurve(...)     // line → cubic-chain, exactly straight
planConvertWallToLine(...)      // cubic-chain → line (explicit flatten)
planInsertWallCurveKnot(...)    // exact subdivision at a physical arc position
planMoveWallCurveKnot(...)      // author one bend point
planDeleteWallCurveKnot(...)    // merge two adjacent cubics
planBendWallCurveKnot(...)      // insert + place as ONE candidate (Bend gesture)
```

Exact names/signatures may follow local conventions.

Every planner must:

* derive a candidate from immutable input;
* mutate only canonical Layout data;
* use deterministic IDs;
* pass through `finalizeWallGeometryCandidate`;
* return one accepted document or stable rejection;
* leave the baseline untouched on rejection.

### Straight → curve

* preserve Wall/Junction/Openings IDs;
* create one deterministic knot at the Wall midpoint with spans whose controls lie on the chord, so both cubics are **exactly** the straight span and nothing moves on screen until a knot is dragged;
* commit one Layout history entry.

### Curve → straight

* preserve Wall/Junction/Openings IDs;
* remove the chain;
* validate the resulting straight Wall and hosted Openings;
* reject atomically if invalid.

### Insert / move / delete bend knot

* insert by **exact subdivision** at the projected physical arc position — inserting a knot **without moving it is geometrically identity-preserving**, unlike the superseded anchor-insertion rule;
* move a knot by applying the single canonical smoothness rule to that knot and the two facing controls of its neighbours, then persist the result — this reproduces today's creative spline feel while keeping one authority; only the two adjacent cubics change, so the effect is local;
* delete merges the two adjacent cubics by the rule in §2.1;
* deleting the last knot leaves a knot-less single-cubic chain; converting to `line` is the explicit conversion planner.

### Existing operations

* Junction move: endpoint moves, chain controls remain in place, curve reshapes.
* Rigid Wall move: both endpoint Junctions, every knot position **and** every control point on that Wall receive the same delta.
* Existing rigid Room translation: same rule for every moved curved Wall.
* Exact length / exact angle: reject curve.
* Subdivision / Add Junction: **now supported** for curves through the exact split path.

## 5. Editor interaction contract

Reuse the P23.10 gesture lifecycle exactly.

The selected entity remains `{ kind: 'physicalWall'; wallId }`. A bend knot is transient editing state keyed by `{ wallId, knotId }`; it is not a new `LayoutSelection` variant and not a hierarchy row.

Transient gesture kinds:

* `junction-move` (P23.10);
* `wall-move` (P23.10 rigid translation);
* `curve-control-move` (bend-knot drag on an existing knot);
* **new** `wall-bend` — the Bend-command body drag: pointer-down intent plus a deferred insert. Mirrors the `pendingWallBend` shape (claim at pointer-down, insert only once the threshold is crossed) but owned by the named command and committed through one canonical planner call.

Hit priority stays:

```text
Junction / endpoint
> Opening body/handle
> bend knot
> Wall body
```

Gesture flow (see slice 9 for the current lifecycle):

```text
pointer-down
→ resolve hit
→ resolve command intent (frozen into the gesture)
→ baseline snapshot + one transaction
→ threshold crossed
→ proposal from the frozen baseline (pure, installs nothing)
→ cheap canonical preflight → pending | known-invalid
→ transient attempt rendered from the proposal
→ pointer-up: canonical planner (rigid move | bend insert+place | knot move)
  at the actual release point, full validation and compile
→ one commit or full cancel
```

Do not commit a remembered last-valid preview.

**P23.11 perf amendment (slice 9).** Running the full canonical transaction on every pointermove is measurably too slow on a multi-Room document (see slice 9), so the per-move canonical planner of the original revision is replaced by a **transient proposal** per move and exactly one canonical transaction at release. The planner remains the sole acceptance authority and the release re-resolves the release point; a proposal is overlay truth only and never installs a document.

Escape, pointer cancel, lost capture, tool/mode/view change and project replacement follow the existing P23.10 cancellation path (`LayoutPlanViewport.svelte:3006–3020` order: pending bend → architecture edit → room drag → …).

No new curve drawing tool is introduced; the Bend command is an intent, not a mode.

### Slice 4 — Exact subdivision and chain-algebra primitives

**Work**

* A cubic arc-length function (the one genuinely new geometry primitive; the kernel has none today).
* Document two tolerances explicitly: the numerical arc-length inversion tolerance, and the knot-identity promotion tolerance. De Casteljau at the resolved `t` stays exact.

**Tests**

* **pointwise exactness:** for the left and right halves, `cubicBezierPoint(half, u)` equals the original cubic evaluated at the mapped parameter to float epsilon;

### Slice 9 — Direct-manipulation transient preview (performance amendment)

**Supersedes the per-move canonical transaction.** A profiler-off trace of the canonical Bend gesture on a real 10 Room / 40 Walls document measured ~56 ms per pointermove **after** the two passes below, because each valid move restored the baseline, ran the planner's acceptance compile, installed the candidate, rebuilt meshes and re-derived the whole Plan model. Slice 9 keeps the same planners, the same validation, the same history authority and the same render parity, and changes only **when** the canonical transaction runs.

**Perf passes landed before this slice** (measure-first; no geometry or validation semantics changed by either):

* **Duplicate move-path work.** The unchanged pointer-down baseline was rebuilt (meshes, pick index, deep-cloned model) on every restore, the accepted candidate was compiled a second time for preview install, and the curve crossing gate enumerated every sampled segment pair. Fixed by memoizing the derived wall-mesh/pick-index bundle per compiled geometry, carrying the acceptance compile on the precision plan behind an accepted-document canonical-JSON guard, and sweeping tolerance-expanded segment boxes for crossings with identical classifications and rejections.
* **Wall-extent recovery in Snap.** `dedupeWallSpans` found each Wall's farthest endpoint pair with an all-pairs scan over its compiled sample endpoints, and every read crossed the editor's `$state` proxy; on the real document that was ~98 ms of a ~142 ms move. Fixed by recovering the authored extent in O(k) from the compiled `startDistance`/`endDistance` traversal metadata (falling back to the exact farthest-pair scan when the metadata cannot prove an extent), and memoizing the derived Wall snap index per compiled geometry. Split authority, tolerances, acquisition radius, candidate families and winners are unchanged.

**Work**

* Move the direct-edit proposal out of the preview-state install path into one gesture-local seam (`layout-transient-edit.ts`):
  * `transientArchitectureEdit({ gesture, baseline, moved })` receives no preview state, so it structurally cannot install or mutate a document; it derives overlay geometry + intent from the **frozen pointer-down baseline** through the existing non-validating `proposeWallFirstArchitectureGeometry()`;
  * `releaseArchitectureEdit({ plan, commit, cancel, restoreBaseline })` owns only the count and order — at most one planner call, exactly one commit-or-cancel, an exact baseline on refusal, silence on `no_op`, nothing below the drag threshold.
* Add the **cheap canonical preflight** `preflightWallFirstArchitectureCandidate(document, intent)` for live feedback: it applies the intent as a shallow splice and runs exactly the one gate the planner runs first (`validateWallFirstTopology` with `{ openingSet: 'defer' }`), then stops. It can refute an attempt early and never accept one, so a failure it reports is a failure at release too, and a miss is merely pending.
* Make the attempt status three-state (`pending | known-invalid`) instead of "derivable ⇒ pending". `known-invalid` is only ever a canonical, cheap refutation (crossing, self-intersection, duplicate Junction point, zero-length Wall, broken Room boundary) or an underivable intent; Room reconciliation, the Opening set, the portal relations and the compile stay pending and are decided once at release.
* Share one intent→candidate mapping between the render proposal and the preflight (`architectureCandidatePatch` + `spliceWallFirstArchitectureCandidate`), so the drawn attempt and any preflight verdict can never describe different geometry.
* Extend the existing overlay seam and its refused language; the validity verdict (`markLayoutArchitectureEditValidity`) stays the planner's at release.
* Scope is the existing immutable-baseline gestures only: Junction move, rigid Wall move, curve-knot move, Bend. Layout objects, Opening editing, Room move and Scene/Camera are untouched.

**Not permitted here** (would each be a new owner decision or another authority): pointer throttling/debouncing, lowered curve sampling quality, weakened or approximated validation, incremental canonical compilation, approximate release geometry, a remembered last-valid preview, writing proposal geometry into `LayoutPreviewState.project.layout`, or a second planner/renderer path.

* pointermove mutates no canonical document, installs no preview geometry, writes no history, and leaves Scene/Camera and selection untouched, for all four gesture kinds;

**Deferred debt (recorded, not fixed here — promote only on evidence)**

## 10. Stop conditions

Stop and report rather than broadening P23.11 if:

* the explicit cubic chain cannot reuse the existing kernel evaluator without duplicating or replacing it;
* keeping one sampler requires a second centerline or segment authority;
* simple curved Room support requires implicit graph nodes or general curve noding;
* exact subdivision cannot be expressed without persisting a second geometry model alongside the chain;
* the Bend command cannot be resolved without a second gesture-ownership or selection authority;
* renderer validity cannot be expressed as one shared pure geometry predicate;
* editor and museum mesh validity rules materially differ and cannot be reconciled without a wider architecture decision;
* Layout curve editing appears to require Scene or Camera mutation;
* implementation begins adding migration/backward-compatibility machinery.

P23.11 is complete only when canonical curved Walls use one Wall-owned representation, one evaluator/compiler path, one topology/reconciliation authority, one mutation/history path, one named bend command and one renderability rule.
