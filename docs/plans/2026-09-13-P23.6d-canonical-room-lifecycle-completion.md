## Why this slice exists

After P23.6c, wall-first authoring can create Rooms (birth from topology), move them (P23.6a unit move, including the connected-group amendment), duplicate eligible isolated Rooms (P23.4), and delete one Wall with deterministic Room reconciliation — but the **Room itself** is not yet a fully lifecycle-managed entity:

- **Room removal is canonical-only by omission.** `deleteLayoutRoom` (`apps/editor/src/lib/editor/layout/layout-preview-state.svelte.ts`) **rejects wall-first documents outright** (`wallFirstLegacyEditMessage()`), and no `planDeleteRoom` exists in `layout-core`. A wall-first user has **no way to remove a Room as a Room** — the only demolition path is deleting boundary Walls one by one (P23.6c), which is physics, not product intent.
- **Room metadata is legacy-only.** `updateLayoutRoomFields` resolves the Room through `layout.floors` (legacy shape) and is exactly what P23.6b forbade wall-first Room rows from reaching. `LayoutWallFirstRoom` carries `{ id, name, boundary, floorThickness, ceilingThickness }`; `name` (the hierarchy's primary label) and the two thicknesses have **no canonical wall-first edit operation** — P23.6b verified there is none ("wall-first Room rows are interactive but cannot reach the legacy `updateLayoutRoomFields` rename"). The P23.6e Hierarchy design (Room pages, `Assigned Layout Objects`, Room naming) assumes authoritative Room naming exists.
- **Duplicate/move are narrower than the identity model.** `planDuplicateIsolatedRoom` refuses shared-boundary subgraphs by design; P23.6a moves only *isolated* units and its amendment A moves a *connected group* rigidly. Neither is a gap this slice widens into topology editing — the boundaries are pinned below — but their contracts must be restated as part of the lifecycle so P23.6e and P23.7 accept the whole surface coherently.
- **P23.6e and P23.7 both depend on the outcome.** P23.6e's final hierarchy presents Room pages with authoritative names; P23.7's closeout currently lists "wall-first Room rename / Room metadata" as an **open deferral** and "Room delete/topology edits" only as adapter-regression smoke. A UI overhaul cannot be the slice that invents Room removal.

This slice closes exactly that debt through the **one** canonical planner path. It creates no second geometry, ownership, history, or Room-identity authority.

## The invariant (unchanged, load-bearing)

> A Room is persistent semantic identity over a derived enclosed face. Room removal must not be implemented as deleting a `LayoutRoom` record while leaving the same enclosure intact.

Consequences:

- Topology-changing Room lifecycle operations use the P23.8 face-extraction/reconciliation pipeline — candidate document through `extractBoundaryCandidateFaces` → `buildCorrespondenceComponents` → `reconcileRooms` → `validateAndCompile`, the same pipeline as `planWallRoleChange`/`planDeleteWall` (`packages/layout-core/src/layout-wall-topology-ops.ts`). Metadata-only operations preserve Room identity/boundary directly and pass canonical validation + compile **without** topology reconciliation (review correction: renaming or re-thickening a Room must not run face extraction just because its name/thickness changed).
- Any operation that would leave an enclosed face with no Room, or a Room record with no face, is not a valid lifecycle operation — it is a rejection.
- "Remove Room" therefore means **open or dissolve the enclosure** (demolish a boundary Wall through the P23.6c pipeline) — never a bare record splice. See §What "Remove Room" means.

## What "Remove Room" means (product-level decision)

Three plausible semantics were considered:

1. **Demolish the Room's full boundary (chosen — the intuitive product model).** The authoring gesture is "draw four Walls → it becomes a Room"; the matching removal is "delete each Wall, or select the Room and delete **the whole thing**". "Remove Room" is one command that demolishes every boundary Wall the Room owns alone — for a standalone drawn Room that is its entire boundary, so **nothing survives** (no open shell of leftover Walls). Its *candidate* is the demolition of the Room's **exclusive** boundary Walls (those no other Room's `boundary` references) through the shared Wall-removal pipeline: shared Walls are one physical Wall a neighbour still needs, so they are kept; removing the exclusive Walls still opens the enclosure, so the Room **retires through normal P23.8 reconciliation** (retiredRoomIds, portal clear, object-association clear) with the removed Walls' hosted Openings going atomically. The command rejects when the Room has an empty boundary or owns **no exclusive** boundary Wall (a fully interior Room whose every Wall is shared — the user must delete shared Walls explicitly and see each reconciliation) rather than silently demolishing a neighbour's Walls.
2. **Record-splice removal** — drop the `LayoutRoom` record, keep the enclosure. **Forbidden by the invariant**; stated here only to record the rejection.
3. **Single-Wall "Room-forward" intent (rejected — superseded by (1)).** Deleting exactly one exclusive boundary Wall and calling it "Remove room" leaves an open shell of Walls behind and only *retires* the Room indirectly: it reads as "delete one wall", not "delete the room". P23.6d first shipped this narrow guard-rail, then replaced it with the whole-room demolition in (1) so the enclosure and the Room go together.

## New operations (semantic planner boundaries)

All planners live beside `planDeleteWall` in `packages/layout-core/src/layout-wall-topology-ops.ts` (or a sibling module in the same package re-exported by the same `WallFirstOpPlan` vocabulary). All are pure, reject with stable codes, and pass the final `validateAndCompile` gate; the topology-changing ones (`planRemoveRoom`) additionally run the P23.8 face-extraction/reconciliation engine, while the metadata-only one (`planRoomMetadataUpdate`) does not (see the invariant above). None is a direct record mutation.

### 1. `planRoomMetadataUpdate(document, roomId, patch)`

- **Patch scope (v1):** `name` (non-empty, trimmed; duplicates in `name` are legal since `id` is identity — mirroring legacy behavior), `floorThickness`, `ceilingThickness` — validated by the **existing canonical numeric rule only**: strictly positive finite numbers, exactly what the wall-first codec already requires of these fields. **No new tolerance, range, or "0.1 m tolerance" contract is invented**: `0.1` is the P23.8 creation *default* (`ROOM_CREATION_DEFAULTS`), not a bound; metadata updates validate like the codec validates, nothing more.
- **Boundary is NOT patchable.** The boundary is correspondence-owned; the operations that change it are Wall ops (P23.1/P23.6c) and Room move. A patch containing `boundary` rejects with `invalid_patch`.
- **No-op patch rejects** (`no_op`) so callers write zero history — same convention as `planWallRoleChange`'s same-role rejection.
- Topology does not change (no face extraction, no reconciliation); the candidate runs the full canonical validation + compile gates. Metadata-only edits cannot invalidate faces, but the gate stays uniform.
- Rejection codes: `unknown_room`, `invalid_patch`, `invalid_value`, `no_op`, plus the gate codes.
- `PrecisionOperation` gains `'room-metadata'` (alongside `'wall-delete'`), riding the same operation-typed document-install path.

### 2. `planRemoveRoom(document, roomId)`

- Whole-room demolition per the decision above: `roomId` must exist and own at least one **exclusive** boundary Wall (referenced by no other Room's `boundary`); the Room's exclusive boundary Walls are removed as one atomic set. An empty boundary or a Room whose every boundary Wall is shared rejects `ambiguous_room_removal` (nothing the Room owns alone can be demolished without touching a neighbour).
- The candidate demolishes the Room's exclusive boundary Walls in one command through the shared Wall-removal **set** pipeline: hosted Openings of every removed Wall go atomically, endpoints prune only when no surviving Wall references them (P23.6c's endpoint-scoped cleanup — unrelated orphan Junctions elsewhere in the document are untouched), face extraction runs, P23.8 reconciliation retires the Room deterministically, portals of surviving openings remap/clear per the existing contract, document-level `LayoutObject.roomId?` associations **clear** (retirement has no merge survivor — per the P23.8 rule already implemented in `reconcileRooms`).
- Reuses the `planDeleteWall` **pipeline**, generalised to a Wall-id set (`planWallRemovalSet`), so single-Wall deletion and Room removal stay one authority. The wrapper contributes only the whole-room intent and the exclusivity guard.
- Rejection codes: `unknown_room`, `wall_not_in_room_boundary` (a boundary reference to a missing Wall), `ambiguous_room_removal`, plus every P23.6c/P23.8 downstream code unchanged.
- **Surfaced as the canonical Room Delete** on the Inspector Room panel, the hierarchy Room-row context menu, and the viewport `Delete`/`Backspace` over a selected Room — the enclosure and the Room go together, so deleting an individual Wall stays plain `planDeleteWall`.

### 3. Restated (not new): move / duplicate boundaries

- **Move** stays P23.6a's contract: rigid X/Z of the isolated unit (or connected group per amendment A), explicit predecessor→candidate correspondence, zero birth/retirement. This slice adds nothing.
- **Duplicate** stays P23.4's contract: eligible isolated subgraphs only; shared-boundary subgraphs reject. Widening duplicate to shared boundaries is a topology-merge problem and stays out of scope.

### Explicit non-goals

- No record-splice Room deletion, ever (the invariant).
- No demolition of a Wall shared with a neighbouring Room (it is one physical Wall the neighbour still needs).
- No boundary-edit-by-metadata, no geometry healing, no spatial inference of "which room did the user mean".
- No multi-select Room operations (Issue #28 deferral unchanged).
- No legacy behavior change: `deleteLayoutRoom`/`updateLayoutRoomFields` keep their current legacy-only semantics untouched.
- No second selection, history, or reconciliation authority.

## Cross-cutting contracts (pinned by the P23.6c precedent)

Every new operation follows the same rules; each is regression-pinned in the test plan.

- **Shared-Wall behavior:** a Wall bounding two Rooms is one physical Wall, so it belongs to neither Room alone: Room removal demolishes only the Room's **exclusive** boundary Walls and **keeps** shared ones (the neighbour still needs them, and opening the enclosure retires the Room through reconciliation). If *every* boundary Wall is shared, the Room owns nothing alone → `ambiguous_room_removal`. Merging 2→1 remains exclusively the P23.6c Wall-delete outcome.
- **Exclusive vs shared boundary handling:** exclusivity is computed from the baseline document's `rooms[].boundary` references, never from geometry or coordinates.
- **Hosted Openings:** the removed Wall's Openings go atomically (P23.6c rule); surviving-Wall Openings keep their host and remap/clear portals through the P23.8 contract.
- **Junction cleanup:** endpoint-scoped only — the removed Wall's `startJunctionId`/`endJunctionId` are pruned when no surviving Wall references them; unrelated pre-existing orphan Junctions anywhere in the document survive (P23.6c review regression stays green).
- **Adjacent Room consequences:** retirement/split/merge/disappearance outcomes come from `reconcileRooms` as-is; P23.6d never overrides a correspondence result. If the resulting topology is unsupported (many↔many), the operation rejects atomically.
- **`LayoutObject.roomId?` remap/clear:** through `reconcileRooms` — merge maps to the survivor, retirement clears (no survivor to inherit). Transforms never move.
- **Portal semantic remapping:** the existing `remapPortalRelations` contract (split descendants via wall-side adjacency, collapsed tuples clear, unresolved rejects `unresolved_portal_remap`). No new portal semantics.
- **Selection outcome is operation-specific, not a generic mutation rule** (review correction): P23.6c's clear-to-`none` policy is correct *because the selected Wall no longer exists* — it must not become a blanket rule for every Room-affecting mutation.
  - `planRoomMetadataUpdate` **preserves** the selected Room: the Room survives the edit, and clearing selection would make the Inspector workflow unusable (rename → panel disappears → floor/ceiling thickness can never be edited in one stay). The Inspector follows canonical selection, so keeping the Room selected keeps its panel — exactly P23.6e's Inspector/navigation separation.
  - Room move preserves the existing P23.6a selection policy (unchanged by this slice).
  - `planRemoveRoom` clears canonical selection to `none`: the Room retires, so a dangling `roomId` selection is impossible to keep (same reasoning as P23.6c's deleted Wall). Never a nearest-survivor.
  - Room duplicate keeps the existing P23.4 policy (unchanged by this slice).
  - Rejection changes nothing in every case.
- **Undo/Redo / one command = one history transaction:** every operation runs through the existing guarded runner + `applyWallFirstDocumentPlan`-style single commit; one successful command = exactly one history entry; rejections write zero entries; Undo/Redo restores exact Room/Wall/Junction/Opening IDs; Redo never re-runs correspondence or allocation.
- **Deterministic IDs/reconciliation:** any Room birth inside these flows allocates through the authoring allocator (`createAuthoringRoomAllocator`) — face-key-seeded deterministic IDs, `Draft Room N` naming, collision-free; nothing timestamp- or random-based.
- **Unsupported/ambiguous topology:** rejects atomically with zero partial mutation; the planner is input-pure (baseline document never mutated).
- **Legacy compatibility:** byte-identical compile output for legacy documents; legacy editors/mutators untouched.

## Surfaces (after implementation — target state)

- **Inspector Room panel (wall-first):** authoritative name + floor/ceiling thickness fields (`planRoomMetadataUpdate`), and a `Remove room` danger action listing the Room's exclusive boundary Walls (`planRemoveRoom`), disabled with a reason when none is eligible.
- **Hierarchy Room row (wall-first):** context menu may expose `Remove room…` under the same `isUnifiedTreeRowInteractive` row-authority contract P23.6c's review pinned (menu obeys the activation gate; inert rows expose nothing).
- **Viewport Delete/Backspace:** over a selected wall-first Room, `Delete`/`Backspace` removes the **whole Room** (`planRemoveRoom`) — the same semantics as the Inspector and hierarchy actions; over a selected Wall it deletes that Wall (P23.6c). The legacy viewport `Rename…`/`Delete room` entries no longer appear for wall-first Rooms (they re-joined the legacy `updateLayoutRoomFields`/`deleteLayoutRoom` paths, which reject wall-first documents); the canonical Room menu is the only Room action.

## Acceptance (minimum)

- rename/thickness update on a wall-first Room via the canonical planner; no-op and invalid patches reject with zero history, and the selection stays on the Room so an Inspector rename→thickness stay works;
- `Remove room` on a drawn Room demolishes its **whole** boundary and retires the Room deterministically through P23.8 reconciliation (exact `retiredRoomIds`, object associations cleared, portals cleared/remapped per contract, hosted Openings of every removed Wall gone atomically, no leftover open shell of Walls);
- `Remove room` **keeps** a Wall shared with a neighbouring Room and still retires the Room through reconciliation; it rejects `ambiguous_room_removal` when the Room has an empty boundary or owns no exclusive boundary Wall — zero partial mutation;
- `Delete`/`Backspace` over a selected Room and the Inspector/hierarchy `Remove room` actions all drive the one `planRemoveRoom` planner (no keystroke-only path, no legacy Room delete);
- unrelated orphan Junctions survive every Room-affecting operation (endpoint-scoped cleanup regression);
- one command = one history entry; rejection = zero entries; Undo/Redo restores exact IDs; Redo reruns nothing;
- operation-specific selection: metadata update preserves the selected Room, removal clears selection to `none` (no dangling `roomId`);
- planner input purity (baseline never mutated) and byte-identical legacy compile;
- hierarchy/Inspector surfaces obey the row-authority context-menu contract (Camera domain and Plan Arrange expose nothing);
- existing suites stay green; legacy Room editing behavior unchanged.

  - `planRoomMetadataUpdate(document, roomId, patch)` — metadata is **not**

    only the whole-room intent and the exclusivity guard: unknown Room →
