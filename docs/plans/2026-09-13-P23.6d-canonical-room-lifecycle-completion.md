## Why this slice exists

After P23.6c, wall-first authoring could create Rooms (birth from topology), move them (P23.6a unit move, including the connected-group amendment), duplicate eligible isolated Rooms (P23.4), and delete one Wall with deterministic Room reconciliation — but the **Room itself** was not yet a fully lifecycle-managed entity:

- **Room removal was canonical-only by omission.** `deleteLayoutRoom` (`apps/editor/src/lib/editor/layout/layout-preview-state.svelte.ts`) rejects wall-first documents outright (`wallFirstLegacyEditMessage()`), and no canonical Room-removal planner existed. The only demolition path was deleting boundary Walls one by one (P23.6c), which is physics, not product intent.
- **Room metadata was legacy-only.** `updateLayoutRoomFields` resolves the Room through `layout.floors` (legacy shape). `LayoutWallFirstRoom` carries `{ id, name, boundary, floorThickness, ceilingThickness }`, but `name` and the two thicknesses had no canonical wall-first edit operation.
- **Duplicate/move are narrower than the identity model.** `planDuplicateIsolatedRoom` refuses shared-boundary subgraphs by design; P23.6a moves only isolated units and, after amendment A, connected groups rigidly. This slice does not widen either capability into general topology editing.
- **P23.6e and P23.16 depend on the outcome.** P23.6e's final hierarchy presents Room pages with authoritative names and deletion actions; P23.16 must close against a coherent Room lifecycle rather than inventing one during integration.

This slice closes that debt through the **one** canonical planner path. It creates no second geometry, ownership, history, or Room-identity authority.

## The invariant (unchanged, load-bearing)

> A Room is persistent semantic identity over a derived enclosed face. Room removal must not be implemented as deleting a `LayoutRoom` record while leaving the same enclosure intact.

Consequences:

- Topology-changing Room lifecycle operations use the P23.8 face-extraction/reconciliation pipeline — candidate document through `extractBoundaryCandidateFaces` → `buildCorrespondenceComponents` → `reconcileRooms` → `validateAndCompile`, the same pipeline as `planWallRoleChange`/`planDeleteWall` (`packages/layout-core/src/layout-wall-topology-ops.ts`). Metadata-only operations preserve Room identity/boundary directly and pass canonical validation + compile **without** topology reconciliation.
- Any operation that would leave an enclosed face with no Room, or a Room record with no face, is not a valid lifecycle operation — it is a rejection.
- "Remove Room" therefore means **open or dissolve the enclosure by demolishing the Room's exclusive boundary Walls through the shared P23.6c Wall-removal pipeline** — never a bare record splice.

## What "Remove Room" means (product-level decision)

> **Authoritative product model:** Delete Room removes the selected Room and every boundary Wall exclusive to it. Physical Walls shared with surviving Rooms remain because they are one canonical Wall in the layout topology, not owned by either Room. Adjacent Rooms remain intact wherever the resulting topology permits. Stated as a rule: *remove the Room and its exclusive enclosure Walls while preserving shared physical Walls required by adjacent Rooms* — never "delete the Room's whole boundary", which implies shared physical Walls disappear.

Three plausible semantics were considered:

1. **Demolish the Room's exclusive enclosure (chosen — the intuitive product model).** The authoring gesture is "draw four Walls → it becomes a Room"; the matching removal is "delete each Wall, or select the Room and delete **the whole thing**". `Remove Room` is one command that demolishes every boundary Wall the Room owns alone. For a standalone drawn Room that is its entire boundary, so **nothing survives** (no open shell of leftover Walls). The candidate is the demolition of the Room's **exclusive** boundary Walls (those no other Room's `boundary` references) through the shared Wall-removal pipeline. Shared Walls are one physical Wall a neighbour still needs, so they are kept. Removing the exclusive Walls still opens the enclosure, so Room identity consequences flow through normal P23.8 reconciliation. The command rejects when the Room has an empty boundary or owns **no exclusive** boundary Wall rather than silently demolishing a neighbour's Walls.
2. **Record-splice removal** — drop the `LayoutRoom` record, keep the enclosure. **Forbidden by the invariant**.
3. **Single-Wall "Room-forward" intent** — delete one exclusive boundary Wall and call it `Remove room`. **Rejected/superseded** because it leaves an open shell of Walls and reads as "delete one wall", not "delete the room".

## New operations (semantic planner boundaries)

All planners live beside `planDeleteWall` in `packages/layout-core/src/layout-wall-topology-ops.ts` (or a sibling module in the same package re-exported by the same `WallFirstOpPlan` vocabulary). All are pure, reject with stable codes, and pass the final `validateAndCompile` gate; topology-changing `planRemoveRoom` additionally runs the P23.8 face-extraction/reconciliation engine, while metadata-only `planRoomMetadataUpdate` does not. None is a direct Room-record mutation.

### 1. `planRoomMetadataUpdate(document, roomId, patch)`

- **Patch scope:** `name` (non-empty, trimmed; duplicate names legal because `id` is identity), `floorThickness`, `ceilingThickness` — validated by the existing canonical strictly-positive-finite numeric rule only. No new tolerance/range contract.
- **Boundary is not patchable.** A patch containing `boundary`, or any legacy/unrecognized key, rejects `invalid_patch`.
- **No-op patch rejects** (`no_op`) so callers write zero history.
- Topology does not change: no face extraction, no reconciliation. The candidate still runs canonical validation + compile.
- Rejection codes: `unknown_room`, `invalid_patch`, `invalid_value`, `no_op`, plus the shared gate codes.
- `PrecisionOperation` includes `'room-metadata'`.

### 2. `planRemoveRoom(document, roomId)`

- `roomId` must exist and own at least one **exclusive** boundary Wall (referenced by no other Room's `boundary`).
- The Room's complete exclusive Wall set is removed atomically through the shared private `planWallRemovalSet` pipeline — never a `LayoutRoom` record splice.
- Hosted Openings of every removed Wall go atomically. Endpoints prune only when no surviving Wall references them; unrelated orphan Junctions survive.
- Face extraction and P23.8 reconciliation own all Room identity outcomes. Portals and document-level `LayoutObject.roomId?` associations follow the existing reconciliation/remap rules.
- Shared boundary Walls survive because adjacent Rooms still require that one physical Wall.
- Rejection codes: `unknown_room`, `wall_not_in_room_boundary` (boundary reference to a missing Wall), `ambiguous_room_removal` (empty boundary or no exclusive Wall), plus every downstream P23.6c/P23.8 rejection unchanged.
- `PrecisionOperation` includes `'room-remove'`.

### 3. Restated (not new): move / duplicate boundaries

- **Move** stays P23.6a's contract: rigid X/Z of the isolated unit (or connected group per amendment A), explicit predecessor→candidate correspondence, zero birth/retirement.
- **Duplicate** stays P23.4's contract: eligible isolated subgraphs only; shared-boundary subgraphs reject.

### Explicit non-goals

- No record-splice Room deletion, ever.
- No demolition of a Wall shared with a neighbouring Room as part of `Remove Room`.
- No boundary-edit-by-metadata, geometry healing, or spatial inference of "which room did the user mean".
- No multi-select Room operations (Issue #28 deferral unchanged).
- No legacy behavior change: `deleteLayoutRoom`/`updateLayoutRoomFields` keep their legacy-only semantics.
- No second selection, history, reconciliation, Scene-reference, or geometry authority.

## Cross-cutting contracts

- **Shared-Wall behavior:** Room removal demolishes only exclusive boundary Walls and keeps shared ones. If every boundary Wall is shared, `ambiguous_room_removal` rejects. Merging 2→1 remains a direct Wall-delete topology outcome, not a special Room-delete rule.
- **Exclusive vs shared handling:** exclusivity comes from baseline `rooms[].boundary` references, never coordinates/proximity.
- **Hosted Openings:** Openings hosted by removed Walls disappear atomically; surviving-Wall Openings keep their host and remap/clear portal relations through P23.8.
- **Junction cleanup:** endpoint-scoped only, reusing the P23.6c rule.
- **Adjacent Room consequences:** retirement/split/merge/disappearance come from `reconcileRooms` as-is; P23.6d never overrides correspondence. Unsupported many↔many topology rejects atomically.
- **LayoutObject association:** `LayoutObject.roomId?` remap/clear remains P23.8-owned; object transforms never move because a Room retires.
- **Portal semantic remapping:** reuse `remapPortalRelations`; unresolved relations reject rather than guess.
- **Scene-reference safety:** Layout planning occurs first. Before installing the planned Layout candidate, the editor checks **every** `plan.retiredRoomIds` against the authoritative `SceneDocument` using the existing `listLayoutRoomSceneReferences` / total / summary policy. If any retiring Room is referenced, the entire command rejects atomically: no Layout install, zero history, unchanged Scene, unchanged selection. The Layout planner never sees or mutates Scene state.
- **Selection policy is operation-specific:** metadata preserves the selected Room; Room removal clears canonical selection to `none` only after successful commit; rejection changes nothing. Room move/duplicate retain their existing policies.
- **Undo/Redo:** one semantic command = one history entry; rejection = zero; Undo/Redo restores exact IDs and Redo does not rerun reconciliation/allocation.
- **Arrange authority:** a committed Layout Room selection may remain remembered after switching to Arrange, but canonical Room Delete/Backspace dispatch requires `interaction.planViewMode === 'layout'`. Remembered structural selection is memory, not mutation authority.
- **Legacy compatibility:** legacy compiler/editor behavior remains untouched.

## Surfaces

- **Inspector Room panel (wall-first):** authoritative name + floor/ceiling thickness fields through `planRoomMetadataUpdate`, plus a `Remove room` danger action through the canonical Room-removal adapter.
- **Hierarchy Room row (wall-first):** `Remove room…` under the same `isUnifiedTreeRowInteractive` row-authority contract as activation; inert rows expose no mutation menu.
- **Viewport context menu:** wall-first Rooms expose canonical `Remove room…`, not legacy rename/delete commands.
- **Viewport Delete/Backspace:** a selected wall-first Room dispatches canonical removal only in Layout mode; a selected Wall remains P23.6c `planDeleteWall`.
- **Scene-reference preview:** `wallFirstRoomSceneBlockedRoomIds(state, roomId, authoritativeScene)` is a read-only companion using the same reference helpers as execution. It is available for surfaces to explain/disable a blocked action; runtime safety does not depend on surfaces pre-checking it.

## Acceptance

- rename/thickness update through the canonical planner; invalid/no-op patches reject with zero history and selection stays on the Room;
- standalone Room removal deletes all exclusive boundary Walls, hosted Openings, and the derived Room in one transaction with no leftover open shell;
- adjacent Room removal keeps shared physical Walls and preserves neighbouring Room identity wherever P23.8 permits;
- all-shared or empty-boundary Room removal rejects atomically;
- all surfaces route through the one `planRemoveRoom` semantic planner;

## Implementation record (final — 2026-09-13)

Implemented on branch `P23.6d` from merged P23.6c baseline `main` @ `5657dd0`.

- **Topology architecture unchanged:** P23.6c's private `planWallRemovalSet` remains the single Wall-removal pipeline. `planDeleteWall` supplies one Wall; `planRemoveRoom` supplies the target Room's exclusive boundary Wall set.
- **Metadata:** `planRoomMetadataUpdate(document, roomId, patch)` is metadata-only and performs no face extraction/reconciliation.
- **Room removal:** `planRemoveRoom(document, roomId)` removes the Room's exclusive enclosure Walls, preserves shared physical Walls required by adjacent Rooms, and lets P23.8 own exact retirement/survivor identity. No replacement/duplicate shared Wall system exists.
- **Editor adapter:** `removeWallFirstRoom(state, roomId, authoritativeScene)` produces the canonical Layout plan first, checks **all** planned `retiredRoomIds` against the authoritative Scene with the existing Room-reference helpers, then installs that exact already-planned candidate. A block installs nothing and writes zero history. No Scene reference is cleared or mutated by Layout code.
- **Read-only preview:** `wallFirstRoomSceneBlockedRoomIds(state, roomId, authoritativeScene)` exposes the same reference policy for UI explanation. It is not a second safety authority.
- **Call sites:** both viewport mounts, Inspector, and hierarchy pass `store.document`, matching the legacy ownership seam.
- **Arrange authority:** wall-first Room Delete/Backspace requires `interaction.planViewMode === 'layout'`; remembered Room selection is not cleared and cannot mutate from Arrange.
- **Selection:** metadata preserves the Room selection; successful removal clears to `none`; failure preserves exact state.
- **P23.6b supersession:** wall-first Room rows now expose the canonical removal command; legacy rename/delete remains unavailable on wall-first documents.
- **Regression proof:** the nested outer/inner enclosure fixture proves reconciliation can retire `room-z` collaterally while selected `room-a` survives under the existing deterministic lexical-ID tie-break; a Scene reference to that collateral retirement blocks the entire command. The test pins the existing P23.8 result rather than introducing deletion-specific identity preference.
