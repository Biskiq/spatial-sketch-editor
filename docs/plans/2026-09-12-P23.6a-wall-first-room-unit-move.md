## Why this slice exists

In wall-first Layout a Room is **persistent semantic identity reconciled from
topology**, not an authored polygon. There is therefore no way to translate a
Room today: the legacy transform (`transformLayoutRoomUnit()` in
`apps/editor/src/lib/editor/layout/layout-room-transform.ts`) mutates the legacy
Room's `boundary`/`frame`/owned objects, and the editor's wall-first preview
adapter explicitly refuses it (`previewLayoutRoomUnit()` calls
`wallFirstLegacyEditMessage()`). Dragging a wall-first Room interior currently
only selects it
(`LayoutPlanViewport.svelte`: *"Canonical Rooms have no Room-unit drag gesture"*).

P23.6a adds the missing interaction with a semantics that is narrow enough to be
implementable and provable:

```text
selected persisted Room
→ resolve the connected Room group containing it
→ prove the group is isolated from stationary architecture
→ translate the group's boundary Junctions (and explicitly associated objects)
→ preserve Wall / Opening / Room identity
→ explicit predecessor-Room → candidate-face correspondence
→ one canonical reconciliation
→ validate + compile once
→ exactly one Layout history entry
```

Rigid relocation of the **connected Room group** containing the dragged Room
only. It is not a topology-editing tool, not a persisted-polygon translation, and
not a Layout multi-selection feature — dragging one Room of a group moves that
group with no selection set at all, and selecting *disjoint* Rooms as one set is a
registered deferral (umbrella → Deferred capability register → issue #28).

## Product outcome

In Scene → Plan → Layout, dragging a Room's interior moves the whole **connected
Room group** containing it — that Room, the boundary architecture of the group
(including Walls shared by two members, which travel once), and any Rooms joined
to it through shared boundary Junctions — rigidly in X/Z. An isolated Room is a
group of one, so the single-Room case is discovered, not special-cased.

A group that is still tied to stationary architecture refuses whole-unit
movement and stays editable through its constituent Walls/Junctions. Room
rotation stays deferred.

## Approved semantic decisions

### D1 — Rigid translation of the canonical boundary graph

The move translates the **group's** canonical boundary **Junctions**. The
persisted `LayoutRoom` record is never rewritten to fake movement, and the
compiler/reconciliation pipeline produces the committed Room order. One valid
move = one rigid X/Z delta applied to every boundary Junction of the group.

### D2 — The movable unit, and what makes it immovable

**The movable unit is the connected Room group containing the dragged Room**: the
transitive closure over Rooms joined through shared boundary **Junctions**. A
shared Wall shares both of its endpoints, so the closure subsumes shared-Wall
adjacency; corner-only contact (a shared Junction with no shared Wall) counts too,
because a shared Junction is exactly what makes translating one member alone
impossible. An isolated Room is a group of one.

Membership decides the subgraph: the group's boundary Junctions, every Wall on
them (including an interior Wall shared by two members, which travels **once**) and
the Openings hosted by those Walls.

Reject when **any** of:

1. a group Junction has an incident Wall outside the group — a partition stub, or
   a corner-only single-Wall connection to a Room outside the group — so the unit
   would tear away from stationary architecture;
2. a hosted Opening on a group Wall carries a `connectsRoomIds` portal relation
   with an endpoint **outside** the group (a relation recorded entirely inside the
   group stays valid and travels with it);
3. an explicitly associated LayoutObject (`object.roomId` is a member Room) is a
   read-only `profile` object;
4. the candidate fails canonical topology, Opening-set, portal or compiler gates.

Rules 1–3 are the **same policy P23.4 proves** for isolation; they must be shared,
not re-derived (S1). Duplication deliberately keeps the **single-Room** scope — a
clone needs a private copy of the shared Wall and its Junctions, so
`room_not_isolated` remains correct there. Both scopes share every rule helper and
differ only in membership (see §Amendment A).

### D3 — What translates

For a valid delta `[dx, dz]`:

- every boundary **Junction**: `X += dx`, `Z += dz`;
- **Walls**: `wallId`, `startJunctionId`/`endJunctionId`, `thickness`, `role`
  and authored `height` are **unchanged** — they move because their Junctions
  move;
- **Openings**: `openingId`, `wallId`, `offset`, `width`, `height`,
  `sillHeight`, `profile`, `connectsRoomIds` unchanged; they move physically with
  the host Wall;
- **Room**: every member keeps its `roomId`, its name, its surface metadata, its
  shape and its dimensions — relocated through reconciliation.

**P23.6H / P23.6I interaction (hard rule):** a Room move must preserve the exact
existing `wall.height` of every moved Wall. Never regenerate moved Wall height
from any Floor-level quantity — under P23.6I the canonical Floor has no `height`
at all. A moved Room's derived ceiling is simply the `max` over its (unchanged)
boundary Wall heights, so the move recompiles the same ceiling as the source.

### D4 — LayoutObjects: explicit association only

- `object.roomId` is a Room in the moving group → translate the object's X/Z by
  the same delta. Preserve Y/elevation, dimensions, rotation/yaw, identity and
  kind.
- No other object moves. Coordinate containment never decides ownership.
- A `profile` object associated with any moved Room **rejects the entire move**
  (never partially moves the unit, never silently strands an explicitly
  associated object). This mirrors the shipped duplicate policy
  (`profile_object_read_only`).
- Unassociated objects, freestanding interior Walls, Rooms outside the group and
  unrelated architecture stay exactly where they are.

### D5 — SceneDocument is never mutated

A Room move is a Layout-owned gesture: it mutates `LayoutDocument` only. No
inferred Scene ownership, no compound Layout+Scene transaction, no Room-frame
resolution. Scene content that happens to sit inside the Room stays world-local
where it is.

### D6 — Explicit Room correspondence (the critical amendment)

Generic correspondence (`buildCorrespondenceComponents()`) connects predecessor
Rooms to candidate faces through **geometric overlap or interior-witness
containment**. A large translation invalidates both signals: a probe moving an
isolated Room 100 m preserved the candidate face key but produced a component
with **no predecessor Room**. Relying on that helper plus a final "roomId
survived" assertion would reject ordinary long-distance moves.

**Chosen strategy — exact boundary-lineage correspondence, no geometry:**

1. Face keys are already derived from the rotation-normalized oriented boundary
   cycle (`canonicalFaceKey(keyFloorlessTokens(boundaryRefs))` in
   `layout-face-extraction.ts`, tokens `wallId~F|R`).
2. A persisted Room's `boundary` **is** that same oriented cycle (reconciliation
   writes `boundary: [...face.boundary]` for preserved/split/merged Rooms), so
   `canonicalBoundaryCycleKey(room.boundary)` is computable from the persisted
   Room with no geometry.
3. Under a pure translation with unchanged `wallId`s and directions, that key is
   **invariant** (probe-verified: identical key before/after a 100 m shift), and
   the translated candidate face carries the same key.
4. Therefore P23.6a builds correspondence **directly by key equality**:

```text
for each predecessor Room r:
    key(r) = canonicalBoundaryCycleKey(r.boundary)
    component = { candidateFaceKeys: [key(r)], predecessorRoomIds: [r.id] }
require: every predecessor key resolves to exactly one candidate face
         every candidate face is claimed by exactly one component
```

5. Feed those components to the existing `reconcileRooms()`
   (`packages/layout-core/src/layout-room-reconciliation.ts`), whose 1→1 branch
   preserves the predecessor `roomId` and adopts the candidate face boundary.
6. Face keys stay **transient evidence** — never persisted as Room identity.

Reuse the existing reconciliation API; do not create a second Room allocator, a
second correspondence engine, or a persisted lineage field.

### D7 — Global identity preservation is asserted, not just the selected Room

The move must assert **globally**: every moved Room keeps its `roomId` (and the
anchor stays selected); zero Room births; zero Room retirements; zero Room splits;
zero Room merges; Room count unchanged; every predecessor Room id present in the result with an identical
boundary cycle key. If any of that cannot be proven, reject the whole operation.

### D8 — Snapping is guidance only

Existing Plan snap/grid may influence the **translation delta** only. Snapping
must not merge Junction IDs, reconnect Walls, create noding, split Walls, detach
topology, or birth/retire Rooms. Because a grid-snapped delta can land a boundary
Junction exactly on an unrelated existing Junction coordinate, the canonical
topology gate (which rejects duplicate Junction points) is what protects this —
the move rejects rather than silently merging. No new clearance or collision
system; no swept-path solver.

### D9 — Validation gates are the existing canonical ones

A rejected candidate rejects because of the existing canonical
topology/geometry/Opening/portal/compiler rules — not a bespoke Room-move rule
set. "Collision" in earlier proposal language means exactly these gates.

### D10 — Rotation stays deferred

Room rotation (the legacy yaw transform) is not part of P23.6a. No wall-first
Room exposes a rotation handle (currently true: `rotationHandleHit()` resolves
through the legacy Room list, which is empty for wall-first documents — preserve
that).

## Amendment A — why the unit is the connected Room group (2026-09-12)

**This section is the record of a review-time correction, not a second
contract.** The normative sections above (D2–D4), §Exact in-scope behavior, the
rejection table and seams S1/S3/S5/S6 are stated in group terms; there is no
remaining isolation-only rule to reconcile against. What follows explains why they
are, and what the first cut got wrong.

**Found during review.** A Room that shares a boundary Wall with another Room could
not be moved at all: D2 rejected any shared boundary Wall as `room_not_isolated`, so
in a two-Room layout neither Room could be translated and the only recourse was
moving Walls and Junctions individually. That is not the product need — the need is
*"move this Room and everything rigidly attached to it"*.

**Ratified unit.** The movable unit is the **connected Room group** containing the
dragged Room: the transitive closure over Rooms joined through shared boundary
**Junctions** (which subsumes shared Walls, since a shared Wall shares both of its
endpoints). That is exactly the rigid-connectivity graph — moving any member alone
would tear the shared Junction. An isolated Room is a group of one, so the original
P23.6a behaviour is discovered rather than special-cased.

Consequences:

- **Shared interior Walls travel once** with the group and keep their `wallId`,
  `role`, `thickness` and `height`. No detach, no copy-on-write, no re-noding, no
  new Wall and no `wallId` change.
- **Corner contact counts as connected**, because the shared Junction (not the
  shared Wall) is what makes separate translation impossible.
- **Portal relations narrow from "always reject" to "reject only when the relation
  leaves the group"**: a door whose `connectsRoomIds` are both members stays valid
  and moves with them; a relation with an endpoint outside the group still rejects
  as `external_portal_relation`.
- **The surviving isolation rejection** is a stationary Wall attached to a group
  Junction — a partition stub, or a Room outside the group for any other reason —
  plus the untouched read-only `profile`-object rule.
- **Duplication deliberately keeps the single-Room scope.** A clone needs a private
  copy of the shared Wall and its Junctions, so P23.4's `room_not_isolated` stays
  correct there. Both scopes share every rule helper (`collectBoundaryGraph`,
  `outsideIncidentWallIds`, `externalPortalOpeningIds`,
  `readOnlyProfileObjectIds`) and differ only in membership, so they cannot drift.
- **Result shape:** `RoomMovePlan` gained `movedRoomIds` (anchor first, then document
  order); `movedRoomId` remains the dragged Room. The adapter returns
  `movedRoomIds`, so the status line reports the unit honestly ("Moved 2 rooms").
- **Presentation:** `LayoutRoomUnitDrag.groupRoomIds` (transient) carries the
  resolved unit, and the Plan overlay draws `selection-bounds` for every member
  while the gesture is live, so the set that will commit is visible before release.

Explicitly **not** implied: Layout multi-selection. Dragging any member moves the
whole group with no selection-set authority at all; selecting *disjoint* Rooms as one
set is a separate registered deferral (umbrella → Deferred capability register →
Issue #28).

## Authority boundaries

- One canonical Layout selection authority (`LayoutInteractionState.selection`);
  the move extends the existing Room-interior branch, adding no second hit path.
- One canonical geometry path and one compiler.
- One canonical reconciliation engine (`reconcileRooms`) and its
  `ComponentLineage` input — no second allocator.
- One canonical history/mutation path (guarded Layout transaction).
- `SceneDocument`, Arrange owner-aware routing and visitor/editor isolation
  untouched.

A owns: Room-move eligibility and group resolution; connected-group boundary-graph
translation; explicit Room lineage correspondence; associated LayoutObject
translation; gesture lifecycle; Room-move history/rejection and release feedback.

## Current repository evidence

E1. `apps/editor/src/lib/editor/layout/layout-interaction.ts` already defines
`LayoutRoomUnitDrag`, `LayoutRoomUnitTransform`, `beginLayoutRoomUnitDrag()`,
`updateLayoutRoomUnitDrag()` (translate mode computes
`translation = snappedTarget − startWorld`, rotate mode computes yaw),
`cancelLayoutRoomUnitDrag()`, and `LayoutSelection { kind: 'room' }`.
`updateLayoutRoomUnitDrag` snapping is pointer-level → one rigid delta.

E2. `apps/editor/src/lib/editor/layout/LayoutPlanViewport.svelte` owns the whole
gesture today: `beginRoomUnitDrag()` opens the transaction and captures
`roomUnitSnapshot = captureLayoutPreviewSnapshot(preview)`; `onPointerMove`
recomputes from the baseline (`restoreLayoutPreviewSnapshot()` then
`previewLayoutRoomUnit()`); `onPointerUp` calls `onLayoutTransactionCommit()`,
restoring the snapshot when `changed === false`; `onPointerCancel` restores +
cancels; the Escape branch cancels the transaction and the drag. The wall-first
Room branch currently only calls `selectLayoutRoom()`.

E3. `previewLayoutRoomUnit()` (`layout-preview-state.svelte.ts`) refuses
wall-first documents with `wallFirstLegacyEditMessage()`. The legacy planner
`transformLayoutRoomUnit()` (`layout-room-transform.ts`) transforms the legacy
Room `boundary`/`frame` and `object.roomId`-owned objects — a behavioural
reference only; its geometry mutation is not reusable.

E4. `packages/layout-core/src/layout-duplicate.ts` already implements the
isolation policy for duplication: shared-boundary-Wall check
(`room_not_isolated`), every Wall incident to a boundary Junction that is not in
the cloned set (`room_not_isolated`, includes corner-only contacts), hosted
Opening `connectsRoomIds` (`external_portal_relation`), and read-only associated
profile objects (`profile_object_read_only`). Its `finalizeCandidate()` runs
codec → topology → `validateWallFirstOpeningSet` → compiler.

E5. `reconcileRooms()` accepts declared `ComponentLineage`
(`{ candidateFaceKeys, predecessorRoomIds }`), rejects unclaimed or
double-claimed faces (`unsupported_component` / `ambiguous_room_correspondence`),
allocates IDs only for `0→1` births and `1→2` split losers, and overwrites the
preserved Room's `boundary` with the candidate face boundary. `1→1` and `2→1`
are preserved/merged; anything else rejects.

E6. Face keys: `extractBoundaryCandidateFaces()` →
`canonicalFaceKey(keyFloorlessTokens(boundaryRefs))`. The token form is
`${wallId}~F|R`; the key rotates to the lexicographically smallest rotation and
is wrapped by `geometryId(['face', …])`. Probe: a 100 m translation of an
isolated Room produced an **identical** face key.

E7. `validatePrecisionTopology()` (`layout-wall-first-precision.ts`, currently
module-private) enforces no duplicate Junction points, non-zero Wall lengths,
explicit-junction-only Wall relationships (collinear overlap rejected), Room
boundary connectivity/role, and translates the first canonical Opening-set
issue.

E8. Plan hit priority is fixed in `plan-hit.ts`
(`resolvePlanHit`): vertex/anchor → opening → object → wall/physicalWall → room.
LayoutObjects therefore already win over the Room beneath them; only the final
`target.kind === 'room'` branch needs the new drag entry.

E9. History: `layoutMutationRunnerFor()` + `runLayoutMutation()` give exactly one
entry per successful mutation and nothing on failure; the editor's
`onLayoutTransactionBegin/Commit/Cancel` props drive the shared store bracket.

E10. `CompiledRoom.floorPolygon` is available in the Plan preview for a wall-first
Room (rooms keep floor polygons and bounds; only `walls`/`openings` are emptied) —
usable for Room hit/containment context. It is not needed for the move delta
itself (E1: the delta is `startWorld` → snapped pointer).

## Exact in-scope behavior

1. Dragging any wall-first Room's interior translates the **connected Room group**
   containing it — boundary Junctions, the Walls on them (a shared interior Wall
   once) and associated objects — rigidly in X/Z.
2. Eligible groups commit exactly one Layout history entry, reporting the unit
   size; an ineligible Room reports a concise reason and mutates nothing.
3. Escape, pointer cancellation, lost capture, workspace/mode change and
   project/document replacement cancel safely to the baseline.
4. An invalid final release commits nothing (including after an earlier valid
   preview).
5. `wall.height`, Wall/Opening/Room/Junction IDs, `role`, thickness and authored
   Opening semantics are preserved exactly.
6. Explicitly associated editable LayoutObjects follow by the same delta; others
   do not move.
7. `SceneDocument` is not mutated at all.

## Explicit non-goals

- Room rotation; detaching or splitting a connected Room group;
- Layout multi-selection (arbitrary or *disjoint* Room sets as one movable unit —
  registered deferral, issue #28);
- automatic Wall duplication; proximity/containment-based content following;
- `SceneDocument` mutation or compound Layout+Scene gestures;
- collision/clearance solving or swept-path tests;
- topology-changing snapping (Junction merging, re-noding, Wall splitting);
- 3D Room manipulation; Camera/timeline behaviour;
- Room deletion, Room rename, Room surface-metadata editing;
- a second hit path, selection slot, Room allocator or reconciliation engine.

### S3 — A's Room move planner

New file: `packages/layout-core/src/layout-room-move.ts` (proposed new pure
module). Do not extend `layout-duplicate.ts` with a second responsibility.

```ts
export type RoomMoveRejectionCode =
  | 'unknown_room' | 'invalid_value' | 'no_op' | 'invalid_reference'
  | 'room_not_isolated' | 'external_portal_relation' | 'profile_object_read_only'
  | 'room_identity_lost' | 'ambiguous_room_correspondence'
  | 'topology_invalid' | 'opening_set_invalid' | 'portal_relation_invalid'
  | 'invalid_candidate_document' | 'candidate_does_not_compile';

export type RoomMovePlan =
  | { kind: 'success'; document: LayoutDocumentWallFirst; operation: 'room-move';
      /** The dragged Room — always a member of `movedRoomIds`. */
      movedRoomId: string;
      /** The whole unit: anchor first, then document order. */
      movedRoomIds: readonly string[];
      changedJunctionIds: readonly string[];
      changedWallIds: readonly string[]; changedObjectIds: readonly string[] }
  | { kind: 'rejected'; rejection: { code: RoomMoveRejectionCode; message: string;
      targetIds?: readonly string[]; issues?: readonly (LayoutDocumentIssue | LayoutGeometryIssue)[] } };

export function planWallFirstRoomMove(
  document: LayoutDocumentWallFirst,
  roomId: string,
  delta: LayoutVec2
): RoomMovePlan;
```

Pipeline (one canonical operation):

```text
validate intent (finite delta; exact-zero delta → no_op)
→ resolve persisted Room (unknown_room)
→ resolveIsolatedRoomGroupSubgraph()                           (S1, group scope)
→ clone candidate; record predecessor keys for every Room
  (canonicalBoundaryCycleKey(room.boundary))
→ translate the group's boundary Junctions by delta (an interior shared Wall
  travels once)
→ translate associated non-profile objects (X/Z only)
→ build correspondence components by key equality              (D6)
→ reconcileRooms(baseline, candidate, extraction, components, allocator)
→ assert global identity preservation                          (D7)
→ validateWallFirstLayoutDocument()
→ validateWallFirstTopology()                                  (S4 export)
→ validateWallFirstOpeningSet()
→ validateWallFirstPortalRelations()
→ compileWallFirstLayoutGeometry() + hasBlockingLayoutIssues()
→ success | reject
```

Notes for the implementer:

- Preserve Wall `height` exactly (D3). No field other than Junction points and
  associated object X/Z may change.
- Preserve `candidate.objects` for all unassociated objects; the candidate must
  be byte-identical to the baseline everywhere outside the moved graph.
- Do not persist face keys, and do not persist a Room "position".
- **Opening validation is a defensive final canonical gate, not an expected
  move-specific failure.** Rigid X/Z translation changes no Opening `width`,
  `offset`, `sillHeight`, `height`, `profile`, `connectsRoomIds`, and no Wall
  `height`, so an Opening that fit its host Wall before the move still fits after
  it. The opening-set gate stays in the pipeline (it is part of the one canonical
  `finalize` chain, and it is the cheapest proof that nothing else drifted), but a
  rejection there means an unrelated invariant broke — not that the Room "did not
  fit". Do not invent move-specific Opening-fit logic.
- The `1→1` outcome requires exactly one claimed face per predecessor and one
  predecessor per face; any other shape rejects with
  `room_identity_lost` / `ambiguous_room_correspondence`.

  the drag is live, so the set that will commit is visible before release. `beginRoomUnitDrag` already opens the transaction and captures the
  immutable `roomUnitSnapshot`; the wall-first branch passes the pointer-down world
  point as both `startWorld` and `pivot`. Translation mode reads only `startWorld`
  (`updateLayoutRoomUnitDrag` computes `target − startWorld`; `pivot`/`startAngle`
  are read exclusively in rotate mode), so **no Room centroid/pivot derivation is
  needed and no `polygonCentroid` export is introduced** — a canonical Room's
  polygon centroid belongs to the deferred Room-rotation problem, not to this
  translation.
- Each pointer move: `updateLayoutRoomUnitDrag()` (total delta from
  `startWorld`, never accumulated), then `restoreLayoutPreviewSnapshot(preview,
  roomUnitSnapshot)`, then `previewWallFirstRoomMove()` with that total delta.
  The candidate is always derived from the immutable baseline.
- Pointer release: **re-derive the candidate once from the release world point**,
  then commit only if that final derivation succeeded; otherwise
  `onLayoutTransactionCancel()` + restore the snapshot, then re-apply the rejection
  message *after* the restore. Never commit the previously previewed candidate
  when the final pointer position is invalid, and never commit when the delta is a
  no-op.
- Escape: cancel the transaction, cancel the drag, ensure the baseline is
  restored (verify `onLayoutTransactionCancel()` restores the snapshot; restore
  `roomUnitSnapshot` explicitly if it does not), and do not commit.
- `pointercancel` / lost capture: existing restore + cancel branch already covers
  the drag state; extend it to the wall-first path.
- Mode/view/tool switch during a drag: cancel (the existing
  `setLayoutViewMode`/`setLayoutDraftTool`/`setPlanViewMode` clear
  `roomUnitDrag`). Add a status-message-free silent cancel.
- Project/document replacement during a drag: **the protection is the existing
  project-load replacement guard, not a revision token invented here.**
  `EditorApp.svelte`'s `canStartProjectMutation()` refuses at load start when
  `store.isEditorInteractionActive || store.isDocumentTransactionActive`
  ("Stop the current interaction before changing projects"), and `loadProject()`
  re-checks the same condition inside its awaits (`loadIsCurrent()`) before
  `store.replaceProjectDocument(...)` (which itself returns `false` instead of
  replacing). The resumed-pending-save path applies the same gate. So a Room-drag
  transaction that is open when a project replacement is attempted makes the
  replacement refuse/cancel rather than letting the drag commit into the
  replacement document. P23.6a adds **no** second guard: it relies on the
  existing one and must not create a stale-drag commit path around it.
- Hit priority unchanged (E8): the new drag entry lives in the existing
  `target.kind === 'room'` branch after objects/walls/openings/Junctions have had
  their chance.

### S7 — Status/feedback

Reuse the existing `preview.statusMessage` / `store.setStatusMessage` path, with
the planner's rejection message. No new notification surface, no modal. Two cases
differ, and the difference is normative:

- **A rejection must survive the cancel.** Cancel and the snapshot restore both
  return the baseline *including* `statusMessage`, so the reason is re-applied
  after the restore; otherwise the unit snaps back with no reason on screen.
- **A no-op release is not a rejection.** Pointer down and up with no movement
  rejects as `no_op` — that is the gesture asking for nothing, so the status line
  is left exactly as it was, like the select-only click an ineligible Room gets.

## Mutation / history behavior

- One successful move (drag commit) → exactly one Layout history entry.
- Undo restores the exact original Junction points **and** associated
  LayoutObject positions; Redo restores the exact move.
- Rejected, cancelled, invalid-final-release and no-op → zero history entries and
  no durable mutation.
- The gesture opens exactly one transaction at pointer down (never one per
  pointer move), and closes it at commit/cancel.
- Selection survives the commit: the same `roomId` stays selected. If the
  reconciliation could not preserve it, the move rejects instead of selecting a
  newly allocated Room.

## Failure / rejection behavior

| Condition | Result |
|---|---|
| Unknown Room | reject `unknown_room` |
| Non-finite delta | reject `invalid_value` |
| Zero delta | reject `no_op`; zero history |
| Stationary Wall incident to a group Junction (incl. corner-only, or a Room outside the group) | reject `room_not_isolated` |
| Portal relation (`connectsRoomIds`) with an endpoint outside the group | reject `external_portal_relation` |
| Shared interior Wall between two group members | **not** a rejection — it travels once with the group |
| Portal relation recorded entirely inside the group | **not** a rejection — it stays a door and moves |
| Associated `profile` object | reject `profile_object_read_only` |
| Junction lands on an existing Junction point | reject `topology_invalid` (duplicate Junction point) — never merge |
| Candidate crosses/overlaps another Wall | reject `topology_invalid` |
| Opening no longer fits after the move (defensive) | reject `opening_set_invalid` (`opening_exceeds_wall`) |
| Room identity / global identity not provable | reject `room_identity_lost` / `ambiguous_room_correspondence` |
| Codec or compile failure | reject `invalid_candidate_document` / `candidate_does_not_compile` |

No partial mutation, no auto-repair, no topology surgery, no forced success.

## Compatibility / migration consequences

- No schema change, no formatVersion change: A writes format 5 documents
  unchanged in shape (P23.6H/P23.6I own the version; final format-5 semantics are
  the H + I combination).
- Legacy (Room-owned) documents keep the legacy transform path; A adds no legacy
  behaviour and does not unify the two.
- No migration is required; existing wall-first Rooms become movable immediately
  when their connected group is isolated from stationary architecture.
- Persisted Room identity is unchanged: no new Room fields, no persisted
  position/lineage/anchors, no ordering change.

## Deterministic identity requirements

- Junction, Wall, Opening, Room and LayoutObject IDs are never reallocated by a
  move.
- The move performs zero `nextRoomId`/`nextRoomName` calls (no births, no split
  losers); reconciliation must never reach an allocating branch.
- No timestamps, no randomness, no traversal-order dependence: correspondence is
  key equality, and iteration order follows document order.
- Undo/Redo restores snapshots exactly; reconciliation never reruns on Redo.

- **D2 / D9** — isolation and destination validity are the existing canonical
  rules. `room_not_isolated`, `external_portal_relation` and
  `profile_object_read_only` keep the P23.4 diagnostics through the shared
  policy; destination failures surface as `topology_invalid`,
  `opening_set_invalid`, `portal_relation_invalid`,
  `invalid_candidate_document` or `candidate_does_not_compile`. No move-specific
  rule set exists.
- **D3** — only boundary Junction points and explicitly associated object X/Z
  change. Wall `id`/`role`/`thickness`/`height`, Opening identity and metrics,
  and Room identity/metadata survive verbatim; no Floor-level quantity is
  consulted (P23.6I).
- **D6** — correspondence is built directly from
  `canonicalBoundaryCycleKey(room.boundary)` per predecessor Room, so a 100 m
  translation resolves exactly like a 1 m one; `reconcileRooms()` remains the
  only reconciliation engine and allocator.
- **D7** — global identity preservation is asserted, not assumed: lineage kind
  and count, no retirements, per-Room boundary-key and name equality, unchanged
  Room count — and the allocator handed to reconciliation is a guard that turns
  any allocation attempt into `room_identity_lost`.
- **Authority boundaries** — `plan-hit.ts` is untouched: the new drag entry
  lives in the existing `target.kind === 'room'` branch, after objects, Walls,
  Openings and Junctions have had their chance (its golden priority tests remain

  authority, and no second document/history/compilation path was introduced.
- **D8 / D10** — translation only. Snapping may shape the delta, but a
  grid-snapped delta that lands a Junction on an existing Junction point rejects
  through the canonical topology gate instead of merging. Rotation stays
  deferred: the pointer-down world point is the pivot, so no Room centroid or
  persisted Room position is introduced.

### Deviations from this plan

1. **Profile rejection lives in the shared policy.** `resolveIsolatedRoomSubgraph()`
   is the single place that rejects an associated `profile` object, so duplicate
   and move cannot drift; the duplicate planner's now-redundant check was removed
   and the shared diagnostic reads "…resolve or remove them before duplicating or
   moving". Codes and target IDs are unchanged, which is what the P23.4 suite
   pins.
2. **The non-movable hint is adapter-owned.** Instead of formatting the status
   text in the component, `wallFirstRoomMoveEligibility()` returns a `hint`
   beside the unchanged rejection, so `LayoutPlanViewport.svelte` duplicates no
   policy and no phrasing.
3. **`isSupportedDuplicateLayoutObject` is a re-export alias** of the shared
   `isSupportedLayoutObject()` (one predicate, two names) to leave existing
   duplicate call sites and tests untouched.
4. **The release re-derivation cancels on failure rather than only asserting:**
   pointer-up recomputes the candidate from the release point and, when it
   fails, cancels the transaction and restores the baseline, so the previously
   previewed candidate can never be committed by a stale release.
5. **Amendment A (connected Room group)** landed after the first review round —
   see §Amendment A. The P23.6a test suite's two shared-Wall-move assertions were
   rewritten to the group semantics on purpose (they were pinning the limitation
   the amendment removes); the duplicate-side pin is unchanged and still asserts
   the single-Room rejection. Layout Room multi-select remains registered as a
   deferral (Issue #28), not implemented here.
6. **Review closeout — release feedback is ordered, not incidental.** The
   pointer-up path originally set `preview.statusMessage` from the failed final
   derivation and then cancelled + restored the baseline, and the restore also
   restores `statusMessage` — so a real rejection was instantly erased and the
   Room snapped back with no reason shown. The release now captures the reason,
   cancels/restores, and re-applies it afterwards; the adapter returns the
   planner's `code` so a `no_op` release (a press/release that never moved) stays
   silent instead of printing "delta must be non-zero". The gesture suite mirrors
   the viewport's release branch and asserts the resulting `statusMessage` — the
   earlier test only asserted the returned message, which is why the erase was
   invisible.
