# P23.6d — Final product-semantics reconciliation

All thirteen points reconcile with the previous model. Decisions below; disagreements flagged where they exist.

---

## 1. Scene / Camera domain boundary

**Agree.** P23.6d scopes to the Scene-domain Hierarchy only.

- `Camera Flow` is removed from the Scene Hierarchy root.
- The Camera domain keeps whatever hierarchy/navigation it has today; it is not touched.
- No domain switcher inside Hierarchy. The existing `Scene | Camera` switch is the only one.
- The only shell-level dependency to verify before planning: if any current Camera-domain flow relies on the Scene Hierarchy rendering `Camera Flow`, that flow needs its own destination first. That's a check, not a redesign.

## 2. Root IA and section labels

**Agree that non-interactive labels help first use** — they answer "what kind of thing is this" without adding a click. One correction: a heading over a single row (`ROOMS / Rooms`) reads as redundant and looks like a bug. Final root:

```
HIERARCHY
[ Search… ]

Rooms                            50

ARCHITECTURE
Walls                           200
Openings                         31
Junctions                       118

PLACED CONTENT
Layout Objects                   64
Scene Content                   212
```

Rules for labels: eyebrow text, not focusable, not in tab order, not collapsible, not destinations, no counts. Every row is a one-click page. `Layout Objects` is acceptable as a label because the `PLACED CONTENT` heading now gives it a sibling it must be distinguished from.

## 3. Ownership under grouping

**Absolute.** `PLACED CONTENT` is presentational only. Layout Objects → LayoutDocument; Scene Content → SceneDocument. No shared selection owner, no drag/drop across the two rows or pages, no combined mutation, no inferred common Room association. Each page talks only to its own domain's selection and reveal contract.

## 4. Room page — final structure and naming

```
← Rooms
Gallery A

Boundary (6 walls)                       authoritative boundary order
  W014
  W031        also in Gallery B
  W044        also in Gallery B, +1      ▸ 1 opening
  W052
  …
▸ Boundary Junctions (6)                 collapsed
▸ Assigned Layout Objects (4)            collapsed; present only if the model has explicit Room association
```

- Expanding a Wall row shows its hosted Openings and one `Ends  J021 · J022` row.
- **Naming: `Assigned Layout Objects`.** "Objects in this room" implies spatial containment the model doesn't guarantee; "Associated" is accurate but vague. "Assigned" is plain language and truthfully describes an explicit authored relationship. Tooltip on the header: *Layout Objects explicitly assigned to Gallery A.*
- If the association field exists but is empty, show `(0)` collapsed; if the model has no association at all, omit the section.
- **No Scene Content section.** No point-in-polygon, no bounding-box inference, ever.
- "Corners" is dropped in favour of `Boundary Junctions` so the word matches the global page and the Inspector.

## 5. Opening home / index semantics — confirmed

- **Home of an Opening is under its host Wall on the Walls page.** `Show in Walls` for D007 → Walls page, scrolled to W044, W044 expanded, D007 highlighted.
- The global `Openings` page is an index. Every row there carries `on W044` as its secondary line and `Show in Walls` as its action.
- An Opening selected while the Openings page is current is *revealed on that page* (it has a representation there). Representation ≠ home; both statements hold.

## 6. Same-page reveal vs pinned selection — confirmed

The rule as you stated it is the rule I intended, tightened:

> **Representation** means the entity has a row in the current page's projection (including rows under collapsed parents and rows outside the viewport). It does not mean "currently visible".

- Representation exists → scroll to and highlight the row. No page change, no history, no strip.
- Representation excluded by the page's projection (Room context, active filter, active search results, wrong entity type for the page) → keep the page, show the pinned strip.

Consistency with existing contracts:

- Plan → Wall reveal: on Walls page, scroll; elsewhere, strip. Same as today's reveal, now page-aware.
- Opening reveal through host Wall: on Walls page, auto-expand W044 (see §7); on Openings page, direct row.
- Junction reveal: on Junctions page, scroll to the row and nothing else expands; on a Room page where it's a boundary Junction, expand `Boundary Junctions` and highlight; elsewhere, strip. The topology inventory is never exploded.

## 7. Pinned strip — final behaviour

```
Selected W092
Not in Gallery A                          Show in Walls ›
```

- One-line neutral status surface pinned to the bottom of the rail; no colour, no icon, no animation; updates in place during rapid clicking.
- Second line states only what the current projection knows:
  `Not in Gallery A` · `Outside active filter` · `Not in search results` · `Not on this page` (fallback).
  Avoid `Outside current view` — it reads as viewport, which is exactly what the strip must *not* mean.
- Action label names the home page: `Show in Walls ›`, `Show in Junctions ›`, `Show in Layout Objects ›`, `Show in Scene Content ›`.
- Never shown for off-screen rows.

**Collapsed-ancestor case: yes, auto-disclose.** If D007 is selected and its only representation on the Gallery A page is under a collapsed W044, expand W044 and reveal D007. Rules:

- Expand only the direct ancestor chain of the entity's primary representation on this page; never sibling rows, never a whole section other than the one containing it.
- Each page defines one primary representation per entity type (Room page: Opening → under host Wall; Junction → `Boundary Junctions`; on the Walls page a Junction has no representation → strip).
- Auto-disclosure mutates the current history entry's disclosure state; it pushes nothing.

## 8. Search semantics — confirmed settled

All eight statements stand. Two clarifications so there are no gaps:

- Search query, scroll, filter and disclosure are all fields of the *current* history entry. `Show in…` from results pushes a new entry with an empty query; Back restores the previous entry including its query and disclosure.
- Selection excluded from the current result set shows the strip with `Not in search results`. Clearing search re-evaluates: if the entity is on the underlying page, the strip disappears and the row is revealed.

No serious problem seen.

## 9. Retrieval depth — final rule

**Result shape (fixed, never deeper):**

1. **Direct** — name, authored label, or display reference matches the query.
2. **Directly related** — entities in an authoritative relationship with a direct match, grouped by type:
   Room → boundary Walls, assigned Layout Objects · Wall → participating Rooms · Opening → host Wall · Junction → incident Walls · Layout Object → assigned Room.
3. **Dependents, nested only** — hosted Openings and `Ends` under a level-2 Wall. Never their own top-level group.
4. **Topology, summarised** — `Boundary Junctions (6) [Show]`. Junctions appear as a count, never traversed through.
5. **Stop.** No traversal from a level-2 Wall into its *other* Rooms as new results (the `also in …` secondary line is display text, not a hop), no traversal through Junctions into neighbouring Walls, no Scene Content unless it directly matches.

`Gallery B`:

```
Gallery B
Walls in Gallery B (7)
  W031        also in Gallery A
  W044        also in Gallery A, +1      ▸ D007
  …
▸ Assigned Layout Objects (3)
▸ Boundary Junctions (7)                 [Show]
```

**Retrievability invariant:** every relationship the Hierarchy renders — as a row, a secondary line, a section, or a count — is indexed, so a query on either end of that relationship returns the other end. This is what closes the "W044 says Gallery B but searching Gallery B doesn't find it" defect by construction rather than by patch.

## 10. Walls filter — final presentation

**Single dropdown.** It is calmer than chips at 268 px, its header always states the active projection, and the useful facets are a partition (multi / single / none) that single-select expresses honestly.

```
← Hierarchy
Walls (200)          All Walls ▾

   All Walls
   In multiple rooms
   In one room
   No room participation
   With openings
```

- Filter state lives in the current history entry; not persisted, not history-pushing.
- Resting rows under `All Walls`: ID only, plus `▸ n opening` where applicable. **No participation metadata on 200 rows** — the question isn't being asked there.
- Under `In multiple rooms`, rows gain the secondary line `in Gallery A, Gallery B, +1`, because that filter *is* the question. Under `No room participation`, no secondary line (nothing to say). The cost is paid only when the user opts in.
- Junctions page: no filter for P23.6d. Openings page: `All Openings ▾ / Doors / Windows` only if type is authoritative.

## 11. Junctions in Room context — final

**Keep the calmer form:**

```
W014
W031
W044
  Ends  J021 · J022
…
▸ Boundary Junctions (6)
```

Reasons: interleaving doubles the row count and demotes Walls, which are what people read a room by; adjacency is already implied by authoritative boundary order; and when #29 lands, Junction dragging happens on the canvas, not in a list, so the list needs to *reveal* a selected Junction (which it does via `Boundary Junctions` auto-disclosure), not spatially diagram it. Junctions are presented as structural control points — `J022 · 3 walls`, never diagnostic language. If interleaving is ever wanted, it becomes a view toggle later, not the default now.

## 12. Inspector / navigation separation — confirmed

`Navigator: Gallery A · Selected: W092 · Inspector: W092` is fully valid. Entering a page never selects; Back never selects; the Inspector changes only when canonical selection changes.

## 13. Manipulation stress — confirmed, with the selection caveat

Navigator is a projection keyed by canonical ID: pages, history entries, disclosure state and highlight all key on IDs, never row index. Junction moves, Wall moves, boundary membership changes, splits, Opening rebases and Undo surface as row diffs on the current page and, at most, a strip appearing or disappearing. A new fragment after a split renders collapsed with its own deterministic reference; the Navigator makes **no** selection-transfer decision — it renders whatever selection the canonical mutation/reconciliation contract leaves in place, including "nothing selected".

## Blockers

**None that prevent planning.** Four inputs must be confirmed authoritative during P23.6d planning, because the design relies on them existing rather than being invented:

1. Deterministic short display references (`W044`, `J022`, `D007`) derivable from canonical IDs.
2. An explicit Room ↔ Layout Object association field (else the section is omitted, not approximated).
3. Opening type (Door/Window) as model data (else the Openings page is one flat list).
4. Whether any Camera-domain flow currently depends on `Camera Flow` living in the Scene Hierarchy.

None of these changes the model; each only toggles a section or a filter on or off. The product semantics are settled.
