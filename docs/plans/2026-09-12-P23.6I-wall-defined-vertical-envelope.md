# P23.6I — Wall-defined vertical envelope

**Parent:** [P23 Layout Depth — minimum useful Build set](2026-09-07-P23-layout-depth-minimum-build.md).

**Placement:** after the P23.6H implementation work and **before PR #25 merges**,
and before P23.6a / P23.6b. P23.6I is a **forward amendment to P23.6H**, not a new
schema generation: H and I together are the single vertical-model cutover that
reaches `main` as format 5.

**Status:** `implemented` (2026-09-12). See §Implementation record.

**Depends on:** P23.6 canonical Wall selection + Inspector; **P23.6H**
(authoritative `LayoutWall.height`, host-Wall Opening fit, mesh parity, exact
Height planner + history); P23.0/P23.8 wall-first schema, compiler and Room
reconciliation; P23.9 segment-first continuous Wall/Partition authoring.

**Blocks:** P23.6a (Room Unit Move); P23.6b (architecture hierarchy + Inspector
reconciliation); P23.7 (integration closeout).

**Supersedes:** the earlier P23.6I proposal memo (deleted; git history preserves
it) and, before merge, the specific P23.6H decisions listed in
§Relationship to P23.6H.

**Amended 2026-09-12 — pre-Compatibility-Baseline decision (review).** Wall-first
`formatVersion: 4` is **not** migrated. That generation did reach `main` before
this branch, but reaching `main` does not by itself create a backward-compatibility
obligation before the Compatibility Baseline (`docs/north-star.md` →
*Development-stage schema compatibility*). This slice therefore recognizes exactly
**one** wall-first version (`5`): no historical types, no version-aware Floor
parser, no normalization, no `migratedFromVersion`. The rejected alternatives
below are retained as design history, marked where they were superseded.

---

## Why this slice exists

P23.6H correctly made `LayoutWall.height` the authoritative physical height of a
Wall, and moved Wall extent, Opening fit, mesh parity and Height editing onto the
canonical path. It deliberately retained `floor.height` as four things at once:

1. a hard upper bound on `LayoutWall.height` (`0 < height <= floor.height`);
2. the Wall birth default;
3. the source of the Room ceiling elevation (`floor.elevation + floor.height`);
4. the compiled Floor/storey extent (`CompiledFloor.height`).

Reviewing the result surfaced two problems.

**First, the bound is effectively immutable.** Wall-first documents have no
Floor-height editor anywhere: the only `Floor height (m)` inputs in the app sit
on the **legacy Room-owned** Inspector panels (`EditorInspector.svelte`,
`selectedLayoutFloor`, derived through `project.layout.floors`), and their handler
ends in `updateLayoutRoomFields()` → `floors[…].height`. A wall-first document has
no `floors` array, so that input never renders and `floor.height` can only arrive
from the new-project boot, legacy migration or import. A creator therefore cannot
author a Wall taller than the storey, and cannot raise the storey either.

**Second, retaining it keeps a storey-first vertical authority inside the
canonical model.** That is exactly the Room-first residue P23 has spent ten
slices retiring: the enclosure should be defined by its Walls, not by a
document-wide number.

P23.6I completes the cutover:

```text
legacy storey height
    ↓ migration only (one conversion, then it is gone)
per-Wall height
    ↓
canonical physical Walls
    ↓
derived flat Room ceiling
```

Because PR #25 is unmerged, format 5 has **not** become a released canonical
contract. P23.6I therefore does not invent format 6 or 7 and does not preserve
H's Floor-capped semantics as a persisted generation; it replaces those semantics
before the format-5 contract reaches `main`.

## Product outcome

A creator can author, in one canonical model:

- a 1.2 m display Wall;
- an ordinary ~3 m boundary Wall;
- a 4 m or taller Wall;
- adjacent Rooms whose derived ceilings differ;
- a freestanding Wall taller than the Rooms near it.

No global storey height blocks any of it, and no Floor-height control is needed or
added. Plan stays X/Z authoring: Height is exact Inspector authoring that appears
in 3D, never a Plan Y gesture.

## Approved semantic decisions

### D1 — `LayoutWall.height` is the sole Wall vertical authority

```text
finite
strictly > 0
no global upper bound

bottomY = floor.elevation
topY    = floor.elevation + wall.height
```

`WALL_HEIGHT_EPSILON` remains, used only for equality/derivation comparisons and
the Opening-fit boundary — never as a cap tolerance. Opening fit stays host-Wall
based:

```text
opening.sillHeight + opening.height
  <= hostingWall.height + epsilon
```

No clamping anywhere: a violating value rejects.

**Message provenance comes from source presence, never numeric equality.** The
shared geometry validator currently infers which rule applied by comparing
`heightLimit === floor.height`. That is wrong whenever a wall-first Wall's height
happens to equal the legacy Floor height: the Opening is still constrained by its
**hosting Wall**, and must say so.

```ts
const wallHeightLimit = openingHeightLimitBySegmentId?.[opening.segmentId];
const heightLimit = wallHeightLimit ?? floor.height;
const usesWallHeight = wallHeightLimit !== undefined;
```

The message is chosen from `usesWallHeight` (legacy room compiler → Floor message;
wall-first compiler → hosting-Wall message), and the fit check is skipped only
when neither limit is known. A regression must pin the numerically-equal case:
`wall.height === legacy floor.height` still names the Wall on the wall-first path.

### D2 — the canonical Floor carries elevation, not height, and the types are split

```ts
type LayoutWallFirstFloor = {
  id: string;
  name: string;
  elevation: number;
};

type LayoutDocumentWallFirst = {
  units: 'meters';
  formatVersion: typeof LAYOUT_WALL_FIRST_FORMAT_VERSION; // 5, not `4 | 5`
  floor: LayoutWallFirstFloor;
  junctions: LayoutJunction[];
  walls: LayoutWall[];
  rooms: LayoutWallFirstRoom[];
  openings: LayoutWallOpening[];
  objects: LayoutObject[];
};
```

`floor.elevation` stays authoritative for Wall bottoms and the Room floor plane.
`floor.height` is absent from the current canonical schema, and **no replacement
Floor-level vertical scalar is introduced** (see D8).

**There is no historical-type split.** The first draft of this plan kept
`PreHWallFirstFloorV4` / `PreHWallFirstLayoutV4` plus a version-aware Floor parser
so a `4` payload could be normalized to `5`. **Superseded 2026-09-12:** the v4
normalization was dropped (D3), so with one recognized version there is exactly one
document type — no `height?: number` compatibility variant, no version-tagged parse
union, and no downstream `if (layout.formatVersion === 4)`.

```ts
export const LAYOUT_WALL_FIRST_FORMAT_VERSION = 5 as const;
export const KNOWN_LAYOUT_FORMAT_VERSIONS = [LAYOUT_WALL_FIRST_FORMAT_VERSION] as const;
```

`KNOWN_LAYOUT_FORMAT_VERSIONS` keeps its job as the single fail-closed list — its
only member is now the current version — so an unrecognized `formatVersion` still
fails by name rather than by shape.

### D3 — one recognized version: 5, with no v4 migration

```text
version 5:
    the only recognized wall-first version
    Wall height finite, strictly positive, unbounded
    floor.height key forbidden (unknown_key)
    Room ceiling is Wall-derived

every other declared version (including 4):
    unsupported_format_version
    no decoder, no normalization, no writer path
```

`LAYOUT_WALL_FIRST_FORMAT_VERSION = 5` (unchanged);
`KNOWN_LAYOUT_FORMAT_VERSIONS = [5]`. There is no 4 → 5 cutover, no canonical
format 6 or 7, and never a `[4, 5, 6, 7]` ladder.

**Rejected alternative, kept for the record.** The first draft normalized `4` → `5`
(Wall heights rewritten from `floor.height`, Floor scalar dropped) so old projects
kept their appearance. That mechanism is sound, and it was rejected on **policy,
not feasibility** — this slice runs before the Compatibility Baseline, so
development-era data is disposable and a version that reached `main` during active
development is still development data. Two consequences decided it:

1. A rewrite is only *approximately* faithful: it reproduces the visible result for
   the files that pass through the normalizer, but a v4 payload that legitimately
   meant `floor.height` as a storey envelope would be reinterpreted by any path
   that did not. Refusing the version is honest where silently migrating it is not.
2. A permanent decoder is maintenance for data that is expected to be reset.
   `docs/north-star.md` forbids adding exactly this kind of machinery by default
   before the baseline.

A `4` payload therefore fails identically on every boundary — strict codec,
compatible decode, canonical writer, session handoff — with
`unsupported_format_version`, and it fails **before** structural parsing so the
diagnosis names the version rather than a pile of shape complaints about fields
that are correct for `5`.

### D4 — legacy Room-owned migration

Legacy documents keep their own `floors[].height` semantics on their
compatibility path; nothing about the legacy read/write shape changes.

Lossless legacy → wall-first migration:

```text
legacy floor.height    → each produced canonical Wall.height
legacy floor.elevation → canonical floor.elevation
canonical floor        → { id, name, elevation }   // no height key
```

The legacy storey value has completed its conversion job and does not survive as
canonical wall-first truth. All existing migration behaviour is otherwise
unchanged: multi-floor rejection, curve/arc handling, portal/adjacency rules,
conflict rejection and deterministic IDs.

### D5 — Wall creation: one named default, a core birth rule, and editor run state

One canonical creation constant:

```ts
export const WALL_AUTHORING_DEFAULT_HEIGHT = 3;
```

It is a **creation default only** — not an architectural envelope, not a
validation cap, not a Room height, not a Floor height, and nothing but the initial
value of a newly authored Wall. It is the only Wall-birth literal allowed
anywhere.

**The durable birth meaning belongs to the core, not to the editor.** UI and
headless/domain callers must execute the same semantic operation; a rule that
lives only in the editor would give a headless `planWallSegment()` a different
result for the same document topology. So there are two layers, with the split
stated explicitly:

```text
layout-core (pure, document-only — the durable rule)
    planWallChain / planWallSegment → resolveWallBirthHeight(document, startJunctionId?, explicitHeight?)

editor session (transient, never persisted)
    wallChainRunHeight → continuation inside ONE active draw run
```

**Core rule — `resolveWallBirthHeight()`** (name may vary; pure; deterministic from
canonical topology, never iteration order):

```text
explicitHeight
    → explicitHeight

startJunctionId is null (isolated / new start)
    → WALL_AUTHORING_DEFAULT_HEIGHT

existing start Junction, exactly one unique incident Wall height
    → that height    (covers one incident Wall and several identical ones)

existing start Junction, more than one distinct incident height
    → WALL_AUTHORING_DEFAULT_HEIGHT

existing start Junction, zero incident Walls
    → WALL_AUTHORING_DEFAULT_HEIGHT
```

Implementation shape (reuse an existing canonical adjacency/query helper if one
exists rather than re-deriving):

```ts
function uniqueIncidentWallHeight(document, junctionId): number | undefined {
  const heights = new Set(
    document.walls
      .filter((wall) => wall.startJunctionId === junctionId || wall.endJunctionId === junctionId)
      .map((wall) => wall.height)
  );
  return heights.size === 1 ? [...heights][0] : undefined;
}
```

`planWallSegment()` resolves the start Junction from its start point through the
same deterministic coordinate match the chain planner already uses (never
`createdWallIds`), then passes the resolved explicit height into `planWallChain`.
**`planWallChain` itself is the bounded compound planner and stays uniform:** it
uses `options.height ?? WALL_AUTHORING_DEFAULT_HEIGHT` for the whole generated
chain and performs **no** per-leg or per-vertex inheritance, because one
Rectangle/Polygon gesture must produce one coherent height.

**Editor session rule — `wallChainRunHeight`.** Owned by
`layout-interaction.ts`, transient, never persisted, never history state:

```text
first segment of a run
    → no explicit height passed; the core rule decides
    → on success: wallChainRunHeight = committed authored Wall height

later segment of the SAME active run
    → the committed wallChainRunHeight is passed explicitly
    → a turn that lands on a mixed-height Junction never overrides it
```

So the durable rule is:

```text
first segment   → core topology-derived birth rule
later segments  → explicit editor run height into the same core planner
```

The editor never invents a second document rule. `Escape`, explicit closure,
cancel, tool switch, view-mode switch, document replacement/import/reset,
Undo/Redo-driven state replacement and every other existing run-reset path must
clear `wallChainRunHeight` together with the rest of the Wall-run state (they
already funnel through `cancelWallChainRun()` / `clearLayoutDraft()`).
Continuation is never inferred from selection, and a mixed-height Junction never
silently resolves to the lower or higher Wall.

**Layering constraint:** `layout-core` must not read Svelte/editor state, and
`planWallChain` must not inspect mutable UI/session state.

**Bounded compound tools.** Rectangle and Polygon remain bounded compound
commands: one explicit height override **or** `WALL_AUTHORING_DEFAULT_HEIGHT`,
uniform for the whole command. No per-leg inheritance inside a single gesture.

**Unchanged inheritance:** Wall split (`planWallSplitAtPoint`) and isolated-Room
duplicate (`planDuplicateIsolatedRoom`) keep copying the source Wall height
exactly.

### D6 — derived flat Room ceiling

For every canonical Room whose boundary Walls resolve:

```ts
roomHeight      = max(room.boundary.map(ref => wallById(ref.wallId).height))
ceilingElevation = floor.elevation + roomHeight
```

Computed once in the wall-first compiler adapter and fed into the existing shared
Room compile path. No `floor.height` fallback. No document-wide Wall max for a
normal Room.

### D7 — degenerate Rooms reject; they never acquire an invented ceiling

**Verified: the current codec does permit `boundary: []`.** `parseBoundaryRefs`
accepts an empty array (it only requires an array whose entries all parse), and no
other codec rule rejects a zero-reference boundary. So this is a real hole, not a
hypothetical one, and the codec **does** need a `room_boundary_empty` rule in this
slice.

Two layers, both required:

- **Canonical codec rule (primary, named).** A wall-first Room with zero boundary
  references rejects:

  ```text
  path    $.rooms[i].boundary
  code    room_boundary_empty
  message A canonical Room boundary must reference at least one Wall
  ```

  Where the boundary array is entirely absent the existing `invalid_type` /
  `missing_field` handling still applies; this rule adds only the empty case. Do
  not duplicate the stronger topology requirement here (>= 3 Walls / a closed
  cycle) unless that is already codec ownership — it is not; face extraction and
  reconciliation own it.
- **Compiler defense-in-depth.** If an internal candidate can still present a Room
  whose boundary Walls do not *resolve*, the wall-first compiler emits an explicit
  blocking issue (code `room_ceiling_undefined`) rather than a ceiling. It must
  **not** manufacture one from `document max Wall height` or
  `WALL_AUTHORING_DEFAULT_HEIGHT`.

Creation defaults belong to authoring. They are never geometry recovery.

### D8 — no Floor-level envelope authority

`CompiledFloor.height` is removed. `CompiledFloor` keeps its identity
(`id`/`cacheKey`), `floorId`, `elevation`, `roomIds` and `bounds3`.

**Do not** replace it with `Floor envelope = max(Room envelopes)`. Wall-first
permits physical Walls without Rooms, so a room-only maximum would under-report
real architecture. Aggregate spatial extent stays where it already is: compiled
physical Wall bounds, Room floor/ceiling bounds (`roomBounds3`), LayoutObject
bounds and the existing aggregate `CompiledFloor.bounds3` /
`CompiledLayoutGeometry.bounds` (which already expand over canonical physical
Walls so roomless Walls are included).

Every consumer of the removed scalar must be migrated to the datum it actually
needs:

```text
needs a Wall top            → CompiledPhysicalWall.height / bounds3
needs a Room ceiling        → CompiledRoom.ceilingElevation
needs the Floor base        → CompiledFloor.elevation
needs aggregate extent      → bounds3 / CompiledLayoutGeometry.bounds
```

### D9 — topology purity

Wall height remains outside face extraction. A height change must not create,
retire, split or merge Rooms, must not alter Junction connectivity or Wall
`role`, and must not change Wall, Junction, Opening or Room identity. P23.6a later
moves Rooms while preserving Wall heights exactly.

### D10 — compatibility and publication isolation

Stored format-4 publications remain immutable bytes; the visitor cold runtime
continues through compatible project/Layout decode before any canonical compile;
there is no visitor-specific normalization branch. A canonical Save after a
compatible load writes format 5. Canonical writers keep failing closed on a raw
pre-H payload — the writer rules H shipped (`serializeWallFirstLayoutDocument`,
`validateWallFirstProject`, `wallFirstCanonicalProjectFormatIssue` in
`serializeProject`, and the editor session handoff) stay in force, with the
current-format value unchanged at 5.

### D11 — a flat ceiling is not watertight-volume semantics

```text
boundary Wall heights = [4, 2, 2, 2]
→ Room ceiling plane at 4
→ the three 2 m Walls stay physically 2 m
→ the vertical band above them is intentional under this minimum model
```

Name the semantics accurately everywhere: a **derived flat Room ceiling plane**.
This slice does not infer wall-top infill, stepped ceilings, sloped ceilings,
per-edge ceiling profiles, watertight 3D volumes or multi-storey Walls.

## Authority boundaries

- `LayoutDocument` owns canonical architecture; `SceneDocument` is untouched.
- `floor.elevation` and `wall.height` are the only Layout vertical authorities.
- One `compileLayoutGeometry()` path feeds Plan, editor 3D, museum and visitor.
- One Room reconciliation path; no second geometry truth.
- No hit-testing, selection, gizmo or Camera changes.
- One Layout history system (`layoutMutationRunnerFor` + guarded transactions).
- Editor and visitor consume compiled output; no renderer derives a Room ceiling
  or Wall top from source document fields, and no `{ elevation: 0, height: 3 }`
  compatibility fallback survives in a canonical renderer path.
- Plan remains X/Z authoring: no Y gesture is added.

## Implementation stages

One plan, one format bump (none — the version stays 5), ordered internal stages.

### I1 — schema + compatibility contract

- `LayoutWallFirstFloor` loses `height`; `LayoutDocumentWallFirst.formatVersion`
  narrows to `5` (the constant's type, not `4 | 5`).
- One Floor key set, `id`/`name`/`elevation`, with `height` rejected as
  `unknown_key`. No historical Floor type and no version-aware Floor parser
  (amendment); `KNOWN_LAYOUT_FORMAT_VERSIONS = [5]` and no `migratedFromVersion` on
  the validation result or the compatible decode.
- `validateWallFirstLayoutDocument()` returns the canonical v5 type in every
  success case. A `4` payload fails inside `readFormatVersion()` as
  `unsupported_format_version`, before any structural parsing, so the diagnosis is
  the version rather than shape noise.
- The canonical **writers** keep calling `wallFirstCanonicalFormatVersionIssue()`
  and fail closed. That gate is current-format strictness rather than a
  compatibility branch — it compares against the current version, never against
  `4` — so it stays exactly as H shipped it, and the editor's cloud-save handoff
  keeps sharing it.
- The tolerant-read boundary that remains is the **legacy Room-owned** one (no
  declared version): publication and session reads still validate through
  `validateProject()`, so legacy documents keep loading. See
  §Legacy Room-owned adapter.
- Add the `room_boundary_empty` codec rule (D7).
- Fix the shared Opening-fit **message provenance** to use source presence, not
  numeric equality (D1).
- `createEmptyWallFirstLayoutDocument()` emits the final v5 Floor.
- Migration emits final v5 directly (`floor` record without `height`).

**Acceptance:** a payload declaring `4` fails as `unsupported_format_version` on
**every** boundary (strict codec, compatible decode, canonical writer, session
handoff) and is never rewritten in place; a `4` payload that is otherwise a valid
current document still reports only the version; a v5 payload containing
`floor.height` rejects with `unknown_key` at `$.floor.height`; the current empty
fixture carries no Floor `height`; legacy Room-owned migration still preserves the
previously visible extent and writes v5.

### I2 — unbounded Wall validation

- Rule becomes `0 < wall.height` (finite, strictly positive).
- Remove `wall_height_exceeds_floor`, the Floor-envelope messages, the
  `planExactWallHeight` cap check, `canonicalWallBirthHeight(floor)` and the
  `invalid_floor_height` Wall-birth rejection; `WALL_CHAIN_DEFAULTS` keeps only
  thickness.
- Keep finite/positive validation and the shared epsilon (still used for the
  Opening-top equality boundary).
- `planExactWallHeight()` accepts any finite positive value, including values
  above any former Floor height; only a hosted Opening that no longer fits blocks
  a *lowering* edit, atomically.

**Acceptance:** a 6 m Wall validates; zero/negative/NaN/infinity reject; a 6 m
Wall with a fitting Opening compiles; lowering a Wall below a hosted Opening's
top still rejects atomically.

### I3 — creation semantics

- Add `WALL_AUTHORING_DEFAULT_HEIGHT` (the only Wall-birth literal).
- Add the pure core rule `resolveWallBirthHeight(document, startJunctionId,
  explicitHeight?)` and have `planWallSegment` resolve its start Junction
  deterministically and pass the resolved height explicitly into `planWallChain`.
  A headless `planWallSegment()` call and the editor's first segment must produce
  the same result for the same document.
- `planWallChain` becomes explicitly the **bounded compound** planner:
  `options.height ?? WALL_AUTHORING_DEFAULT_HEIGHT`, uniform for the whole chain,
  no per-leg inheritance.
- Add `wallChainRunHeight` to the existing continuous Wall/Partition state in
  `layout-interaction.ts` with the D5 lifecycle: set from the first committed
  segment's authored height, passed explicitly for later segments of the same run,
  cleared on every existing run-end/cancel/reset path (they all funnel through
  `cancelWallChainRun()` / `clearLayoutDraft()`).
- The commit result carries the committed Wall's authored height so the viewport
  can seed the run state without re-reading the document.
- `captureWallChainRun()` / `restoreWallChainRun()` (rejection retry) include the
  run height.
- Rectangle/Polygon (`commitWallChain` with `close: true`) stay uniform.

**Acceptance (tests named in the test plan):** isolated run → default; start on a
single 4 m incident Wall → 4 m; start on `[4, 4]` → 4 m; start on mixed `[4, 2]` →
default; later segments inherit through turns; Escape/new run does not leak the
previous height; closure clears it; Undo/Redo never depends on stale tool state;
Rectangle/Polygon uniform; split/duplicate preserve the source height.

### I4 — compiler Room ceiling

- The wall-first adapter derives each Room's `max(boundary Wall heights)` once and
  passes it as an explicit per-room derived ceiling into the shared Room compile
  path (the existing optional-`CompilerRoomSource` pattern, so the legacy source —
  which passes nothing — stays byte-identical).
- `compileRoom` uses the derived value for `ceilingElevation`, Room wall
  `bounds3` and room bounds; physical Walls keep compiling independently and
  exactly once.
- Degenerate Room boundaries produce a blocking issue per D7.

**Acceptance:** all-3 m boundary → ceiling 3; all-1.2 m → ceiling 1.2;
`[4, 2, 2, 2]` → ceiling 4 with the 2 m Walls' bounds still 2; adjacent Rooms
derive different ceilings; a shared Wall participates in each Room's max; a pure
height edit re-derives the ceiling with no topology or identity change.

### I5 — remove compiled Floor height and migrate its consumers

- Remove `CompiledFloor.height`; the Floor record's `cacheKey` drops it and keys

## Mutation / history behavior

- One successful Height edit → exactly one Layout history entry through the
  existing guarded transaction; Undo/Redo restore the exact previous height and
  the recompiled ceiling/geometry.
- Rejected edits (unknown Wall, non-finite, non-positive, Opening-invalidating),
  blank input and no-ops write zero entries.
- Wall creation commits stay one entry per segment/chain as today; the run-height
  state is editor state and never enters history.

## Failure / rejection behavior

| Condition | Result |
|---|---|
| Wall not found | reject `unknown_wall`, message names the ID |
| non-finite / ≤ 0 / blank | reject (planner for non-finite, presentation for blank) |
| hosted Opening no longer fits | reject atomically; Wall, Opening and history unchanged |
| candidate fails codec/topology/compile | reject; no mutation, no history |
| Room boundary empty / unresolved | reject at the codec, or compiler blocking issue `room_ceiling_undefined` — never a manufactured ceiling |
| raw pre-H payload at a canonical writer | reject `unsupported_format_version` |
| v5 payload declaring `floor.height` | reject `unknown_key` |

## Compatibility / migration consequences

- **Format:** 5 is the only recognized version and the only canonical one. A `4`
  payload is rejected on read and on write; no v6/v7 symbol, fixture, doc or
  comment may exist, and no `4` decoder may be reintroduced.
- **Mutable projects:** a project saved on this branch is v5 from the start. A
  project saved by a build that still wrote v4 is **not** loadable — accepted, since
  it is pre-baseline development data (D3).
- **Immutable publications:** stored bytes are never rewritten, and no
  normalization happens in the visitor cold path. A stored legacy (Room-owned)
  release still loads through the tolerant read; a stored v4 wall-first release no
  longer decodes, which is the same disposable-data decision as above.
- **Migration:** legacy output is v5 directly, with migrated Wall heights equal to
  the legacy storey height and no canonical Floor height.
- **Writers:** the fail-closed current-format rules H shipped stay in force; the
  gate's expected value is still 5.
- **API publication:** the publish/compile path remains P23.7's; this slice does
  not change `apps/api`.

## Deterministic identity requirements

- Wall/Junction/Opening/Room IDs are never affected by a height edit or by the
  derived ceiling; a rejected v4 payload is never rewritten, so no decode path
  allocates IDs or mutates its input.
- No allocation occurs during a height edit or during a decode.
- Room ceiling derivation is a deterministic `max` over the resolved boundary
  cycle, independent of boundary traversal order or Wall document order.

### Final rules

- **Wall birth** — first segment of a run: explicit height, else the unique
  incident height at the exact-coordinate start Junction, else
  `WALL_AUTHORING_DEFAULT_HEIGHT` (3), which is the only Wall-birth literal.
  Continuation inside one run: the editor's transient `wallChainRunHeight`,
  passed explicitly and cleared with the rest of the run state on every run-end
  path. Rectangle/Polygon stay one uniform bounded command.
- **Room ceiling** — `floor.elevation + max(boundary Wall heights)`, a derived flat
  plane; shorter Walls stay physically short and no infill is generated.
- **No Floor vertical scalar** — `CompiledFloor.height` is gone and nothing
  replaced it; aggregate extent comes from actual bounds, so roomless physical
  Walls still count.
