## Outcome

P23 closes only when wall-first authoring, exact identity/history, migration/compatibility, Preview and Publish all work through one canonical Layout compiler/runtime path without regressing Scene/Camera/editor/visitor boundaries.

P23.7 is **not** the owner of topology robustness anymore. H3 topology is foundational in P23.8. This slice owns whole-product integration and final regression/compatibility gates.

P23.7 explicitly depends on P23.6H / P23.6I / P23.6a / P23.6b / P23.6c / P23.6d / P23.6e: final closeout validates the authoritative per-Wall height (P23.6H) **as amended by P23.6I** — no canonical `floor.height`, unbounded Wall heights and Wall-derived flat Room ceilings — together with the single format-5 contract (the pre-baseline policy refuses the superseded wall-first `4` by name rather than migrating it), the isolated Room-unit move (P23.6a), the actual P23.6b hierarchy/Inspector — ownership-truthful rows for document-global Walls/Openings/LayoutObjects, no duplicated shared Walls — rather than the transitional read-only bridge P23.6 ships with, the one-planner canonical Wall deletion (P23.6c, endpoint-scoped Junction cleanup), the **complete wall-first Room lifecycle** (P23.6d — canonical Room metadata/name editing and the guard-railed `planRemoveRoom` retirement through P23.8 reconciliation), and the final P23.6e Hierarchy/product-semantics UI overhaul. P23.7 retains its own broader gates: integrated Save/Load proof, Preview, immutable publication behavior, canonical Save/Load/Publish acceptance plus internal legacy-dependency smoke (see Compatibility scope), visitor isolation and final whole-product regression.

P23.7 also carries the **open deferral** registered in the umbrella's Deferred
capability register: **canonical wall-first 3D Wall/Opening picking +**
**highlighting** is deliberately not implemented by P23.6H or P23.6b. P23.7 must
restate it as an explicit open deferral in its closeout report and must not mark it
complete merely because Plan selection, Inspector panels and hierarchy continuity
work.

One formerly listed deferral is **closed by [P23.6d](2026-09-13-P23.6d-canonical-room-lifecycle-completion.md)**:

- **wall-first Room rename / Room metadata** — P23.6d ships the canonical
  `planRoomMetadataUpdate` (name, floor/ceiling thickness) and the guard-railed
  `planRemoveRoom` (retirement through P23.8 reconciliation, never a record
  splice), so P23.7 accepts the complete Room lifecycle instead of carrying
  this deferral. (The legacy `updateLayoutRoomFields`/`deleteLayoutRoom`
  rejection paths remain the untouched compatibility behavior.)

One previously listed deferral is **closed by design**: wall-first **Floor-height
editing / propagation**. P23.6I removes `floor.height` from the canonical schema,
so there is no Floor-height quantity left to edit or propagate and no
Floor-height control is added for wall-first or legacy. P23.7 records this as
resolved, not open.

Wall-first version acceptance is v5-only (H finalised by I, pre-baseline
policy): P23.7 must prove a fresh wall-first project saves, reloads and
publishes as format 5 end-to-end — Save/Load, Preview, immutable publication
and cold visitor. Wall-first `formatVersion: 4` is unsupported development
data, not a migration source: it is refused by name on every boundary and
there is deliberately **no** v4→v5 migration acceptance, no stored-v4
publication gate, and no "compatible-load then Save as v5" proof. The
tolerated read boundary that remains is the version-less legacy Room-owned
shape (see Compatibility scope below).

*Development-stage schema compatibility*): development-era schemas are
disposable unless a plan names an explicit durable consumer, and a retained

conflict-read-only / curves / portal semantics / legacy packages / legacy
publish flow):

```text
→ retire the legacy Room-owned stack
```

## Manual owner-facing Build fixture

Start from an empty Floor and complete this flow:

```text
1. draw an outer boundary-Wall loop (click-click per segment; second click commits each Wall; Escape cancels only the active preview)
2. verify one persistent Room appears
3. draw a complete internal boundary divider (same per-segment commit; do not use a Commit button)
4. verify the original Room becomes two Rooms with H5 identity rules
5. add one Door to the shared Wall
6. verify one physical Opening/cut serves the shared Wall
7. draw one interior Wall, then disable **Defines room boundary** (same per-segment commit; Escape ends the run)
8. verify physical Wall appears but Room count does not change
9. select each canonical Wall and set exact Length/Angle in the Inspector (reuses P23.1 precision/topology/history paths)
10. use non-default grid + semantic snaps
11. add Column + Platform/Plinth
12. align a supported Layout object to bounds/Wall
13. repeat supported Opening/object records
14. duplicate one eligible isolated Room/subgraph and edit it independently
15. place/retain a Scene object outside every Room
16. place/retain a Camera node outside every Room
17. edit/move architecture and verify Scene/Camera world placement does not move implicitly
```

Exercise Plan at representative zooms and 3D in the same project.

## Legacy Project migration acceptance

nothing more). No new migration behavior, no product-level
backward-compatibility gate, no wall-first v4 migration acceptance. Full

### Lossless migration

- isolated legacy Room preserves Room ID;
- compatible shared straight boundary collapses to one Wall;
- reversed boundary normalizes opening offset correctly;
- compatible paired opening records collapse deterministically;
- Scene entity world position preserved;
- Scene entity arbitrary world rotation preserved;
- clusters preserve grouping/member IDs without Room spatial ownership;
- Camera eye + target preserved;
- Camera path anchors/waypoints/view-key targets preserved;
- migrated project validates before install;
- migration establishes editor history baseline rather than user-visible migration commands.

### Trustworthy frame context

- legacy full Project uses its own decoded Layout Room frames and succeeds;
- standalone legacy Scene + explicitly supplied trusted frame mapping succeeds;
- standalone legacy Scene + merely matching IDs in current Project does **not** count as trusted source context;
- standalone legacy Scene without trusted frame context rejects with specific diagnostic;
- wrong/partial mapping rejects before install.

### Double-transform regression

- read-only legacy-compatible Scene resolves through its retained Room frame exactly once for Preview/visitor;
- migrated/new world-local Scene bypasses Room transform resolution;
- same authored placement renders at the same world matrix before/after lossless migration;
- visitor and editor Preview agree.

### Wall/Junction/Opening selection cutover acceptance

path remains authoritative.

  (extended by P23.6, accepted here) — no second selection store, no parallel
  hit-test path, no renderer-local selection model;
- a legacy `(roomId, segmentId)` selection cannot outlive the cutover: it is

- canonical Wall/Junction selection, hover and editing affordances behave

- P23.3's minimal canonical Opening target remains the Opening authority once

### Wall-drawing UX acceptance (segment-first)

P23.7 owns acceptance proving the ratified P23.9 segment-first Wall drawing UX:

- **second click commits the Wall.** A normal straight Wall is committed by the
  second click; there is no separate Commit segment button in the normal drawing
  flow. Each click after the first completes the current Wall and establishes the
  start of the next candidate;
- **Escape cancels only the active transient candidate/run.** It clears the
  preview, creates no history entry, and leaves committed Walls intact. The Wall
  tool remains selected unless existing editor convention strongly requires
  otherwise. Escape must never remove committed Walls;
- **no redundant Commit/Cancel action bar is required.** The large bottom-right
  Wall-drawing action bar whose only purpose is Length / Commit / Cancel is
  removed. Cancel draft is keyboard-first via Escape and must not keep a large
  persistent cancel button that blocks the Plan canvas / XZ axis overlay;
- **successful commits do not emit noisy implementation-count messages.** Text
  such as `Committed wall`, `Committed 4 walls + 1 room`, or similar
  implementation-oriented commit counts is removed. Successful authoring is
  communicated primarily by the resulting geometry/Room appearing in Plan. Keep
  explicit status messaging for rejection, invalid geometry, conflicts, or other
  cases where the user needs explanation;
- **invalid/rejected operations still surface useful diagnostics.** Rejection
  reasons, invalid topology, and conflicts remain visible on the plan surface;
- **exact selected-Wall Length/Angle edits reuse canonical precision/topology/history paths.**
  Select a canonical Wall; the Inspector exposes exact Length and Angle operations
  alongside Thickness and Height. These edits reuse the existing canonical
  P23.1 precision operations; they do not add a stored `wall.length` field or
  bypass Junction/topology reconciliation. Every exact edit runs normal
  validation, topology/Room reconciliation, Opening-fit checks, compiler
  validation, and one deterministic history transaction;
- **Plan UI does not obscure the XZ axis or important viewport affordances.**
  The removed action bar and keyboard-first cancel must not leave a persistent
  control that blocks the canvas or axis overlay.

### Boundary/partition behavior acceptance

P23.7 owns proving the Wall boundary/partition semantic behavior:

- ordinary Wall drawing defaults to room-bounding (`role: 'boundary'`);
- drawing a supported Wall across an existing Room can split it into two Rooms
  through canonical P23.8 reconciliation;
- disabling **Defines room boundary** on a room-bounding Wall keeps the physical
  Wall while reconciling affected Rooms correctly — the Wall stops participating
  in Room face extraction;
- enabling **Defines room boundary** on a non-room-bounding Wall can create/split
  Rooms where supported topology is formed;
- every role change uses the one canonical Layout operation: structural
  validation → P23.8 topology/face extraction and persistent Room
  reconciliation → Opening/portal validation and remap → compiler validation →
  one deterministic Layout history transaction;
- Wall/Junction/Room/Opening IDs follow the existing deterministic reconciliation
  rules;
- Opening host identity and fit remain valid;
- portal relations are preserved, remapped, cleared, or rejected according to the
existing portal contract;
- ambiguous/unsupported role changes reject atomically;
- one role change produces one history result;
- invalid/no-op changes produce none;
- Undo/Redo restores the exact prior Wall role, Room identities, topology, Opening
  state, and portal state;
- Save/Load preserves the authored Wall role;
- no separate Partition authoring UI remains authoritative.
