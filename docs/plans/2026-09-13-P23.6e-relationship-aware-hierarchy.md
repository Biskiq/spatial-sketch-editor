# P23.6e — Relationship-aware Scene Hierarchy

**Status:** `implementation-ready — frozen` — planning-only reconciliation, 2026-09-13; final four-point precedence/search/count reconciliation incorporated.  
**Depends on:** P23.6 canonical Wall/Junction/Opening/Room selection; P23.6a Room-unit move; P23.6b ownership-truthful hierarchy + canonical-only Inspector; P23.6c canonical Wall deletion; P23.6d canonical Room lifecycle.  
**Blocks:** P23.7 integration closeout.  
**Scope authority:** [`P23.6e-directive.md`](P23.6e-directive.md). This plan implements those settled semantics; it does not reopen the UX proposal.

## Outcome

Replace the canonical wall-first Scene-domain accordion tree with a page-based,
relationship-aware Navigator. It provides calm root inventory, Room context,
global Architecture indexes, bounded global search, current-page reveal, and a
factual pinned-selection strip without changing canonical selection, document
history, geometry, topology, Scene ownership, or Camera behavior.

The Scene-domain root is:

```text
HIERARCHY
Search…

Rooms

ARCHITECTURE
Walls
Openings
Junctions

PLACED CONTENT
Layout Objects
Scene Content
```

`ARCHITECTURE` and `PLACED CONTENT` are presentational eyebrow labels only:
not focusable, not selectable, not collapsible, not persisted, not destinations,
and not owners. Each named row beneath them opens one page with one click.

P23.6e is planning and implementation of the Scene Navigator only. The existing
`Scene | Camera` axis remains the sole domain authority. The Camera hierarchy is
not redesigned.

## Non-goals

- no Wall/Junction direct manipulation, geometry editing, topology/face extraction,
  Room reconciliation, or selection-transfer policy;
- no Camera UX, camera graph, route, motion, or timeline changes;
- no new Layout/Scene persistence or schema fields;
- no Scene-content containment or Room ownership inferred from coordinates,
  bounds, point-in-polygon, proximity, or render geometry;
- no cross-document mutation, combined selection owner, drag/drop, or common
  `PLACED CONTENT` mutation path;
- no replacement for editor Undo/Redo and no Navigator keyboard binding that
  conflicts with it;
- no visitor/relic work and no imports from this editor-only Navigator into
  `/museum` or `/p/:publicationId` chunks.

### Reveal, disclosure, and scroll today

- `layoutSelectionRevealTarget()` maps canonical Layout selection to one root
  target; `layoutSelectionAncestorRoomId()` preserves the legacy qualified path.
- `UnifiedProjectTree.svelte` watches `activeSelection.active`. It opens root
  booleans, expands a host Wall for an Opening, and calls `scrollIntoView()` on

- The current code treats “filtered out” specially with `hiddenRevealTarget` and
  `Selection hidden by filter / Reveal / Clear filter`. It does not distinguish
  off-screen-but-represented from excluded-by-page, Room context, filter, or
  search. Junction reveal deliberately opens only Architecture and does not
  expose a row.
- `treeExpandedRoomIds` / `treeExpandedClusterIds` live in
  `EditorSessionState`; canonical Architecture booleans live locally. There is
  no Navigator back stack and the rail's outer `<aside>` currently owns scroll.

P23.6e replaces `layoutSelectionRevealTarget()` as the canonical reveal decision
with page-projection representation lookup. Keep the helper during the migration
for legacy compatibility and existing tests; remove canonical call sites only
after representation tests cover the same cases.

### Search/filter today

`filterUnifiedProjectTreeModel()` performs case-insensitive substring pruning on
the rendered tree. It preserves ancestors of matching descendants and resolves
cluster member display names, but it is not relationship retrieval:

- a Room-name query does not retrieve its Walls from `boundedRoomIds`;
- Wall participation labels are displayed but not indexed;
- it cannot express direct match versus directly related result;
- it has no bounded traversal rule or Junction summary;
- its query is one transient component string and is not restorable by Back.

P23.6e replaces this function for the canonical Navigator. Retain it only for the
quarantined legacy tree until that compatibility UI is retired.

### Plan hover/focus emphasis today

Hierarchy rows have CSS hover only. There is no Hierarchy → Plan emphasis feed.
Plan already has the correct renderer seam:

- `LayoutPlanViewport.svelte` keeps a local `layoutHover: PlanHitIdentity | null`;
- `buildPlanInteractionProjection(..., hovered)` and
  `plan-render-model.ts` already render hovered Rooms, canonical Walls,
  Openings, Junctions, and Layout Objects without making them selected;
- Scene footprints already have a presentation-only Arrange/bridge hover outline.

P23.6e may bridge row pointer hover **and keyboard focus** through the Navigator
UI store to those existing presentation inputs. It must not use `store.focusRoom`,
camera framing, selection, or a new Plan renderer model. Viewport-local hover wins
while present; Navigator emphasis clears on row leave/blur, page change, and
unmount. Cluster emphasis is row-local only because there is no single canonical
Plan footprint for a cluster; do not invent one.

## Four product gates

### Gate 1 — stable short references (`W044`, `J022`, `D007`)

**Code evidence.** Canonical Layout identities are stable strings in
`layout-wall-first-types.ts`. Allocators create deterministic IDs such as
`wall-chain-1`, `junction-chain-1`, split-derived IDs, and
`opening:door:1`. `formatPlacementLabel()` only title-cases arbitrary IDs.
There is no shared `W044`/`J022`/`D007` formatter, no stable ordinal registry,
and imported canonical IDs may be arbitrary strings.

**Result:** gate unavailable as a general facility.

**Scope effect:** P23.6e uses the safest existing identity presentation:
authored names where present; otherwise `formatPlacementLabel(canonicalId)` with
the raw canonical ID in `title`, accessible name, Advanced/debug, and search.
Examples in this plan use W/J/D shorthand conceptually, not as a promise that
the current ID `wall-chain-1` will be renamed or numbered.

**Fallback:** do not derive ordinals from document/row order because deletion,
split, Undo, or import would relabel unaffected entities. Do not add persistence.
A future display-only helper is acceptable only if it is a pure function of
`{kind, canonicalId}`, collision-safe without document order, and tested across
split/Undo/import. That is not required for P23.6e acceptance.

### Gate 2 — explicit Room ↔ Layout Object association

**Code evidence.** `LayoutObject` in `packages/layout-core/src/layout-types.ts`
has `roomId?: string`; wall-first documents reuse `LayoutObject[]`.
`planExactLayoutObjectTransform()` validates explicit assignment changes;
P23.6a moves assigned objects, P23.8 reconciliation remaps/clears assignments,
and the current Inspector labels the field `Associated Room`.

**Result:** gate available and authoritative.

**Scope effect:** every canonical Room page includes collapsed
`Assigned Layout Objects (n)`, including `(0)`. Membership is exactly
`layout.objects.filter(object => object.roomId === room.id)` in document order.
The header tooltip is `Layout Objects explicitly assigned to <Room name>.`

**Fallback:** retained as a guard in the projection API: if a future supported
document shape lacks the association capability, omit the section rather than
infer it. Never put Scene Content in the Room page.

### Gate 3 — authoritative Opening type

**Code evidence.** Both legacy `LayoutOpening` and canonical
`LayoutWallOpening` require `kind: 'door' | 'window'`; the wall-first codec
validates it; authoring and `nextWallFirstOpeningId()` consume it.

**Result:** gate available and authoritative.

**Scope effect:** the Openings page exposes one calm single-select control:
`All Openings / Doors / Windows`. Rows remain in `layout.openings` order and
show their host Wall. Kind filtering is Navigator UI state only.

**Fallback:** the projection accepts “no authoritative kind facet” and renders
one flat index, but current canonical wall-first documents use the typed facet.

### Gate 4 — Camera dependence on Scene `Camera Flow`

**Code evidence.** `EditorSidebar.svelte` mounts `CameraSidebar` whenever
`domain === 'camera'`; `CameraSidebar.svelte` mounts `CameraFlowPanel` itself.
`UnifiedProjectTree.svelte` is mounted in the opposite branch, yet contains an
unreachable Scene-side `Camera Flow` duplicate. Camera flow selection/history
remain owned by `CameraFlowPanel` and the Camera stores.

**Result:** no current Camera-domain dependency.

**Scope effect:** remove `Camera Flow`, `cameraTourOpen`, camera expansion effects,
`cameraInteractive`, and the `CameraFlowPanel` import from
`UnifiedProjectTree.svelte`. Keep `CameraSidebar` and Camera behavior untouched.
After `CameraSidebar` receives a narrower Environment projection, remove the
unused `cameraTour` field from the Scene hierarchy model and update its tests.

**Fallback:** if implementation finds an untested direct consumer, isolate the
smallest adapter in `CameraSidebar`; do not keep Camera UI in the Scene Navigator
and do not redesign Camera.

## Navigator state (UI-only)

Add `apps/editor/src/lib/editor/app/hierarchy-navigator-state.svelte.ts`, using
the same Svelte 5 class-store pattern as `active-editor-selection.svelte.ts` and
`session-state.svelte.ts`. Construct one instance in `EditorApp.svelte`, provide
it through `HIERARCHY_NAVIGATOR_KEY`, and consume it only from editor components.
It must not import a codec, mutation planner, history controller, or visitor code.

```ts
type HierarchyPage =
  | { kind: 'root' }
  | { kind: 'rooms' }
  | { kind: 'room'; roomId: string }
  | { kind: 'walls' }
  | { kind: 'openings' }
  | { kind: 'junctions' }
  | { kind: 'layoutObjects' }
  | { kind: 'sceneContent' };

type WallFilter = 'all' | 'multiple-rooms' | 'one-room' | 'no-room' | 'with-openings';
type OpeningFilter = 'all' | 'door' | 'window';

type HierarchyHistoryEntry = {
  page: HierarchyPage;
  query: string;
  wallFilter: WallFilter;
  openingFilter: OpeningFilter;
  disclosure: string[]; // stable contextual row/section keys
  scrollTop: number;
};
```

The store owns `$state` for `current`, `backStack`, and transient
`emphasis: HierarchyEntityKey | null`. It also publishes a monotonically keyed,
one-render-cycle transition intent (`ordinary-entry | history-restore | show-in`)
so the renderer can distinguish a page change from a selection change. The
transition intent is coordination state, not part of a history entry, and is
consumed after the destination render/scroll step. The current projection and
pinned strip are `$derived` by the component from current documents + active
selection; do not store projected rows or selected identity as competing truth.

Rules:

- `open(page)` snapshots the current entry, pushes it, installs a new entry at
  its intended top/default state, and emits `ordinary-entry`. A pre-existing
  represented selection highlights immediately but does **not** auto-disclose or
  auto-scroll merely because the page changed.
- explicit `showIn(destination)` pushes the current snapshot and installs a new
  entry with `query: ''`, calm filter defaults, disclosure containing the
  required target chain, and `scrollTop: 0`. It emits `show-in` carrying the exact
  canonical reveal target; this is the page-entry exception that intentionally
  scrolls after render.
- `back()` snapshots no new entry, pops one, restores page, query, filters,
  disclosure, and scroll, and emits `history-restore`. During that restoration
  render, selection highlight and pinned-state derivation happen normally, but
  selection-driven disclosure and scrolling are suppressed. The exact restored
  `scrollTop` wins. Normal reveal resumes on the next genuine selection change or
  same-page excluded-to-represented projection transition. Back never calls
  selection.
- search, filter, and disclosure update the **current entry in place** and do not
  push history;
- auto-disclosure for a represented selection updates only the current entry's
  disclosure and does not push history;
- selection changes do not mutate page/history/query/filter; they only trigger
  representation/reveal recomputation;
- same-page query/filter/document changes may schedule reveal only when the
  selected entity becomes represented (or its primary `rowKey` changes), not on
  every reactive recomputation. Expanding a disclosure that newly renders the
  selected descendant may scroll to it; collapsing that ancestor never
  auto-reopens it. Disclosure alone does not manufacture a selection-change
  event;
- scroll events replace `current.scrollTop`; after projection/page render,
  restoration writes that exact value to a Navigator-owned scroll viewport;
- pinned selection is derived from selection + projection exclusion, never saved;
- reset/import/document replacement reprojects. If a page parameter no longer
  exists, replace the current page with `rooms` (for a missing Room) or `root`
  without selecting or creating document history; prune invalid back entries on
  use, not by mutating documents;
- Navigator Back has a visible button. Do not bind Cmd/Ctrl-Z, Cmd/Ctrl-Shift-Z,
  Delete, or Backspace. Browser-style Alt-Left may be added only if it does not
  conflict with the shell; it is not required.

Use an explicit inner scroll viewport in `UnifiedProjectTree.svelte` so the
component can reliably capture/restore `scrollTop`; adjust `EditorSidebar.svelte`
flex/overflow styles rather than querying an incidental ancestor.

## Pure relationship index (not a second graph)

Refactor the canonical branch of `unified-project-tree-model.ts` into a pure
`HierarchySourceIndex` built fresh from the current `LayoutDocument` and
`SceneDocument` whenever Svelte dependencies change:

```ts
type HierarchySourceIndex = {
  orderedRooms; orderedWalls; orderedOpenings; orderedJunctions;
  orderedLayoutObjects; orderedSceneClusters; orderedSceneEntities;
  roomById; wallById; openingById; junctionById; objectById; entityById;
  openingsByWallId; roomIdsByWallId; incidentWallIdsByJunctionId;
  boundaryRoomIdsByJunctionId;
  assignedObjectIdsByRoomId; clusterByMemberId;
};
```

Every relation is obtained by one pass over authoritative fields:

- Room → Walls: `room.boundary[]`, preserving its order and direction;
- Wall → Rooms: inverse of those explicit refs (equivalent to extending/reusing
  `wallFirstAdjacentRooms()` from `layout-portals.ts`);
- Wall → Openings: `opening.wallId` in `layout.openings` order;
- Wall → endpoint Junctions: `startJunctionId` / `endJunctionId`;
- Junction → incident Walls: inverse of endpoint IDs in `layout.walls` order;
- Junction → boundary Rooms: inverse of explicit Room boundary Wall refs. For
  each Room boundary ref, resolve that canonical Wall's two endpoint IDs and add
  the Room once in `layout.rooms` order. This is strictly topological identity;
  never use coordinates, proximity, or point-in-polygon;
- Room → Layout Objects: explicit `object.roomId` only;
- cluster → members: `cluster.memberIds`, with entities resolved from Scene.

This index is an ephemeral read model, not persisted topology. It must not use
compiled coordinates to infer relations and must not become a mutation API.
Reuse/export a pure incident-Wall helper only if doing so avoids the current
private duplicates in `layout-wall-first-precision.ts`; do not move Navigator
types into `layout-core` merely for UI convenience.

## Page projections

Every page builder returns deterministic rows plus a representation registry:

```ts
type HierarchyPageProjection = {
  rows: HierarchyProjectedRow[];
  representations: Map<HierarchyEntityKey, HierarchyRepresentation[]>;
  unfilteredRepresentations: Set<HierarchyEntityKey>;
};

type HierarchyRepresentation = {
  rowKey: string;
  entity: HierarchyEntityKey;
  ancestorDisclosureKeys: string[];
  primary: boolean;
};
```

`HierarchyEntityKey` includes the owner and canonical IDs, so `layout:object:x`
and `scene:entity:x` cannot collide. `rowKey` additionally includes page/context,
so the same Wall can have one canonical identity and several legitimate
representations. Each page defines one primary representation per supported
entity type. Ordering never depends on selection, hover, viewport, timestamps,
or map insertion from a query.

### Root

Direct destination rows with counts: Rooms; Walls, Openings, Junctions; Layout
Objects, Scene Content. Counts come from authoritative arrays. `Scene Content`
means canonical content entities, so its count is exactly
`scene.entities.length`; clusters are organizational rows and add zero to the
root count. Clustered and unclustered entities are therefore each counted once,
and an empty cluster does not inflate the number. Root rows are navigation only
and never selection representations.

### Rooms page

Rooms in `layout.rooms` order. Clicking the Room's selection surface calls
`selectLayoutRoom` and does not navigate. A separate explicit `Open <name> ›`
action opens `{kind:'room', roomId}` and does not select. This separation is
keyboard accessible and avoids ambiguous click semantics.

### Room page

Header/back label `← Rooms`, authored Room name, and a title representation for
that Room. Sections:

1. `Boundary (n walls)` — always open. Resolve `room.boundary[]` in its exact
   authoritative order. Each row is the same canonical Wall identity; a Wall
   shared by multiple Rooms is not copied in the document. Secondary text names
   other participating Rooms (`also in …`, bounded to two names plus `+n`).
2. Wall disclosure — hosted Openings from `openingsByWallId` followed by one
   non-selectable `Ends <start> · <end>` relation row. Opening is the canonical
   `{wallId, openingId}` selection. Ends use canonical Wall orientation, not a
   coordinate guess.
3. `Boundary Junctions (n)` — collapsed by default. Derive IDs by walking the
   oriented boundary refs: take each ref's oriented start Junction, de-duplicate
   by first encounter; append any unmatched oriented end only for a still-
   renderable malformed intermediate projection. Rows are canonical Junctions.
4. `Assigned Layout Objects (n)` — collapsed by default and present because Gate
   2 passed. Filter only by explicit `roomId`; `(0)` remains visible.

Never render Scene Content here. An Opening's primary Room-page representation is
under its host Wall. A Junction's is in Boundary Junctions. Auto-reveal expands
only the relevant section and direct Wall ancestor.

### Walls page

Walls in `layout.walls` order. Header count reflects the unfiltered inventory.
One dropdown exposes Gate-3-independent Wall facets:

```text
All Walls
In multiple rooms
In one room
No room participation
With openings
```

Partition by `roomIdsByWallId.length`; “With openings” uses the authoritative
host index. Under All, rows show identity and only `▸ n opening(s)` where useful.
The multiple-Room filter adds `in A, B, +n`; other resting rows do not pay the
metadata cost. Hosted Openings disclose beneath their Wall. Junctions have no
representation on this page. The primary Opening representation is under its
host Wall.

The filter implementation should be a pure predicate list internally rather
than hard-wiring one `switch` into the renderer, so future composable predicates
remain possible; the P23.6e UI remains single-select.

### Openings page

An index, not an owner. Rows are in `layout.openings` order and show type/reference
plus `on <host Wall>`. Row selection calls `selectLayoutWallOpening` and stays on
the index. `Show in Walls ›` explicitly pushes the Walls page with the host Wall
and exact Opening reveal chain. Gate 3 enables `All Openings / Doors / Windows`.

### Junctions page

Junctions in `layout.junctions` order. Each row shows canonical identity and the
factual count from `incidentWallIdsByJunctionId` (`3 walls`). No filter in this
slice. Selection scrolls only to its direct row; it never expands incident Walls
or another topology region. Relation actions may select an incident Wall but do
not navigate unless explicitly labelled `Show in Walls`.

### Layout Objects page

Objects in `layout.objects` order. Rows use canonical object identity and existing
kind label. If `roomId` resolves, show `assigned to <Room>`; if absent, no Room
claim. Selection uses `selectLayoutObject` and existing Arrange-owner behavior.
Its home is this page.

### Scene Content page

Scene-owned clusters in Scene order with member entities in `memberIds` order,
then unclustered entities in document order. Existing Scene selection writers,
visibility, frame, delete, cluster actions, and owner rules stay intact. Cluster
disclosure is Navigator UI state. No Layout Room association is inferred or
displayed for canonical world-local Scene content. Its home is this page.

### Search results projection

Search is a global projection over the current canonical documents while the
underlying page remains in the current history entry. It does not become a page
or push history. Empty/Escape returns to that underlying page exactly.

Result blocks are ordered by direct entity category (Rooms, Walls, Openings,
Junctions, Layout Objects, Scene clusters/entities), then authoritative document
order. Each direct block has bounded groups:

1. **Direct:** name, authored label, current display reference, or raw canonical
   ID contains the normalized query.
2. **Directly related:** Room → boundary Walls + assigned Objects; Wall →
   participating Rooms; Opening → host Wall; Junction → incident Walls +
   boundary Rooms; Layout Object → assigned Room; cluster ↔ member entities.
3. **Dependents nested only:** hosted Openings and `Ends` beneath a related Wall.
4. **Topology summarized:** Room `Boundary Junctions (n) [Show]`; no top-level
   Junction expansion caused by Room retrieval.
5. **Stop.** Never traverse a related Wall into its other Rooms as new results,
   through Junctions to neighbours, or into Scene Content unless Scene directly
   matches.

Within each group use the source array/boundary order stated above and de-duplicate
by canonical key. Secondary `also in …` text is display, not a graph hop.
Selecting a result changes canonical selection only; query and page remain. Each
explicit Show action pushes its named home with an empty query.

**Retrievability invariant:** every relationship rendered as a row, secondary
line, section, or count has a reverse lookup in the source index and a search
test from both ends. Thus searching `Gallery B` retrieves its boundary Walls;
searching a Junction retrieves incident Walls **and Rooms whose explicit boundary
Walls meet at that Junction**; searching a Wall retrieves its participating Rooms
and nested hosted Openings; searching an assigned Object or Room retrieves the
other end. The Junction → boundary Room result is direct and terminal: do not then
expand that Room into its other Walls. Do not index relationships the UI does not
render.

## Representation, reveal, and pinned selection

Add pure helpers beside the page projection, using existing identity types:

```ts
activeSelectionToHierarchyEntity(active): HierarchyEntityKey | null
findHierarchyRepresentation(projection, entity): HierarchyRepresentation | null
canonicalHierarchyHome(index, entity): HierarchyDestination | null
explainHierarchyExclusion(current, base, entity): PinnedReason
```

Do not add a second selected-entity store. For Scene multi-selection, use the
existing primary convention (`ids.at(-1)`) for reveal; the strip may factually
show `<n> selected` while its Show action targets Scene Content.

Reveal is event/cause aware, not an effect that blindly scrolls on every reactive
run. Schedule selection-driven reveal only for:

- a genuine canonical selection identity change;
- a same-page active projection transition where the unchanged selection moves
  from excluded to represented (for example Clear search/filter), or where a
  canonical edit changes its primary representation row;
- a same-page user disclosure expansion that newly renders the already-selected
  descendant (scroll only; never turn a collapse into immediate re-expansion);
- an explicit `show-in` transition carrying a target.

Do **not** schedule it for ordinary page entry or the `history-restore` cycle.
For an eligible reveal event:

```text
representation exists in the active search/filter/page projection
→ add only representation.ancestorDisclosureKeys to current disclosure
→ after Svelte renders, scroll the exact rowKey into the Navigator viewport
→ existing row matcher highlights canonical selection
→ no navigation, no history push, no strip

representation absent
→ preserve page/query/filter/disclosure/scroll and canonical selection
→ derive pinned strip and reason
```

Rows under collapsed ancestors and rows outside the viewport are represented.
DOM presence and current visibility are not the test. Auto-disclosure changes the
current entry before scrolling; it never opens siblings or a whole unrelated
inventory.

### Navigation/reveal precedence (frozen)

```text
Back / history-restore
→ render the restored page/query/filter/disclosure
→ restore the exact saved scrollTop
→ highlight represented selection immediately
→ suppress selection-driven auto-disclosure/scroll for this restoration cycle

ordinary explicit page entry
→ render at the new entry's intended/default scroll state
→ highlight represented selection immediately
→ do not auto-scroll for a selection that predates navigation

explicit Show in…
→ enter the named home with its explicit canonical reveal target
→ disclose required ancestors and scroll to the target

subsequent selection change or same-page excluded-to-represented transition
→ normal auto-disclose/reveal resumes
```

Example: Gallery A has selection D007 and a saved scroll position elsewhere.
`Show in Walls → Back` restores that Gallery A scroll exactly even though D007 is
still represented and highlighted there. A later new selection of D007, or a
same-page filter/search transition that newly reintroduces it, may reveal it.

Example: W044 is already selected and the user ordinarily opens Gallery A.
Gallery A starts at its intended top/default state and shows W044 highlighted;
it does not land halfway down the page. An explicit `Show in…` action carrying
W044 would be the intentional reveal path.

Reason priority:

1. active query and not in search projection → `Not in search results`;
2. underlying page contains it but active filter excludes it →
   `Outside active filter`;
3. Room page excludes it → `Not in <Room name>`;
4. otherwise → `Not on this page`.

The bottom-pinned strip is neutral, no icon/color/animation, and updates in place:

```text
Selected <reference>
<reason>                         Show in <home> ›
```

Homes: Room → Rooms; Wall/Opening → Walls (Opening includes host expansion);
Junction → Junctions; Object → Layout Objects; cluster/entity → Scene Content.
No strip appears merely because the row is off-screen.

## Hover/focus → Plan emphasis

Every selectable Layout row publishes its canonical `HierarchyEntityKey` to
`HierarchyNavigatorStore.emphasis` on `pointerenter` and `focusin`, and clears
only if the leaving row still owns the current emphasis. Convert it purely to
the existing `PlanHitIdentity` in `PlanWorkspace.svelte` and pass it as a new
optional presentation prop to `LayoutPlanViewport.svelte`.

`LayoutPlanViewport` uses:

```text
viewport-local layoutHover ?? hierarchyLayoutEmphasis
```

as the existing `buildPlanInteractionProjection()` hover input. Scene entity
focus may reuse the existing Scene footprint hover outline; Layout Object uses
the existing object hit style. Room, Wall, Opening, Junction, and Object mappings
carry only canonical IDs. No emphasis updates selection, opens disclosure,
navigates, frames a camera, or writes history. Page navigation clears emphasis.

## Projection under future topology mutations

The Navigator keys pages, row instances, representations, disclosure, and pending
reveal by canonical IDs, never row indexes. Junction move, Wall move, boundary
membership change, split, Opening rebase, and Undo/Redo remain authoritative
operations elsewhere:

```text
canonical mutation/reconciliation/history result
→ current LayoutDocument/SceneDocument changes
→ source index and active page re-project
→ representation/pinned state re-derives
```

After a split, a new Wall/Opening/Junction uses its canonical resulting ID and is
collapsed unless selection requires its ancestor disclosure. The Navigator does
not decide whether selection transfers to a fragment or clears; it renders the
result left by the canonical mutation/reconciliation contract. Invalid disclosure
keys are ignored/pruned as UI state. No geometry, topology, Room identity,
Opening rebase, or Undo replay is implemented here.
