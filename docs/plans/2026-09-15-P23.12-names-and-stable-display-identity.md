## 3. Conflicts with landed code, and the smallest architecture-consistent resolution

### C1 — the codec rebuilds records, so a "tolerated" key is erased

A new key must be *parsed into the returned document*, not merely allowed, or it
disappears on the next install (which happens on every mutation) and breaks
Save/Load, dirty-baseline comparison and Undo determinism.
**Resolution:** explicit parse functions for every new block, plus a codec test
asserting the block survives `decode → serialize` and that the ledger survives a
full `derivePreviewBundle` install.

### C2 — "retired references are never reassigned" vs recyclable canonical IDs (§2.5)

A reference *derived from* the canonical ID would be handed to a
different entity after a delete + create. **Resolution:** references are
**allocated from a persisted, monotone-in-the-session cursor and stored as data**
(the cursor is the document's; monotonicity is held by the preview state's
high-water mark — revision 2, [D1](#d1--where-references-live-and-how-they-are-allocated));
the derivation approach is rejected.

### C3 — P23.11's fresh-authority precedent vs the required default for documents without the new metadata

P23.11 added `centerline` to format 5 as a *required*
key with no missing-field tolerance. Doing the same here would invalidate every
already-saved project **and every already-published release**, because the visitor
path re-validates released documents with the same codec
(`visitor-cold-runtime.ts` ~203, `project-codec.ts` ~112), and there is no
`formatVersion: 6` to introduce. **Resolution:** the new blocks are **optional on
read and always present on write for editor-held documents**; completeness is
guaranteed at the single install seam rather than by the codec. No version bump,
no migration.

### C4 — `planRepeatWallOpening` spreads the source record

The spread is (`{...source, id, offset}`). A reference stored *on the entity record* would be **copied**, giving
two entities the same reference. **Resolution:** references live in a
document-level ledger keyed by canonical ID, which removes the spread hazard
entirely *and* makes duplicate semantics match the contract (names copy through
the spread as required; a reference cannot). The one genuine gap is
`planDuplicateIsolatedRoom`, which builds cloned Walls/Openings explicitly and so
needs explicit name propagation.

### C5 — import and load baselines are computed from the pre-normalization payload

`importLayoutPreviewJson` sets
`state.baselineLayoutJson = canonicalLayoutJson(parsed.document)` (~749) and the
load path calls `markLayoutPreviewSaved(layoutPreview,
serializeActiveLayout(validation.project.layout))` (`EditorApp.svelte` ~1524;
also ~1273). With normalization at install, both baselines are stale and the
session reads dirty immediately. **Resolution:** both call sites baseline the
**installed** document from the derived bundle.

### C6 — `derivePreviewBundle` is on the pointermove transient-preview path

`derivePreviewBundle` (~601) serves every install path **and** the transient ones:
`deriveLayoutCandidate` (`layout-gizmo-candidate.ts` ~309) runs **once per
pointermove** and its bundle is installed into live state by
`commitLayoutCandidate` (`layout-gizmo-adapter.svelte.ts` ~254);
`preview-coordinator.ts` (~105, ~173) projects 3D previews per change; the P23.11
direct-preview mutators install and are rolled back by
`restoreTransientArchitectureBaseline` (`layout-transient-edit.ts` ~176).
**Resolution (revision 2):** derivation is **allocation-free with respect to the
durable mark**. It may mint **provisional** identity — into its own copy, from the
frozen baseline it was derived from — so a mid-gesture candidate renders honest
references; it never writes the live ledger, never advances the mark, and returns
the input object unchanged when identity is already complete and consistent
(copy-on-write; a live Svelte `$state` document is never mutated). Because the
candidate has already resolved every live entity into its ledger, promotion finds
nothing left to mint: it only records what the candidate displayed. (The one case
where promotion *does* assign an unseen token is a live entity that no derivation
ever resolved — a path that bypassed the install seam; S2 asserts every install
path derives.) Promotion happens only at
the durable seams ([D1](#d1--where-references-live-and-how-they-are-allocated)
rule, [C10](#c10--history-restore-rewinds-the-whole-document-including-allocation-state)).
This supersedes revision 1's claim that "minting into a candidate cannot leak,
because the cursor travels with the candidate" — with a monotone mark held outside
the snapshot, a candidate *did* leak whenever the candidate was installed and later
rolled back.

### C7 — `formatPlacementLabel` is shared with legacy/Camera/Scene surfaces

It is used by `UnifiedProjectTree`, `CameraSidebar` and `EditorSceneTree` as well.
**Resolution:** the
identity layer sits *beside* it; only canonical wall-first surfaces switch.
Layout objects, Scene content, Camera and the legacy Room-owned tree keep the
existing formatter.

### C8 — an Opening's ID embeds its kind

`planUpdateWallFirstOpening` may flip door↔window.
**Resolution:** the reference is keyed by opening ID and
**never changes on a kind flip**; the ID scheme is not "fixed" here (out of
scope). The quirk becomes invisible once the label is `O-…`.

### C9 — gate 1 in `hierarchy-page-projection.ts`

Gate 1 states labels are "authored names or
`formatPlacementLabel(canonicalId)` — never an invented ordinal", and a test pins `label !== /^W\d+$/`. **Resolution:** preserve the intent, supersede the
implementation — rewrite the gate-1 comment to "identity labels come from the one
identity layer; references are opaque, document-unique, and carry no user-visible
or semantic ordering, position, role or ancestry meaning", and re-pin the test on
reference properties (uniqueness; stability across reorder, insertion, deletion
and Undo; successive tokens non-adjacent) instead of formatted IDs.

### C10 — history restore rewinds the whole document, including allocation state

`restoreLayoutPreviewSnapshotUnmeasured` (`layout-preview-state.svelte.ts` ~2384)
installs `cloneJson(snapshot.project)` verbatim, so a cursor stored inside the
layout document is rewound by Undo — and a user who branches history after an Undo
would then mint a token that a retired entity already used:

```text
cursor 10
create Wall A → W-XXXX, cursor 11
undo → cursor 10
create a different Wall B → W-XXXX again   ← retired reference reassigned
```

Plan v1 could not hold "cursor inside the snapshot" + "Undo restores exactly" +
"never reused" simultaneously. **Owner decision: the monotone high-water mark
wins (option B).** Revision 1 resolved it by clamping at the restore seam
(`cursor = max(snapshot, live)`); **revision 2 supersedes the clamp**, because a
clamp at that seam also makes *transient* states consume allocations: a pointermove
candidate mints, the gesture is cancelled, the snapshot restores the ledger and the
clamp preserves the raised cursor — so a rejected candidate permanently burns
allocations and the next committed reference depends on pointermove history.

**Resolution (revision 2) — allocation advances only at a durable seam.**
Monotonicity moves out of the snapshot into the preview state
(`identityHighWater`, a plain field that `captureLayoutPreviewSnapshot` does **not**
copy), and every restore — transient or history — reverts the document's cursor and
ledger **exactly**. The mark is advanced in exactly two places: the **promote seam**
immediately before a live state is captured as a history boundary
(`promoteLayoutIdentity` at the five `commitLayoutTransaction(capture…)` call sites)
and the **three persistence seams**, all promoted *before* they serialize.
Revision 2 got the first of them *late*, and revision 4 completes the list:

* **(a) Cloud Save.** `captureValidatedSaveSnapshot()` (`EditorApp.svelte` ~1205)
  builds the payload from `layoutPreview.project.layout`, `submitSaveSnapshot`
  calls `projectApi.saveProject(snapshot.project, …)` (~1266) and only **then**
  calls `markLayoutPreviewSaved` (~1273) — so a payload built at the old seam
  carries a cursor **below** the session mark and a later Load could reissue a
  committed token. Promotion moves before payload construction; the success
  callback keeps the baseline only.
* **(b) Resumed save.** `resumePendingCloudSave()` (~1380) installs a bundle
  derived from `pending.project.layout` and then submits
  `{ project: pending.project, layoutCanonicalJson: serializeActiveLayout(pending.project.layout) }`
  (~1443) — the *original payload*, while promotion acts on
  `layoutPreview.project.layout`. Resumed save must therefore submit the
  **installed, promoted snapshot** (install, then `captureValidatedSaveSnapshot()`),
  so the project's `layout` and its `layoutCanonicalJson` cannot disagree;
  `projectId === pending.project.id` is asserted immediately before (~1389), so the
  captured identity is unchanged.
* **(c) Actual export.** The Layout **Copy JSON** / **Download JSON** commands live
  in `EditorProjectMenu.svelte` (`copyLayoutJson` ~196, `downloadLayoutJson` ~211)
  and serialize `layoutPreviewCanonicalJson(layoutPreview)` directly — they never
  touch `captureValidatedSaveSnapshot()`. Promotion goes immediately before that
  serialization, so an exported file is never behind the session mark. The scene
  export commands (`copySceneJson`/`downloadSceneJson`, ~165/~180) serialize the
  `SceneDocument`, which carries no identity, and need nothing.

Because promotion re-syncs the document cursor to the mark (T6), all three seams
serialize a cursor ≥ the session mark **even when no entity needed allocation**. A
failed API call leaves the raised bookkeeping cursor in place — not authored
content, so the session does not read dirty. Everything else is
allocation-free with respect to the mark: candidate derivation on pointermove,
transient architecture previews, `restoreTransientArchitectureBaseline`, drag /
room-unit / arrange-delete rollbacks, and the `capture` closures used for
*pre*-gesture baselines (which stay pure reads). A cancelled gesture therefore
returns the document **and** the mark exactly as they were, and the next committed
reference cannot depend on pointermove history.

Consequences, pinned in [D1](#d1--where-references-live-and-how-they-are-allocated),
[D2](#d2--lifecycle) and slice [S2](#s2--the-four-seam-kinds-provisional-derivation-durable-promotion-exact-restore-persistence-and-baselines):

* Undo/Redo still restore **authored content, canonical IDs and reference
  assignments** exactly; the mark survives them, so a branch after an Undo still
  mints a **fresh** token for B (the case above), while a branch that restores the
  same content restores the same tokens.
* Authored-change comparisons (`layoutPreviewIsDirty` ~366,
  `layoutPreviewSnapshotMatchesLive` ~416, the `markLayoutPreviewSaved` baseline
  ~659, both hosts' `matches` and `currentProjectFingerprint`) keep using
  `layoutAuthoredCanonicalJson` (canonical JSON with `identity.cursor` omitted), so
  neither the mark nor a rewound cursor can create a phantom history entry or a
  spurious dirty state. This is now *defensive*, not load-bearing: with the mark
  outside the snapshot, a cursor-only difference between live and an
  authored-equal boundary should not arise at all — the evidence that it cannot is
  asserted in S2.
* Save keeps the full canonical JSON including the cursor, and promotes before
  serializing (order pinned in S2).

### C11 — Publish does not strip metadata, so the visitor criterion must be code-based

Verified: a release is built from the **saved project version document** — the API re-validates the stored version with `validateProject` and
compiles it (`apps/api/src/publication-persistence.ts` ~437/~443) — and the visitor
validates the released document again through `prepareCompatibleRuntime`
(`visitor-cold-runtime.ts` ~203). `layout` (hence `identity` and Wall/Opening
`name`) therefore travels in released data by construction; nothing strips it.
**Resolution:** the visitor requirement is stated as *consumption and code*
(C11 rules below), **not** as absence of data; P23.12 adds **no** publish-stripping
behavior, since that would be new architecture for no product gain. The same
finding also strengthens [C3](#c3--p23-11s-fresh-authority-precedent-vs-the-required-default-for-documents-without-the-new-metadata):
republishing an older saved version must keep validating, so the new blocks stay
optional on read.

**C11 rules (carry into S8 and the invariant matrix).**

1. The visitor does **not** consume, render, mutate or import editor
   display-identity logic: no visitor module imports the identity layer, no
   reference/name string is rendered in visitor output, and no visitor behavior
   reads the ledger.
2. Inert `identity` / `name` metadata in canonical released data is **expected and
   accepted** — it is the same canonical document the editor saved.
3. P23.12 adds no stripping, no separate release schema and no publish-path
   change.
4. The visitor's re-validation must keep accepting documents **without** the
   blocks (already required by C3).

## 4. Ratified P23.12 decisions

### D1 — Where references live and how they are allocated

One **identity ledger** owned by the wall-first `LayoutDocument`:

```ts
identity: {
  cursor: number,                        // next allocation index (bookkeeping)
  rooms:     { [roomId]: 'R-XXXX' },
  junctions: { [junctionId]: 'J-XXXX' },
  walls:     { [wallId]: 'W-XXXX' },
  openings:  { [openingId]: 'O-XXXX' }
}
```

* **Token:** `family + '-' + 4 characters`, from the 31-character unambiguous
  alphabet `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (excludes `0 O 1 I L`). Footprint is
  exactly **6 characters** (`W-7K3M`) — the contract's hard ceiling.
* **Mapping (revision 2 — now exactly invertible):**
  `suffixIndex = (cursor × K + C) mod 31⁴`, with `31⁴ = 923 521`,
  `K = 1 000 003 mod 31⁴ = 76 482` and the fixed translation
  `C = 20 979`, so the very first allocation is not the all-zero suffix.
  `gcd(K, 31⁴) = 1` (verified), so multiply-then-translate is a **bijection** on
  the index space (verified: a full sweep of all 923 521 indices produces zero
  collisions), and its inverse is available in closed form —
  `indexOfReference(token) = ((tokenIndex − C) × K⁻¹) mod 31⁴` with
  `K⁻¹ = 298 772` (verified: `(K × K⁻¹) mod 31⁴ = 1`, and the round trip is exact
  for 200 000 cursors). That inverse is what makes the persisted-cursor
  consistency check of the next bullet possible.
* **The token is an opaque permutation of the allocation sequence.** It is
  *derived from* allocation order (unavoidably — so is every allocated identifier,
  including the canonical ID), but it **carries no user-visible or semantic
  ordering, topology, spatial, role or ancestry meaning**, and no consumer can read
  one out of it. Concretely: successive allocations are non-adjacent — verified for
  the first 50 000 allocations, where consecutive tokens differ in **all four**
  suffix characters (e.g. `W-2QUS` → `W-5AEX`) — and the index step is far larger
  than the suffix's own positional weight (76 482 of 923 521). Exhaustion
  (923 521 lifetime allocations in one document) fails closed with the named
  `identity_space_exhausted` rejection.
* **Cursor semantics.** `cursor` is the **next** allocation index (first token
  consumes index 0, then `cursor = 1`, …). It is *allocation bookkeeping, not
  authored content*: persisted, and excluded from every authored-change
  comparison (see the rule table below).
* **Consistency invariant and repair (owner ask 3).** A document is internally
  consistent iff, for every token in the ledger,
  `indexOfReference(token) < cursor` — i.e. the cursor never points at an index
  that a live token already consumed. `layoutIdentityCursorIssues(document)`
  reports violations in O(#tokens) with no lookup table, and the install seam
  **repairs** a short/stale cursor by `cursor := max(index of every live token) + 1`
  (deterministic, non-authored, and idempotent). This closes the stale or
  hand-edited-payload hazard where a rewound cursor would hand a live token to a
  *different* canonical ID. It is a *consistency* check, not a validity gate: a
  legacy document with no ledger has nothing to check and is unaffected.
* **Allocation:** one pure function that (i) mints a token for every live entity
  with no ledger entry, in a fixed documented order (rooms → junctions → walls →
  openings), from **one base latched once per operation** —
  `base = max(document cursor, identityHighWater)` **measured at operation start**,
  never recomputed from live state mid-operation, and used identically by that
  operation's provisional mints and by its promotion; (ii) **prunes** entries whose
  canonical ID is no longer live; and (iii) advances the cursor per mint.
* **Why the base is latched, and why it can never be lowered (revision 3).** After
  `create A → Undo`, the document cursor legitimately rewinds while
  `identityHighWater` does not. Any allocation that read the *document cursor* alone
  would therefore hand **A's retired reference to B** — the exact contract
  violation C10 exists to prevent. Latching `max(document cursor, highWater)` at
  operation start makes the base a function of committed history only:
  `create A → Undo → create B` allocates B strictly above A's index, and no
  candidate of the second operation can dip below the mark. The base is **threaded
  explicitly** (an `identityBase` input on derivation and promotion, §5) rather
  than read from hidden mutable state, so a gesture's allocations stay deterministic
  and testable.
* **Reusing a token that was only ever *displayed* is permitted (revision 3).** The
  guarantee is about **assignments**: a token that appears in a durable document
  (captured, promoted or saved) is never issued again. A token that a rejected,
  cancelled or superseded candidate merely displayed may be issued by a later
  successful operation, because nothing ever held it — T2b tests the leak of
  *state*, not the immortality of a value.

**One rule — durable vs transient (reconciles C6 and C10).**
Allocation is a **durable-write-only effect**. Every seam is exactly one of four
kinds, and no seam may be more than one:

| Kind | Seams | Required behavior |
|---|---|---|
| **D — durable promote** | the five `commitLayoutTransaction(capture…)` call sites (`layout-mutation-runner.ts:64`, `EditorViewport.svelte:327`, `PlanWorkspace.svelte:391`, `arrange-delete.ts:83`, gizmo adapter ~257 `commitLayoutSession`) plus **three persistence seams, each promoted *before* it serializes**: **(a)** `captureValidatedSaveSnapshot()` (`EditorApp.svelte` ~1205), before the payload is built; **(b)** the **resumed-save path** (~1438–1447); **(c)** the **actual Layout export paths** — `copyLayoutJson` (~196) and `downloadLayoutJson` (~211) in `EditorProjectMenu.svelte`, which serialize `layoutPreviewCanonicalJson(layoutPreview)` directly and bypass the save seam entirely. `markLayoutPreviewSaved` keeps the baseline only and stays after the API call (~1273). | **P — provisional** | `derivePreviewBundle` (~601) and everything downstream: `deriveLayoutCandidate` (per pointermove), `preview-coordinator`, the transient P23.11 preview mutators | mint/prune **into its own copy only**, from the **operation's latched base** (falling back to `max(document cursor, identityHighWater)` for a one-shot install); **never** write the live document, **never** advance `identityHighWater`; identity when already complete+consistent, so the input object is returned unchanged |

| **C — pure read** | the identity layer, `captureLayoutPreviewSnapshot` (**every** use, including pre-gesture baselines and the snapshot handed to `commitLayoutTransaction`), `layoutPreviewIsDirty`, `layoutPreviewSnapshotMatchesLive`, both hosts' `capture` closures, `currentProjectFingerprint`, all UI consumers | read only; must not mint, prune, promote or advance anything. A capture is a read even when it is *followed by* a promotion — the promotion is the write, and it happens first |

Six invariants follow (T1–T6), plus the scope boundary; all are asserted in S2:

* **T1 — a rejected/abandoned/cancelled state consumes no allocation.** After any
  sequence of transient derivations and rollbacks, `identityHighWater` and the
  live document are byte-identical to their pre-gesture values.
* **T2 — a committed reference is a function of the document, not of input
  history.** `N` pointermove derivations (or 0, or 50 cancelled gestures followed
  by the same edit) commit to exactly the tokens the same edit commits to without
  them; the cursor advances by the number of entities the commit created and never
  by the derivation count. Authored creation *order* still decides which of two
  brand-new entities in one commit gets which token — invisible to consumers and
  pinned by the permutation test, not a violation.
* **T3 — monotonicity survives history.** `identityHighWater` lives in the preview
  state, is not part of `LayoutPreviewSnapshot`, and is therefore untouched by
  Undo/Redo, so a history branch can never re-issue a retired token.
* **T4 — the mark is not authored content.** It never participates in a change
  comparison, a dirty check, a history entry or a fingerprint; only the document's
  own cursor is persisted.
* **T5 — Undo then create cannot inherit a retired reference (revision 3).**
  `create A → Undo → create B` gives B an allocation index strictly above A's,
  because the base is `max(document cursor, identityHighWater)`. No derivation,
  candidate or promotion of that operation may read the rewound document cursor
  alone.
* **T6 — the mark is nondecreasing (revision 3).** Every promotion returns
  `max(received, document cursor)`, so a commit that mints nothing cannot lower it,
  and the serialized cursor is always ≥ the session mark — which is why a later
  Load/import continues above every token that was ever committed (not only above
  the ones still live).
* **Scope boundary of the high-water mark (stated so it cannot be mistaken for a
  bug).** The mark is scoped to **one live document, including its history**. A
  wholesale document replacement — import, reset, project load, boot
  (`createState` / `importLayoutPreviewJson` / `installLayoutPreviewBundle`) —
  **re-seeds the mark from the payload's cursor**, exactly as it adopts the
  payload's canonical IDs and Rooms (and repairs a stale payload cursor per the
  consistency invariant above). Never-reused therefore means: never reused while a
  document (or its history) is live. Cross-replacement reuse is document
  replacement, not reference reassignment, and is out of the guarantee.
* **Rejected alternative (recorded for the roadmap's ratification requirement):**
  a deterministic derivative of the canonical ID. Rejected because canonical IDs
  are recycled by the authoring allocators (§2.5), which would reassign a retired
  reference to a different entity — a direct contract violation. Also rejected:
  per-entity `reference` fields (spread-copy hazard, C4) and any
  document-order/position/topology ordinal (forbidden).
* **"No document-order-derived references":** ledger keys are canonical IDs and
  the token value depends only on the cursor; assignment happens exactly once per
  entity and is then immutable, so reorder, insertion and deletion never change an
  existing reference. Batch order decides only *which brand-new entity in one
  commit* receives which opaque token — invisible to every consumer, stable
  thereafter, and pinned by a permutation test. Undo/Redo restore the exact
  assignments recorded in the snapshot, cursor included; nothing inside the
  document is monotone — the only monotone state is the mark the preview holds
  outside the snapshot (T3).

### D2 — Lifecycle

| Event | Behavior |
|---|---|
| create (any planner) | planner unchanged; the install seam mints a fresh token for each new entity |
| split / subdivide | **survivor keeps its ID and therefore its reference**; the **new fragment gets a new token and no name** |
| T/X noding | newly created Junctions get new tokens; a reused Junction keeps its own |
| duplicate Room / repeat Opening / repeat object | clones get new IDs → new tokens; **Wall/Opening names copy**; Rooms keep `${name} copy[n]` |
| delete Wall/Opening, Room removal, collateral Room retirement | the entity leaves; its ledger entry is pruned at install; the **cursor is untouched → no reuse** |
| Undo / Redo | snapshots carry the ledger → **exact restore of the same tokens and names**, and the document's cursor reverts with them; allocation stays monotone because `identityHighWater` lives outside the snapshot (T3), so an entity created after an Undo branch always receives a fresh token; the mark is not authored content and never marks the session dirty (T4) |
| Save / export | promoted **before** the payload is built or the export is serialized — cloud Save (`captureValidatedSaveSnapshot`), resumed save (which submits the installed, promoted snapshot rather than the pending payload) and the real Layout **Copy JSON / Download JSON** paths in `EditorProjectMenu.svelte`; the serialized cursor is therefore always ≥ the session mark; ledger and names persist in canonical JSON; the baseline still comes from the saved snapshot (C5); a Save that fails does not dirty the session. Scene export (`copySceneJson`/`downloadSceneJson`, ~165/~180) serializes the `SceneDocument`, which carries no identity, and needs nothing |
| Load / import | the mark is re-seeded from the payload's cursor and the cursor is repaired if a live token sits at or above it (T6 + the consistency invariant); importing a pre-P23.12 wall-first document backfills deterministically (identical payload → identical tokens); Save → Load → Save is byte-stable |
| kind flip, role flip, line↔curve, move, thickness/height edit | no reference change, no name change |
| transient gesture (pointermove preview, drag, room-unit drag, architecture Edit preview) | provisional identity in the candidate copy only; **no allocation consumed, no mark movement**; on rollback the document — cursor and ledger included — returns exactly (T1) |
| rejected operation | candidate discarded; live ledger, cursor and `identityHighWater` untouched; zero history; the next committed reference is unaffected (T2) |

### D3 — Wall/Opening optional names

`LayoutWall.name?: string` and `LayoutWallOpening.name?: string`. Rooms keep
their **required** `name`; Junctions never gain one. Absence is the only
representation of "unnamed" (the codec rejects a present-but-blank name as
`invalid_value`). Names are trimmed, duplicates are legal.

Mutation path and **exact patch semantics** (owner-required lock):
`planWallMetadataUpdate(document, wallId, patch)` and
`planOpeningMetadataUpdate(document, openingId, patch)` with

```ts
type OptionalNamePatch = { name?: string | null };
```

* `name: 'North Gallery Wall'` → trim and set;
* a string that trims to empty → **reject `invalid_value`** (blank is never a
  name, matching the codec and the Room planner);
* `name: null` → **remove** the property (clear; the entity returns to
  reference-led presentation);
* the key absent → that field is not part of the patch;
* a patch that changes nothing — including `null` for an already-unnamed entity —
  rejects `no_op`, so callers write zero history;
* the Inspector maps an emptied text field to `null` (not to `''`).

Both planners are siblings of `planRoomMetadataUpdate` in the same module and
share one private name-patch helper. The Room planner keeps its own shape
(`name: string` only, blank rejects) and stays byte-compatible with its pinned
codes and messages.

### D4 — Room naming authority preserved

`planRoomMetadataUpdate` + `updateWallFirstRoomMetadata` + the single Inspector
`Name` field remain the only Room rename authority, unchanged. No menu item, no
inline rename, no second Room field, no new Room planner.

### D5 — One shared display-identity/query layer

A pure editor module resolves, for any canonical entity,
`{kind, kindLabel, canonicalId, reference|null, name|null, primaryLabel,
secondaryReference|null, searchTerms[]}` with
`primaryLabel = name ?? reference ?? formatPlacementLabel(canonicalId)` — the
last only for entities outside the `R/W/O/J` family (Layout objects, Scene
content, Camera). Consumers: the Navigator read model/projection, search, the
pinned selection strip, the Inspector, Plan selected-target feedback and status
messages.

### D6 — Raw canonical IDs behind Technical details

A collapsed **Technical details** disclosure in each selected-entity Inspector
block exposes the selectable full canonical ID with **Copy ID**; **Copy
reference** sits with the identity block (never on Navigator rows, which must not
look actionable). The disclosure state is component-local UI state — it survives
selection changes, is never persisted, and never enters history or the document.
The Navigator row `title` keeps the raw ID as the rail's existing escape hatch.

### D7 — Search

Four term families: authored name, compact reference, raw canonical ID, and the
**existing** kind/role/facet terms (retained verbatim). A match the visible label
cannot explain adds `ID match: <canonicalId>`; a Wall matched only by its role
adds `<Boundary|Partition> match` (the one facet with no visible representation).
Visible matches are highlighted in the identity text. Exact-reference matches are
emphasised **inside their existing group** — no new group, no reordering, and the
bounded retrieval shape (direct → related → nested dependents → summarized
topology → stop) is unchanged.

### D8 — Navigator density (bounded)

**Identity line.** `primaryLabel` + the reference. The reference is never
truncated, wrapped or shrunk (monospaced, muted, **no pill, border or button
styling**); the name ellipsises only after everything else has degraded.

**Optional context line (final-design freedom — owner-required, revision 3).**
Relationship context may occupy its own second line or the existing right-aligned
meta slot. **The current right-aligned meta slot is not a product constraint**; it
is one available implementation of the requirement. **`title` alone is not an
allowed presentation for distinguishing context (revision 3):** an Opening's
kind/host and a Wall's shared-Room participation must be **visibly** available in
the row, with the summary shortened concisely under width pressure rather than
demoted to a tooltip. What is fixed is the *behavior*:

* a context line appears **only when it adds distinguishing information** — the
  host for an Opening (`Door · on W-7K3M`), participation for a Wall reached from
  a Room (`also in Gallery A, …`, including under the multiple-rooms filter), and
  never a bare restatement of kind;
* **no automatic two-line rows**: an entity with nothing distinguishing to say
  stays one line, and no row gains a permanent kind/role restatement
  (`Wall · Boundary` is not repeated beneath every Wall);
* **routine counts disappear first** (`N walls` on Junction rows, `▸ N openings`
  on Wall rows) — they are inventory, not disambiguation, and the disclosure that
  owns them already shows them;
* degradation order under width pressure stays: redundant metadata → relationship
  summaries → name; the reference and `primaryLabel` survive as long as the row
  exists.

**Pinned selection strip (revision 3).** The strip shows **name + the complete
reference** for a named entity (`Gallery A · R-7K3M`), not `primaryLabel` alone —
two Walls or Openings that share a name must stay unambiguous there, and the raw
canonical ID stays in `title` as the existing escape hatch. For an unnamed entity
the strip shows the reference once.

Nothing else about the Navigator changes: no new pages, filters, actions, inline
editing, relationship explorers or disclosure-hierarchy redesign.

### D9 — Plan (bounded, no P23.13)

Room labels keep their current source and legibility rules. The only changes are
selected-target feedback: the Plan `.plan-meta` selection string and the selected
Opening's screen label adopt name/reference (and use the reference to disambiguate
duplicate Room names). No permanent reference labels, no collision, zoom, line
weight, symbol or dimension work.

### D10 — Family membership

Rooms, Walls, Openings and Junctions have references. Junctions are
reference-only and never editable. Layout objects, Scene content, Camera content
and Wall curve bend points are outside the `R/W/O/J` family and keep
`formatPlacementLabel` / their existing presentation, including their current
Inspector headers (owner-required revision: **no Layout object Inspector
unification in P23.12**; see S6).

| A retired reference can never be reassigned, including after Undo (revision 3) | The allocation base is **latched per operation** as `max(document cursor, identityHighWater)` and never read from the rewound document cursor alone (T5); promotion is **nondecreasing** in the mark, including a commit that mints nothing (T6); the operation threads `identityBase` explicitly rather than relying on hidden state |

## 9. Stop conditions

Stop and report rather than broadening P23.12 if:

* the identity ledger cannot be persisted without changing what the canonical
  codec already guarantees for topology;
* reference stability requires a second identity authority, a document-order
  ordinal, or a derived token;
* the install seam cannot normalize without mutating live `$state` documents or
  changing transaction/history semantics, or the durable-vs-transient rule cannot
  be expressed without a *second* allocation authority (a second mark, a mark that
  must be captured into history snapshots, or a promotion that forces a recompile);
* a transient path has to call `promoteLayoutIdentity`, or a rollback has to keep
  a raised cursor, to make identity render mid-gesture;
* the allocation base cannot be latched per operation without introducing hidden
  mutable state, or a candidate's token cannot be made to equal the token its
  promotion assigns;
* Rename has to move out of the Inspector, or a second Room rename path becomes
  necessary;
* Junction naming, inline Navigator rename or a new Navigator page becomes
  necessary to make identity readable;
* Plan work starts requiring P23.13 label placement/collision decisions;
* Navigator work starts requiring P23.14 IA or styling decisions;
* any change makes a visitor module consume, render or import editor
  display-identity logic, or requires stripping metadata on the publish path;
* implementation begins adding migration or backward-compatibility machinery
  beyond the optional-on-read tolerance in C3.

P23.12 is complete only when one identity vocabulary is consumed by Navigator,
Inspector, search, existing Plan identity feedback and architecture-related
messages; every Room/Wall/Opening/Junction has a stable, document-unique compact
reference with the name/reference/raw-ID tiering above; references survive
reorder, deletion, insertion, split, duplication, Save/Load and Undo/Redo
unchanged and are never reassigned to a different entity — including after an
Undo branch, where monotonicity comes from the preview state's high-water mark
rather than from the document, so transient, cancelled and rejected states
consume no allocation at all, and where every operation allocates above
`max(document cursor, highWater)` latched at its start, so a retired reference
cannot be reassigned even after Undo and even across Save/export → Load/import;
and canonical identity, connectivity, selection, authored content, history and
the Layout/Scene boundary are provably untouched.
