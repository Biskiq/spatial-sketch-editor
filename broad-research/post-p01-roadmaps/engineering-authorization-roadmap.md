# Engineering foundations and production boundaries

This roadmap explains what justifies engineering progress and where it must stop for an unresolved
product or technical decision. The [coordination record](./README.md) owns the single capability
disposition ledger and research triggers; the [prototype program](./prototype-roadmap.md) supplies
creative evidence. Neither replaces a live plan.

**Convergence scope, revised 2026-10-22:** the [convergence plan](../../docs/roadmap/product-convergence-2026-10-21.md#scope-and-sequence)
includes research, product/design/architecture and contract reconciliation, and the canonical
roadmap/DAG with a re-derived next batch, all in PR #173. The
[owner production hold](../../docs/roadmap/README.md#production-implementation-hold) includes
existing authorizations. Step 1 updates scope/briefs only. The source/gap map below remains dated
evidence, not an activation checklist; P4 remains deferred.

## 1. Independent progress, bounded commitments

T1/T2/T3 work with an existing consumer, contract and authorization remains independently justified,
but implementation is held until explicit owner release. Core Editor Stability, ordinary editing,
persistence, Camera/Experience foundations and truthful ingest need no speculative UX dependency.
An "independent foundation" must still not preselect an unresolved model.

A useful increment has a named consumer, a domain owner, a bounded interface and verification through
the applicable plan. It should survive the plausible answers to the nearby open design question.
A present need for contact placement does not justify an attachment framework; a rich explanation
does not justify a universal behavior graph; an agent proof does not justify a general agent platform.

Capabilities below are rationale and candidates. Implementation needs its authorization and explicit
owner release from the current hold.
New scope follows the normal phase/slice procedure even when no prototype or research is necessary.
No ordinary operation acquires a new UX gate merely because it appears in a creative prototype.

correctness requirements depends on a new creative prototype, and none authorizes unrelated cleanup.

This table expresses stop lines, not a second disposition ledger. Apply the decisions and research
triggers in the [coordination record](./README.md#5-focused-research-triggers) to the named consumer.

| [API routes](../../apps/api/src/app.ts) | Project read/Save and resource upload/registration, not a semantic agent transport | Existing storage endpoints do not supply operation discovery or agent authoring |

**Exact missing work and limits.** Registry metadata plus F1 resolution are ingredients, not a
client-facing capability/schema/read projection. P4 should test a small adapter exposing only actual
operations and required inputs. Current Scene admission and provider-tested unit admission cannot be
treated as one live project interface before cutover connects them; separate-fixture evidence must say
so. Asset upload does not establish imported component/clip identity, invocation or cancellation/reset.
Rich Presentation controls and reuse likewise need their owning operations before P4 can claim them.

Begin with meaningful supported edits, including stale intent, invalid reference, unsupported capability
and atomic failure cases. Re-read after a human edit, propose against the new revision, preserve
unrelated changes and leave inspectable ordinary state. Demonstrate manual refinement and Undo/Redo.
A script can establish these mechanics; only an actual model connection/trace establishes LLM
orchestration. The smallest missing domain operation may become a production candidate, but P4 never
authorizes its implementation by needing it.

## 6. From evidence to an authorized consumer

For an adopted direction, identify the smallest useful production outcome and its owner. State what
the current contracts already cover; name any missing identity, persistence, channel, content or
shell interface precisely. Use the focused research packet only if the uncertainty remains after
source inspection and existing evidence.

If an amendment is necessary, route it through the owning F/domain/PLATE process with a real consumer
and conformance examples. A shell departure and a domain extension are different changes. Register
the consuming phase, authorize the slice, start through its track runbook and verify under the
[editor test contract](../../apps/editor/tests/README.md). Prototype code/data is not the implementation
plan. Normal review, acceptance and closeout remain required; only the owner closes a major phase.

If no verdict exists when a foundation plan needs to finish, stay within its justified scope:
ordinary pose instead of unapproved following, property edits instead of Look machinery, contracted
semantic navigation instead of a speculative discovery surface, and real supported operations instead
of invented agent capabilities. Record the deferred consumer question where that plan owns it. Do not
silently weaken an existing promise such as Guide-free access or recovery to avoid the dependency.
